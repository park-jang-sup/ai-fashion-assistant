# 작업 지시서 — 신규 등록 아이템 실시간 임베딩 트랙 (task_realtime_embedding_v1)

## 0. 이 트랙의 위치와 승계 원칙

`task_selfeval_validity_v1`(자기 평가 척도 검증, 커밋 `e0c68f6`) →
`task_selfeval_followup_v1`(자기 평가 후속 조치, App Check·폴백
판정 제외, 종결)의 다음 축이다. 사용자 결정으로 자기평가 축은
접었다 — 자기평가가 남긴 결함(폴백 응답 후보의 최종 추천 구조적
우위)은 등록만 된 채 열려 있고, 다음에 그 코드를 만질 때
처리한다(`docs/handoff_2026-08-07.md` §4 참고, 이 트랙에서
손대지 않는다).

**승계 원칙은 옮겨 적지 않는다** — `task_selfeval_followup_v1.md`
§0(그 문서가 `task_selfeval_validity_v1.md` §0을 가리키고, 그
문서는 다시 `task_hardening_v2.md` §0을 가리킨다)을 그대로
참조한다. 판정 기준 사전 등록, 계측 우선, 미확정 불인정, 재빌드
대조, "무료 진단 먼저", 측정 하네스 우선 원칙 — 전부 그 링크를
따라간다.

**기록 원칙**도 `docs/handoff_2026-08-07.md` §2를 그대로 따른다
(원문을 지우지 않고 정정 블록을 덧붙인다, 실측치에 재현 코드를
남긴다, 추정을 실측으로 포장하지 않는다 등).

**이번 세션의 범위: 조사와 설계 후보 제시까지다. 구현·배포에
착수하지 않는다.**

## 1. (a) 현재 파이프라인 정밀 확인 (2026-08-13, 코드 확인)

수동 3단계 배치다. 신규 등록 시점에 자동으로 걸리는 트리거가
**어디에도 없다** — 세 스크립트 전부 개발자가 로컬에서 직접
실행해야 한다.

| 단계 | 스크립트 | 입력 | 출력 | 실행 주체 |
|---|---|---|---|---|
| 1 | `tools/export_for_kaggle/export.py` | Firestore `wardrobe` 컬렉션(Admin SDK로 직접 읽음, `isDemo` 제외, `--owner-uid`로 좁힐 수 있음) + Storage 이미지(cutout 우선, 없으면 원본) | `output/images/{itemId}.jpg`(긴 변 512px 리사이즈, 투명 배경은 흰색 합성 후 JPEG) + `items.csv`/`items.json`(6개 속성 + 메타데이터) + `history.json` + `matcher_spec.md`, 전부 `wardrobe_export.zip`으로 묶임 | 개발자, 로컬 |
| 2 | `tools/export_for_kaggle/kaggle_embedding_comparison.ipynb` | 1단계 zip을 Kaggle에 업로드 | `embeddings.json`(3종 모델 비교 — OpenCLIP ViT-B/32, **FashionCLIP 2.0**, EfficientNet-B0 대조군. 실제 채택된 것은 FashionCLIP) | 개발자, Kaggle 노트북(GPU) |
| 3 | `tools/backfill_embeddings/backfill.py` | 2단계 `embeddings.json` | Firestore `wardrobe/{itemId}.embedding` 필드 쓰기(기본 dry-run, `--apply`로만 실제 반영) | 개발자, 로컬 |

**FashionCLIP 추출 코드(Kaggle 노트북, 2단계) 확인**:
```python
from transformers import CLIPModel, CLIPProcessor
fashionclip_model = CLIPModel.from_pretrained("patrickjohncyh/fashion-clip").to(DEVICE).eval()
fashionclip_processor = CLIPProcessor.from_pretrained("patrickjohncyh/fashion-clip")
# ...
feats = F.normalize(fashionclip_model.get_image_features(**inputs), dim=-1).cpu().numpy()
```
`transformers`의 `CLIPModel`(HuggingFace) — CLIP 아키텍처(ViT-B/32
기반) 그대로, 이미지 인코더만 쓴다(`get_image_features`, 텍스트
인코더는 이 용도에 안 씀). `torch` 배치 추론(`batch_size=32`),
`F.normalize`로 L2 정규화.

**Firestore 저장 형태(3단계, `backfill.py:203-215`로 확인)**:
```
wardrobe/{itemId}:
  embedding:
    model:     "fashionclip"        # embeddings.json에 박힌 값
    dim:       512
    vector:    [float, ...]         # 길이 512, L2 정규화(저장 전 norm 0.99~1.01 검증)
    createdAt: <클라이언트 UTC 시각>  # SERVER_TIMESTAMP 아님(update()의 필드 경로 충돌 회피)
```
실제 `embeddings.json`(현재 저장소 파일)을 읽어 확인: `model:
"fashionclip"`, `dim: 512`, 103개 아이템. `category=="전신"`인
문서는 컷아웃이 아니라 착장 스냅이라 대상에서 스킵, 이미 `embedding`
필드가 있는 문서는 `--force` 없으면 스킵.

## 3. (c) FashionCLIP 실행 위치 후보 비교

**배경 제거(`functions_bg_removal`, `task_background_removal_v1.md`
§2-3~2-6)의 실측 수치를 인용하기 전에, 그 수치가 어느 구성에서
나온 것인지부터 확인했다 — 그대로 옮겨 쓸 수 있는 것과 없는 것이
갈린다.**

**배경 제거 실측의 진짜 원인(중요, 인용 전 확인)**: §2-4가 처음
관측한 68~70초 콜드스타트는 **모델(u2netp)도 onnxruntime도 원인이
아니었다** — `rembg` 패키지가 모듈 로드 시점에 `pymatting.alpha`를
무조건 임포트하는데, 이 경로는 실제로 쓰이지 않는 죽은 코드였다
(`alpha_matting=False`가 기본값). `pymatting`→`numba`(LLVM JIT
초기화)로 이어지는 무거운 임포트 체인이 클라우드 콜드 컨테이너의
느린 디스크 I/O에서 로컬 대비 극단적으로 불균형하게 느려진 것이
원인이었다(§2-5). 이 체인을 걷어낸 `minimal_runtime`(bare
onnxruntime, `rembg` 없이 직접 호출)으로 교체하자 콜드스타트가
**64~70초 → 1.2~2.1초**(GCP 공식 `startup_latencies` 지표,
§2-6)로 떨어졌다 — 이게 지금 배포된 구성이다.

**→ FashionCLIP에 그대로 적용 가능한가**: **68초 쪽은 적용 불가로
적는다.** 그 수치는 `rembg`라는 특정 패키지의 죽은 코드 임포트가
만든 이례적 현상이지, "Python ONNX 비전 모델을 서버리스에 올리면
느리다"는 일반 법칙이 아니다. Kaggle 노트북이 쓰는 경로는
`transformers`+`torch`(`CLIPModel.from_pretrained`)이지 `rembg`가
아니므로 그 68초의 원인(죽은 `pymatting` 임포트)이 그대로 재현될
근거가 없다. **다만 같은 위험 범주(무거운 ML 라이브러리의 임포트
체인이 콜드스타트를 지배한다)는 FashionCLIP 쪽에도 그대로 열려
있다** — `torch`+`transformers` 임포트 자체가 로컬에서도 수 초가
걸리는 것으로 널리 알려져 있고(이번 세션에서 실측하지 않음), 이
조합이 클라우드 콜드 컨테이너에서 배경 제거와 비슷한 배율로
불균형하게 느려질지는 **미실측 — 비교 불가로 남긴다.** 1.2~2.1초
(minimal_runtime) 쪽은 "무거운 프레임워크 임포트를 걷어내면
콜드스타트가 급감한다"는 **패턴**으로는 참고할 수 있지만, 그
수치 자체가 FashionCLIP에도 나온다고 가정하지 않는다 — FashionCLIP을
CLIP 가중치를 ONNX로 export해 bare onnxruntime으로 돌리는 것이
가능한지(변환 난이도, 정확도 손실 여부)는 별도 확인이 필요하다.

**비용은 부분적으로 전이 가능하다.** Cloud Run 최소 인스턴스 1
상시 유지 비용은 `cloud.google.com/run/pricing`(asia-northeast3,
Instance-based billing) 공식 가격표 기준이므로 **메모리 구성만
맞으면 어느 모델이든 같은 표를 그대로 쓸 수 있다** — 1GiB 약
$56/월, 2GiB 약 $62/월(무료 등급 적용 후, 배경 제거 실측 인용).
다만 FashionCLIP(+torch+transformers)이 1GiB에 들어가는지는
확인 안 됨(§4 측정 후보).

## 4. (d) 착수 전 측정할 것 (측정 하네스 우선 원칙, 후보 나열만 — 사전 등록)

**이 목록은 착수 순서가 아니라 "무엇을 재야 결정할 수 있는가"의
후보다. 판정 기준은 실제로 측정하기 전에, 결과를 보지 않은
상태에서 고정한다(다음 세션 이후 과제).**

- **FashionCLIP 추론 시간** — CPU 전용 환경(로컬 또는 Cloud
  Functions/Run과 유사 사양)에서 이미지 1장 처리 시간. 배치
  크기별(1장씩 실시간 처리 vs Kaggle 노트북의 batch_size=32)
  차이도 함께.
- **`torch`+`transformers` 임포트 시간** — 배경 제거의 `rembg`
  사례가 정확히 이 지점에서 틀렸으므로, 클라우드 콜드 컨테이너
  환경에서 직접 재보지 않고는 로컬 값을 못 믿는다(§2-4의 교훈
  그대로 재적용).
- **콜드스타트 실측** — 로컬 하한이 아니라 **실제 배포 후** GCP
  공식 지표(`startup_latencies`)로. 배경 제거가 로컬 추정(1.29초)과
  실측(68초)이 50배 어긋난 전례가 있으므로 로컬 값으로 판단하지
  않는다.
- **ONNX 변환 가능성과 정확도 손실** — FashionCLIP(CLIP ViT-B/32
  기반)을 ONNX로 export해 bare onnxruntime으로 돌릴 수 있는지,
  변환 후 임베딩이 원본 대비 얼마나 달라지는지(코사인 유사도
  등으로 검증). 가능하면 배경 제거의 minimal_runtime 패턴을 그대로
  재사용할 수 있다.
- **상시 인스턴스 비용 — 실제 메모리 요구량 확인 후 재계산** —
  1GiB/2GiB 어느 쪽이 필요한지 실측한 뒤 배경 제거 가격표에 대입.
- **기존 배치 결과와의 벡터 일치성** — 실시간 경로가 만드는 벡터가
  배치 경로(Kaggle, `transformers.CLIPModel`)가 만든 벡터와 같은
  분포/스케일인지. 다르면(예: ONNX 변환 후 미세한 수치 차이,
  전처리 파라미터 불일치) 기존에 백필된 94건과 신규 벡터가 섞였을
  때 유사도 비교가 깨질 수 있다 — 배경 제거의 minimal_runtime도
  픽셀 단위(0.0000/255) 동일성을 직접 검증했었다(§2-5), 같은
  수준의 검증이 필요하다.
- **결측 46건(§2) 백필 방식** — 실시간 트리거를 만들면 그 이후
  등록분만 자동으로 채워진다. 기존 결측 46건을 실시간 트리거
  배포와 별개로 배치 재실행할지, 실시간 트리거가 기존 문서도
  훑게 할지는 별도 결정 사항(이번엔 등록만).

## 5. (e) 범위 질문 — 답을 정하지 않고 등록만

목표를 어디까지로 둘지에 따라 설계가 갈린다. **결정하지 않는다
— 사용자에게 묻는다.**

**질문**: 이 트랙의 목표를 다음 중 어느 쪽으로 둘 것인가?

1. **"신규 등록분에 벡터를 붙인다"** — 지금 파이프라인이 다루는
   대상(사용자가 자기 옷장에 등록하는 아이템)에만 실시간 트리거를
   추가한다. 함의: 옷장 문서 생성/수정 이벤트(Firestore 트리거
   또는 이미지 업로드 시 Storage 트리거, 배경 제거와 같은 지점)에
   붙이면 된다 — 배경 제거의 구조를 거의 그대로 재사용할 수 있다.
   범위가 좁고 다음 단계(상점 옷 카탈로그 연결)를 위한 준비 단계
   성격이 강하다.
2. **"임의의 외부 카탈로그 아이템도 같은 파이프라인으로 벡터화한다"**
   — 처음부터 최종 목표(홈쇼핑·소규모 매장 옷)까지 염두에 두고
   설계한다. 함의: 옷장 문서 트리거가 아니라 **이미지 URL(또는
   업로드)을 받는 독립 엔드포인트**가 필요하다 — 인증·요청 한도·
   외부에서의 남용 방지(이 저장소가 이미 §3.11절 계열에서 겪은
   "프록시 호출량 상한" 문제와 같은 종류)를 처음부터 설계에
   넣어야 한다. 범위가 넓고, 지금 당장 상점 카탈로그 데이터
   소스가 없는 상태에서 설계만 앞서가는 위험도 있다.

각각의 함의만 적었다 — **어느 쪽을 택할지는 사용자가 정한다.**

### 사용자 결정 (2026-08-13) — 1번(신규 등록분만)

**결정: 1번.** 근거:

- **2번의 진짜 비용은 코드가 아니라 공격 표면이다.** 이미지 URL을
  받는 독립 엔드포인트는 `task_hardening_v2`가 다룬 문제를 전부
  다시 연다 — 익명 uid 무제한 생성, 호출량 상한, App Check, 요청
  본문 검증. 그런데 **지금 카탈로그 데이터 소스가 없다** — 소비자
  없는 엔드포인트를 위해 그 표면적을 여는 것은 나쁜 거래이고,
  소스가 정해지면 요구사항이 달라져 지금 만든 인증 설계를 다시
  손봐야 할 공산이 크다.
- **결측률이 악화 방향이다.** 인계 기록의 83%(99/119)가 지금
  68.6%(94/140, §2)로 떨어졌다. 옷은 늘고 벡터는 안 붙으므로
  배치를 한 번 더 돌려 메꿔도 다음 달에 같은 자리다.

**제약(설계에 명시적으로 반영할 것 — 다음 세션 이후 구현 시
지켜야 한다)**: 임베딩 계산부(모델 로딩·전처리·512차원 벡터
산출)를 **트리거와 분리해서** 설계한다. 1번과 2번이 다른 것은
"무엇이 계산부를 호출하는가"뿐이다(Storage 트리거 vs HTTP
엔드포인트) — 분리해 두면 나중에 2번으로 확장할 때 얇은 호출
계층 하나만 얹으면 된다. **이것은 "지금 안 쓸 기능을 만들라"가
아니라 "결합을 만들지 말라"는 제약이다** — 지금 엔드포인트를
만들지는 않는다(금지 사항).

## 7. 콜드스타트·메모리 측정 — 로컬 1차 스크리닝 (2026-08-13)

**성격이 다른 문제라는 지적을 그대로 받는다.** `rembg`의 68초는
임포트 오버헤드(죽은 코드)였지 모델 자체의 무게가 아니었다.
FashionCLIP은 반대로 **실제로 605MB급 가중치를 로딩해야 하는
모델**이다 — 원인이 다르므로 배경 제거의 결론(전이든 위안이든)을
그대로 갖다 쓰지 않는다. §3에서 이미 "비교 불가"로 유지한 판정을
그대로 두고, 이번엔 추측 대신 로컬에서 직접 쟀다.

### 판정 기준 (사전 등록, 결과 보기 전 고정)

이 저장소가 배경 제거에서 이미 쓴 기준을 그대로 가져온다
(`task_background_removal_v1.md`: "콜드스타트가 사용자 체감상
허용 범위 — 수 초~10초대는 자연스럽게 가려짐, 그 이상이면 문제").
**로컬 측정만으로는 최종 실행 위치를 확정하지 않는다** — 배경
제거 §2-4가 로컬 하한(1.29초)과 클라우드 실측(68초)이 50배
어긋난 전례를 남겼으므로, 로컬 값은 "클라우드 스파이크가 필요한지"
를 정하는 1차 스크리닝으로만 쓴다.

- **로컬 총 소요(임포트+모델로드+첫 추론) < 5초** → 클라우드에서도
  합리적일 가능성이 있다는 뜻으로만 해석. Cloud Functions/Run
  최소 인스턴스 0으로 클라우드 스파이크를 제안한다.
- **5초 ≤ 로컬 총 소요 < 20초** → 배경 제거의 로컬→클라우드
  배율(최대 50배) 전례를 감안하면 위험 구간이다. **클라우드
  스파이크가 필수**이고, 최소 인스턴스 1(상시)도 병행 후보로
  준비한다.
- **로컬 총 소요 ≥ 20초** → 로컬에서 이미 무겁다는 뜻이므로
  클라우드에서 더 나빠질 개연성이 높다. 최소 인스턴스 0 후보는
  사실상 기각하고 처음부터 최소 인스턴스 1·온디바이스·외부 API
  쪽으로 방향을 좁힌다.

### 측정 방법·결과

로컬(Windows, `torch 2.12.1+cpu`, `transformers 5.15.0` 신규
설치), **완전히 새 Python 프로세스로 3회 반복**(배경 제거 §2-4/
§2-6과 같은 방법론 — 매번 새 프로세스라야 임포트 캐시가 없는
"진짜 콜드"를 잰다). 대상: `patrickjohncyh/fashion-clip`
(현재 배치가 실제로 쓰는 것과 같은 모델·경로, `CLIPModel.
from_pretrained`). 합성 300×300 RGB 이미지 1장(실제 옷장 이미지를
로컬에 새로 내려받지 않기 위함 — 추론 자체의 소요 시간에는 이미지
내용이 영향을 주지 않는다).

| # | import torch | import transformers | model+processor load | 첫 추론 | 콜드스타트 총합 |
|---|---|---|---|---|---|
| 1 | 1.776s | 4.939s | 4.071s | 0.175s | **11.135s** |
| 2 | 2.021s | 4.945s | 4.662s | 0.174s | **11.967s** |
| 3 | 1.857s | 4.801s | 4.470s | 0.180s | **11.471s** |

- **(a) 가중치 크기**: 151.3M 파라미터(이미지 인코더만 87.5M),
  fp32 추정 605.1MB. 실제 HuggingFace 캐시 디스크 사용량 실측
  581MB(디스크 표기 단위 차이만큼의 오차, 추정과 근접) — 컨테이너
  이미지 번들링 시 이 정도 크기가 그대로 들어간다.
- **(b) 추론 1건 소요**: 첫 추론 ~0.18초, 웜 추론(3회 평균)
  ~0.04초. 배치의 `batch_size=32`가 아니라 실시간 1장 처리를
  가정한 값이다.
- **(c) 메모리**: RSS(측정 시점, 피크 아님) 약 772MB — Cloud Run

  피크). 2GiB 티어(§62/월)를 기본 후보로 잡는 편이 안전해 보인다
  (미확정 — 실제 피크는 이번에 못 쟀다, 아래 "확인 못 한 것" 참고).
- **(d) 콜드스타트 총합**: **11.1~12.0초(3회 평균 ~11.5초)** —
  대부분이 `transformers` 임포트(~4.9초)와 모델 로드(~4.1~4.7초)에서
  나온다. `import torch` 자체는 ~1.9초로 상대적으로 가볍다.

### 판정 적용

**로컬 총합 11.1~12.0초는 5초~20초 구간에 들어간다 →
클라우드 스파이크가 필수다.** 참고로 `transformers` 임포트
(~4.9초)만으로도 이미 `rembg`의 로컬 전체 임포트(1.04~1.36초,
배경 제거 §2-5)보다 **3.5~4.7배 무겁다** — 그런데 `rembg`의
그 1초대 로컬 임포트가 클라우드에서 63~67초로 불어났다(§2-4).
같은 배율(50배 안팎)이 이번에 재현되면 로컬 11.5초가 클라우드
에서 **9~10분대**가 될 수 있다는 뜻이다 — 물론 이건 배율을
그대로 대입한 **추정이지 예측이 아니다**(§2 원칙 7번, "추정을
실측으로 포장하지 않는다"). 배경 제거의 원인(죽은 `pymatting`
임포트)이 여기 똑같이 있다는 근거는 없지만, 없다는 근거도 없다
— 그래서 판정 기준대로 클라우드 스파이크가 필요하다는 결론
자체는 바뀌지 않는다.

### 확인 못 한 것 (미검증으로 남김)

- **클라우드 실측 자체** — 이번엔 로컬만 쟀다. 아래 "다음 제안"
  참고, 배포는 사용자 확인 후.
- **피크 메모리** — `psutil`로 측정 시점 RSS만 쟀다(772MB). 배경
  제거처럼 `container/memory/utilizations` 같은 클라우드 공식
  지표로 잰 피크값이 아니다.
- **`get_image_features()` API 버전 불일치 — 별도 결함으로 등록만.**
  로컬에 새로 설치한 `transformers`(5.15.0, 최신)에서는
  `CLIPModel.get_image_features()`가 Kaggle 노트북 작성 시점
  API처럼 순수 텐서를 바로 안 주고 `BaseModelOutputWithPooling`을
  돌려준다 — `.pooler_output`을 꺼내야 512차원 정규화된 임베딩이
  나온다(직접 확인). Kaggle 노트북 코드(`F.normalize(model.
  get_image_features(**inputs), dim=-1)`)는 이 최신 버전에서 그대로
  돌리면 깨진다. **Kaggle 쪽이 어떤 `transformers` 버전을 실제로
  쓰고 있는지는 확인하지 않았다**(Kaggle 기본 이미지의 버전에
  따라 아직 안 깨졌을 수도 있다) — 이번 범위 밖이라 고치지 않고
  등록만 한다. 배치 파이프라인은 이번 트랙에서 손대지 않는다는
  금지 사항과도 맞다.

### 다음 제안 — 클라우드 스파이크 (실행 전 승인 필요)

판정 기준대로 클라우드 스파이크가 필요하다. 제안 내용(착수하지
않음, 승인 대기):

2. 콜드스타트 3회, 웜스타트 3회를 GCP 공식 지표(`startup_latencies`)
   와 외부 wall-clock 양쪽으로 실측.
3. 피크 메모리(`container/memory/utilizations`)로 1GiB vs 2GiB
   티어를 확정.
4. 위 판정 기준(20초 문턱)을 그대로 적용해 Cloud Functions(최소

착수하지 않는다.**

## 9. 벡터 호환성 검증 — 사전 등록 (2026-08-13, 결과 보기 전)

**동기**: 새 파이프라인이 기존 94벌과 다른 벡터 공간의 값을 내면
비교 자체가 성립하지 않아 트랙 목적이 무너진다. §7의 부수 발견
(최신 `transformers`에서 `get_image_features()` API가 바뀌어
`.pooler_output`을 꺼내야 함)이 "버전이 다르면 산출 벡터도 다를
수 있다"는 첫 신호다 — 결함 등록만 하고 넘기지 않는다.

**선정 규칙(임의성 없음, 결과 보기 전 고정)**: `embedding` 필드가
있는 문서를 카테고리별로 묶고, 각 카테고리에서 **itemId 오름차순
첫 번째**를 1건씩 뽑는다. 카테고리 5개(상의/신발/아우터/하의/
액세서리 — 전신은 embedding 보유 0건이라 대상 자체가 없음, §2)
전부에서 뽑으면 5건.

**전처리 경로 대조(코드로, 실행 전 확인)**: Kaggle 노트북의
`load_rgb()`는 `export.py`가 이미 만들어 둔 `images/{itemId}.jpg`
(cutout 우선, 512px 리사이즈, 흰 배경 합성, JPEG q90)를 열어
`.convert("RGB")`(no-op)만 하고 그대로 `CLIPProcessor`에 넘긴다.
즉 실질적 전처리는 **`export.py`의 `download_and_resize_image`
함수 하나가 전부** 한다. 검증 스크립트는 이 함수를 재구현하지
않고 **`export.py`에서 직접 import해 그대로 호출**한다 — 전처리
경로 자체가 다를 위험을 원천 차단한다.

**판정 기준(결과 보기 전 고정)**: 저장된 벡터와 새로 낸 벡터의
코사인 유사도(둘 다 L2 정규화이므로 내적으로 계산):
- **≥ 0.9999** → 부동소수점 오차 수준, 사실상 동일 연산.
- **0.99 ≤ x < 0.9999** → 재현 가능으로 판정하되, 완전 동일
  연산은 아닐 가능성(예: JPEG 재인코딩 손실 등 사소한 차이)을
  같이 등록.
- **0.90 ≤ x < 0.99** → "비슷하지만 다른 모델/버전/전처리" 수준
  — **재현 불가로 판정.**
- **< 0.90** → 명백히 다른 벡터 — **재현 불가로 판정.**

**이분 판정선은 0.99다** — 이상이면 "재현 가능", 미만이면 "재현
불가"로 트랙을 멈춘다.

**이번 5건·이번 transformers 버전(5.15.0)에서 확인된 사실**이지,
"어떤 버전 차이든 벡터가 안 바뀐다"는 일반 법칙으로 확대하지
않는다 — 모델 가중치 자체가 바뀌는 경우(예: `patrickjohncyh/
fashion-clip`이 새 리비전을 올리는 경우)는 이번 검증 범위 밖이다.

**1단계 통과 — 2단계(ONNX)로 진행한다.**

## 10. ONNX 경로 로컬 측정 (2026-08-13)

**동기 — 11초 중 진짜 중요한 숫자는 0.18초다.** §7 측정에서
콜드스타트 11.1~12.0초 중 첫 추론 자체는 ~0.18초뿐이었다 — 거의
전부(`import transformers` ~4.9초 + 모델 로드 ~4.1~4.7초 = 총
~9초)가 "파이썬 ML 스택을 올리는 비용"이었다. 추론만 할 거라면
`torch`도 `transformers`도 굳이 필요 없다 — `onnxruntime`으로
바꾸면 이 임포트·로딩 비용이 통째로 빠질 수 있는지 쟀다. **같은
변수 하나만 바꾼다**(양자화는 이번에 안 함, (d) 후보로만 등록).

### (a) ONNX 변환

`patrickjohncyh/fashion-clip`(1단계와 같은 모델·경로,
`CLIPModel.from_pretrained`)의 **이미지 인코더만** 감싸는 래퍼
(`get_image_features(...).pooler_output` → L2 정규화)를
`torch.onnx.export`(`torch 2.12.1+cpu`, dynamo 기반 익스포터,
`onnxscript` 설치 필요)로 변환했다. 텍스트 인코더는 이 트랙의
용도(이미지→벡터)에 안 쓰이므로(§1) 처음부터 그래프에서 뺐다 —
dynamo 트레이싱이 실제로 실행된 서브그래프만 캡처해 자동으로
텍스트 타워를 들어냈다(파일 크기가 이를 뒷받침 — 아래 참고).

- opset 17 요청 → 버전 변환 실패로 opset 18로 자동 폴백(경고만,
  변환 자체는 성공).
- **같은 프로세스 안에서 파리티 검증**(torch 출력 vs onnxruntime
  출력, 같은 더미 입력): 코사인 유사도 **1.0**, 최대 절대 오차
  **2.5×10⁻⁷**(부동소수점 잡음 수준) — 변환 자체는 수치적으로
  무손실이라고 봐도 된다.
- **산출물이 두 파일로 나뉜다**: 그래프 파일(`.onnx`, 1.4MB) +
  외부 가중치 파일(`.onnx.data`, 351.4MB) — 합계 **352.8MB**.
  §7의 전체 모델 fp32 추정(605.1MB)보다 작다 — 텍스트 인코더
  (전체 151.3M 중 vision 87.5M을 뺀 나머지)가 실제로 그래프에서
  빠졌다는 증거다.

### (b) 콜드스타트 측정 — §7과 같은 하네스, 완전히 새 프로세스 3회

`torch`/`transformers`는 이 스크립트에서 아예 임포트하지 않는다
— `onnxruntime` + `numpy` + `PIL`만 쓴다. 전처리는 1단계에서
`processor.image_processor`로 직접 확인한 실제 설정값(shorter-edge
224 리사이즈 BICUBIC, 224 center crop, rescale 1/255, CLIP
mean/std)을 수작업으로 재현했다(아래 (c)가 이 재현이 정확한지
검증한다).

| # | import onnxruntime | import numpy+PIL | 세션 로드(가중치 포함) | 첫 추론 | 콜드스타트 총합 |
|---|---|---|---|---|---|
| 1 | 0.410s | 0.029s | 0.681s | 0.051s | **1.356s** |
| 2 | 0.258s | 0.029s | 0.658s | (첫 추론에 포함) | **1.173s** |
| 3 | 0.167s | 0.017s | 0.730s | (첫 추론에 포함) | **1.154s** |

RSS(측정 시점) ~434MB(3회 모두 433.7~435.2MB) — §7의 torch+
transformers 버전(~772MB)의 약 56%.

### 비교표 갱신(§7 대비)

| 항목 | torch+transformers(§7) | onnxruntime(§10) | 배율 |
|---|---|---|---|
| 콜드스타트 총합(3회 평균) | ~11.5초 | ~1.23초 | **~9.4배 감소** |
| 가중치/모델 크기 | 605MB(fp32 전체 모델) | 352.8MB(이미지 인코더만, 그래프+외부데이터 합계) | ~42% 감소 |
| RSS(측정 시점) | ~772MB | ~434MB | ~44% 감소 |
| 판정(§7 기준, 5~20초=스파이크 필수) | 스파이크 필수 구간 | **5초 미만 — "클라우드에서도 합리적일 가능성" 구간** | — |

**판정 적용**: onnxruntime 경로의 로컬 콜드스타트(~1.2초)는 §7이
사전 등록한 기준의 **"< 5초" 구간**에 들어간다 — "클라우드에서도
합리적일 가능성이 있다"는 잠정 해석과 함께 Cloud Functions/Run
최소 인스턴스 0 스파이크를 제안할 수 있는 구간이다. **다만 이것도
로컬 값이다** — 배경 제거 §2-4가 로컬 1.29초→클라우드 68초로
50배 벌어진 전례가 있으므로, **이 1.2초도 클라우드에서 그대로
재현된다고 가정하지 않는다.** onnxruntime은 `rembg`처럼 무거운
불필요 의존성(예: `pymatting`/`numba`)을 안 끌고 오는 가벼운
런타임이라는 점에서 배경 제거의 **최종 채택 구성**(minimal_runtime,
클라우드 1.2~2.1초)과 성격이 더 가깝다 — 하지만 "성격이 비슷하다"는
관측이지 "수치가 같다"는 보장이 아니다.

### (c) ONNX 산출 벡터의 호환성 검증 — 1단계와 같은 5건, 같은 판정 기준

1단계와 **완전히 같은 선정 규칙**(카테고리별 itemId 오름차순
첫 건)으로 같은 5건을 다시 썼다. `export.py`의
`download_and_resize_image`로 512px 중간 이미지를 만든 뒤(1단계와
동일 — 이 경로는 안 바꿨다), 그 위에 (b)의 수작업 전처리 +
onnxruntime 추론을 적용해 저장된 벡터와 코사인 유사도를 쟀다.

| 카테고리 | itemId | 코사인 유사도(ONNX vs 저장값) | 1단계(transformers) 대비 |
|---|---|---|---|
| 상의 | `09v2UrBJX8GmeqMs5IBz` | 0.9999997920 | 거의 동일(둘 다 ≥0.9999) |
| 신발 | `2efbE3mfLC08D3OlEQDK` | 0.9999988078 | 거의 동일(둘 다 ≥0.9999) |
| 아우터 | `665OXTTw9jJB8uCxWfPf` | **0.9948499858** | **1단계는 1.0000000182 — 이번이 뚜렷이 낮다** |
| 액세서리 | `08IS2RoIPQgmoEsxbSeP` | **0.9985815256** | **1단계는 1.0000000288 — 이번이 낮다** |
| 하의 | `0PGRnY39FstR95fRVNTZ` | 0.9999995319 | 거의 동일(둘 다 ≥0.9999) |

**판정: 5건 전부 ≥ 0.99 → 이분 판정선 통과, "재현 가능".** 다만
등록한 3단 구분을 그대로 적용하면 5건 중 3건(상의·신발·하의)만
"≥0.9999(부동소수점 오차 수준)" 구간이고, **2건(아우터·액세서리)은
"0.99 ≤ x < 0.9999"(재현 가능하되 사소한 차이) 구간**이다 — 확대
해석하지 않고 있는 그대로 등록한다.

**원인 후보(확정 안 함, 등록만)**: 1단계(transformers `CLIPProcessor`)
대비 이번 2단계(수작업 전처리)에서만 유독 두 아이템이 더 벌어진
것으로 보아, `CLIPProcessor`의 리사이즈/센터크롭 구현과 내 수작업
구현(반올림 방식, 리사이즈 필터의 세부 구현체 차이 등) 사이에
**아이템의 원본 종횡비에 따라 갈리는 미세한 차이**가 있을 가능성이
있다 — 두 아이템이 유독 벌어진 이유(예: 정사각형이 아닌 원본
비율)를 이번엔 파고들지 않는다. 여전히 0.99 이상이라 실질적
유사도 검색 용도로는 문제없어 보이지만, 다음에 이 경로로 실제
구현할 때는 전처리를 `transformers` 없이도 픽셀 단위로 재검증하는
절차가 필요하다(배경 제거의 minimal_runtime이 34건 픽셀 단위
0.0000/255 동일성까지 검증했던 것과 같은 수준, §3 인용).

### (d) 양자화 — 시도 안 함, 후보로만 등록

이번엔 fp32 ONNX만 측정했다. fp16/int8 양자화는 변수를 하나 더
바꾸는 것이라 이번에 하지 않는다 — **다음 후보로만 등록**: 가중치
352.8MB를 int8로 양자화하면 이론상 ~4분의 1(약 88MB)까지 줄어들
수 있고, 콜드스타트의 남은 성분(세션 로드 ~0.7초)이 더 줄어들지
확인할 가치가 있다. 정확도 손실(코사인 유사도 저하 폭)은 별도
검증 필요.

### 결론 — 어느 스택으로 클라우드 스파이크를 할지 제안

**onnxruntime(이미지 인코더 전용 ONNX) 경로를 클라우드 스파이크
대상으로 제안한다.** 근거:
- 벡터 호환성 통과(위 (c), 5건 전부 ≥0.99).
- 로컬 콜드스타트가 §7 판정 기준의 "5초 미만" 구간으로 이동
  (~11.5초 → ~1.2초, ~9.4배 감소).
- 가중치·RSS 둘 다 축소(605MB→352.8MB, 772MB→434MB).

**다만 이 제안 자체가 클라우드 실측을 생략해도 된다는 뜻은
아니다** — §7이 이미 등록한 원칙(로컬로 클라우드를 추정하지
않는다) 그대로, 클라우드 스파이크는 여전히 필요하다. 달라진
것은 "무엇을 스파이크할지"이지 "스파이크가 필요한지"가 아니다.

**이번 세션은 로컬 측정까지다 — 클라우드 스파이크·배포에
착수하지 않았다. 승인을 기다린다.**

## 11. §10 (c)의 0.9948을 통과로 넘기지 않는다 — 원인 규명 (2026-08-13)

**문제 재정의**: 이분 판정선(0.99)은 통과했지만, §9(1단계, transformers
경로)가 보여준 "같다"의 실제 모습은 0.9999997이었다. 0.9948은 그보다
네 자릿수 낮다 — 부동소수점 오차가 아니라 실제 수치 차이이고, 이분
판정선 하나로 질적으로 다른 두 결과("사실상 동일"과 "어딘가 다르다")를
같은 "통과"로 묶은 것 자체가 문제였다(이 트랙 밖이지만 같은 형태의
함정을 자기평가 트랙이 SD 문턱에서 이미 겪었다).

**갱신된 판정 기준(결과 보기 전 고정)**: 이번엔 이분 통과선이 아니라
**§9가 보여준 수준(≥0.9999)을 목표로 잡는다.** 도달하면 "재현
복원"으로 등록하고 원인을 함께 남긴다. 도달 못 하면 거기서 멈추고
남은 차이의 크기와 좁힌 범위를 보고한다(지시 (d)).

### (a) 전처리 줄 단위 대조 — 원인이 코드 읽기만으로 나왔다

`§10`의 수작업 전처리(PIL `Image.resize(..., Image.BICUBIC)` 직접
호출)와 실제 `CLIPImageProcessor`(`transformers/models/clip/
image_processing_clip.py`)를 대조했다:

```python
# transformers/models/clip/image_processing_clip.py
class CLIPImageProcessor(TorchvisionBackend):
    resample = PILImageResampling.BICUBIC
    ...
```

`CLIPImageProcessor`가 상속하는 `TorchvisionBackend`
(`transformers/image_processing_backends.py:205-257`)의 `resize()`:

```python
def resize(self, image, size, interpolation, antialias: bool = True, ...):
    ...
    return tvF.resize(image, new_size, interpolation=interpolation, antialias=antialias)
```

**`tvF`는 `torchvision.transforms.v2.functional`이다 — PIL이 아니라
torchvision으로 리사이즈한다, 기본값 `antialias=True`.** 즉 §10의
수작업 구현(PIL `Image.resize`, 안티앨리어싱 옵션 없음)과 실제
경로(torchvision `resize`, 안티앨리어싱 적용)는 **"둘 다 bicubic"
이라는 이름은 같지만 다운샘플링 시 적용하는 커널이 다르다** — 이게
0.99 대 유사도를 만든 진짜 원인이다(모델 자체는 §10(a)에서 이미
파리티 1.0으로 무결함이 확인됐다 — 차이는 입력 쪽에 있다는 지목이
정확했다). 이 발견은 코드를 읽는 것만으로 나왔고, 실행 전에 원인을
좁혔다.

**대조 결과 요약**:

| 항목 | §10 수작업 구현 | 실제 `CLIPImageProcessor` |
|---|---|---|
| 리사이즈 엔진 | PIL `Image.resize` | torchvision `tvF.resize`(`TorchvisionBackend`) |
| 안티앨리어싱 | 없음(PIL 기본 bicubic) | `antialias=True`(기본값) |
| 리사이즈 대상 | shorter-edge 224 | shorter-edge 224 — **동일** |
| 중앙 크롭 | 224×224, 수작업 반올림 | 224×224, `tvF.crop` |
| 정규화 상수(mean/std) | `OPENAI_CLIP_MEAN/STD`와 동일 값 하드코딩 | `OPENAI_CLIP_MEAN/STD` — **동일** |
| rescale(1/255) | 있음 | 있음 — **동일** |
| dtype/채널 순서 | float32, NCHW | float32, NCHW(내부 텐서) — **동일** |

**차이는 리사이즈 엔진·안티앨리어싱 하나뿐이다.**

### (b) 수정 — 재구현하지 않고 `CLIPProcessor`를 그대로 호출

지시대로 재구현하지 않았다. 검증 스크립트가 `export.py`의
`download_and_resize_image`(1단계 대상, 원래도 공유하고 있었다)에
더해, **224 전처리 단계도 `CLIPProcessor.from_pretrained(...)`를
그대로 호출**해 `pixel_values`를 얻고, 그 텐서만 onnxruntime
세션에 넣도록 바꿨다 — 리사이즈·크롭·정규화 코드를 내가 다시
짜지 않는다.

**중요한 한계를 여기서 명시한다**: 이 수정은 **검증 스크립트의
정확성 확인용**이지 프로덕션 콜드스타트 경로의 해법이 아니다 —
`CLIPProcessor`를 쓰면 다시 `transformers`+`torch`(§7이 무겁다고
지목한 그 스택)가 필요해진다. 이 수정으로 "ONNX 모델과 전처리가
정확히 무엇을 재현해야 하는가"는 확정되지만, "그걸 무거운 임포트
없이 어떻게 재현할지"는 여전히 열린 문제다 — §12에서 다룬다.

### (c) 재실행 결과 — 재현 복원됨

같은 5건, 같은 선정 규칙. `export.py`의 `download_and_resize_image`
(1단계 대상 확보, 원래도 공유)로 512px 중간 이미지를 만든 뒤,
**224 전처리를 `CLIPProcessor.from_pretrained(...)` 그대로 호출**해
`pixel_values`를 얻고, 그 텐서만 onnxruntime 세션에 넣었다.

| 카테고리 | itemId | §10(수작업 전처리) | §11(c)(CLIPProcessor 재사용) | 목표(§9 수준, ≥0.9999) |
|---|---|---|---|---|
| 상의 | `09v2UrBJX8GmeqMs5IBz` | 1.0000000e+00(참고: §9) | 0.9999997545 | ✅ |
| 신발 | `2efbE3mfLC08D3OlEQDK` | 1.0000000e+00(참고: §9) | 0.9999999436 | ✅ |
| 아우터 | `665OXTTw9jJB8uCxWfPf` | **0.9948499858** | **0.9999998839** | ✅ (0.995→1.000, 4자릿수 개선) |
| 액세서리 | `08IS2RoIPQgmoEsxbSeP` | **0.9985815256** | **0.9999997666** | ✅ (0.999→1.000) |
| 하의 | `0PGRnY39FstR95fRVNTZ` | 1.0000000e+00(참고: §9) | 0.9999998960 | ✅ |

**5건 전부 ≥0.9999997 — 목표(§9 수준) 도달, "재현 복원"으로
등록한다.** 특히 §10에서 유독 낮았던 아우터(0.9948→0.99999988)와
액세서리(0.9986→0.99999977)가 §9 수준까지 회복됐다 — (a)에서
지목한 원인(torchvision 안티앨리어싱 리사이즈 vs PIL 비-안티앨리어싱
리사이즈)이 실제 원인이었다는 것을 5건 실측이 직접 뒷받침한다.
가설을 확정한다(추측이 아니라 재현 실측으로 닫힘).

## 12. 남은 열린 문제 — 프로덕션 전처리를 가볍게 재현하는 법 (등록만)

§11(b)에서 명시한 한계가 여전히 유효하다. **검증은 닫혔지만
구현 경로는 안 열렸다** — `CLIPProcessor`를 그대로 쓰면 콜드스타트
개선(§10, 11.5초→1.2초)이 다시 사라진다(`transformers`+`torch`
재도입). 이 트랙이 구현에 착수하지 않으므로 여기서 풀지 않고
다음에 실제 구현할 때 풀어야 할 문제로만 등록한다:

- **후보 1 — torchvision만 가져오기.** `transformers` 전체가
  아니라 `torchvision.transforms.v2.functional.resize(...,
  antialias=True)` + `crop`만 직접 호출하면 `CLIPImageProcessor`와
  같은 리사이즈 커널을 쓰면서도 `transformers` 임포트는 피할 수
  있을지 모른다 — 다만 `torchvision`도 `torch`에 의존하므로
  §7의 "import torch"(~1.9초) 비용은 그대로 남는다(그래도
  `transformers`의 ~4.9초는 없앨 수 있다).
- **후보 2 — 안티앨리어싱 리샘플링 커널을 numpy로 정확히
  재현.** torchvision의 `interpolate`가 쓰는 안티앨리어싱
  bicubic 커널을 수작업으로 재구현 — 가능하지만 이번에 겪은
  것과 같은 미세한 불일치 위험을 다시 감수해야 한다. 권장하지
  않음(등록만).
- **후보 3 — Pillow의 `reducing_gap`/`Image.thumbnail` 등 PIL
  자체의 고품질 다운샘플링 옵션을 재검토.** PIL도 안티앨리어싱
  리사이즈를 지원하지만 torchvision과 알고리즘이 다를 수 있어
  똑같이 검증이 필요하다.

**판정 기준(등록만, 이번에 재지 않는다)**: 어느 후보를 골라도
§11의 방법론(같은 5건, 목표 ≥0.9999)으로 재검증해야 "재현 가능"을
주장할 수 있다 — 검증 없이 "가벼워졌으니 됐다"고 넘기지 않는다.

### 추가 로컬 측정 — "검증된 경로"가 실제로 얼마나 가벼운지 먼저 쟀다

스파이크 대상을 정하기 전에, 위 후보들을 고르지 않고도 답할 수
있는 질문이 하나 있었다 — **§10의 큰 개선(11.5초→1.2초)이
`CLIPModel`(605MB 가중치)을 안 실은 덕분이었나, 아니면 전처리
자체가 가벼워서였나?** §11(c)에서 검증에 쓴 조합
(`CLIPProcessor`만 로드 + `onnxruntime`으로 추론, `CLIPModel`은
안 씀)의 콜드스타트를 새 프로세스 2회로 격리해서 쟀다:

| # | import torch | import transformers | `CLIPProcessor.from_pretrained` | import onnxruntime | 총합(모델 가중치 로드 제외) |
|---|---|---|---|---|---|
| 1 | 1.805s | 4.005s | 3.424s | 0.074s | **9.375s** |
| 2 | 1.561s | 3.860s | 4.426s | 0.067s | **9.974s** |

**답은 "전처리 자체가 무겁다"였다 — 예상 밖이었다.** `CLIPModel`의
605MB 가중치를 아예 안 실었는데도(onnxruntime 세션 로드 ~0.7초
별도 추가하면 총 ~10.1~10.7초) §7의 원래 총합(~11.5초)과 **겨우
1~1.5초밖에 차이 나지 않는다.** `CLIPProcessor.from_pretrained`
자체가 3.4~4.4초나 걸린다(토크나이저·설정 로딩 등, 큰 가중치가
없는데도) — **"모델이 무겁다"가 아니라 "`transformers` 패키지
자체(임포트 + `.from_pretrained()` 초기화)가 무겁다"는 것이
진짜 병목이었다.**

**함의 — §10의 9.4배 개선은 절반이 부정확한 전처리 덕이었다.**
§10이 보여준 극적인 개선(11.5초→1.2초)은 **§9(1단계)가 이미
증명한 "검증된" 경로가 아니라, 이번에 틀렸다고 밝혀진 수작업
전처리(PIL 비-안티앨리어싱 리사이즈) 버전에서 나온 수치였다.**
**검증된 경로(`CLIPProcessor`+onnxruntime)의 실제 콜드스타트는
~10.1~10.7초로, §7의 판정 기준(5~20초 = 스파이크 필수)에서
전혀 벗어나지 못했다** — "5초 미만" 구간으로 이동했다던 §10의
결론은 **부정확한 벡터를 낸 구성에서만 성립**했던 것이었다.

### 그래서 무엇을 스파이크하는가

이 발견이 스파이크 대상을 바꾼다:

- **검증된 경로(`CLIPProcessor`+`onnxruntime`, ~10.1~10.7초 로컬)**
  는 여전히 §7 기준 "스파이크 필수" 구간이고, **부정확한 벡터를
  낼 위험이 없는 유일한 후보**다.
- §12의 세 후보(torchvision 직접 호출 등)는 **콜드스타트를 더
  줄일 수 있는 유일한 방향**이지만, 이번에 검증하지 않았다 —
  스파이크하면 "빠르지만 벡터가 맞는지 모르는" 결과가 나온다.

**결정(제안, 승인 필요)**: 이번 스파이크는 **검증된 경로
(`CLIPProcessor`+`onnxruntime`)를 그대로 컨테이너에 올려서**
콜드스타트·메모리를 잰다 — "느릴 수 있지만 벡터는 맞다"는 기준선을
먼저 확보한다. §12의 경량화 후보(torchvision 직접 호출 등)는
**이 기준선을 확보한 뒤에, 그리고 §11과 같은 방법론으로 벡터
정확성을 다시 검증한 뒤에만** 별도로 재고한다 — 이번 스파이크
범위에 넣지 않는다.

### (a) 범위 — 최소 기능 엔드포인트 하나

이미지 1장을 받아 512차원 벡터를 반환하는 것까지다. Firestore

### (d) 비용 추정

**스파이크 자체**: 콜드 3회+웜 3회, `max_instances=1`로 제한 —
배경 제거 스파이크 실측(콜드 5회+웜 2회 ≈350 vCPU-초, 무료 등급의
0.19%)과 같은 자릿수일 것으로 예상한다(모델 로딩 시간이 더 길
수 있어 vCPU-초 자체는 더 클 수 있으나, 여전히 무료 등급 월
180,000 vCPU-초 대비 미미할 것으로 추정 — 실측 전까지는 추정으로만
남긴다).

**실제 운영 시 예상 비용(등록 빈도 가정 명시)**:
- **가정: 옷 등록이 며칠에 한 번**(배경 제거가 이미 쓴 가정,
  §2-3 인용 — 이 저장소의 실제 사용 패턴 그대로 재사용).
- `min_instances=0`으로 확정되면: 요청당 과금, 이 빈도에서는
  무료 등급 내일 가능성이 높다(배경 제거와 같은 결론).
- `min_instances=1`로 가야 하면: 1GiB 약 $56/월, 2GiB 약 $62/월
  (배경 제거 §2-3이 확인한 공식 가격표, 같은 리전·같은 과금
  방식이라 그대로 재사용). 등록 빈도가 며칠에 한 번인 워크로드에
  상시 인스턴스는 과하다는 배경 제거의 판단 근거가 여기도
  적용되지만, 이건 판단 근거 등록이지 스파이크 결과가 5~20초로
  나왔을 때 자동으로 `min_instances=0`을 고수하라는 뜻은 아니다
  (위 (c) 참고, 트레이드오프는 사용자가 정한다).

## 14. 배포 직전 마지막 로컬 측정 — torchvision 직접 호출 변형 (2026-08-13)

**동기**: §11(추가 로컬 측정)이 병목을 `transformers` 패키지
자체(임포트 + `CLIPProcessor.from_pretrained()`)로 좁혔다. 우리가
`transformers`에서 실제로 쓰는 건 `CLIPImageProcessor`(정확한
설정값은 이미 코드로 확인됨, §9/§11) 하나뿐이고, §11(a)가 원인을
`torchvision.transforms.v2.functional.resize(antialias=True)`로
이미 지목했다 — **`transformers`를 거치지 않고 그 함수를 직접
부르면 파리티가 나올 개연성이 있다는 뜻**이므로 "미검증 후보"가
아니라 "이제 검증 가능해진 후보"다.

**판정 기준(결과 보기 전 고정, 낮추지 않는다)**: 5건 전부
코사인 유사도 **≥ 0.9999997**(§11이 실제로 도달한 수준)이면
"파리티 통과" → 콜드스타트를 마저 측정한다. **하나라도 미달이면
그 자리에서 폐기** — 원인을 더 파지 않고 검증된 경로
(`CLIPProcessor`+`onnxruntime`)로 스파이크한다. 이 트랙은 변형을
**하나만** 만든다.

### (a) 전처리 로직 — 코드에서 그대로 옮김(기억·문서 참조 아님)

`image_processing_backends.py`의 `get_resize_output_image_size`와
`TorchvisionBackend.center_crop`을 이번에 다시 직접 읽고, **§10에서
놓쳤던 세부 사항 하나를 더 발견했다**:

```python
# get_resize_output_image_size — 반올림(round)이 아니라 절삭(int)이다
new_short, new_long = requested_new_short, int(requested_new_short * long / short)
```
```python
# TorchvisionBackend.center_crop — 여기도 절삭(int)이다
crop_top = int((image_height - crop_height) / 2.0)
crop_left = int((image_width - crop_width) / 2.0)
```

§10의 수작업 구현은 두 곳 다 `round()`를 썼다 — 안티앨리어싱
유무(§11(a)가 이미 지목)에 더해 **반올림/절삭 차이도 있었다**는
뜻이다. 이번 변형은 리사이즈를 `tvF.resize(..., interpolation=
BICUBIC, antialias=True)`로, 크롭 좌표 계산을 `int()` 절삭으로,
전부 이 코드 그대로 옮겼다.

**이건 컨테이너 이미지 전체 크기가 아니라 그 안에 들어갈 파이썬
패키지+모델 파일의 합계다** — Cloud Functions/Run의 Python
베이스 이미지(OS 레이어, 파이썬 런타임 자체, 빌드팩 오버헤드)가
따로 더해진다. 그 베이스 크기는 이번에 재지 않았다(등록만) —
실제 빌드된 이미지 크기는 배포 후 Artifact Registry에서 직접
확인해야 정확하다. **또한 이 측정은 Windows CPU 빌드다** — Cloud
Functions는 Linux 컨테이너이므로 `pip install`이 받는 실제 wheel이
다를 수 있다(보통 비슷한 자릿수이나 동일하다고 가정하지 않는다).

**빌드 노트로 등록**: `requirements.txt`에 CPU 전용 `torch` 인덱스
(`--index-url https://download.pytorch.org/whl/cpu` 또는 동등한
방법)를 명시해야 한다 — 기본 PyPI 인덱스의 `torch`는 CUDA 빌드를
같이 끌고 와 이보다 훨씬 커질 수 있다(이번 로컬 환경은 이미
`torch 2.12.1+cpu`라 이 문제를 우연히 피했다 — 스파이크
`requirements.txt`에서는 명시적으로 강제해야 한다).

### (c) 롤백 절차 보강 — Artifact Registry 이미지 정리 단계 추가

**현재 §13(e) 롤백 절차의 빈틈**: "함수 삭제"만 있고 컨테이너
이미지 정리가 없다. Cloud Functions v2/Cloud Run은 배포마다
컨테이너 이미지를 **Artifact Registry**(또는 구 Container
Registry)에 쌓는다 — 함수를 지워도 그 이미지들은 별도로 지우지
않으면 남아 저장 비용을 계속 낸다.

**`bgremovalspike` 정리 때 이미지까지 지웠는지 확인했다 — 지우지
않은 것으로 보인다.** `handoff_2026-08-04.md:1224`의 정리 기록
(위 (a) 인용)에는 `firebase functions:delete`와 `firebase.json`
코드베이스 항목 제거만 있고, Artifact Registry 이미지 삭제 명령이나
확인 절차가 없다. `task_background_removal_v1.md`에서도 Artifact
Registry 관련 언급을 찾지 못했다(위에서 확인). **즉 `bg_removal_
coldstart_spike`가 만든 컨테이너 이미지가 지금도 Artifact Registry에
남아 있을 가능성이 있다** — 이번엔 확인도 삭제도 하지 않는다
(콘솔 접근 필요 + 금지 사항: 기존 이미지 삭제 금지). **이 자체를
결함으로 등록한다**: 이 저장소의 스파이크 정리 절차가 지금까지
컨테이너 이미지 계층을 빠뜨려 왔다.

**보강된 롤백 절차(§13(e) 원문 유지, 여기 덧붙임)**:
1~4번은 §13(e) 그대로.
5. **(신규) Artifact Registry에서 이 스파이크가 만든 이미지를
   확인하고 지운다.** 리전 `asia-northeast3`, 저장소 이름은 보통
   `gcf-artifacts`(Cloud Functions v2 기본) — `gcloud artifacts
   docker images list` 또는 콘솔 → Artifact Registry에서
   `embeddingspike`/`bg_removal_coldstart_spike` 등 함수명이 포함된
   리포지토리를 찾아 확인한다.
6. **(신규) 정리 후 실제로 지워졌는지 확인하는 법**: 같은 조회
   명령을 다시 실행해 목록에서 사라졌는지 확인하거나, Storage
   사용량(콘솔 → Artifact Registry → 저장소별 크기)이 줄었는지
   확인한다.

**`bg_removal_coldstart_spike`의 남은 이미지 자체는 지금 지우지
않는다** — 이번 트랙 범위 밖이고, 지시 사항(기존 이미지 삭제
금지)이기도 하다. 등록만 하고 다음에(배경 제거 트랙을 다시 다룰
때) 처리한다.

### (d) 요약과 배포 승인 요청

**한 줄 요약**: 스파이크 자체(콜드 3회+웜 3회, `max_instances=1`,
`min_instances=0`)는 배경 제거 선례(무료 등급 내로 추정되나 실측
청구액은 미확인)와 같은 자릿수일 가능성이 높지만 **확정 근거는
없다** — 실제 청구액은 GCP 콘솔에서 사용자가 직접 확인해야

자체가 이번에 새로 드러난 결함**이다 — 이번 스파이크의 롤백에는
그 단계를 포함한다.

이대로 배포를 진행해도 될지 확인해 달라 — (a)의 청구 내역은
사용자가 별도로 콘솔에서 확인해 주셔야 한다(이 세션 도구로는
못 본다).

## 17. 배포 직전 확인 (2026-08-13, 무료 — 배포 전)

### (a) 호출 인증 경로 — 명령을 손에 쥔 상태로 배포에 들어간다

배경 제거 스파이크가 실제로 쓴 호출 명령은 문서에 남아 있지
않았다(`task_background_removal_v1.md`/`handoff_2026-08-04.md`
전수 검색, 못 찾음) — **재사용할 전례 명령이 없어서 새로

`invoker=[_ADMIN_SA]`(Cloud IAM 수준 제한)를 호출하려면 그
서비스 계정 자격으로 발급된 **OIDC ID 토큰**(대상 함수 URL을
audience로 함)이 필요하다. `gcloud` CLI가 이 환경에 없으므로
(§15(a)에서 이미 확인), **서비스 계정 키 파일로 Python에서 직접
ID 토큰을 발급**하는 경로를 준비했다(`google.oauth2.service_account.
IDTokenCredentials.from_service_account_file`, `google-auth`
라이브러리 — 이미 `firebase_admin`의 의존성으로 설치돼 있어
추가 설치 없이 사용 가능함을 확인).

URL을 audience로 하는 ID 토큰을 얻어 `Authorization: Bearer`
헤더로 POST한다.

없을 때의 1x1 JPEG 폴백(`main.py`에 이미 구현됨)은 순수 콜드스타트

## 18. 배포 (2026-08-13)

### 장애물 — 로컬 배포 검사 10초 타임아웃, `core.init`으로 우회

**1차 배포 시도가 실패했다**: `firebase deploy --only
functions:embeddingspike:embedding_coldstart_spike` 실행 직후
`Error: User code failed to load. Cannot determine backend
specification. Timeout after 10000`. `firebase-debug.log`를 직접
읽어 원인을 좁혔다 — `functions.yaml`이 없으면 Firebase CLI가
**로컬에서 함수를 한 번 임포트해(HTTP discovery) 시그니처를
알아내는 단계**를 거치는데, 이게 10초 안에 끝나야 한다. 우리
모듈 스코프의 무거운 임포트(`torch`+`torchvision`+`onnxruntime`)와
352.8MB ONNX 모델 로딩이 이 10초를 넘겼다 — **실제 Cloud Run
콜드스타트와는 별개의, 로컬 전용 제한**이다.

Firebase 공식 문서("avoid deployment timeouts during
initialization")를 확인해 원인과 해법을 대조했다: 무거운 초기화를
`firebase_functions.core.init` 훅으로 감싸면 **로컬 배포 검사
단계에서는 건너뛰고, 실제 배포된 인스턴스가 뜰 때만 실행된다.**
`main.py`를 이 패턴으로 재구성했다(로직은 그대로, 실행 위치만
모듈 스코프→`@core.init` 콜백으로 이동, 커밋 `b1dc67e`) — **콜드
스타트 측정 유효성에는 영향 없다**: 공식 문서가 `init` 훅을
"인스턴스당 1회, 함수 코드 실행 전"으로 명시하고 있어 여전히
