# 작업 지시서 — 신규 등록 아이템 실시간 임베딩 트랙 (task_realtime_embedding_v1)

## 0. 이 트랙의 위치와 승계 원칙

`task_selfeval_validity_v1`(자기 평가 척도 검증, 커밋 `e0c68f6`) →
`task_selfeval_followup_v1`(자기 평가 후속 조치, App Check·폴백
판정 제외, 종결)의 다음 축이다. 사용자 결정으로 자기평가 축은
접었다 — 자기평가가 남긴 결함(폴백 응답 후보의 최종 추천 구조적
우위)은 등록만 된 채 열려 있고, 다음에 그 코드를 만질 때
처리한다(`docs/handoff_2026-08-07.md` §4 참고, 이 트랙에서
손대지 않는다).

**승계 원칙은 옮겨 적지 않는다** — `task_selfeval_followup_v1.md`
§0(그 문서가 `task_selfeval_validity_v1.md` §0을 가리키고, 그
문서는 다시 `task_hardening_v2.md` §0을 가리킨다)을 그대로
참조한다. 판정 기준 사전 등록, 계측 우선, 미확정 불인정, 재빌드
대조, "무료 진단 먼저", 측정 하네스 우선 원칙 — 전부 그 링크를
따라간다.

**기록 원칙**도 `docs/handoff_2026-08-07.md` §2를 그대로 따른다
(원문을 지우지 않고 정정 블록을 덧붙인다, 실측치에 재현 코드를
남긴다, 추정을 실측으로 포장하지 않는다 등).

**이번 세션의 범위: 조사와 설계 후보 제시까지다. 구현·배포에
착수하지 않는다.**

## 1. (a) 현재 파이프라인 정밀 확인 (2026-08-13, 코드 확인)

수동 3단계 배치다. 신규 등록 시점에 자동으로 걸리는 트리거가
**어디에도 없다** — 세 스크립트 전부 개발자가 로컬에서 직접
실행해야 한다.

| 단계 | 스크립트 | 입력 | 출력 | 실행 주체 |
|---|---|---|---|---|
| 1 | `tools/export_for_kaggle/export.py` | Firestore `wardrobe` 컬렉션(Admin SDK로 직접 읽음, `isDemo` 제외, `--owner-uid`로 좁힐 수 있음) + Storage 이미지(cutout 우선, 없으면 원본) | `output/images/{itemId}.jpg`(긴 변 512px 리사이즈, 투명 배경은 흰색 합성 후 JPEG) + `items.csv`/`items.json`(6개 속성 + 메타데이터) + `history.json` + `matcher_spec.md`, 전부 `wardrobe_export.zip`으로 묶임 | 개발자, 로컬 |
| 2 | `tools/export_for_kaggle/kaggle_embedding_comparison.ipynb` | 1단계 zip을 Kaggle에 업로드 | `embeddings.json`(3종 모델 비교 — OpenCLIP ViT-B/32, **FashionCLIP 2.0**, EfficientNet-B0 대조군. 실제 채택된 것은 FashionCLIP) | 개발자, Kaggle 노트북(GPU) |
| 3 | `tools/backfill_embeddings/backfill.py` | 2단계 `embeddings.json` | Firestore `wardrobe/{itemId}.embedding` 필드 쓰기(기본 dry-run, `--apply`로만 실제 반영) | 개발자, 로컬 |

**FashionCLIP 추출 코드(Kaggle 노트북, 2단계) 확인**:
```python
from transformers import CLIPModel, CLIPProcessor
fashionclip_model = CLIPModel.from_pretrained("patrickjohncyh/fashion-clip").to(DEVICE).eval()
fashionclip_processor = CLIPProcessor.from_pretrained("patrickjohncyh/fashion-clip")
# ...
feats = F.normalize(fashionclip_model.get_image_features(**inputs), dim=-1).cpu().numpy()
```
`transformers`의 `CLIPModel`(HuggingFace) — CLIP 아키텍처(ViT-B/32
기반) 그대로, 이미지 인코더만 쓴다(`get_image_features`, 텍스트
인코더는 이 용도에 안 씀). `torch` 배치 추론(`batch_size=32`),
`F.normalize`로 L2 정규화.

**Firestore 저장 형태(3단계, `backfill.py:203-215`로 확인)**:
```
wardrobe/{itemId}:
  embedding:
    model:     "fashionclip"        # embeddings.json에 박힌 값
    dim:       512
    vector:    [float, ...]         # 길이 512, L2 정규화(저장 전 norm 0.99~1.01 검증)
    createdAt: <클라이언트 UTC 시각>  # SERVER_TIMESTAMP 아님(update()의 필드 경로 충돌 회피)
```
실제 `embeddings.json`(현재 저장소 파일)을 읽어 확인: `model:
"fashionclip"`, `dim: 512`, 103개 아이템. `category=="전신"`인
문서는 컷아웃이 아니라 착장 스냅이라 대상에서 스킵, 이미 `embedding`
필드가 있는 문서는 `--force` 없으면 스킵.

## 3. (c) FashionCLIP 실행 위치 후보 비교

**배경 제거(`functions_bg_removal`, `task_background_removal_v1.md`
§2-3~2-6)의 실측 수치를 인용하기 전에, 그 수치가 어느 구성에서
나온 것인지부터 확인했다 — 그대로 옮겨 쓸 수 있는 것과 없는 것이
갈린다.**

**배경 제거 실측의 진짜 원인(중요, 인용 전 확인)**: §2-4가 처음
관측한 68~70초 콜드스타트는 **모델(u2netp)도 onnxruntime도 원인이
아니었다** — `rembg` 패키지가 모듈 로드 시점에 `pymatting.alpha`를
무조건 임포트하는데, 이 경로는 실제로 쓰이지 않는 죽은 코드였다
(`alpha_matting=False`가 기본값). `pymatting`→`numba`(LLVM JIT
초기화)로 이어지는 무거운 임포트 체인이 클라우드 콜드 컨테이너의
느린 디스크 I/O에서 로컬 대비 극단적으로 불균형하게 느려진 것이
원인이었다(§2-5). 이 체인을 걷어낸 `minimal_runtime`(bare
onnxruntime, `rembg` 없이 직접 호출)으로 교체하자 콜드스타트가
**64~70초 → 1.2~2.1초**(GCP 공식 `startup_latencies` 지표,
§2-6)로 떨어졌다 — 이게 지금 배포된 구성이다.

**→ FashionCLIP에 그대로 적용 가능한가**: **68초 쪽은 적용 불가로
적는다.** 그 수치는 `rembg`라는 특정 패키지의 죽은 코드 임포트가
만든 이례적 현상이지, "Python ONNX 비전 모델을 서버리스에 올리면
느리다"는 일반 법칙이 아니다. Kaggle 노트북이 쓰는 경로는
`transformers`+`torch`(`CLIPModel.from_pretrained`)이지 `rembg`가
아니므로 그 68초의 원인(죽은 `pymatting` 임포트)이 그대로 재현될
근거가 없다. **다만 같은 위험 범주(무거운 ML 라이브러리의 임포트
체인이 콜드스타트를 지배한다)는 FashionCLIP 쪽에도 그대로 열려
있다** — `torch`+`transformers` 임포트 자체가 로컬에서도 수 초가
걸리는 것으로 널리 알려져 있고(이번 세션에서 실측하지 않음), 이
조합이 클라우드 콜드 컨테이너에서 배경 제거와 비슷한 배율로
불균형하게 느려질지는 **미실측 — 비교 불가로 남긴다.** 1.2~2.1초
(minimal_runtime) 쪽은 "무거운 프레임워크 임포트를 걷어내면
콜드스타트가 급감한다"는 **패턴**으로는 참고할 수 있지만, 그
수치 자체가 FashionCLIP에도 나온다고 가정하지 않는다 — FashionCLIP을
CLIP 가중치를 ONNX로 export해 bare onnxruntime으로 돌리는 것이
가능한지(변환 난이도, 정확도 손실 여부)는 별도 확인이 필요하다.

**비용은 부분적으로 전이 가능하다.** Cloud Run 최소 인스턴스 1
상시 유지 비용은 `cloud.google.com/run/pricing`(asia-northeast3,
Instance-based billing) 공식 가격표 기준이므로 **메모리 구성만
맞으면 어느 모델이든 같은 표를 그대로 쓸 수 있다** — 1GiB 약
$56/월, 2GiB 약 $62/월(무료 등급 적용 후, 배경 제거 실측 인용).
다만 FashionCLIP(+torch+transformers)이 1GiB에 들어가는지는
확인 안 됨(§4 측정 후보).

### 최종 판정 — §20·§21 결론 반영 (2026-08-13, 표는 원문 그대로 둔다)

**표 작성 시점엔 "미실측"이던 항목들이 §17~§21에서 전부 실측·
판정됐다 — 원문 표는 지우지 않고, 이 절에서 결론만 덧붙인다.**

**채택: 1행("Cloud Functions(Python), Storage 트리거") — 배경
제거와 같은 구조, `min_instances=0`.** 근거:

- **콜드스타트·비용은 이제 미실측이 아니라 실측이다**
  (§19: GCP 공식 `request_latencies` 기준 평균 15.75초, §21:
  이 지연을 지켜보는 사용자 화면이 없음을 코드로 확인). 표 작성
  시점의 우려("무거운 임포트 체인이 배경 제거와 같은 함정에
  빠질지 미확인")는 해소됐다 — 빠지긴 했지만(로컬 대비 3.2배,
  §19), 배경 제거만큼 극단적이지 않았고(§19의 "죽은 코드 임포트
  없음" 분석), 무엇보다 **그 지연 자체가 사용자에게 안 보이므로
  판정에 영향이 없다**(§21).
- **2행(Cloud Run 상시 인스턴스 1)은 §21로 기각한다.** 상시
  비용($56/월)을 낼 이유였던 "콜드스타트 제거로 사용자 체감
  개선"이라는 전제 자체가 §21에서 무너졌다 — 지켜보는 사용자가
  없으므로 콜드스타트를 없애도 체감이 개선되지 않는다.
- **3행(온디바이스)은 검토할 이유가 사라진다.** 존재 이유가
  "콜드스타트·상시 비용 문제 회피"였는데, 그 문제가 애초에
  사용자에게 보이지 않는 문제였다면 회피할 대상 자체가 약하다.
  변환 난이도(높음)라는 비용만 남고 얻는 이득이 없다.
- **4행(외부 API)도 같은 이유로 기각한다.** 벤더 SLA·과금·데이터
  정책이라는 새 리스크를 감수하고 얻는 것이 "콜드스타트 회피"인데,
  그 콜드스타트가 사용자에게 안 보이므로 감수할 이유가 약하다.

**남은 미확정은 성능이 아니라 비용 축 — 아래 "웜 이상 —
성능 축은 닫히고 비용 축은 열려 있다" 참고.**

### 결측 46벌 백필 — 이 트랙 범위 밖으로 확정

§5(사용자 결정 2026-08-13)가 이미 이 트랙의 목표를 **"신규
등록분에 벡터를 붙인다"**로 좁혀 뒀다(188-235) — 문언 그대로
읽으면 **기존에 이미 결측인 아이템(§2 기준 46벌, 이후 등록 증가로
더 늘었을 수 있음)을 소급 처리하는 것은 이 문장에 포함되지
않는다.** 실시간 트리거를 붙여도 **그 시점 이후 신규 등록분만**
자동으로 채워지고, 기존 46벌은 트리거 배포와 무관하게 여전히
결측 상태로 남는다 — §4(183-186)가 이미 "별도 결정 사항(이번엔
등록만)"으로 미뤄 둔 그대로다. **범위 밖으로 확정한다 — 이번
트랙에서 처리하지 않는다.**

백필 후보만 등록한다(**구현하지 않는다**):

1. **기존 수동 배치를 한 번 더 돌린다** —
   `tools/export_for_kaggle/export.py` →
   `kaggle_embedding_comparison.ipynb` → `tools/backfill_embeddings
   /backfill.py`. 이미 동작이 확인된 경로이고 새 코드가 필요
   없다 — 가장 낮은 리스크. 다만 개발자 수동 실행 3단계가
   그대로 남는다(§1이 이미 이 파이프라인 자체의 결함으로 지적한
   부분).
2. **실시간 트리거 함수에 "기존 문서 훑기" 모드를 추가한다** —
   본 구현 범위를 넘는 새 코드(일괄 조회+순차 처리+속도 제한)가
   필요해 이 트랙(조사·설계까지)의 범위를 벗어난다.
3. **아무것도 안 하고 다음 결측 실태 측정 때 다시 판단한다** —
   §2가 확인했듯 결측률은 계속 악화 방향이라(83%→68.6%), 방치
   비용이 시간이 갈수록 커진다는 점은 위험으로 남긴다.

이 세 후보 중 어느 것을 택할지는 본 구현 착수 시점에 결정한다
(이번 트랙 범위 아님).

### 웜 이상 — 성능 축은 닫히고 비용 축은 열려 있다 (§20 결론 보강)

§20이 "웜 이상"(같은 인스턴스인데 매 요청마다 초기화가 반복됨,
7~9초)을 원인 미확정으로 남겼고, §21은 "그 지연이 사용자에게
안 보이므로 성능 판정에는 영향 없다"고 결론지었다 — **이 결론은
성능(지연 시간) 축에서만 맞다. 비용 축은 별개로 여전히 열려
있다.**

**왜 별개인가**: Cloud Functions/Run 과금은 요청 처리 시간
(vCPU-초·GB-초) 기준이다(§13(d)/§16이 이미 확인한 과금 구조,
§17에서 실제 비용의 90%가 Functions 항목이었음도 확인). **매
요청이 초기화를 반복하면(웜 이상이 원인 불명인 채 실제로
발생하고 있다면) 등록 1건당 실행 시간이 0.2초가 아니라 7~9초로,
약 40배** 청구된다 — 지연이 사용자에게 안 보이는 것과 별개로,
**그 40배가 청구서에는 그대로 찍힌다.**

**지금은 무시할 수준이다** — 등록 빈도가 며칠에 한 번인 현재
워크로드(§2-3 인용)에서는 40배를 곱해도 절대액이 무료 등급
안에 있을 가능성이 높다(§13(d)/§16 추정 그대로). **하지만 이
결론은 현재 빈도에서만 유효하다** — 결측 46벌(또는 그 이상)을
백필하거나(위 항목) 사용자·등록 건수가 늘면, 이 40배 배율이
그대로 곱해져 무료 등급을 넘길 수 있다.

**등록**: 웜 이상은 성능 판정(min_instances 결정)에서는 닫혔지만,
**비용 예측에서는 열려 있는 미확정 항목이다.** 본 구현 착수
전에 확인해야 한다 — 그때 쓸 값싼 수단은 이미 §20에 등록해
둔 "재배포 없는 연속 8~10회 호출 진단"(gunicorn 워커 가설
반증 가능 예측)이다. **지금 실행하지 않는다** — 본 구현 착수
직전 항목으로 남긴다.

## 4. (d) 착수 전 측정할 것 (측정 하네스 우선 원칙, 후보 나열만 — 사전 등록)

**이 목록은 착수 순서가 아니라 "무엇을 재야 결정할 수 있는가"의
후보다. 판정 기준은 실제로 측정하기 전에, 결과를 보지 않은
상태에서 고정한다(다음 세션 이후 과제).**

- **FashionCLIP 추론 시간** — CPU 전용 환경(로컬 또는 Cloud
  Functions/Run과 유사 사양)에서 이미지 1장 처리 시간. 배치
  크기별(1장씩 실시간 처리 vs Kaggle 노트북의 batch_size=32)
  차이도 함께.
- **`torch`+`transformers` 임포트 시간** — 배경 제거의 `rembg`
  사례가 정확히 이 지점에서 틀렸으므로, 클라우드 콜드 컨테이너
  환경에서 직접 재보지 않고는 로컬 값을 못 믿는다(§2-4의 교훈
  그대로 재적용).
- **콜드스타트 실측** — 로컬 하한이 아니라 **실제 배포 후** GCP
  공식 지표(`startup_latencies`)로. 배경 제거가 로컬 추정(1.29초)과
  실측(68초)이 50배 어긋난 전례가 있으므로 로컬 값으로 판단하지
  않는다.
- **ONNX 변환 가능성과 정확도 손실** — FashionCLIP(CLIP ViT-B/32
  기반)을 ONNX로 export해 bare onnxruntime으로 돌릴 수 있는지,
  변환 후 임베딩이 원본 대비 얼마나 달라지는지(코사인 유사도
  등으로 검증). 가능하면 배경 제거의 minimal_runtime 패턴을 그대로
  재사용할 수 있다.
- **상시 인스턴스 비용 — 실제 메모리 요구량 확인 후 재계산** —
  1GiB/2GiB 어느 쪽이 필요한지 실측한 뒤 배경 제거 가격표에 대입.
- **기존 배치 결과와의 벡터 일치성** — 실시간 경로가 만드는 벡터가
  배치 경로(Kaggle, `transformers.CLIPModel`)가 만든 벡터와 같은
  분포/스케일인지. 다르면(예: ONNX 변환 후 미세한 수치 차이,
  전처리 파라미터 불일치) 기존에 백필된 94건과 신규 벡터가 섞였을
  때 유사도 비교가 깨질 수 있다 — 배경 제거의 minimal_runtime도
  픽셀 단위(0.0000/255) 동일성을 직접 검증했었다(§2-5), 같은
  수준의 검증이 필요하다.
- **결측 46건(§2) 백필 방식** — 실시간 트리거를 만들면 그 이후
  등록분만 자동으로 채워진다. 기존 결측 46건을 실시간 트리거
  배포와 별개로 배치 재실행할지, 실시간 트리거가 기존 문서도
  훑게 할지는 별도 결정 사항(이번엔 등록만).

## 5. (e) 범위 질문 — 답을 정하지 않고 등록만

목표를 어디까지로 둘지에 따라 설계가 갈린다. **결정하지 않는다
— 사용자에게 묻는다.**

**질문**: 이 트랙의 목표를 다음 중 어느 쪽으로 둘 것인가?

1. **"신규 등록분에 벡터를 붙인다"** — 지금 파이프라인이 다루는
   대상(사용자가 자기 옷장에 등록하는 아이템)에만 실시간 트리거를
   추가한다. 함의: 옷장 문서 생성/수정 이벤트(Firestore 트리거
   또는 이미지 업로드 시 Storage 트리거, 배경 제거와 같은 지점)에
   붙이면 된다 — 배경 제거의 구조를 거의 그대로 재사용할 수 있다.
   범위가 좁고 다음 단계(상점 옷 카탈로그 연결)를 위한 준비 단계
   성격이 강하다.
2. **"임의의 외부 카탈로그 아이템도 같은 파이프라인으로 벡터화한다"**
   — 처음부터 최종 목표(홈쇼핑·소규모 매장 옷)까지 염두에 두고
   설계한다. 함의: 옷장 문서 트리거가 아니라 **이미지 URL(또는
   업로드)을 받는 독립 엔드포인트**가 필요하다 — 인증·요청 한도·
   외부에서의 남용 방지(이 저장소가 이미 §3.11절 계열에서 겪은
   "프록시 호출량 상한" 문제와 같은 종류)를 처음부터 설계에
   넣어야 한다. 범위가 넓고, 지금 당장 상점 카탈로그 데이터
   소스가 없는 상태에서 설계만 앞서가는 위험도 있다.

각각의 함의만 적었다 — **어느 쪽을 택할지는 사용자가 정한다.**

### 사용자 결정 (2026-08-13) — 1번(신규 등록분만)

**결정: 1번.** 근거:

- **2번의 진짜 비용은 코드가 아니라 공격 표면이다.** 이미지 URL을
  받는 독립 엔드포인트는 `task_hardening_v2`가 다룬 문제를 전부
  다시 연다 — 익명 uid 무제한 생성, 호출량 상한, App Check, 요청
  본문 검증. 그런데 **지금 카탈로그 데이터 소스가 없다** — 소비자
  없는 엔드포인트를 위해 그 표면적을 여는 것은 나쁜 거래이고,
  소스가 정해지면 요구사항이 달라져 지금 만든 인증 설계를 다시
  손봐야 할 공산이 크다.
- **결측률이 악화 방향이다.** 인계 기록의 83%(99/119)가 지금
  68.6%(94/140, §2)로 떨어졌다. 옷은 늘고 벡터는 안 붙으므로
  배치를 한 번 더 돌려 메꿔도 다음 달에 같은 자리다.

**제약(설계에 명시적으로 반영할 것 — 다음 세션 이후 구현 시
지켜야 한다)**: 임베딩 계산부(모델 로딩·전처리·512차원 벡터
산출)를 **트리거와 분리해서** 설계한다. 1번과 2번이 다른 것은
"무엇이 계산부를 호출하는가"뿐이다(Storage 트리거 vs HTTP
엔드포인트) — 분리해 두면 나중에 2번으로 확장할 때 얇은 호출
계층 하나만 얹으면 된다. **이것은 "지금 안 쓸 기능을 만들라"가
아니라 "결합을 만들지 말라"는 제약이다** — 지금 엔드포인트를
만들지는 않는다(금지 사항).

## 7. 콜드스타트·메모리 측정 — 로컬 1차 스크리닝 (2026-08-13)

**성격이 다른 문제라는 지적을 그대로 받는다.** `rembg`의 68초는
임포트 오버헤드(죽은 코드)였지 모델 자체의 무게가 아니었다.
FashionCLIP은 반대로 **실제로 605MB급 가중치를 로딩해야 하는
모델**이다 — 원인이 다르므로 배경 제거의 결론(전이든 위안이든)을
그대로 갖다 쓰지 않는다. §3에서 이미 "비교 불가"로 유지한 판정을
그대로 두고, 이번엔 추측 대신 로컬에서 직접 쟀다.

### 판정 기준 (사전 등록, 결과 보기 전 고정)

이 저장소가 배경 제거에서 이미 쓴 기준을 그대로 가져온다
(`task_background_removal_v1.md`: "콜드스타트가 사용자 체감상
허용 범위 — 수 초~10초대는 자연스럽게 가려짐, 그 이상이면 문제").
**로컬 측정만으로는 최종 실행 위치를 확정하지 않는다** — 배경
제거 §2-4가 로컬 하한(1.29초)과 클라우드 실측(68초)이 50배
어긋난 전례를 남겼으므로, 로컬 값은 "클라우드 스파이크가 필요한지"
를 정하는 1차 스크리닝으로만 쓴다.

- **로컬 총 소요(임포트+모델로드+첫 추론) < 5초** → 클라우드에서도
  합리적일 가능성이 있다는 뜻으로만 해석. Cloud Functions/Run
  최소 인스턴스 0으로 클라우드 스파이크를 제안한다.
- **5초 ≤ 로컬 총 소요 < 20초** → 배경 제거의 로컬→클라우드
  배율(최대 50배) 전례를 감안하면 위험 구간이다. **클라우드
  스파이크가 필수**이고, 최소 인스턴스 1(상시)도 병행 후보로
  준비한다.
- **로컬 총 소요 ≥ 20초** → 로컬에서 이미 무겁다는 뜻이므로
  클라우드에서 더 나빠질 개연성이 높다. 최소 인스턴스 0 후보는
  사실상 기각하고 처음부터 최소 인스턴스 1·온디바이스·외부 API
  쪽으로 방향을 좁힌다.

  fp32 추정 605.1MB. 실제 HuggingFace 캐시 디스크 사용량 실측
  581MB(디스크 표기 단위 차이만큼의 오차, 추정과 근접) — 컨테이너
  이미지 번들링 시 이 정도 크기가 그대로 들어간다.
- **(b) 추론 1건 소요**: 첫 추론 ~0.18초, 웜 추론(3회 평균)
  ~0.04초. 배치의 `batch_size=32`가 아니라 실시간 1장 처리를
  가정한 값이다.
- **(c) 메모리**: RSS(측정 시점, 피크 아님) 약 772MB — Cloud Run
  1GiB 티어에 여유가 크지 않다(배경 제거는 1GiB로 충분했다, 693MB
  피크). 2GiB 티어(§62/월)를 기본 후보로 잡는 편이 안전해 보인다
  (미확정 — 실제 피크는 이번에 못 쟀다, 아래 "확인 못 한 것" 참고).
- **(d) 콜드스타트 총합**: **11.1~12.0초(3회 평균 ~11.5초)** —
  대부분이 `transformers` 임포트(~4.9초)와 모델 로드(~4.1~4.7초)에서
  나온다. `import torch` 자체는 ~1.9초로 상대적으로 가볍다.

### 판정 적용

**로컬 총합 11.1~12.0초는 5초~20초 구간에 들어간다 →
클라우드 스파이크가 필수다.** 참고로 `transformers` 임포트
(~4.9초)만으로도 이미 `rembg`의 로컬 전체 임포트(1.04~1.36초,
배경 제거 §2-5)보다 **3.5~4.7배 무겁다** — 그런데 `rembg`의
그 1초대 로컬 임포트가 클라우드에서 63~67초로 불어났다(§2-4).
같은 배율(50배 안팎)이 이번에 재현되면 로컬 11.5초가 클라우드
에서 **9~10분대**가 될 수 있다는 뜻이다 — 물론 이건 배율을
그대로 대입한 **추정이지 예측이 아니다**(§2 원칙 7번, "추정을
실측으로 포장하지 않는다"). 배경 제거의 원인(죽은 `pymatting`
임포트)이 여기 똑같이 있다는 근거는 없지만, 없다는 근거도 없다
— 그래서 판정 기준대로 클라우드 스파이크가 필요하다는 결론
자체는 바뀌지 않는다.

### 확인 못 한 것 (미검증으로 남김)

- **클라우드 실측 자체** — 이번엔 로컬만 쟀다. 아래 "다음 제안"
  참고, 배포는 사용자 확인 후.
- **피크 메모리** — `psutil`로 측정 시점 RSS만 쟀다(772MB). 배경
  제거처럼 `container/memory/utilizations` 같은 클라우드 공식
  지표로 잰 피크값이 아니다.
- **`get_image_features()` API 버전 불일치 — 별도 결함으로 등록만.**
  로컬에 새로 설치한 `transformers`(5.15.0, 최신)에서는
  `CLIPModel.get_image_features()`가 Kaggle 노트북 작성 시점
  API처럼 순수 텐서를 바로 안 주고 `BaseModelOutputWithPooling`을
  돌려준다 — `.pooler_output`을 꺼내야 512차원 정규화된 임베딩이
  나온다(직접 확인). Kaggle 노트북 코드(`F.normalize(model.
  get_image_features(**inputs), dim=-1)`)는 이 최신 버전에서 그대로
  돌리면 깨진다. **Kaggle 쪽이 어떤 `transformers` 버전을 실제로
  쓰고 있는지는 확인하지 않았다**(Kaggle 기본 이미지의 버전에
  따라 아직 안 깨졌을 수도 있다) — 이번 범위 밖이라 고치지 않고
  등록만 한다. 배치 파이프라인은 이번 트랙에서 손대지 않는다는
  금지 사항과도 맞다.

## 9. 벡터 호환성 검증 — 사전 등록 (2026-08-13, 결과 보기 전)

**동기**: 새 파이프라인이 기존 94벌과 다른 벡터 공간의 값을 내면
비교 자체가 성립하지 않아 트랙 목적이 무너진다. §7의 부수 발견
(최신 `transformers`에서 `get_image_features()` API가 바뀌어
`.pooler_output`을 꺼내야 함)이 "버전이 다르면 산출 벡터도 다를
수 있다"는 첫 신호다 — 결함 등록만 하고 넘기지 않는다.

**선정 규칙(임의성 없음, 결과 보기 전 고정)**: `embedding` 필드가
있는 문서를 카테고리별로 묶고, 각 카테고리에서 **itemId 오름차순
첫 번째**를 1건씩 뽑는다. 카테고리 5개(상의/신발/아우터/하의/
액세서리 — 전신은 embedding 보유 0건이라 대상 자체가 없음, §2)
전부에서 뽑으면 5건.

**전처리 경로 대조(코드로, 실행 전 확인)**: Kaggle 노트북의
`load_rgb()`는 `export.py`가 이미 만들어 둔 `images/{itemId}.jpg`
(cutout 우선, 512px 리사이즈, 흰 배경 합성, JPEG q90)를 열어
`.convert("RGB")`(no-op)만 하고 그대로 `CLIPProcessor`에 넘긴다.
즉 실질적 전처리는 **`export.py`의 `download_and_resize_image`
함수 하나가 전부** 한다. 검증 스크립트는 이 함수를 재구현하지
않고 **`export.py`에서 직접 import해 그대로 호출**한다 — 전처리
경로 자체가 다를 위험을 원천 차단한다.

**판정 기준(결과 보기 전 고정)**: 저장된 벡터와 새로 낸 벡터의
코사인 유사도(둘 다 L2 정규화이므로 내적으로 계산):
- **≥ 0.9999** → 부동소수점 오차 수준, 사실상 동일 연산.
- **0.99 ≤ x < 0.9999** → 재현 가능으로 판정하되, 완전 동일
  연산은 아닐 가능성(예: JPEG 재인코딩 손실 등 사소한 차이)을
  같이 등록.
- **0.90 ≤ x < 0.99** → "비슷하지만 다른 모델/버전/전처리" 수준
  — **재현 불가로 판정.**
- **< 0.90** → 명백히 다른 벡터 — **재현 불가로 판정.**

**이분 판정선은 0.99다** — 이상이면 "재현 가능", 미만이면 "재현
불가"로 트랙을 멈춘다.

**함의 — API 불일치는 결국 벡터를 안 바꿨다.** §7이 등록한

타입)만 바뀐 것이고, 실제 수치 연산(같은 가중치, 같은 전처리,

쓰기만 하면 옛 API와 수치적으로 동일한 결과가 나온다. 다만 이건
**이번 5건·이번 transformers 버전(5.15.0)에서 확인된 사실**이지,
"어떤 버전 차이든 벡터가 안 바뀐다"는 일반 법칙으로 확대하지
않는다 — 모델 가중치 자체가 바뀌는 경우(예: `patrickjohncyh/
fashion-clip`이 새 리비전을 올리는 경우)는 이번 검증 범위 밖이다.

**1단계 통과 — 2단계(ONNX)로 진행한다.**

## 10. ONNX 경로 로컬 측정 (2026-08-13)

**동기 — 11초 중 진짜 중요한 숫자는 0.18초다.** §7 측정에서
콜드스타트 11.1~12.0초 중 첫 추론 자체는 ~0.18초뿐이었다 — 거의
전부(`import transformers` ~4.9초 + 모델 로드 ~4.1~4.7초 = 총
~9초)가 "파이썬 ML 스택을 올리는 비용"이었다. 추론만 할 거라면
`torch`도 `transformers`도 굳이 필요 없다 — `onnxruntime`으로
바꾸면 이 임포트·로딩 비용이 통째로 빠질 수 있는지 쟀다. **같은
변수 하나만 바꾼다**(양자화는 이번에 안 함, (d) 후보로만 등록).

### (a) ONNX 변환

`patrickjohncyh/fashion-clip`(1단계와 같은 모델·경로,
`CLIPModel.from_pretrained`)의 **이미지 인코더만** 감싸는 래퍼
(`get_image_features(...).pooler_output` → L2 정규화)를
`torch.onnx.export`(`torch 2.12.1+cpu`, dynamo 기반 익스포터,
`onnxscript` 설치 필요)로 변환했다. 텍스트 인코더는 이 트랙의
용도(이미지→벡터)에 안 쓰이므로(§1) 처음부터 그래프에서 뺐다 —
dynamo 트레이싱이 실제로 실행된 서브그래프만 캡처해 자동으로
텍스트 타워를 들어냈다(파일 크기가 이를 뒷받침 — 아래 참고).

- opset 17 요청 → 버전 변환 실패로 opset 18로 자동 폴백(경고만,
  변환 자체는 성공).
- **같은 프로세스 안에서 파리티 검증**(torch 출력 vs onnxruntime
  출력, 같은 더미 입력): 코사인 유사도 **1.0**, 최대 절대 오차
  **2.5×10⁻⁷**(부동소수점 잡음 수준) — 변환 자체는 수치적으로
  무손실이라고 봐도 된다.
- **산출물이 두 파일로 나뉜다**: 그래프 파일(`.onnx`, 1.4MB) +
  외부 가중치 파일(`.onnx.data`, 351.4MB) — 합계 **352.8MB**.
  §7의 전체 모델 fp32 추정(605.1MB)보다 작다 — 텍스트 인코더
  (전체 151.3M 중 vision 87.5M을 뺀 나머지)가 실제로 그래프에서
  빠졌다는 증거다.

### (b) 콜드스타트 측정 — §7과 같은 하네스, 완전히 새 프로세스 3회

`torch`/`transformers`는 이 스크립트에서 아예 임포트하지 않는다
— `onnxruntime` + `numpy` + `PIL`만 쓴다. 전처리는 1단계에서
`processor.image_processor`로 직접 확인한 실제 설정값(shorter-edge
224 리사이즈 BICUBIC, 224 center crop, rescale 1/255, CLIP
mean/std)을 수작업으로 재현했다(아래 (c)가 이 재현이 정확한지
검증한다).

| # | import onnxruntime | import numpy+PIL | 세션 로드(가중치 포함) | 첫 추론 | 콜드스타트 총합 |
|---|---|---|---|---|---|

### 비교표 갱신(§7 대비)

| 항목 | torch+transformers(§7) | onnxruntime(§10) | 배율 |
|---|---|---|---|
| 콜드스타트 총합(3회 평균) | ~11.5초 | ~1.23초 | **~9.4배 감소** |
| 가중치/모델 크기 | 605MB(fp32 전체 모델) | 352.8MB(이미지 인코더만, 그래프+외부데이터 합계) | ~42% 감소 |
| RSS(측정 시점) | ~772MB | ~434MB | ~44% 감소 |
| 판정(§7 기준, 5~20초=스파이크 필수) | 스파이크 필수 구간 | **5초 미만 — "클라우드에서도 합리적일 가능성" 구간** | — |

**판정 적용**: onnxruntime 경로의 로컬 콜드스타트(~1.2초)는 §7이
사전 등록한 기준의 **"< 5초" 구간**에 들어간다 — "클라우드에서도
합리적일 가능성이 있다"는 잠정 해석과 함께 Cloud Functions/Run
최소 인스턴스 0 스파이크를 제안할 수 있는 구간이다. **다만 이것도
로컬 값이다** — 배경 제거 §2-4가 로컬 1.29초→클라우드 68초로
50배 벌어진 전례가 있으므로, **이 1.2초도 클라우드에서 그대로
재현된다고 가정하지 않는다.** onnxruntime은 `rembg`처럼 무거운
불필요 의존성(예: `pymatting`/`numba`)을 안 끌고 오는 가벼운
런타임이라는 점에서 배경 제거의 **최종 채택 구성**(minimal_runtime,
클라우드 1.2~2.1초)과 성격이 더 가깝다 — 하지만 "성격이 비슷하다"는
관측이지 "수치가 같다"는 보장이 아니다.

### (c) ONNX 산출 벡터의 호환성 검증 — 1단계와 같은 5건, 같은 판정 기준

1단계와 **완전히 같은 선정 규칙**(카테고리별 itemId 오름차순
첫 건)으로 같은 5건을 다시 썼다. `export.py`의
`download_and_resize_image`로 512px 중간 이미지를 만든 뒤(1단계와
동일 — 이 경로는 안 바꿨다), 그 위에 (b)의 수작업 전처리 +
onnxruntime 추론을 적용해 저장된 벡터와 코사인 유사도를 쟀다.

| 카테고리 | itemId | 코사인 유사도(ONNX vs 저장값) | 1단계(transformers) 대비 |
|---|---|---|---|
| 상의 | `09v2UrBJX8GmeqMs5IBz` | 0.9999997920 | 거의 동일(둘 다 ≥0.9999) |
| 신발 | `2efbE3mfLC08D3OlEQDK` | 0.9999988078 | 거의 동일(둘 다 ≥0.9999) |
| 아우터 | `665OXTTw9jJB8uCxWfPf` | **0.9948499858** | **1단계는 1.0000000182 — 이번이 뚜렷이 낮다** |
| 액세서리 | `08IS2RoIPQgmoEsxbSeP` | **0.9985815256** | **1단계는 1.0000000288 — 이번이 낮다** |
| 하의 | `0PGRnY39FstR95fRVNTZ` | 0.9999995319 | 거의 동일(둘 다 ≥0.9999) |

**판정: 5건 전부 ≥ 0.99 → 이분 판정선 통과, "재현 가능".** 다만
등록한 3단 구분을 그대로 적용하면 5건 중 3건(상의·신발·하의)만
"≥0.9999(부동소수점 오차 수준)" 구간이고, **2건(아우터·액세서리)은
"0.99 ≤ x < 0.9999"(재현 가능하되 사소한 차이) 구간**이다 — 확대
해석하지 않고 있는 그대로 등록한다.

**원인 후보(확정 안 함, 등록만)**: 1단계(transformers `CLIPProcessor`)
대비 이번 2단계(수작업 전처리)에서만 유독 두 아이템이 더 벌어진
것으로 보아, `CLIPProcessor`의 리사이즈/센터크롭 구현과 내 수작업
구현(반올림 방식, 리사이즈 필터의 세부 구현체 차이 등) 사이에
**아이템의 원본 종횡비에 따라 갈리는 미세한 차이**가 있을 가능성이
있다 — 두 아이템이 유독 벌어진 이유(예: 정사각형이 아닌 원본
비율)를 이번엔 파고들지 않는다. 여전히 0.99 이상이라 실질적
유사도 검색 용도로는 문제없어 보이지만, 다음에 이 경로로 실제
구현할 때는 전처리를 `transformers` 없이도 픽셀 단위로 재검증하는
절차가 필요하다(배경 제거의 minimal_runtime이 34건 픽셀 단위
0.0000/255 동일성까지 검증했던 것과 같은 수준, §3 인용).

### (d) 양자화 — 시도 안 함, 후보로만 등록

이번엔 fp32 ONNX만 측정했다. fp16/int8 양자화는 변수를 하나 더
바꾸는 것이라 이번에 하지 않는다 — **다음 후보로만 등록**: 가중치
352.8MB를 int8로 양자화하면 이론상 ~4분의 1(약 88MB)까지 줄어들
수 있고, 콜드스타트의 남은 성분(세션 로드 ~0.7초)이 더 줄어들지
확인할 가치가 있다. 정확도 손실(코사인 유사도 저하 폭)은 별도
검증 필요.

### 결론 — 어느 스택으로 클라우드 스파이크를 할지 제안

**onnxruntime(이미지 인코더 전용 ONNX) 경로를 클라우드 스파이크
대상으로 제안한다.** 근거:
- 벡터 호환성 통과(위 (c), 5건 전부 ≥0.99).
- 로컬 콜드스타트가 §7 판정 기준의 "5초 미만" 구간으로 이동
  (~11.5초 → ~1.2초, ~9.4배 감소).
- 가중치·RSS 둘 다 축소(605MB→352.8MB, 772MB→434MB).

**다만 이 제안 자체가 클라우드 실측을 생략해도 된다는 뜻은
아니다** — §7이 이미 등록한 원칙(로컬로 클라우드를 추정하지
않는다) 그대로, 클라우드 스파이크는 여전히 필요하다. 달라진
것은 "무엇을 스파이크할지"이지 "스파이크가 필요한지"가 아니다.

**이번 세션은 로컬 측정까지다 — 클라우드 스파이크·배포에
착수하지 않았다. 승인을 기다린다.**

## 11. §10 (c)의 0.9948을 통과로 넘기지 않는다 — 원인 규명 (2026-08-13)

**문제 재정의**: 이분 판정선(0.99)은 통과했지만, §9(1단계, transformers
경로)가 보여준 "같다"의 실제 모습은 0.9999997이었다. 0.9948은 그보다
네 자릿수 낮다 — 부동소수점 오차가 아니라 실제 수치 차이이고, 이분
판정선 하나로 질적으로 다른 두 결과("사실상 동일"과 "어딘가 다르다")를
같은 "통과"로 묶은 것 자체가 문제였다(이 트랙 밖이지만 같은 형태의
함정을 자기평가 트랙이 SD 문턱에서 이미 겪었다).

**갱신된 판정 기준(결과 보기 전 고정)**: 이번엔 이분 통과선이 아니라
**§9가 보여준 수준(≥0.9999)을 목표로 잡는다.** 도달하면 "재현
복원"으로 등록하고 원인을 함께 남긴다. 도달 못 하면 거기서 멈추고
남은 차이의 크기와 좁힌 범위를 보고한다(지시 (d)).

### (a) 전처리 줄 단위 대조 — 원인이 코드 읽기만으로 나왔다

`§10`의 수작업 전처리(PIL `Image.resize(..., Image.BICUBIC)` 직접
호출)와 실제 `CLIPImageProcessor`(`transformers/models/clip/
image_processing_clip.py`)를 대조했다:

```python
# transformers/models/clip/image_processing_clip.py
class CLIPImageProcessor(TorchvisionBackend):
    resample = PILImageResampling.BICUBIC
    ...
```

`CLIPImageProcessor`가 상속하는 `TorchvisionBackend`
(`transformers/image_processing_backends.py:205-257`)의 `resize()`:

```python
def resize(self, image, size, interpolation, antialias: bool = True, ...):
    ...
    return tvF.resize(image, new_size, interpolation=interpolation, antialias=antialias)
```

**`tvF`는 `torchvision.transforms.v2.functional`이다 — PIL이 아니라
torchvision으로 리사이즈한다, 기본값 `antialias=True`.** 즉 §10의
수작업 구현(PIL `Image.resize`, 안티앨리어싱 옵션 없음)과 실제
경로(torchvision `resize`, 안티앨리어싱 적용)는 **"둘 다 bicubic"
이라는 이름은 같지만 다운샘플링 시 적용하는 커널이 다르다** — 이게
0.99 대 유사도를 만든 진짜 원인이다(모델 자체는 §10(a)에서 이미
파리티 1.0으로 무결함이 확인됐다 — 차이는 입력 쪽에 있다는 지목이
정확했다). 이 발견은 코드를 읽는 것만으로 나왔고, 실행 전에 원인을
좁혔다.

**대조 결과 요약**:

| 항목 | §10 수작업 구현 | 실제 `CLIPImageProcessor` |
|---|---|---|
| 리사이즈 엔진 | PIL `Image.resize` | torchvision `tvF.resize`(`TorchvisionBackend`) |
| 안티앨리어싱 | 없음(PIL 기본 bicubic) | `antialias=True`(기본값) |
| 리사이즈 대상 | shorter-edge 224 | shorter-edge 224 — **동일** |
| 중앙 크롭 | 224×224, 수작업 반올림 | 224×224, `tvF.crop` |
| 정규화 상수(mean/std) | `OPENAI_CLIP_MEAN/STD`와 동일 값 하드코딩 | `OPENAI_CLIP_MEAN/STD` — **동일** |
| rescale(1/255) | 있음 | 있음 — **동일** |
| dtype/채널 순서 | float32, NCHW | float32, NCHW(내부 텐서) — **동일** |

**차이는 리사이즈 엔진·안티앨리어싱 하나뿐이다.**

### (b) 수정 — 재구현하지 않고 `CLIPProcessor`를 그대로 호출

지시대로 재구현하지 않았다. 검증 스크립트가 `export.py`의
`download_and_resize_image`(1단계 대상, 원래도 공유하고 있었다)에
더해, **224 전처리 단계도 `CLIPProcessor.from_pretrained(...)`를
그대로 호출**해 `pixel_values`를 얻고, 그 텐서만 onnxruntime
세션에 넣도록 바꿨다 — 리사이즈·크롭·정규화 코드를 내가 다시
짜지 않는다.

**중요한 한계를 여기서 명시한다**: 이 수정은 **검증 스크립트의
정확성 확인용**이지 프로덕션 콜드스타트 경로의 해법이 아니다 —
`CLIPProcessor`를 쓰면 다시 `transformers`+`torch`(§7이 무겁다고
지목한 그 스택)가 필요해진다. 이 수정으로 "ONNX 모델과 전처리가
정확히 무엇을 재현해야 하는가"는 확정되지만, "그걸 무거운 임포트
없이 어떻게 재현할지"는 여전히 열린 문제다 — §12에서 다룬다.

### (c) 재실행 결과 — 재현 복원됨

같은 5건, 같은 선정 규칙. `export.py`의 `download_and_resize_image`
(1단계 대상 확보, 원래도 공유)로 512px 중간 이미지를 만든 뒤,
**224 전처리를 `CLIPProcessor.from_pretrained(...)` 그대로 호출**해
`pixel_values`를 얻고, 그 텐서만 onnxruntime 세션에 넣었다.

| 카테고리 | itemId | §10(수작업 전처리) | §11(c)(CLIPProcessor 재사용) | 목표(§9 수준, ≥0.9999) |

| 상의 | `09v2UrBJX8GmeqMs5IBz` | 1.0000000e+00(참고: §9) | 0.9999997545 | ✅ |

리사이즈)이 실제 원인이었다는 것을 5건 실측이 직접 뒷받침한다.
가설을 확정한다(추측이 아니라 재현 실측으로 닫힘).

## 12. 남은 열린 문제 — 프로덕션 전처리를 가볍게 재현하는 법 (등록만)

§11(b)에서 명시한 한계가 여전히 유효하다. **검증은 닫혔지만
구현 경로는 안 열렸다** — `CLIPProcessor`를 그대로 쓰면 콜드스타트
개선(§10, 11.5초→1.2초)이 다시 사라진다(`transformers`+`torch`
재도입). 이 트랙이 구현에 착수하지 않으므로 여기서 풀지 않고
다음에 실제 구현할 때 풀어야 할 문제로만 등록한다:

- **후보 1 — torchvision만 가져오기.** `transformers` 전체가
  아니라 `torchvision.transforms.v2.functional.resize(...,
  antialias=True)` + `crop`만 직접 호출하면 `CLIPImageProcessor`와
  같은 리사이즈 커널을 쓰면서도 `transformers` 임포트는 피할 수
  있을지 모른다 — 다만 `torchvision`도 `torch`에 의존하므로
  §7의 "import torch"(~1.9초) 비용은 그대로 남는다(그래도
  `transformers`의 ~4.9초는 없앨 수 있다).
- **후보 2 — 안티앨리어싱 리샘플링 커널을 numpy로 정확히
  재현.** torchvision의 `interpolate`가 쓰는 안티앨리어싱
  bicubic 커널을 수작업으로 재구현 — 가능하지만 이번에 겪은
  것과 같은 미세한 불일치 위험을 다시 감수해야 한다. 권장하지
  않음(등록만).
- **후보 3 — Pillow의 `reducing_gap`/`Image.thumbnail` 등 PIL
  자체의 고품질 다운샘플링 옵션을 재검토.** PIL도 안티앨리어싱
  리사이즈를 지원하지만 torchvision과 알고리즘이 다를 수 있어
  똑같이 검증이 필요하다.

**판정 기준(등록만, 이번에 재지 않는다)**: 어느 후보를 골라도
§11의 방법론(같은 5건, 목표 ≥0.9999)으로 재검증해야 "재현 가능"을
주장할 수 있다 — 검증 없이 "가벼워졌으니 됐다"고 넘기지 않는다.

### 추가 로컬 측정 — "검증된 경로"가 실제로 얼마나 가벼운지 먼저 쟀다

스파이크 대상을 정하기 전에, 위 후보들을 고르지 않고도 답할 수
있는 질문이 하나 있었다 — **§10의 큰 개선(11.5초→1.2초)이
`CLIPModel`(605MB 가중치)을 안 실은 덕분이었나, 아니면 전처리
자체가 가벼워서였나?** §11(c)에서 검증에 쓴 조합
(`CLIPProcessor`만 로드 + `onnxruntime`으로 추론, `CLIPModel`은
안 씀)의 콜드스타트를 새 프로세스 2회로 격리해서 쟀다:

| # | import torch | import transformers | `CLIPProcessor.from_pretrained` | import onnxruntime | 총합(모델 가중치 로드 제외) |
|---|---|---|---|---|---|
| 1 | 1.805s | 4.005s | 3.424s | 0.074s | **9.375s** |
| 2 | 1.561s | 3.860s | 4.426s | 0.067s | **9.974s** |

**답은 "전처리 자체가 무겁다"였다 — 예상 밖이었다.** `CLIPModel`의
605MB 가중치를 아예 안 실었는데도(onnxruntime 세션 로드 ~0.7초
별도 추가하면 총 ~10.1~10.7초) §7의 원래 총합(~11.5초)과 **겨우
1~1.5초밖에 차이 나지 않는다.** `CLIPProcessor.from_pretrained`
자체가 3.4~4.4초나 걸린다(토크나이저·설정 로딩 등, 큰 가중치가
없는데도) — **"모델이 무겁다"가 아니라 "`transformers` 패키지
자체(임포트 + `.from_pretrained()` 초기화)가 무겁다"는 것이
진짜 병목이었다.**

**함의 — §10의 9.4배 개선은 절반이 부정확한 전처리 덕이었다.**
§10이 보여준 극적인 개선(11.5초→1.2초)은 **§9(1단계)가 이미
증명한 "검증된" 경로가 아니라, 이번에 틀렸다고 밝혀진 수작업
전처리(PIL 비-안티앨리어싱 리사이즈) 버전에서 나온 수치였다.**
**검증된 경로(`CLIPProcessor`+onnxruntime)의 실제 콜드스타트는
~10.1~10.7초로, §7의 판정 기준(5~20초 = 스파이크 필수)에서
전혀 벗어나지 못했다** — "5초 미만" 구간으로 이동했다던 §10의
결론은 **부정확한 벡터를 낸 구성에서만 성립**했던 것이었다.

### 그래서 무엇을 스파이크하는가

이 발견이 스파이크 대상을 바꾼다:

- **검증된 경로(`CLIPProcessor`+`onnxruntime`, ~10.1~10.7초 로컬)**
  는 여전히 §7 기준 "스파이크 필수" 구간이고, **부정확한 벡터를
  낼 위험이 없는 유일한 후보**다.
- §12의 세 후보(torchvision 직접 호출 등)는 **콜드스타트를 더
  줄일 수 있는 유일한 방향**이지만, 이번에 검증하지 않았다 —
  스파이크하면 "빠르지만 벡터가 맞는지 모르는" 결과가 나온다.

**결정(제안, 승인 필요)**: 이번 스파이크는 **검증된 경로
(`CLIPProcessor`+`onnxruntime`)를 그대로 컨테이너에 올려서**
콜드스타트·메모리를 잰다 — "느릴 수 있지만 벡터는 맞다"는 기준선을
먼저 확보한다. §12의 경량화 후보(torchvision 직접 호출 등)는
**이 기준선을 확보한 뒤에, 그리고 §11과 같은 방법론으로 벡터
정확성을 다시 검증한 뒤에만** 별도로 재고한다 — 이번 스파이크
범위에 넣지 않는다.

## 13. 클라우드 스파이크 설계 (2026-08-13, 설계만 — 배포하지 않음)

배경 제거의 `tools/bg_removal_spike/cloud_run_spike/`(콜드스타트
재측정에 실제로 쓰인 것)를 선례로 그대로 따른다 — 어디를 그대로
쓰고 어디를 바꾸는지 아래에 명시한다.

### (a) 범위 — 최소 기능 엔드포인트 하나

이미지 1장을 받아 512차원 벡터를 반환하는 것까지다. Firestore

배경 제거 스파이크(`bg_removal_coldstart_spike`)가 이미 증명한

함수 하나. 요청 바디가 이미지 바이트, 응답이 벡터 JSON.

### (c) 측정 항목·판정 기준 (결과 보기 전 고정)

**측정**:
- **콜드스타트 3회** — 배경 제거 §2-6의 교훈(자연 스케일다운
  대기가 예측 불가능, 재배포로 매번 새 리비전을 강제해야 진짜
  콜드스타트를 잰다) 그대로 적용한다. 회차 사이 간격: 기능
  무변경 마커 주석만 바꿔 즉시 재배포(자연 유휴 종료를 기다리지
  않는다). 배포 간 대기 시간 자체는 각 리비전의 빌드·배포 완료를
  기다리는 시간만큼(정확한 값은 실행 시 기록).
- **웜스타트 3회** — 같은 리비전에 연속 호출.
- **최대 메모리 사용량** — GCP 공식 지표
  (`run.googleapis.com/container/memory/utilizations`)로. 로컬
  RSS(§10/§11)는 참고치일 뿐 판정에 안 쓴다.
- **GCP 공식 지표 대조** — 외부 wall-clock과
  `run.googleapis.com/container/startup_latencies`를 나란히
  기록한다. 배경 제거에서 두 지표가 0.5~0.7초 차이 났다(§2-6) —
  판정은 GCP 공식 지표를 우선한다(선례 그대로).

**판정 기준(§7·§11이 이미 쓴 문턱을 그대로 재사용 — 새로 만들지
않는다)**:
- **GCP 공식 콜드스타트 < 5초** → `min_instances=0`으로 확정한다.
- **5초 ≤ GCP 공식 콜드스타트 < 20초** → `min_instances=1` 전환
  또는 §12의 경량화 후보(별도 트랙에서 먼저 검증)를 재고한다.
  **이번 스파이크만으로는 자동 결정하지 않고 사용자 판단으로
  넘긴다** — 상시 비용을 받아들일지, 경량화를 먼저 시도할지는
  트레이드오프 선택이지 측정으로 자동 결정되는 게 아니다.
- **GCP 공식 콜드스타트 ≥ 20초** → `min_instances=0` 후보는
  사실상 기각. 처음부터 `min_instances=1` 또는 §3의 다른 후보
  (온디바이스·외부 API)로 방향을 좁힌다.
- **최대 메모리가 1GiB의 90%(약 921MB)를 넘으면** → 2GiB 티어로
  올려 재측정한다(1회 추가 스파이크, 별도 승인).

### (d) 비용 추정

**스파이크 자체**: 콜드 3회+웜 3회, `max_instances=1`로 제한 —
배경 제거 스파이크 실측(콜드 5회+웜 2회 ≈350 vCPU-초, 무료 등급의
0.19%)과 같은 자릿수일 것으로 예상한다(모델 로딩 시간이 더 길
수 있어 vCPU-초 자체는 더 클 수 있으나, 여전히 무료 등급 월
180,000 vCPU-초 대비 미미할 것으로 추정 — 실측 전까지는 추정으로만
남긴다).

**실제 운영 시 예상 비용(등록 빈도 가정 명시)**:
- **가정: 옷 등록이 며칠에 한 번**(배경 제거가 이미 쓴 가정,
  §2-3 인용 — 이 저장소의 실제 사용 패턴 그대로 재사용).
- `min_instances=0`으로 확정되면: 요청당 과금, 이 빈도에서는
  무료 등급 내일 가능성이 높다(배경 제거와 같은 결론).
- `min_instances=1`로 가야 하면: 1GiB 약 $56/월, 2GiB 약 $62/월
  (배경 제거 §2-3이 확인한 공식 가격표, 같은 리전·같은 과금
  방식이라 그대로 재사용). 등록 빈도가 며칠에 한 번인 워크로드에
  상시 인스턴스는 과하다는 배경 제거의 판단 근거가 여기도
  적용되지만, 이건 판단 근거 등록이지 스파이크 결과가 5~20초로
  나왔을 때 자동으로 `min_instances=0`을 고수하라는 뜻은 아니다
  (위 (c) 참고, 트레이드오프는 사용자가 정한다).

### (e) 롤백 경로

배경 제거의 `bgremovalspike` 코드베이스가 스파이크 종료 후
`firebase.json`에서 실제로 빠진 것을 이번에 직접 확인했다(현재
`default`/`bgremoval` 둘뿐) — 같은 절차를 따른다:

1. `firebase.json`의 `functions` 배열에서 `embeddingspike` 항목을
   추가했다면, 스파이크 종료 후 그 항목을 제거한다.
2. 배포된 함수 자체를 지운다 — `firebase functions:delete
   <함수명> --region=asia-northeast3`(정확한 삭제 명령은 실행
   시 `firebase functions:list`로 결과를 확인하며 진행한다 —
   배경 제거 사례의 정확한 삭제 절차 자체는 이번에 재확인하지
   않았다, 등록만).
3. `tools/embedding_spike/`(소스 디렉터리)는 배경 제거의
   `tools/bg_removal_spike/`처럼 저장소에 남겨 둔다 — 다음에
   같은 실험을 재현할 근거 코드로(재현 코드 원칙).
4. 무엇을 지우면 원상복구되는지: **함수 배포 하나뿐이다** —
   Firestore/Storage에 아무것도 안 쓰므로(범위 (a)) 되돌릴 데이터
   자체가 없다.

### 승인 요청

이 설계대로 진행해도 될지 확인해 달라. 승인되면: (1)
`tools/embedding_spike/cloud_run_spike/` 소스 작성(코드 작성 —
아직 배포 아님, 이것도 별도로 보고), (2) `firebase.json`에
`embeddingspike` 코드베이스 임시 등록, (3) `firebase deploy
--only functions:embeddingspike` 실행. **배포 명령 자체는 실행
직전에 다시 한번 확인받는다**(금지 사항).

## 14. 배포 직전 마지막 로컬 측정 — torchvision 직접 호출 변형 (2026-08-13)

**동기**: §11(추가 로컬 측정)이 병목을 `transformers` 패키지
자체(임포트 + `CLIPProcessor.from_pretrained()`)로 좁혔다. 우리가
`transformers`에서 실제로 쓰는 건 `CLIPImageProcessor`(정확한
설정값은 이미 코드로 확인됨, §9/§11) 하나뿐이고, §11(a)가 원인을
`torchvision.transforms.v2.functional.resize(antialias=True)`로
이미 지목했다 — **`transformers`를 거치지 않고 그 함수를 직접
부르면 파리티가 나올 개연성이 있다는 뜻**이므로 "미검증 후보"가
아니라 "이제 검증 가능해진 후보"다.

**판정 기준(결과 보기 전 고정, 낮추지 않는다)**: 5건 전부
코사인 유사도 **≥ 0.9999997**(§11이 실제로 도달한 수준)이면
"파리티 통과" → 콜드스타트를 마저 측정한다. **하나라도 미달이면
그 자리에서 폐기** — 원인을 더 파지 않고 검증된 경로
(`CLIPProcessor`+`onnxruntime`)로 스파이크한다. 이 트랙은 변형을
**하나만** 만든다.

### (a) 전처리 로직 — 코드에서 그대로 옮김(기억·문서 참조 아님)

`image_processing_backends.py`의 `get_resize_output_image_size`와
`TorchvisionBackend.center_crop`을 이번에 다시 직접 읽고, **§10에서
놓쳤던 세부 사항 하나를 더 발견했다**:

```python
# get_resize_output_image_size — 반올림(round)이 아니라 절삭(int)이다
new_short, new_long = requested_new_short, int(requested_new_short * long / short)
```
```python
# TorchvisionBackend.center_crop — 여기도 절삭(int)이다
crop_top = int((image_height - crop_height) / 2.0)
crop_left = int((image_width - crop_width) / 2.0)
```

§10의 수작업 구현은 두 곳 다 `round()`를 썼다 — 안티앨리어싱
유무(§11(a)가 이미 지목)에 더해 **반올림/절삭 차이도 있었다**는
뜻이다. 이번 변형은 리사이즈를 `tvF.resize(..., interpolation=
BICUBIC, antialias=True)`로, 크롭 좌표 계산을 `int()` 절삭으로,
전부 이 코드 그대로 옮겼다.

### (b) 일별 곡선의 형태(시점 일치 관측, 인과 확정 아님)

**8월 4일까지 거의 평평 → 5~7일 급상승 → 이후 완만한 상승.**

**다만 이건 시점이 겹친다는 관측이지, 항목별로 어느 함수가

### (c) 8월 7일 이후에도 곡선이 안 내려온다 — 관측만, 원인 미확정

**스파이크는 2026-08-07에 정리됐는데, 곡선은 그 뒤로도 내려오지
않고 완만히 상승했다.** 가능한 설명 둘을 나열한다(확정하지 않음):
- 배경 제거 **본 함수**(`bg_removal_on_upload`, `min_instances=0`
  이지만 실사용으로 계속 호출됨)가 계속 살아 있어 그것만으로
  설명됨.
- **정리되지 않고 남아 과금되는 것이 있음**(컨테이너 이미지 저장
  비용 등) — §15(c)가 이미 등록한 "Artifact Registry 이미지 정리
  누락 의심"과 같은 방향의 관측이다.

**[정정, 2026-08-13 일별 순비용 실측]** 위 (b)(c)는 **누적
그래프를 일별처럼 읽은 오독이었다.** Firebase 콘솔의 그 그래프는
**누적**이다 — 누적 곡선은 그날 비용이 정확히 0이어도 **평평해질
뿐 내려가지 않는다**(음수 비용이 없으므로 구조적으로 단조
비감소). "8월 7일 이후에도 안 내려온다"는 것 자체가 이상 신호가
아니라 누적 그래프의 정의였다 — **잔여 이미지를 의심할 근거로
쓴 것이 틀렸다.** 봤어야 할 것은 절대값이 아니라 **기울기**였다.

사용자가 콘솔에서 **일별 순비용**을 다시 확인했다:

| 날짜(8월) | 일별 순비용(원, 근사) |
|---|---|
| 1 | ~₩5 |
| 2~3 | 0 |
| 5~7 | ₩3~5 |
| **8** | **~₩17(정점)** |
| 9 | ~₩10 |
| 10 | ~₩12 |
| 11 이후 | 사실상 0 |

**이 실측으로 "잔여 이미지가 계속 과금 중"이라는 가설은 상당히
약해진다** — 8/11 이후 순비용이 사실상 0이라면, 뭔가 계속
과금되는 잔여물이 있다는 그림과 안 맞는다. **다만 기각까지는
하지 않는다** — 절감액(위 ₩542)이 워낙 커서 소액 잔여 과금은
일별 그래프 해상도에서 안 보일 수 있다.

**[정정, 2026-08-14, 기각] 잔여 이미지 가설을 원인 후보에서
뺀다.** 사용자가 GCP 콘솔에서 `gcf-artifacts` 리포지터리를 직접
확인한 결과 **스파이크 이미지는 0건**(embedding·bg_removal
둘 다 없음, 상세는 §22(b) [정정] 참고) — "설명할 잔여분" 자체가
존재하지 않는다. 위에서 "기각까지는 하지 않는다"고 유보했던
이유(소액이라 그래프 해상도에 안 보일 수 있음)도 이제 무의미하다
— 액수의 많고 적음이 아니라 **대상 자체가 없다.** 원인은
**배경 제거 본 함수(`bg_removal_on_upload`) 실사용 쪽으로
좁혀진다** — 다만 8/11 이후 일별 순비용이 사실상 0이었던 것을
감안하면, 애초에 설명이 필요한 잔여분 자체가 작았다는 점도
함께 남긴다(정점 8/8 이후 며칠 안에 순비용이 0에 수렴했으므로,
"작은 잔여 원인 하나를 마저 찾아야 한다"는 과제 자체가 크지
않다).

**정점이 8/7이 아니라 8/8이라는 점도 새로 관측됐다.** 배경 제거
스파이크는 2026-08-06~07이었지만(§16(b) 원문), 실제 일별 정점은
**8/8**이다 — 이날은 `git log` 확인 결과 페이로드 상한 재계산
(`image 상한 근거 재계산`)과 실기기 검증 3묶음 종결(`묶음3
실기기 검증 종결 기록`) 등 무거운 작업이 몰려 있었다(2026-08-08
커밋 다수). **§16(b)의 "8/5~7 급상승이 배경 제거 스파이크와
겹친다"는 서술은 누적 그래프의 기울기를 보고 쓴 것**이라, 일별
실측(정점이 8/8)에 비추면 배경 제거 스파이크(8/6~7)보다 8/8의
다른 작업들이 정점과 더 가깝다. **시점이 하루 어긋난다는 것을
등록할 뿐, 무엇이 원인인지 다시 확정하지는 않는다** — 시점 일치를
인과로 보지 않는다는 원칙은 여기도 그대로 적용된다.

### (d) 함의 — §13 롤백 절차의 이미지 정리 단계 근거

**액수 자체는 월 ₩600 수준이라 이번 스파이크도 같은 자릿수일
것이다** — 확정은 아니지만 (a)의 실측이 상한선 역할을 한다.
**의미 있는 것은 금액이 아니라 "무거운 파이썬 함수가 비용의
주된 축"이라는 사실**이다. 이번에 배포할 것(§14, torchvision
직접 호출 변형)은 패키지+모델만 ~976MB에 `torch`까지 포함하므로
(§15(b)), **정리를 안 하면 배경 제거보다 큰 꼬리를 남길 수 있다.**
**§13 롤백 절차에 Artifact Registry 이미지 정리 단계를 추가한
근거(§15(c))를 이 항목이 실측으로 뒷받침한다** — 정리 단계를
빠뜨리면 (c)에서 관측한 "8월 7일 이후에도 안 내려온 곡선"과 같은
패턴이 이번에도 반복될 수 있다.

### (e) 사용자에게 넘길 확인 항목 — 존재 여부 확인이지 금액 역산이 아니다

질문이 뾰족해졌다: "혹시 이미지가 남았나"가 아니라 **"8월 7일
이후 곡선이 안 내려온 이유가 잔여 이미지인가"**를 확인하는 것.

**확인 경로**: GCP 콘솔 → Artifact Registry → 리전 필터
`asia-northeast3` → `gcf-artifacts` 리포지터리 → 이미지 목록과
각 이미지의 크기·마지막 푸시 시각을 확인. `bg_removal_coldstart_spike`
또는 그 함수명을 포함한 이미지가 남아 있는지, 있다면 크기가
얼마인지 확인한다.

**목적은 금액 역산이 아니라 존재 여부 확인이다** — 이미지가
실제로 남아 있다는 것만 확인되면, 그것이 (c)의 "안 내려온 곡선"의
전부인지 일부인지는 따로 확정하지 않는다. **사용자가 답을 주면
문서에 등록한다. 안 주면 "미확인" 그대로 두고 진행한다 —
추정으로 채우지 않는다.**

**[정정, 2026-08-13] 이 확인 항목의 목적을 바꾼다.** 위 (c)의
"안 내려온 곡선"이 오독(누적 그래프)이었고 일별 순비용도 8/11
이후 사실상 0으로 확인된 이상, **"과금 원인 찾기"는 더 이상 이
확인의 목적이 아니다.** `bg_removal_coldstart_spike`의 잔여
이미지 존재 여부는 여전히 미확인이고 여전히 궁금할 수 있지만,
**이번 정리(§22, 이 트랙의 스파이크 롤백)에서 새로 추가한
"함수 삭제 + Artifact Registry 이미지 삭제" 절차가 실제로
작동하는지 검증하는 것이 이제 이 확인의 목적이다** — 다음에
같은 절차를 쓸 때(예: 배경 제거 스파이크 정리를 다시 다룰 때)의
근거가 된다. 사용자에게 넘길 것은 "왜 곡선이 안 내려왔는가"가
아니라 **"이번에 지운 임베딩 스파이크 이미지가 목록에서 실제로
사라졌는가" 하나다**(§22에서 직접 확인·기록한다).

**부수 함의**: 위 (a)의 정정으로 무료 등급이 ₩542(할인 전
₩599의 90% 이상)를 흡수하고 있다는 것이 드러났다 — **사용량이
무료 한도에 근접하면 청구액이 비선형으로 뛸 수 있다**는 뜻이다.
지금은 여유가 크지만(월말 예상 ₩148, 7월 대비 0%), 본 구현
착수 후 등록 빈도·백필(§3 "결측 46벌" 항목)로 사용량이 늘면
다시 볼 지점으로 남긴다.

**[해소, 2026-08-14]** 위에서 이 확인의 목적으로 재설정한
질문("이번에 지운 임베딩 스파이크 이미지가 목록에서 실제로
사라졌는가")에 답이 나왔다 — **사라졌다(애초에 남은 적도
없었다).** §22(b)가 접근 불가로 미확인 남겼던 것을 사용자가
콘솔에서 직접 확인: `embedding_coldstart_spike` 이미지 0건,
`bg_removal_coldstart_spike` 이미지 0건. 상세는 §22(b) [정정]
참고. **다음 달 초 청구 확인(§22 "다음 달 초 청구 확인") 항목
중 (ii)("Artifact Registry 이미지가 남아 있다면 그로 인한 저장
비용")는 전제 자체가 사라져 소거된다** — 확인할 것은 (i)(8월
하순 이후 순비용 유지·감소)만 남는다.

## 17. 배포 직전 확인 (2026-08-13, 무료 — 배포 전)

### (a) 호출 인증 경로 — 명령을 손에 쥔 상태로 배포에 들어간다

배경 제거 스파이크가 실제로 쓴 호출 명령은 문서에 남아 있지
않았다(`task_background_removal_v1.md`/`handoff_2026-08-04.md`
전수 검색, 못 찾음) — **재사용할 전례 명령이 없어서 새로
준비했다.**

`invoker=[_ADMIN_SA]`(Cloud IAM 수준 제한)를 호출하려면 그
서비스 계정 자격으로 발급된 **OIDC ID 토큰**(대상 함수 URL을
audience로 함)이 필요하다. `gcloud` CLI가 이 환경에 없으므로
(§15(a)에서 이미 확인), **서비스 계정 키 파일로 Python에서 직접
ID 토큰을 발급**하는 경로를 준비했다(`google.oauth2.service_account.
IDTokenCredentials.from_service_account_file`, `google-auth`
라이브러리 — 이미 `firebase_admin`의 의존성으로 설치돼 있어
추가 설치 없이 사용 가능함을 확인).

**호출 스크립트를 미리 작성해 뒀다**(저장소 밖 스크래치, 배포
후 함수 URL만 채워 넣으면 즉시 실행): 서비스 계정 키로 대상
URL을 audience로 하는 ID 토큰을 얻어 `Authorization: Bearer`
헤더로 POST한다.

**요청 본문**: 실제 옷장 이미지 1장(§9/§11/§14 검증에 쓴 것과
같은 상의 아이템 `09v2UrBJX8GmeqMs5IBz`, `export.py`의 다운로드
함수로 이미 받아 로컬에 준비해 뒀다 — 27,843바이트 JPEG). 바디가
없을 때의 1x1 JPEG 폴백(`main.py`에 이미 구현됨)은 순수 콜드스타트
핑 전용으로 남겨 두고, 실제 측정은 이 실사진으로 한다.

### (b) ONNX 모델 해시 — 배포 산출물의 동일성 기록

배포할 `fashionclip_vision.onnx`(+`.onnx.data`)의 SHA-256과


읽어 원인을 좁혔다 — `functions.yaml`이 없으면 Firebase CLI가

알아내는 단계**를 거치는데, 이게 10초 안에 끝나야 한다. 우리
모듈 스코프의 무거운 임포트(`torch`+`torchvision`+`onnxruntime`)와
352.8MB ONNX 모델 로딩이 이 10초를 넘겼다 — **실제 Cloud Run
콜드스타트와는 별개의, 로컬 전용 제한**이다.

Firebase 공식 문서("avoid deployment timeouts during
initialization")를 확인해 원인과 해법을 대조했다: 무거운 초기화를
`firebase_functions.core.init` 훅으로 감싸면 **로컬 배포 검사
단계에서는 건너뛰고, 실제 배포된 인스턴스가 뜰 때만 실행된다.**
`main.py`를 이 패턴으로 재구성했다(로직은 그대로, 실행 위치만
모듈 스코프→`@core.init` 콜백으로 이동, 커밋 `b1dc67e`) — **콜드
스타트 측정 유효성에는 영향 없다**: 공식 문서가 `init` 훅을
"인스턴스당 1회, 함수 코드 실행 전"으로 명시하고 있어 여전히
콜드스타트에 포함된다.

**부수 발견 — 로컬 배포에도 venv가 필요하다.** 위 discovery
단계는 `tools/embedding_spike/cloud_run_spike/venv/`(로컬 가상
환경, `requirements.txt` 설치됨)를 전제로 한다 —
`functions_bg_removal/venv/`(기존, 커밋 안 됨)와 같은 요구사항.
처음엔 이 디렉터리가 없어 `ENOENT`로 실패했다 — `python -m venv
venv` + `venv에 requirements.txt 설치`로 해소.

### GCP 공식 지표 대조 — `startup_latencies`가 아니라 `request_latencies`를 봐야 한다

Cloud Monitoring API(`monitoring.timeSeries.list`, 우리 서비스

**`run.googleapis.com/container/startup_latencies`**(콜드스타트
공식 지표, 배경 제거가 §2-6에서 쓴 것과 같은 지표)를 먼저 봤더니

**원인 — `@core.init`이 "콜드스타트"의 정의 자체를 바꿔놨다.**
`startup_latencies`는 **컨테이너가 떠서 트래픽을 받을 준비가

들어왔을 때 그 요청 처리의 일부로(요청 핸들러 안에서) 실행된다.**

### 부수 발견 — "웜스타트"가 예상대로 나오지 않았다, 원인 미확정

**같은 리비전에 연속 호출해도 시간이 0에 가깝게 안 줄었다.**
§14의 로컬 측정에서는 웜 추론이 ~0.04~0.24초로 사실상 즉시였다
(임포트·모델 로드가 프로세스당 1회뿐이므로). 클라우드에서는
같은 리비전(`-00001-nac`)에 대한 2~4번째 호출도 **7.7~9.0초**
로, 최초 호출(19.57초)보다는 뚜렷이 짧지만 **로컬이 보여준
"거의 0"에는 전혀 못 미쳤다.**

`@core.init`은 공식 문서상 "인스턴스당 1회, 함수 코드 실행 전"
실행되는 것으로 돼 있다 — 이 문서화된 동작대로라면 2번째 호출부터는
`_state`가 이미 채워져 있어 `import`/세션 로드 자체가 다시 안
돌아야 한다. 그런데 응답 본문의 `importTorchSeconds` 등 값이
2~4번째 호출에서도 **0이 아니라 2~3초대로 계속 찍혔다** — 재실행
자체가 일어났거나, 최소한 그만큼의 지연이 반복해서 발생했다는
뜻이다.

**원인은 조사하지 않는다(지시 사항)** — RSS 686MB 때와 같은
이유로, 이건 우리 애플리케이션 로직의 버그가 아니라 클라우드
실행 환경(Cloud Run 인스턴스 재사용 정책, Python 프로세스
모델, 또는 `firebase_functions`의 `core.init` 구현 세부사항)
쪽 질문이고, **클라우드 실측 자체가 이미 권위 있는 답**이다.
**미검증으로 남기는 것**: 이게 진짜 매번 새 프로세스인지, 같은
프로세스인데 `core.init`이 재실행되는지, 아니면 다른 무언가인지
— 셋 다 확정하지 않는다.

**[정정, §20에서]** 위 "원인은 조사하지 않는다"는 그 시점 지시를
따른 것이었다 — 이후 사용자가 이 판단을 뒤집고 무료 진단으로
원인 규명을 명시적으로 재지시했다(2026-08-13, §20). 원문은
지우지 않고 그대로 둔다. §20에 진행 결과(부분 규명)를 기록했다.

**함의 — `min_instances=1`의 가치 제안 자체가 불확실해졌다.**
상시 인스턴스(`min_instances=1`)를 쓰는 이유는 보통 "콜드스타트를
없애 모든 요청이 빠르게 응답하게 한다"이다. 그런데 이번 관측대로면
**상시 인스턴스를 켜도 매 요청이 여전히 7~9초대일 수 있다** —
그렇다면 월 $56~62를 내고 얻는 게 "콜드스타트 제거"가 아니라
"콜드스타트를 19초에서 8초로 줄이는 것"뿐일 수 있다. 이 함의는
아래 "결정 사항"에서 트레이드오프 정리에 그대로 반영한다.

- "웜스타트가 왜 완전히 안 줄었는지"의 원인 — 조사 범위 밖으로
  등록.
- 2GiB 메모리 구성에서의 재측정 — 1GiB로 충분해 보여 문턱에
  안 닿았으므로 이번엔 안 함.
- 업로드 패키지 205.43MB와 ONNX 원본 352.8MB 사이 차이의 정확한
  원인(§18에서 이미 미확정으로 등록).

### 결정 사항 — 사용자에게 넘긴다 (사전 등록된 규칙)

**§13(c)가 이미 "5~20초 구간은 자동 결정하지 않는다"고 못박아
뒀다 — 그대로 지킨다.** 트레이드오프:

- **`min_instances=0` 유지**: 상시 비용 없음(요청당 과금, §16
  기준 이 워크로드에서는 무료 등급 내일 가능성 높음). 대신
  **매 콜드 요청이 13~20초 걸린다** — 등록 빈도가 며칠에 한 번인
  현재 워크로드에서는 사실상 매번 콜드일 가능성이 높다(배경
  제거도 같은 결론이었다, §2-3).
- **`min_instances=1` 전환**: 월 $56(1GiB, §13(d))의 상시 비용.
  **다만 이번 관측대로면 그 비용을 내고도 매 요청이 여전히
  7~9초일 수 있다**(위 "부수 발견" 참고, 원인 미확정) — 콜드스타트
  완전 제거를 보장하지 못할 수 있다는 뜻이라, 지불하는 비용
  대비 얻는 게 불확실하다.
- **§12의 경량화 후보(torchvision 직접 호출은 이미 §14~19에서
  검증·배포까지 끝났다 — 남은 것은 §12가 등록한 나머지 후보,
  예: ONNX 자체의 양자화)**: 이번 범위 밖(양자화 시도 금지 —
  이미 지켜졌다).
- **"웜스타트가 왜 완전히 안 줄었는지" 원인을 먼저 규명**하는
  것도 후보다 — 규명되면 `min_instances=1`의 실제 가치를 정확히
  알 수 있다(지금은 추정 불가).

**어느 쪽을 택할지는 사용자가 정한다.**

## 20. [1단계] 웜 이상 원인 규명 — 무료 진단 (2026-08-13, 재측정 없이)

사용자 지시로 §19 "원인 미확정"을 재조사한다. **원칙: API 호출
없이 이미 있는 자료(GCP 지표, 코드, 이미 받은 응답 본문)부터
소진한다 — 새 호출·재배포는 하지 않는다.**

### (a) "웜"이 실제로 웜이었는가 — `instance_count` 지표로 확인

Cloud Monitoring `run.googleapis.com/container/instance_count`를
`-00001-nac`에 대해 07:39~08:03Z 구간(1분 GAUGE)으로 조회했다
(서비스 계정, §19가 이미 열어 둔 경로 그대로).

| 시각(UTC, 매 분) | active | idle |
|---|---|---|
| 07:40 | 0 | 1 |
| 07:41 | 0 | 1 |
| 07:42 | 1 | 0 |
| 07:43 | 1 | 0 |
| 07:44 | 1 | 0 |
| 07:45~07:57 | 0 | 1(매 분 동일) |
| 07:58(마커 재배포 `-00002-ner` active 시작) | 1 | 0 |

**핵심: `active + idle`이 07:40~07:57 구간 내내 한 번도 0으로
떨어지지 않았다.** 즉 `-00001-nac` 컨테이너 인스턴스는 호출
1~4(07:40:25Z~07:42:03Z)는 물론 그 이후로도 `-00002-ner`가
뜨는 07:57~58Z까지 **한 번도 완전히 죽지 않았다** — 새 인스턴스가
매번 대신 뜬 것이 아니다. **1단계(a)의 "가설 (i) 매번 새
인스턴스"는 이 지표로 기각한다.** 호출 2~4는 GCP 기준으로도
같은 컨테이너 인스턴스를 쳤다.

(참고: 이 지표는 1분 GAUGE 샘플이라 호출 사이 초 단위 변화까지는
못 잡는다 — "컨테이너가 완전히 죽었다 살았다"를 배제하는
용도로는 충분하지만, 그보다 미세한 수준의 재시작 여부까지는
이 지표만으로 단정할 수 없다는 한계는 남긴다.)

### (b) 세션·모델이 요청마다 로드되는가 — 코드로 확인

**이미 받은 응답 본문 자체가 답을 갖고 있었다(§19 표 재검토,
새 호출 아님).** `moduleTotalSeconds`(그리고 그 하위
`importTorchSeconds` 등)는 `_state`에 **한 번 쓰이면 그 뒤로는
읽히기만 해야 하는 값**이다(`_initialize()`가 `_state.update(...)`
로 쓰는 값을 핸들러가 그대로 읽어 응답에 싣는 구조,
`main.py:110-123`/`190-197`). `@core.init`이 문서대로 "인스턴스당
1회"만 돌았다면 호출 2~4는 **호출 1이 써 넣은 값을 그대로 반복
출력**해야 한다 — 즉 세 값이 전부 19.075로 동일해야 한다.

실제로는 7.753 / 8.368 / 7.724로 **서로 다르고 19.075와도
다르다.** 값이 매번 다르다는 것은 매번 다시 계산됐다는 뜻이다
(고정된 딕셔너리를 읽기만 했다면 같은 실행에서 나온 같은 숫자가
반복돼야 하는데, 그렇지 않다). **`_initialize()`(무거운
임포트+세션 로드 전체)가 호출 2~4에서도 실제로 다시 실행됐다는
직접 증거다.**

(a)와 (b)를 합치면: **컨테이너 인스턴스는 그대로였는데
`_initialize()`가 다시 실행됐다** — "매번 새 인스턴스"가 아니라
"같은 인스턴스인데 초기화가 반복됐다"는 뜻이다(가설 (ii) 방향).

**왜 그런가 — 배선 자체를 SDK 소스에서 직접 읽어 확인**
(venv에 설치된 실제 패키지 코드, 추측 아님):

- `firebase_functions/core.py:88-126` — `core.init`은 모듈
  전역 `_did_init`(bool) + `_init_callback`을 등록하고,
  `_with_init(fn)`이 반환하는 wrapper가 `if not _did_init:
  callback(); _did_init = True`로 감싼다. **가드 자체는 프로세스
  전역 상태로, 로직상 프로세스당 1회만 돌게 짜여 있다.**
- `firebase_functions/https_fn.py:435` — `on_request`
  데코레이터가 실제로 `func_with_init = _core._with_init(func)`를
  호출해 우리 핸들러를 감싼다. **배선 자체는 문서대로 맞게
  돼 있다** — `main.py`가 이 가드를 우회하거나 잘못 쓰는
  코드는 없다.
- `functions_framework/_http/gunicorn.py:32-39` — 실제 서빙은
  gunicorn(`GThreadWorker`)이 맡고, **`workers = int(os.environ
  .get("WORKERS", 1))`로 기본값은 1**(단일 프로세스, 스레드
  `os.cpu_count()*4`로 동시성 처리). 기본값 그대로라면 프로세스가
  하나뿐이라 `_did_init` 전역이 유지돼야 한다.

**즉 우리 코드(`main.py`)에는 결함이 없다** — `@core.init` 사용법,
가드 배선 둘 다 문서·SDK 소스와 정확히 일치한다. 그런데도
재실행이 관측됐다는 것은, **원인이 `main.py`가 아니라 배포된
컨테이너의 gunicorn 워커 구성(`WORKERS` 환경변수가 로컬 기본값
1이 아닌 값으로 오버라이드돼 있거나, 워커가 요청 사이 재활용됐을
가능성)에 있을 것으로 추정된다 — 다만 이건 추정이다.** 배포된
컨테이너의 실제 `WORKERS` 값이나 워커 PID는 코드 읽기·기존
GCP 지표로는 확인할 수 없었다(Cloud Run Admin API 403, 실행
로그 접근 안 됨 — 아래 참고).

**로컬 하네스(§14)와의 구조적 차이는 이것이다**: 로컬 하네스는
gunicorn/Flask 같은 서빙 계층 자체가 없이 단일 파이썬 프로세스가
직접 함수를 반복 호출했다 — "워커 재사용"이라는 개념이 아예
없는 환경이었다. 반면 배포된 코드는 gunicorn이라는 별도 계층을
거치고, 그 계층의 워커 관리 정책이 `_did_init` 가드의 전제
("계속 같은 프로세스")를 깰 수 있는 지점이다. **이 구조적 차이가
로컬이 못 잡아낸 이유다.**

### 로그 경로 재확인 — 이미 소진됨을 코드로 확정

`firebase functions:log --only embedding_coldstart_spike -n 200`을
필터 없이/`grep -v`로 다시 돌려도 이전과 동일하게 **감사 로그
6줄**(CreateFunction/UpdateFunction 요청·응답 쌍, §18/이전
조사와 동일)만 나온다. **`main.py`를 다시 읽어 확인 — 이 함수는
어디에도 `print()`/`logging` 호출이 없다.** 즉 이건 권한 문제가
아니라(직접 Cloud Logging API 403은 여전히 유효하지만) **볼
실행 로그 자체가 애초에 안 만들어지는 구조**다. 이 경로는 코드
수정(로그 추가) 없이는 더 파고들 수 없다 — 그런데 코드 수정은
재배포를 뜻하므로 아래 (c)로 넘긴다.

### (c) (a)(b)로 완전히 안 풀렸다 — 재측정 계획 제안, 실행하지 않음

**확정된 것**: 같은 컨테이너 인스턴스에서 무거운 초기화가
반복 실행됐다(위 (a)(b)). **우리 코드에는 결함이 없다** — 표준
패턴을 정확히 따랐다. **확정 못 한 것**: 왜 gunicorn 워커
수준에서 재실행이 일어나는지(WORKERS 오버라이드/워커 재활용
정책/그 외) — 이건 배포된 컨테이너 내부 상태(`os.environ`,
워커 PID)를 봐야 하고, 무료 수단(코드 읽기, 이미 있는 GCP
지표, 이미 받은 응답)으로는 여기까지가 한계다.

**제안하는 재측정(승인 전 실행 안 함)**: 마커 재배포(§2-6
방식, 기능 무변경) 1회로 `main.py` 응답 본문에 진단 필드
2개만 추가한다 — `os.getpid()`, `os.environ.get("WORKERS")`.
그 뒤 같은 리비전에 §19와 같은 간격으로 3~4회 순차 호출해
PID가 호출마다 바뀌는지 확인한다. PID가 매번 같은데도
`moduleTotalSeconds`가 계속 다르면 "같은 프로세스인데 가드가
안 먹는다"는 더 좁은 문제로, PID가 바뀌면 "워커가 요청마다
재활용/신규 스폰된다"는 문제로 원인이 명확히 갈린다. **비용은
재배포 1회(빌드) + 호출 3~4회**(§15(b)/(d) 기준 소액) — 실행
여부는 사용자 승인을 받는다.

### (d) 원인이 코드 결함으로 밝혀지면 고치지 않는다 — 등록만

위에서 확인한 대로 **`main.py`/`@core.init` 사용법 자체는 결함이
아니다**(SDK 문서·소스와 일치). 재실행의 실제 원인(추정: gunicorn
워커 구성)이 무엇이든, **고칠지 여부는 2단계 결론(지연이
사용자에게 보이는지)에 달려 있으므로 여기서는 고치지 않고
등록만 한다.**

### 결론 — 1단계는 부분 완료

- **확정**: 컨테이너 인스턴스는 죽지 않았다(a). 그런데도
  무거운 초기화가 반복 실행됐다(b, 응답 본문 자체가 증거).
  `main.py`의 `@core.init` 사용법은 SDK 문서·소스와 정확히
  일치해 코드 결함이 아니다(b).
- **미확정**: gunicorn 워커 수준에서 왜 재실행이 일어나는지의
  정확한 메커니즘 — 이건 배포 컨테이너 내부 상태를 봐야 하고,
  무료 수단으로는 여기까지가 한계다. (c)에 재측정 계획을
  제안해 뒀다 — **승인 전에는 실행하지 않는다.**

다음: 사용자 승인 여부와 무관하게, [2단계](판정 기준 재검토)로
넘어갈 수 있다 — 2단계가 "이 지연이 애초에 사용자에게 보이지
않는다"는 결론에 이르면 (c)의 재측정 자체가 불필요해질 수 있다.

### 더 싼 진단 후보 — 재배포 없이, 연속 호출 횟수만으로 (등록만, 실행 안 함)

**(c)의 재배포안(진단 필드 추가)보다 우선순위가 높다 — 재배포
비용(빌드 1회)이 아예 없다.** gunicorn 워커 가설이 맞다면(위
(b) 참고, `WORKERS`가 로컬 기본값 1이 아니거나 워커가 요청마다
재활용된다면), 워커가 N개일 때 **각 워커 프로세스는 자기만의
`_did_init` 전역을 따로 갖는다** — 요청이 워커들에 분배되므로
**처음 N번의 호출은 각각 처음 만나는 워커일 확률이 높아 매번
초기화 비용(7~9초대)이 나오고, N번을 넘어서면 모든 워커가
이미 초기화를 마쳐 급격히 빨라져야 한다**(로컬이 보여준
~0.2초대로).

지금까지는 §19에서 같은 리비전에 **3회만**(호출 2~3~4) 연속
호출했다 — 워커 수가 3보다 크면 이 전환점을 아예 못 봤을
수 있다.

**예측(사전 등록, 결과 보기 전 고정)**: 같은 리비전에 §19와
비슷한 간격으로 **8~10회 연속 호출**했을 때
- 어느 시점부터 응답이 갑자기 **0.2초대로 떨어지면** → 워커
  가설을 지지하는 증거(그 시점의 호출 순번이 대략 워커 수를
  시사).
- 8~10회를 다 채워도 **계속 7~9초대가 유지되면** → 워커 가설은
  약해진다(다른 메커니즘 — 예: 매 요청 자체가 아니라 시간 간격
  기반 재활용 정책 등 — 을 다시 고려해야 함을 뜻함).

**실행하지 않는다.** [1단계](판정 기준 재검토) 결론에 따라 이
재측정 자체가(이 후보든 (c)의 재배포안이든) 불필요해질 수
있으므로, 실행 여부는 [1단계] 결론 이후 다시 정리해 사용자
승인을 받는다.

## 21. [1단계] 판정 기준의 근거를 다시 세운다 (2026-08-13)

### 5초·20초 문턱의 근거 — 있다, 그런데 조건부다

`§7`이 문턱을 처음 등록할 때 출처를 명시해 뒀다: **"이 저장소가
배경 제거에서 이미 쓴 기준을 그대로 가져온다"**(§7:248). 그
원출처를 다시 읽었다 — `task_background_removal_v1.md:470-472`:

> "콜드스타트가 사용자 체감상 허용 범위(**기준값은 사용자
> 판단** — 예: 수 초~10초대는 **"업로드 중" 스피너로 자연스럽게
> 가려짐**, 그 이상이면 문제)를 넘으면 Cloud Run으로 전환한다."

**근거는 있지만, 그 원출처 자체가 두 가지를 명시적으로 인정하고
있다**: (1) 이건 측정·연구에서 나온 수치가 아니라 **"사용자
판단"이라고 못박은 임의 기준**이고, (2) 그 기준이 성립하는
**전제조건은 "업로드 중 스피너"** — 즉 사용자가 화면에서 그
작업을 실제로 지켜보고 있다는 것이다. 이 전제가 깨지면 문턱
자체가 적용 대상을 잃는다. §7·§13(c)가 이 문턱을 그대로
재사용할 때 이 전제조건까지 같이 옮겨 왔는지는 그때 확인하지
않았다 — 지금 확인한다.

### 핵심 질문 — 이 지연을 누가 기다리는가? (코드 확인)

Explore 에이전트로 코드를 조사하고, 핵심 지점은 직접 다시 읽어
대조했다(파일:줄 인용은 전부 실제 코드 확인, 추정 아님).

**(a) 임베딩 벡터의 실제 소비처**

Firestore `wardrobe/{itemId}.embedding` 필드를 읽는 곳은 앱
전체에서 다음이 전부다:

- **"비슷한 옷" 액션 시트** —
  `lib/screens/wardrobe_screen.dart:255-260`(직접 확인). 사용자가
  옷장 그리드에서 **기존 카드를 탭할 때만** 열린다. 코드 주석
  자체가 이렇게 설명한다: "코사인 계산은 100여 벌×512차원이라
  클라이언트에서 즉시 끝나므로 로딩 인디케이터 없이 시트 빌드
  전에 동기로 계산한다. embedding이 없거나... 섹션 자체를
  렌더링하지 않는다"(`:256-259`). **`embedding == null`을 정상
  상태로 처리하도록 이미 설계돼 있다** — 없다고 에러나 빈 박스를
  보여주지 않는다.
- **`OutfitMatcher`의 임베딩 유사도 축** —
  `lib/services/outfit_matcher.dart` — 프로덕션 기본 정책에서
  **기본값 `false`**(`useEmbeddingRecovery`, A/B 프리셋에서만
  켜짐)이고, 켜지더라도 백그라운드 에이전트(`background_agent.dart`,
  `AgentPlanner.runProactiveCheck`)가 소비하는 **비동기 경로**다.
- Cloud Functions(`functions/src`) 어디에도 `embedding` 참조가
  없다 — 서버 쪽에서 이 필드를 읽는 코드는 현재 전혀 없다.

**등록 직후 자동으로 열리는 화면 중 임베딩을 요구하는 곳은
없다.** "비슷한 옷" 시트는 사용자가 **나중에, 임의 시점에,
스스로 카드를 눌러야만** 열리고, 그마저도 값이 없으면 그냥
섹션을 숨긴다.

**(b) 등록 플로우 자체 — 무엇이 동기이고 무엇이 비동기인가**

`wardrobe_screen.dart:659-719`(직접 확인)를 단계별로 보면:

1. 이미지 선택·크롭·카테고리·치수 입력 — 전부 사용자 조작 UI(동기).
2. **업로드 구간**(`:659-694`): `_isUploading=true`로 스피너
   ("사진을 업로드 중입니다...") 띄우고, Storage 업로드 +
   Firestore 문서 쓰기를 **`await`로 동기 처리**한다. 사용자가
   실제로 기다리는 구간은 여기까지다.
3. **속성 추출은 `unawaited(...)`로 명시적으로 흘려보낸다**
   (`:698`, 주석: "속성 추출은 업로드 완료를 기다리게 하지 않고
   백그라운드로 흘려보낸다"). 성공 스낵바(`"등록되었습니다"`)는
   속성 추출 결과와 무관하게 즉시 뜬다(`:699-706`).

**같은 등록 플로우 안에 이미 "동기로 기다리는 부분"과 "비동기로
흘려보내는 부분"이 코드 수준에서 분리돼 있다.** 임베딩은
지금 이 파이프라인 어디에도 배선돼 있지 않지만(§1이 이미 확인),
**설계 방향(§5 사용자 결정)이 이미 "Storage 트리거, 배경 제거와
같은 지점"으로 정해져 있다** — 즉 애초부터 위 3번(비동기
흘려보내기) 쪽에 가깝게 설계하기로 돼 있었다.

**(c) 배경 제거 선례 — 실제로는 비동기다**

`wardrobe_screen.dart`에 **클라이언트 동기 배경 제거 코드가
존재하기는 한다**(`:150,203-244,726-758`, 자체 스피너 +
컷아웃/원본 선택 시트) — 하지만 **릴리스 빌드에서는 꺼져 있다**
(`_kOnDeviceBgRemovalEnabled = false`, `:47`, 네이티브 ONNX
Android JNI 크래시 때문, `task_background_removal_v1.md`에 이미
등록됨). **지금 실제로 돌아가는 배경 제거는**
`functions_bg_removal/main.py:123-129`의
`bg_removal_on_upload` — `@storage_fn.on_object_finalized`
(Storage 트리거) + **`min_instances=0`**(직접 확인, `main.py:127`)
로, 클라이언트는 이 함수를 호출하지도 기다리지도 않는다. 결과는
나중에 `cutoutPath`/`cutoutImageUrl`을 `merge:true`로 조용히
덧붙인다(`main.py:171-174`, 클라이언트 쪽 `firestore_service
.dart:54-58`의 `merge:true` 쓰기와 경합 없이 병합됨).

**이 사실 자체가 결정적인 선례다**: 배경 제거는 §2-4에서 클라우드
콜드스타트 **68초**(로컬 1.29초 대비 53배)까지 관측됐던
워크로드인데, 그런데도 **프로덕션에 `min_instances=0`으로
배포돼 있고 아무 문제가 되지 않는다** — 왜냐하면 그 68초를
지켜보는 사용자가 아무도 없기 때문이다(비동기 트리거, 실패해도
등록 자체는 안 깨짐, `main.py` 자체 문서화). **5초·20초 문턱이
전제했던 "업로드 중 스피너"는 배경 제거의 실제 배포 형태에도
이미 적용되지 않고 있었다** — §7·§13(c)가 이 문턱을 "배경
제거가 이미 쓴 기준"이라며 가져올 때, 정작 배경 제거 자신은
그 전제(동기 스피너)를 릴리스에서 충족한 적이 없다는 것을 이번에
처음 확인했다.

### 새 요구사항 — 사용자 경험에서 도출 (기술 수치 역산 아님)

위 (a)(b)(c)를 근거로 등록한다:

**"등록 후 N초 안에 끝나야 한다"의 N을 초 단위로 정할 근거가
없다 — 이 기능에는 그런 형태의 요구사항이 적용되지 않는다.**
이유: 등록 직후 자동으로 열리는 화면 중 임베딩을 요구하는 곳이
없고(a), 유일한 소비처는 사용자가 나중에 임의 시점에 스스로
열어야 하는 화면이며 값이 없어도 정상 동작하도록 이미 설계돼
있다(a). 등록 플로우 자체가 "동기로 기다리는 부분"과 "비동기로
흘려보내는 부분"을 이미 분리해 쓰고 있고(b), 이 트랙의 설계
방향도 배경 제거와 같은 비동기 트리거 지점으로 이미 정해져
있다(§5). 배경 제거 자신이 68초 콜드스타트로도 `min_instances=0`
프로덕션 배포를 이미 실증하고 있다(c).

**대신 성립하는, 더 느슨한 요구사항**: "임베딩은 사용자가 실제로
'비슷한 옷' 시트를 열어보기 전 어느 시점까지만 채워지면 된다."
이건 등록 시점부터의 초 단위가 아니라 **"다음에 그 카드를
누르기 전"**이라는, 사용자 행동 기준의 느슨한 시간 여유다 —
실무적으로는 분~시간 단위의 여유가 있다는 뜻이다(며칠에 한 번
등록하는 현재 사용 패턴, §2-3/§13(d)가 이미 확인).

### min_instances 트레이드오프 재정리

새 요구사항에 비추면:

- **`min_instances=0`이 명백히 충분하다.** 콜드스타트가 13~20초든
  §20의 "웜 이상"이 원인 미확정인 채 7~9초든, **어느 쪽도 사용자
  경험에 노출되지 않는다** — 지켜보는 화면 자체가 없다. 배경
  제거가 68초로도 이미 증명한 것과 같은 상황이다.
- **`min_instances=1`(월 $56)을 쓸 이유가 사라진다.** 콜드스타트를
  없애는 값은 "사용자가 기다리는 시간을 줄인다"는 것인데, 그
  대상 자체가 없다. 상시 비용을 낼 근거가 없다.
- **§20의 "웜 이상"은 이 결론 위에서 성능 문제가 아니라 계측
  정합성 문제로만 남는다** — 그 논리를 코드로 검증한다: 웜
  호출이 7~9초든 0.2초든, 이 함수를 부르는 것은 사용자 화면이
  아니라 Storage 트리거(비동기)뿐이므로, 실제 서비스 품질에
  미치는 영향은 "함수 실행 시간이 길어져 vCPU-초 비용이 조금
  더 든다"는 것뿐이다 — §13(d)가 이미 이 워크로드를 무료 등급
  내로 추정했으므로 그 비용 증가분도 사실상 무시할 수 있는
  크기다. **즉 §20(c)/"더 싼 진단 후보"에 등록해 둔 재측정은
  min_instances 결정 자체에는 더 이상 필요하지 않다** — 다만
  "계측이 뭘 재고 있는지"를 정확히 아는 것 자체는 별개로 여전히
  유효한 호기심이라, 실행 여부는 그대로 사용자 승인에 맡긴다
  (지금 이 결론이 그 승인 여부를 바꾸지는 않는다 — 승인은
  여전히 사용자 몫).

**결정은 사용자가 한다** — 위는 새 요구사항에 비춘 트레이드오프
정리이지, 자동 결정이 아니다.

### [정정] — 지연 시간을 판정 축으로 삼은 것 자체가 잘못 잡힌 축이었다

**§7(246-267)·§13(c)(807-838)가 사전 등록한 5초/20초 문턱과
그 문턱으로 §19("콜드스타트 — 판정 기준 적용", 1400-1408)가
내린 "5~20초 구간이라 자동 결정 안 함, 사용자에게 넘김"은
지우지 않는다 — 원문 그대로 둔다.**

**정정 내용**: 그 문턱은 "사용자가 스피너를 보며 기다린다"는
전제(배경 제거 원출처가 명시)에서 나온 것인데, 이번 트랙의
실제 소비 패턴(위 (a)(b)(c))은 그 전제를 충족하지 않는다.
**지연 시간(초 단위)은 애초에 이 기능의 min_instances 결정에
적용 가능한 판정 축이 아니었다** — 적용 가능한 축은 "사용자가
그 지연을 실제로 지켜보는가"이고, 코드로 확인한 답은 "아니다"
이다. §19가 "5~20초 구간이므로 트레이드오프를 정리해 사용자에게
넘긴다"고 한 것 자체는 그 시점 사전 등록 규칙을 정확히 따른
것으로 절차상 틀리지 않았다 — 다만 그 사전 등록된 규칙(문턱)
자체의 전제가 이 기능에는 안 맞았다는 것을 지금 확인했다.

  `call_gemini_text`, `generate_fitting_image`,
  `get_signed_image_urls`, `revoke_token_on_upload`,
  `scheduled_proactive_check`, `send_test_push`,
  `sweep_storage_tokens`. **스파이크 이미지는 0건** —
  `embedding_coldstart_spike`도 `bg_removal_coldstart_spike`도
  없다.
- **함수 개수 대조 — 어긋남 발견, 미확인으로 등록.** §22(a)는
  삭제 후 10개 함수(`triggerScheduledCheckTest` 포함)가 남았다고
  기록했다. 이번 세션에 `firebase functions:list --project
  ai-fashion-assistant-personal`을 다시 실행해 재확인한 결과도
  **현재 10개 함수가 배포돼 있다**(`triggerScheduledCheckTest`
  포함, 읽기 전용 조회). 그런데 Artifact Registry 이미지는
  9개 함수분뿐이다 — **`triggerScheduledCheckTest`에 대응하는
  이미지가 목록에 안 보인다.** 원인은 확인하지 못했다(이 세션
  도구로는 Artifact Registry에 직접 접근할 수 없다는 §22(b)
  원문의 제약이 그대로 적용됨) — 가능한 후보만 등록하고 확정하지
  않는다: (i) 같은 소스 빌드에서 나온 다른 함수와 이미지를
  공유하고 있을 가능성, (ii) Artifact Registry의 이미지 이름
  변환 규칙이 달라 사용자가 세어 본 9개 목록에서 다른 이름으로
  이미 포함돼 있었을 가능성, (iii) 그 외 확인 못 한 원인. **미확인.**
- **부수 관측 — 누적 없음.** 이미지들의 생성일이 전부 4~13일
  전이고, "업데이트됨" 시각이 생성일보다 최신이다 — **재배포
  시 이전 이미지가 쌓이지 않고 교체된다**는 뜻이다. 이 저장소가
  재배포를 반복해도 Artifact Registry 저장 비용이 무한정 커질
  우려는 없다.
- **§16(c)/(e), §15(c) 정정에 이 실측을 근거로 인용함.**

**열린 잡무 갱신**: Artifact Registry 확인 항목은 **여기서
종결한다.** 남는 항목은 §22 "다음 달 초 청구 확인"의 (i)(8월
