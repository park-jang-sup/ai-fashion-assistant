## 3. 1단계 실행 기록 — App Check `activate()` 조치 확정 (2026-08-13)

**조치 채택**: fire-and-forget 전환(사용자 결정). 나머지 두 후보
(디버그 토큰 콘솔 등록, 디버그 빌드에서 생략)는 기각 — 근거는
`docs/task_hardening_v2.md` §3-1-4 "[조치 확정, 2026-08-13]" 블록에
등록(원문 유지, 덧붙임).

**(a) `lib/main.dart` 변경**: `FirebaseAppCheck.instance.activate()`
호출을 `await` 대신 `unawaited(...)`로 감쌌다. `.then()`으로 성공
로그(`[APPCHECK] activate() 성공`), `.catchError()`로 실패 로그
(`[APPCHECK] activate() 실패(무시하고 진행): $e`)를 남긴다 — 실패를
조용히 삼키지 않는다. 앱 기동(`main()`의 나머지 흐름)은 이 호출의
완료를 기다리지 않고 계속 진행한다.

**(b) `SKIP_APPCHECK` 플래그 제거**: `const skipAppCheck =
bool.fromEnvironment('SKIP_APPCHECK')`와 그 분기를 삭제했다 — 이
플래그의 존재 이유는 "activate()가 앱 기동을 막는 문제를 진단
중 우회하는 것"이었는데, fire-and-forget 전환이 그 문제 자체를
없앴으므로 우회 수단이 더 이상 필요 없다. 이제 `SKIP_APPCHECK`
빌드와 일반 빌드가 App Check 초기화 경로에서 갈릴 이유가 없다.

**(c) `flutter analyze`**: 통과(`No issues found!`, 14.7초).

**(d) `task_hardening_v2.md` §3-1-4 갱신**: 원문 유지, "[조치 확정,
2026-08-13]" 블록을 덧붙였다(위 §2 링크 참고, 본문은 그 문서에
있다 — 여기서 옮겨 적지 않는다).

## 4. 2단계 0단계 — [APPCHECK] 로그 성격 확인, 코드 읽기만 (2026-08-13, 빌드 없음)

**(a) 디버그 시크릿 토큰을 찍은 주체 — SDK다, 우리 코드가 아니다.**
1단계 검증에서 관측된 로그 두 줄을 다시 대조한다:

```
08-13 10:52:17.267 ... D com.google.firebase.appcheck.debug.internal.DebugAppCheckProvider: Enter this debug secret into the allow list ...
08-13 10:52:17.276 ... I flutter : [APPCHECK] activate() 성공
```

첫 줄의 태그/클래스는 `com.google.firebase.appcheck.debug.internal.DebugAppCheckProvider`
— Firebase App Check SDK 내부 클래스다. 우리 Dart 코드(`lib/main.dart`)
어디에도 이 문자열("Enter this debug secret...")이나 토큰 값을
다루는 코드가 없다 — 우리가 추가한 로그는 `[APPCHECK] activate()
성공` / `[APPCHECK] activate() 실패(무시하고 진행): $e` 두 문구뿐이고
(90행), **토큰 값을 포함하지 않는다.** 둘째 줄(`I flutter`, 우리 로그)과
첫째 줄(`D`, SDK 태그)이 애초에 로그 레벨·태그부터 다르다. **확인:
SDK 로그다.**

**부수 확인(코드로 파생)**: 이 SDK 디버그 시크릿 로그는
`AndroidProvider.debug`를 쓸 때만 나온다. 우리 코드(`main.dart:83-85`)는
`kReleaseMode ? AndroidProvider.playIntegrity : AndroidProvider.debug`로
분기하므로, **실제 릴리스 빌드(`kReleaseMode=true`)에서는 디버그
공급자 자체를 안 쓴다** — 이 SDK 로그 줄은 릴리스에서 애초에 발생
경로가 없다(코드 확인, 이번 세션에서 릴리스 빌드로 재확인은
안 함 — 빌드 금지 지시 준수).

**(b) 우리 `[APPCHECK]` 로그가 릴리스 빌드에서도 남는가 — 남을
가능성이 높다, 다만 코드+전례 기반 판단이며 이번 세션 실측은
아니다.**

- 우리 로그는 `debugPrint(...)` 호출이다(`main.dart:89-90`).
- `android/app/build.gradle.kts`의 `buildTypes { release { ... } }`
  (39-42행)에는 `isMinifyEnabled`/`shrinkResources` 설정이 없다 —
  Gradle 기본값은 둘 다 `false`, 즉 이 저장소의 릴리스 빌드는
  R8 코드 축소·난독화가 적용되지 않는다.
- `DOT_paper_rev8.md` §5.11.7 "정정 (개정 5판)"이 바로 이 저장소
  설정에서 릴리스 빌드로 진단 로그(표준 출력 계열)가 정상
  출력되는 것을 서버 이관 작업 중 **반복 실측으로 확인**한 전례를
  남겼다 — 원인은 "R8 미적용" + "Flutter 프레임워크의 진단 출력
  함수 자체가 빌드 모드로 게이팅되지 않는다"는 것(그 절이 직접
  실측으로 뒤집은 원래의 잘못된 가정 — "릴리스에서 안 남는다" —
  이 바로 이 결함표가 참조하는 §5.11.7 초판 서술이었다).
- **판단**: 위 두 근거(현재 build.gradle.kts 설정이 §5.11.7 정정
  당시와 같은 패턴, Flutter의 `debugPrint`가 빌드 모드로 게이팅
  안 됨)로 볼 때 이번 `[APPCHECK]` 로그도 릴리스에서 출력될
  가능성이 높다. **다만 이번 세션에서 릴리스 빌드로 직접
  재확인하지 않았다(0단계 지시상 빌드 금지)** — 엄밀히는
  미확정으로 남긴다. §5.12.3이 이미 등록한 별도 문제(PID 회전·
  5MiB 로그 버퍼 상한으로 "찍힌다"와 "사람이 실제로 찾아 읽을 수
  있다"는 별개)도 그대로 유효하다.

**(c) 조합별 함의**

사용자가 제시한 세 갈래("우리 로그+릴리스에 남음" / "우리 로그+
릴리스에 안 남음" / "SDK 로그")는 **토큰 자체**를 누가 찍었는지를
기준으로 나뉜다. (a)에서 확인했듯 토큰은 SDK 로그이므로 해당하는
갈래는 다음과 같다:

- **→ SDK 로그 갈래를 적용한다: 우리 책임 범위 밖, 관측으로만
  등록한다.** 토큰이 로그에 찍히는 것 자체는 Firebase App Check
  SDK의 디버그 공급자 표준 동작이고, 우리 코드가 그 값을 만들거나
  전달하지 않는다. 게다가 위 부수 확인대로 **릴리스 빌드에서는
  이 SDK 로그 줄 자체가 발생 경로가 없다**(디버그 공급자를 안
  쓰므로) — 결함으로 등록할 근거가 약하다.
- **별개 관측(사용자 구조에 없던 조합, 정확성을 위해 추가
  등록)**: 우리 `[APPCHECK]` 로그는 애초에 토큰을 포함하지
  않으므로, 이 로그가 릴리스에 남든 안 남든 "토큰류가 릴리스
  로그로 샐 수 있다"는 결함 시나리오 자체가 **우리 로그 경로로는
  성립하지 않는다.** 다만 `catchError`의 `'$e'`(예외 메시지
  보간)가 향후 다른 예외 타입에서 민감한 값을 포함하게 될
  가능성은 낮은 우선순위로 관측만 남긴다 — 지금 관측된 범위
  에서는(activate 실패 시나리오 자체를 이번에 인위로 만들지
  않았으므로 `$e`의 실제 내용은 미확인) 이 로그 경로가 토큰을
  실어 나른 적이 없다.

**결론**: 이번 확인은 결함으로 등록할 것을 찾지 못했다 — 토큰은
SDK 소관이고 릴리스에서는 애초에 안 찍히며, 우리 로그는 토큰을
담지 않는다. 조치 후보 없음(등록만).

**핵심 발견 — `withTextModelFallback` 자체를 손댈 필요가 없다.**
`OutfitSelfEvaluator.evalOne`(`outfit_self_evaluator.dart:143-167`)은
이미 `withTextModelFallback`에 넘기는 클로저 안에서 `usedModel =
model`로 실제 응답 모델을 캡처하고 있고(147-159행), 그 값을
`SelfEvalOutcome.candidateModels`에 이미 저장하고 있다(24행 필드,

응답했는지 호출자가 알 수 있게 한다"는 요구사항은 함수 시그니처를
바꾸지 않고도 이미 충족되어 있다** — `evalResult.model`(또는
`candidateModels`의 해당 인덱스)을 `GeminiService.textModelFallback`
(공개 상수, `'gemini-3.1-flash-lite'`)과 비교하기만 하면 "이 후보는
폴백 응답인가"를 판정할 수 있다.

**최소 변경 설계**: `withTextModelFallback`의 시그니처·동작은
전혀 바꾸지 않는다. 변경은 `outfit_self_evaluator.dart` 내부에
국한된다 — `evalOne`이 이미 아는 `usedModel`을 이용해 판정 분기를
추가하고(현재 `passed = score != null && score >= threshold`인
자리에, 폴백 응답이면 `passed`를 만들기 전에 "판정 불가" 상태로
따로 분류), `candidateModels`는 그대로 두되 판정 결과를 표현할
새 필드(예: `List<bool> candidateIsFallbackModel` 또는 열거형)를
추가하는 정도로 끝난다. **위 표의 1~5번 호출자는 이 변경의 영향을
전혀 받지 않는다** — 함수 시그니처가 그대로이므로 컴파일 타임에도
런타임에도 부작용이 없다.

여기서 멈추고 보고한다. **1단계 (a) 승인 전에는 구현하지 않는다.**

## 6. 2단계 구현 (2026-08-13, 승인 후 — (a)(i)안·(b)최소변경설계 승인됨)

**승인된 조건 반영**: (조건 1) 화이트리스트로 뒤집었다 — 주 모델과
같을 때만 점수를 판정에 쓴다(fail-closed), 폴백 상수와 비교하는
블랙리스트는 쓰지 않았다. (조건 2) 활동 로그의 판정 라벨만
"판정 불가(대체 모델 응답, 자기 수리 미발동)"로 바꾸고 숫자는
그대로 뒀다.

### (a) 주 모델 상수를 공개하고, 화이트리스트로 판정

`GeminiService`의 `_textModel`(비공개)은 다른 파일에서 참조할 수
없어, 그 값을 그대로 가리키는 공개 별칭을 추가했다
(`gemini_service.dart:63-69`):

```dart
static const _textModel = 'gemini-3.5-flash';

// _textModel의 공개 별칭 — ... 문자열을 새로 하드코딩하면 _textModel이
// 바뀔 때 이 값만 조용히 벌어질 수 있어 값을 그대로 참조한다.
static const primaryTextModel = _textModel;
```

`OutfitSelfEvaluator`에 순수 함수 `judgeCandidate`를 새로 추가했다
(`outfit_self_evaluator.dart:108-141`) — 응답 모델이
`GeminiService.primaryTextModel`과 **같을 때만** 점수를 판정에
쓴다:

```dart
static ({bool passed, bool verdictWithheld}) judgeCandidate({
  required int? score,
  required String? respondingModel,
}) {
  if (respondingModel != GeminiService.primaryTextModel) {
    return (passed: false, verdictWithheld: true);
  }
  return (passed: score != null && score >= threshold, verdictWithheld: false);
}
```

블랙리스트를 쓰지 않은 근거는 함수 바로 위 주석에 그대로
남겼다(향후 세 번째 모델·폴백 상수 변경 시에도 안전한 방향으로
무너지도록). `score == null`(파싱 실패)은 이 화이트리스트와 무관하게
기존 그대로 "판정 없음"으로 떨어지고 `verdictWithheld=false`다 —
모델을 못 믿어서가 아니라 응답을 못 읽어서이므로 서로 다른 원인을
같은 라벨로 뭉개지 않는다.

**두 자리에 적용**: (1) 원본 후보 평가(`run()`의 메인 루프,
236-265행) — `judgeCandidate`로 `passed`·`verdictWithheld`를 정하고,
`verdictWithheld`이면 진단-수리 블록에 아예 안 들어가도록 조건에
`!judgment.verdictWithheld`를 추가했다(276행). (2) **수리 재평가
결과(316-339행) — 지시서가 명시하지 않은 두 번째 자리, 발견해서
추가로 적용했다.** 원래 후보가 신뢰 모델·미달이라 수리가
시작됐더라도, 수리 재평가 자체가 새 Gemini 호출이라 이번에도
폴백이 걸릴 수 있다. 여기에 같은 화이트리스트를 안 걸면 "신뢰
못 할 모델의 점수로 판정한다"는 원래 문제가 형태만 바뀌어

## 7. 3단계 0단계 — 수리 재평가 판정 불가의 귀결, 코드 확인 (2026-08-13, 무료·동작 변경 없음)

### (a) 현재 코드가 어느 쪽으로 동작하는가

`outfit_self_evaluator.dart:350-354`:

```dart
if ((repairedScore ?? 0) > (bestScore ?? 0)) {
  bestMatch = repairedCombo;
  bestText = repairedText;
  bestScore = repairedScore;
}
if (repairedPassed) break;
```

이 비교는 `repairedJudgment.verdictWithheld`를 **전혀 참조하지
않는다.** 즉 "채택한다"도 "원래 후보로 되돌린다"도 아니고, **원점수의
크기만으로 갈린다**:

- **`repairedScore`(신뢰 여부 무관한 원점수)가 현재 `bestScore`보다
  크면** → 수리된 조합이 `bestMatch`/`bestText`/`bestScore`로
  덮어써진다. `repairedPassed`는 `verdictWithheld=true`일 때 항상
  `false`이므로 `break`는 안 걸리지만(다음 후보가 있으면 계속
  평가), **이 수리된 조합은 이미 최종 후보 자리를 차지한 채로
  남는다** — 이후 더 나은(신뢰되는) 후보가 안 나오면 이 상태
  그대로 `SelfEvalOutcome`이 반환된다.
- **작거나 같으면** → `bestMatch`가 갱신되지 않으므로 결과적으로
  원래(신뢰 모델·미달) 후보가 그대로 남는다 — 이건 "되돌리기"라는
  능동적 동작이 아니라 **애초에 덮어쓰기가 안 일어난 것**이다.

**부수 확인 — `repairNote`도 같은 성질이다.** `outfit_self_evaluator.dart:347`의
`repairNote = '${blamed.category} 교체(${_axisLabel(weakAxis)} 개선)';`도
`verdictWithheld`와 무관하게 이 분기에 도달하면 무조건 설정된다.
`home_screen.dart:433-446`이 `repairNote != null`이면 무조건
"한 번 다듬었어요 · 아우터 교체(색상 개선)" 같은 문구를 홈 카드에
띄우므로, **판정이 유보된 수리에도 "다듬었다"는 확정적 문구가
그대로 뜬다.**

### (b) 의도한 선택인가, 기존 구조의 기본 동작인가 — 기본 동작이다

**의도적으로 재검토한 선택이 아니다.** 2단계 구현 시 나는 "홈 카드에
보이는 숫자·문구는 감추거나 보정하지 않는다"(승인된 (i)안)는
근거로 `bestMatch`/`bestScore`/`bestText`의 raw-max 비교 로직
(원본 후보 236-246행, 수리 재평가 350-354행)을 의도적으로
손대지 않았다 — 이 결정 자체는 실제로 내려졌고 문서(§6 (b))에도
등록했다. 하지만 그 결정은 **"화면에 찍히는 숫자를 보정하지
않는다"까지만 염두에 뒀지, "그 결정이 최종 채택(bestMatch) 자체를
좌우한다"는 이 구체적 귀결까지 따로 검토하고 승인한 것은
아니었다.** 즉 지금 동작은 raw-max 비교 로직을 건드리지 않기로
한 더 넓은 결정에서 **자동으로 딸려 나온 기본 동작**이지, "판정
불가 조합도 원점수가 높으면 최종 추천으로 승격시킨다"는 것을
독립적으로 의도해 설계한 결과가 아니다.

### (c) 등록과 제안 (동작 변경 없음 — 승인 대기)

**등록**: 위 (a)의 동작을 사실로 등록한다 — 수리 재평가가 판정
불가(폴백 응답)여도, 그 원점수가 당시 `bestScore`보다 크면 신뢰
여부와 무관하게 최종 추천(`bestMatch`)이 된다. 이는 원본 후보의
다중 평가 루프(242-246행)에도 **동일하게 적용되는 구조적 성질**이다
— 판정 불가인 원본 후보라도 그 시점 최고 원점수면 이미 `bestMatch`
후보가 되고, 이후 더 나은 신뢰 후보가 안 나오면 그대로 반환된다.
즉 이 트랙이 "폴백 응답을 판정 불가로 처리한다"고 한 것은 **통과/
미달 판정과 자기 수리 발동에는 정확히 적용됐지만, "이 조합을
최종 추천으로 내보낼지"에는 적용되지 않았다** — 후자는 여전히
신뢰 여부를 안 보는 순수 최댓값 비교다.

**제안(착수하지 않음, 승인 필요)**: `bestMatch`/`bestScore`/`bestText`
갱신을 "신뢰되는(judgeCandidate 기준) 후보끼리는 최댓값, 신뢰
후보가 하나도 없으면 그때만 판정 불가 후보 중 최댓값을 임시로
채택"하는 2단 비교로 바꾸는 안을 후보로만 남긴다. 근거: 지금은
판정 불가 조합이 원점수 하나로 신뢰 후보를 밀어낼 수 있어, 이번
트랙이 막으려던 "신뢰 못 할 점수로 결론짓기"가 통과/미달 판정
층위에서는 막혔지만 **최종 추천 채택 층위에서는 그대로 열려
있다.** 다만 이 변경은 실질적 위험이 있다 — 평가된 후보 전부가
폴백 응답이면(업스트림이 그 세션 내내 불안정한 경우) "신뢰 후보가
하나도 없으니 그때만 임시 채택"으로 빠지게 설계해야 지금처럼
`null` 반환(재시도 태스크 생성 경로, `wardrobe_screen.dart:99-108`)이
유지된다 — 그 분기까지 함께 설계해야 하는 작지 않은 변경이라
**이번엔 제안만 하고 착수하지 않는다.**

`"후보 1 평가: 75점 — 기준(70점) 통과, 채택"` — 2단계 변경
이전과 **글자 하나 다르지 않은 형식**이다. `logcat`의
`[SELF-EVAL]` 디버그 로그도 동일하게 `후보 1/3 → 점수 75 (기준
통과, 채택)`을 찍었다. 이 후보를 평가한 모델이 주 모델
(`gemini-3.5-flash`)이었다는 뜻이다(`judgeCandidate`가
`verdictWithheld=false`를 돌려줬고, 그래서 라벨 분기가 기존
문구 쪽으로 갔다).

**(d) Firestore `verdictWithheld` — false로 정확히 해석됨, 다만
문서엔 필드 자체가 없다(설계대로).** 위 4번째 문서(75점 통과)에
`verdictWithheld` 필드가 **존재하지 않는다** — 이는 버그가 아니라
설계 그대로다: `AgentLogEntry.toFirestore()`가 `if (verdictWithheld)
'verdictWithheld': verdictWithheld`로 **true일 때만** 쓰도록
했다(`repairAttempted`/`isFallback`과 같은 기존 관례). 필드가
없으면 `AgentLogEntry.fromFirestore()`의 `data['verdictWithheld']
as bool? ?? false`가 `false`로 복원한다 — **읽기 경로 기준으로는
정확히 "false로 기록된 것"과 동일하게 동작함을 실측으로
확인했다.** `verdictWithheld=true`가 실제로 Firestore에 `true`
값으로 찍히는 사례는 이번엔 관찰하지 못했다(폴백이 자기평가
단계에서 안 걸렸으므로) — **미검증으로 남긴다.**

**(e) 자기 수리 — 자연히 안 나옴, 미검증.** 후보 1/3이 첫 시도에
바로 통과(75점 ≥ 70점)해 나머지 2개 후보도, 진단-수리 루프도
돌지 않았다(`[SELF-EVAL] 완료: 1개 평가`). 억지로 미달을 만들지
않았으므로 수리 경로·수리 재평가의 `verdictWithheld` 처리(§7이
등록한 "발견")는 이번 실기기 검증으로 관찰되지 않았다 —
**미검증.**

**부수 관찰(자연 발생, 인위 아님) — 속성 추출 단계에서 폴백
2건.** 새 옷 등록 도중 `logcat`에 다음이 자연히 찍혔다:

```
11:40:26.418 [GEMINI] gemini-3.5-flash 응답 파싱 실패(FormatException) - gemini-3.1-flash-lite로 폴백
11:41:01.967 [GEMINI] gemini-3.5-flash 실패(statusCode=503) - gemini-3.1-flash-lite로 폴백
```

둘 다 `extractSizeFromChart`/`extractAttributes`(속성·사이즈 추출)
경로에서 났다 — **자기평가(`OutfitSelfEvaluator`) 호출이 아니다**
(1단계 (b)가 이미 확인한 "withTextModelFallback의 6개 호출자 중
5개는 자기평가와 무관"이 실기기에서도 그대로 확인된 사례). 이
502가 아니라 503 하나는 자연 발생 상태코드 확인이라는 점에서
`task_selfeval_validity_v1.md` §6-가가 미확정으로 남긴 503/429
질문에 참고가 될 수 있으나, **자기평가 경로가 아니므로 그 질문에
직접 답하지는 않는다** — 관측으로만 등록한다.

## 9. 트랙 종결 — 반쪽짜리 조치임을 명시 (2026-08-13)

### (a)·(b) 종결 요약

이 트랙은 직전 트랙(`task_selfeval_validity_v1`)이 등록한 5개
후보 중 ④(App Check)와 ①(폴백 판정 제외)을 실행했다. **둘 다
"닫혔다"고 과대평가하면 안 된다 — 특히 ①은 반쪽이다.**

**④ App Check — 닫혔다.** `activate()`를 fire-and-forget으로
전환하고 `SKIP_APPCHECK` 플래그를 제거했다. 일반 디버그 빌드로
스플래시 정지 없이 정상 기동함을 실기기로 확인했다(§1). 이 저장소의
디버그 실기기 검증이 "실제 배포 조건과 다른 플래그 빌드에서만
가능하다"는 문제 자체는 해소됐다.

**① 폴백 판정 제외 — 통과/미달 판정과 자기 수리 발동에서는 라우팅
편향을 제거했다. 최종 추천 선택에서는 제거하지 못했다.** §7(0단계)이
코드 확인으로 드러낸 대로, 폴백(주 모델이 아닌) 모델이 응답한
후보라도 원점수가 크면 여전히 `bestMatch`(최종 추천)로 채택된다
— L(lite)이 F(flash)보다 평균 9.85점 높게 나온다는 직전 트랙의
실측을 감안하면, **폴백 응답 후보는 최종 추천 경쟁에서 구조적으로
유리하다.** 이건 작은 잔여 결함이 아니라 이번 조치가 막으려던 것과
같은 성격의 문제가 판정 층위에서 선택 층위로 옮겨간 것이다. 사용자
결정으로 이번엔 고치지 않고 `handoff_2026-08-07.md` §4에 독립
행으로 등록했다(위 §7·§9 (c) 참고).

### (c) 확정한 것 / (d) 미검증·미확정으로 남는 것

**확정한 것**:
1. App Check `activate()`가 앱 기동을 막지 못하게 됐다(단일 설치·
   단일 기동 조건에서 확인).
2. 자기평가 통과/미달 판정과 자기 수리 발동에서 라우팅(모델
   불신뢰) 편향이 제거됐다 — 화이트리스트(fail-closed) 설계,
   단위 테스트 8건, 정상 경로 실기기 회귀 확인 완료.
3. 최종 추천 선택 층위에는 같은 편향이 여전히 남아 있다(§9 (b)) —
   확정된 미해결 결함으로 등록.
4. 수리 재평가 자체에도 같은 화이트리스트가 필요하다는 것(지시서가
   명시하지 않았던 지점)을 발견해 적용했다.

**미검증·미확정으로 남는 것**:
- **폴백 상황의 실동작** — 자기평가 단계에서 `verdictWithheld=true`가
  실제로 Firestore에 기록되는 사례를 자연 발생으로 관찰하지
  못했다(§8 (d)). 인위로 만들지 않았다.
- **릴리스 빌드 동작** — App Check fire-and-forget 전환도, 자기평가
  판정 불가 처리도 디버그 빌드로만 검증했다. 릴리스 고유 결함
  전례(이 저장소가 반복 겪은 것, §2 원칙 15번)가 있으므로 릴리스
  검증 전까지는 완전한 확인이 아니다.
- **반복 재설치 시 App Check 거동** — 이번 검증은 단일 설치·단일
  기동이었다. `task_hardening_v2.md` §3-1-4의 "반복 재설치가
  트리거였을 수 있다" 가설은 확인도 반증도 안 됐다.
- **503/429 상태코드** — 이번 실기기 검증에서 자연 발생 폴백
  (속성 추출 단계, 503 1건 관측)이 있었지만 자기평가 경로가
  아니었다(§8 부수 관찰). `task_selfeval_validity_v1.md` §6-가가
  남긴 미확정은 그대로다.
- **자기 수리 재평가의 판정 유보 흐름 실측** — 코드·단위 테스트로만
  확인했고 실기기에서 관찰하지 못했다(§8 (e)).
- **최종 추천 선택의 라우팅 편향(§9 (b))** — 결함으로 등록만 했고
  고치지 않았다.
