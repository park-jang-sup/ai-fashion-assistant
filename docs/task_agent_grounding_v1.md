## 2. 부분 A — 폴백 점수 신뢰

1. `judgeCandidate`가 응답 모델이 `primaryTextModel` **또는** `textModelFallback`일 때 점수를 판정에 쓰게 한다. 그 밖의 모델명은 지금처럼 판정 유보다(모르는 모델은 믿지 않는다는 원칙은 유지).
2. 이 변경이 성립하는 전제를 서버에 고정한다: `text_model_routes.ts`에 "점수를 믿을 수 있는 모델" 목록(`claude-sonnet-5-5`, `gemini-3.5-flash`)을 두고, **두 별칭의 경로가 모두 이 목록 안에 있는지** 단위 테스트로 검사한다. 목록에 모델을 추가하려면 `task_text_model_v1.md` §3-4 관문을 통과해야 한다고 주석에 적는다.
3. `judgeCandidate` 위의 긴 주석과 관련 테스트(`outfit_self_evaluator_verdict_test.dart`)를 새 규칙에 맞게 고친다. 옛 규칙의 근거 서술은 지우지 말고 "2026-11-13 변경" 블록으로 덧붙인다.
4. `judgeCandidate` 외에 "폴백 응답이면 유보"를 전제로 한 코드(가장 좋은 후보 교체 판정, 활동 내역 문구, 카드의 신뢰도 문구)가 있으면 찾아서, 새 규칙에서 틀린 말을 하게 되는 곳을 보고한 뒤 고친다.

## 3. 부분 B — 분석 텍스트와 추천 카드 통일

### 3-1. 설계

- 추천 후보를 뽑는 로직(`_matchStyleRecommendations`)을 화면 파일에서 서비스로 옮겨, **분석 요청과 카드·팝업이 같은 후보 목록**을 쓰게 한다. 뽑는 규칙 자체는 바꾸지 않는다.
- 분석을 시작할 때 후보(최대 8개)를 먼저 계산해 프롬프트에 넣는다. 사진용·프로필용 프롬프트 둘 다.
- 모델은 그 후보 안에서만 고른다. 고른 번호를 기계가 읽을 수 있는 줄로 함께 낸다.
- 카드는 모델이 고른 후보를 맨 앞에 두고 "AI 추천" 표시를 붙인다. 나머지 후보는 지금 순서대로 뒤에 둔다.

### 3-2. 프롬프트 변경 (초안 — 프로브로 확인한 뒤 확정)

의류 설명과 이력 구간 다음에 넣는다.

```
[내 옷장 후보] (착용자가 실제로 가진 옷입니다)
1. 아우터(추가 가능): 색상 브라운, 스타일 캐주얼, …
2. 신발(추가 가능): …
3. 상의(교체 후보): …
```

- 지금 조합에 그 종류의 옷이 없으면 "추가 가능", 이미 있으면 "교체 후보"로 표시한다. 액세서리는 세부 종류(모자·가방·시계·팔찌) 기준으로 판단한다.

머리 줄에 네 번째 줄을 추가한다.

```
[추천후보] (위 후보 중 이 코디에 가장 도움이 되는 것의 번호 1~2개, 쉼표로 구분. 마땅한 것이 없으면 없음)
```

"1. 스타일링 팁" 지시를 바꾼다.

```
1. 스타일링 팁: [추천후보]에 적은 옷을 이 코디에 어떻게 더하거나 바꾸면 좋은지 설명해 주세요.
   옷은 색상과 종류로 부르고(예: 브라운 블루종) 번호는 쓰지 마세요. [내 옷장 후보]에 없는 옷은 추천하지 마세요.
   추가 가능 후보를 먼저 고려하고, 교체 후보는 지금 옷보다 분명히 나을 때만 고르세요.
   [추천후보]가 없음이면 지금 조합을 그대로 살리는 연출 팁을 써 주세요.
```

출력 예시 블록도 네 줄로 고친다. "2. 다른 색상 추천"은 그대로 둔다.

### 3-3. 지켜야 할 것

- **후보가 0개면 프롬프트는 지금과 한 글자도 다르지 않아야 한다**(옷장이 빈약한 사용자). 변경 전에 현재 출력을 골든으로 저장해 테스트로 고정한다.
- **자기평가용 프롬프트는 한 글자도 바뀌지 않아야 한다.** 같은 방식으로 골든 테스트를 둔다. 오늘 검증한 점수 분포가 이 프롬프트에 묶여 있다.
- `[추천후보]` 줄은 화면에 보이면 안 된다. `analysisResult`를 읽는 곳(화면 표시, 이력 저장, 스크랩 등)을 전부 찾아 처리한다. 스트리밍 도중에 이 줄이 반쯤 온 상태도 화면에 새지 않게 한다.
- 모델이 범위 밖 번호나 형식이 틀린 줄을 내면 무시하고 카드를 지금 순서대로 보여 준다. 줄이 아예 없어도 같다. 분석 자체는 실패로 처리하지 않는다.
- 스트리밍이 실패해 비스트리밍·폴백 경로로 갈 때도 같은 후보를 넘긴다.
- 합성 중 팝업은 분석 결과가 나오기 전이므로 지금처럼 후보 목록만 보여 준다(모델이 고른 것과 같은 집합이므로 모순되지 않는다).

### 3-4. 프로브 (사용자가 실행)

`tools/text_probe`에 과제 T5를 추가한다. 프롬프트는 `task_text_model_v1.md` §3-1과 같은 방식으로 Dart 빌더 출력을 덤프해서 쓴다(프로브에서 다시 작성하지 않는다).

- 대상: 주 모델(`claude-sonnet-5-5`, effort medium)과 폴백 모델(`gemini-3.5-flash`). 폴백도 같은 형식을 지켜야 한다.
- 입력: 전신 사진 + 조합 3개 × 각 2회 = 모델당 6회, 합계 12회. 후보 목록은 실제 옷장 자료에 앱과 같은 로직을 적용해 뽑는다. 조합 하나는 옷장을 비운 입력으로 후보 0개인 경우를 만든다.
- 관문(실행 전 고정):
  1. 머리 세 줄(`[점수]`, `[분위기점수]`, `[분위기]`)이 12/12 파싱된다
  2. 후보가 있는 경우 `[추천후보]` 줄이 전부 파싱되고 번호가 범위 안이다
  3. 본문이 후보에 없는 옷을 추천한 경우가 없다(사용자가 `index.html`에서 읽고 판단)
  4. 스트리밍 첫 글자 중앙값이 주 모델 3초, 폴백 모델 12초 이내
- 관문 1·2를 통과하지 못한 모델이 있으면 프롬프트 문장을 1회 고쳐 다시 돌릴 수 있다. 그래도 안 되면 멈추고 보고한다.

## 4. 부분 C — 날씨를 실제 선택에 반영

### 4-1. 매칭

- `findForTpo`에 선택 인자로 그날 예보를 넘길 수 있게 한다. **예보가 없으면 결과가 지금과 완전히 같아야 한다**(골든 테스트). 기존 평가 도구와 논문의 수치는 예보 없는 조건이므로 영향을 받지 않는다.
- 아이템 점수에 날씨 감점을 더하는 순수 함수를 둔다. 규칙은 주간 플랜의 문구(§1-7)와 맞춘다.

| 조건 | 감점 대상 |
|---|---|
| 비 (강수확률이 기존 임계 이상) | 밝기가 light인 하의·신발, 태그에 니트·스웨이드 계열이 있는 옷 |
| 더운 날 (최고 28°C 이상) | 태그가 겨울·두꺼운 소재 계열인 옷 |
| 추운 날 (최저 5°C 이하) | 태그가 여름·얇은 소재 계열인 옷 |

- 태그 키워드 목록은 추측하지 말고, Firestore의 `wardrobe`·`demo_wardrobe` 태그 분포를 읽기 전용으로 조사해 실제로 쓰이는 표현으로 정하고 보고한다.
- 감점 크기는 정책 필드로 두고 기본 0.3으로 한다. 근거: 격식 한 단계 차이(0.5)를 날씨만으로는 뒤집지 않는다. 이 값은 평가 도구로 검증한 값이 아니라는 점을 주석과 실행 기록에 적는다.
- "추운 날 아우터 우선"은 이번에 넣지 않는다. `findForTpo`가 아우터를 조합에 넣는 방식을 확인해, 옷장에 아우터가 있는데도 추운 날 빠질 수 있는 구조면 보고만 한다.

### 4-2. 적용 지점

- 일일 추천 준비와, 예보가 바뀌어 다시 계획하는 경로 모두 그날 예보를 `findForTpo`에 넘긴다.
- 자기평가 프롬프트에는 날씨를 넣지 않는다.

### 4-3. 문구는 실제로 한 일만 말한다

예보가 특이한 날(비·더위·추위)에는 매칭을 날씨 없이 한 번, 날씨를 넣어 한 번 돌려 비교하고, 그 차이로 문구를 정한다(매칭은 기기 안 계산이라 모델 호출이 늘지 않는다). 순수 함수 + 단위 테스트.

용어:
- **피한 옷** = 날씨 없이 돌린 1순위 조합에 들어 있던 감점 대상 중, 날씨를 넣은 1순위 조합에도 없고 최종 채택 조합에도 없는 옷
- **남은 옷** = 최종 채택 조합에 들어 있는 감점 대상

| 경우 | 문구 방향 |
|---|---|
| 피한 옷이 있다 | 무엇을 피했는지 구체적으로 (예: "비 예보라 밝은 하의 대신 어두운 톤으로 골랐어요") |
| 피한 옷이 없고 남은 옷도 없다 | "비 예보에도 무리 없는 조합이에요" |
| 피한 옷이 없고 남은 옷이 있다 | "비 예보가 있지만 옷장에 더 맞는 옷이 없어 그대로 추천해요" |

"피한 옷"을 이렇게 좁게 정의하는 이유: 자기평가가 다른 이유로 2순위 후보를 채택한 것을 날씨 덕으로 돌리지 않기 위함이다.

- 기존 고정 문구("비 예보가 있어 어두운 톤으로 준비했어요" 등 세 개)는 없앤다.
- 활동 내역에도 "날씨 반영: 조합 변경 있음/없음"을 남긴다.
- 자기평가가 날씨 반영 1순위가 아닌 후보를 채택한 경우에도 문구가 채택된 조합 기준으로 맞아야 한다.

### 4-4. 시연·검증용 예보 가정

날씨는 마음대로 바꿀 수 없으므로, 설정 화면의 진단 영역에 **"예보 가정(테스트용)"** 을 둔다: 없음 / 비 / 더운 날 / 추운 날.

- 켜져 있으면 예보 조회 결과 대신 가정한 값을 쓴다. 기기에만 저장한다.
- 가정한 예보로 만든 추천에는 문구 끝에 "(테스트용 가정 예보)"를 붙이고, 활동 내역에도 가정 예보였음을 남긴다.
- 기본값은 없음이다.

   - C: 다가오는 일정의 추천이 이미 있는 상태에서 예보 가정을 "비"로 바꾸고 "지금 확인" → 예보 변화를 감지해 다시 계획하는지, 조합과 문구가 §4-3대로 나오는지. 이어서 "없음"으로 되돌리고 "지금 확인" → 다시 계획하는지. 다시 계획 횟수 상한에 걸리면 그 사실을 보고한다
   - A: 폴백 리허설 1회(경로 표의 `text-primary`를 없는 Claude 모델명으로 바꿔 배포 → 옷 1벌 등록 → **추천이 만들어지는지** 확인 → 되돌려 배포 → 분석 1회로 복구 확인). 리허설용 변경은 커밋하지 않는다. 이 배포 2회는 사용자가 따로 승인한다.
5. 서버 로그와 활동 내역으로 결과를 표로 만들어 실행 기록에 덧붙인다.

커밋: A 1개, B 1개(프로브 포함), C 1개. `git push`는 사용자가 지시할 때만.

## 6. 금지 사항

- 자기평가용 프롬프트, 통과 기준(70), 평가 횟수 상한을 바꾸지 않는다.
- 후보를 뽑는 규칙(`_matchStyleRecommendations`의 점수·개수)과 `findForTpo`의 기존 점수 항목을 바꾸지 않는다. 날씨 감점만 더한다.
- 주간 플랜 프롬프트, 서버 변환기(`claude_adapter.ts`), 가상 피팅 경로를 건드리지 않는다.
- `firestore.rules`, `storage.rules`, 인증, App Check, 호출량 상한 값을 건드리지 않는다.
- Firestore·Storage에는 읽기만 한다.
- API 키를 파일·로그·커밋·대화에 남기지 않는다. 호출이 필요한 실행은 사용자가 한다.
- `firebase deploy`와 APK 빌드는 사용자 승인 없이 하지 않는다.
- 프로브 관문(§3-4)을 결과를 본 뒤 바꾸지 않는다.
- 논문·handoff 문서를 고치지 않는다. 결과는 이 문서 끝 "실행 기록" 절에 덧붙인다. 논문 서술과 달라지는 설계(폴백 점수 신뢰, 날씨 반영)는 실행 기록에 "논문과 달라진 점"으로 모아 적는다.
- 이 문서에 없는 리팩터링을 하지 않는다. 범위 밖 결함은 고치지 말고 보고한다.
