개선일 수 있음을 시사.

그동안 항상 9.5~19.4초였던 그 축과 동일한데, 이번에 그 축에서
처음으로 60초를 넘는 값이 나왔다. **회귀가 옷 1벌 경로로 번지고
있다는 신호일 수도, 표본이 적어(1벌 경로 총 관측 ~18건 중 이번
1건) 아직 못 본 정상 산포일 수도 있다 — 이 데이터만으로는 못
가른다.** 순차 합성은 **회귀 회피가 아니라 회귀 노출 빈도를
낮추는 것**으로 이해해야 한다: 한 번에 처리하면 옷 2벌 이상
구간에 100% 노출되지만, 순차로 쪼개면 매 단계가 옷 1벌 구간에
속해 그 구간의 낮은(그러나 0은 아닌) 스파이크 확률만큼만
노출된다. 게다가 단계 수만큼 시도 횟수가 늘어(3벌 피팅 = 3번의
"1벌 구간" 시도) 최소 1단계가 스파이크를 맞을 확률은 다시 조금
올라간다. 이 트레이드오프를 아래 (h) 시한 설계에 반영한다.

## a. 순차 루프 구조

`lib/services/gemini_service.dart`의 `generateFittingImage()`를
한 번의 다중 이미지 호출에서 **옷 목록을 순회하는 루프**로 바꾼다.

```
현재 결과 이미지 bytes = userPhotoBytes (최초 입력 = 사용자 전신 사진)
for item in clothingItems (정해진 순서, 아래 b 참고):
  itemBytes = 다운로드(item)
  parts = [prompt(clothingNames: [item.category]), 현재 결과 이미지, itemBytes]
  response = 프록시 호출(callGeminiText 또는 generateFittingImage)
  현재 결과 이미지 bytes = extractImage(response)
반환값 = 현재 결과 이미지 bytes (마지막 단계 결과)
```

**중간 결과는 메모리(`Uint8List`)에서만 다음 요청의 입력으로
넘긴다 — Storage에 올리지 않는다.** 지금 실험 스크립트가 이미 이
방식(파일로 저장한 건 사용자 품질 확인용이었을 뿐, 다음 호출에는
디스크 재읽기 없이 바로 이전 응답의 base64를 재인코딩해 넘김)이고,
이 원칙을 그대로 프로덕션 코드에 반영한다. Storage에 올리면
`fitting_results/`처럼 각 단계마다 고아 파일이 쌓이고
(`TOKEN_REVOKE_PREFIXES`/`revokeTokenOnUpload` 대상도 아니라 정리
경로가 없음), 실패 시 부분 결과 삭제 로직까지 추가로 필요해진다 —
메모리 전달은 이 문제 자체가 안 생긴다.

**프롬프트는 매 단계 옷 1벌 기준으로 재구성**(`_buildFittingPrompt`가
이미 `clothingNames: List<String>` 하나만 받으므로 그대로 재사용
가능, 매 호출에 `[item.category]` 1개짜리 리스트만 넘기면 됨 —
새 함수 불필요).

## b. 옷 순서

**제안: 하의 → 상의 → 아우터 → 신발 → 액세서리.** 근거:

- 사람이 옷을 입는 실제 순서와 유사(하의부터, 겉옷은 마지막)해
  모델이 "다음에 무엇을 덧입힐지" 판단할 때 이미지 사전학습 분포와
  더 잘 맞을 가능성 — 다만 이건 **가설이고 실측하지 않았다.**
- 신발·액세서리처럼 신체 대부분을 안 가리는 항목을 뒤로 두면,
  앞 단계에서 몸통 전체가 크게 바뀌는 옷(상의/아우터/하의)이 먼저
  자리를 잡고, 뒤에는 국소적인 추가만 남아 각 단계의 "재해석 폭"이
  줄어들 것으로 예상.

**이번 실험은 순서 효과를 테스트하지 않았다** — 상의→하의→신발
한 방향만 1~3회 실행했다. **순서가 품질(자세 유지, 이전 단계 옷
보존)이나 소요시간에 영향을 주는지는 별도로 확인이 필요** — 제안:
같은 3벌 조합을 순서만 바꿔(신발→하의→상의 등) 1회 더 실행해
결과 이미지를 나란히 비교하는 것을 구현 착수 전 마지막 확인
항목으로 추가할지 사용자 판단에 맡긴다. 지금 코드에는 카테고리
우선순위 상수(예: `const List<String> fittingOrder = ['하의',
'상의', '아우터', '신발', '액세서리'];`)로 넣어 나중에 순서를
바꾸는 게 한 곳 수정으로 끝나게 한다.

## d. 호출량 상한 — 별도 축 신설

**문제**: `RATE_LIMIT_CONFIG.imageLimit = 20`(`functions/src/index.ts:157`)은
"한 번에 한 번 호출"을 전제로 설계됐다. 순차 합성은 피팅 1회가
옷 개수만큼의 Gemini 이미지 호출이 된다 — 3벌 피팅이면 시간당
`20/3 ≈ 6`회로 정상 사용 가능 횟수가 실질 3분의 1로 준다. 상한
자체를 60으로 올리면 순차 피팅은 다시 20회 가능해지지만, **상한의
원래 목적(Gemini 이미지 모델 호출 비용 통제, `rate_limit.ts` 상단
주석 "논문 5.13.5/7.1 프록시의 호출량 무제한")이 사실상 무력화**된다
— 순차가 아닌 다른 경로로 이미지 모델을 60번 두드리는 것도 똑같이
허용되기 때문.

**제안: `RateLimitKind`에 `"fitting"` 추가, 피팅 1회당 정확히 1회만
소비.** `rate_limit.ts`의 `RateLimitKind`/`RateLimitState`/
`RateLimitConfig`/`countField`/`limitFor`에 `fitting`/`fittingCount`/
`fittingLimit` 한 줄씩 추가(기존 `signCount` 추가 때와 같은 패턴,
`carryOver`의 `?? 0` 방어도 그대로 재사용). `generateFittingImage`
(클라이언트 진입점에 대응하는 서버 쪽 — 지금은 `_callProxyText`를
쓰는 옛 경로와 `generateFittingImage`콜러블을 쓰는 신 경로 둘 다
있음, 아래 g 참고)가 **루프 시작 전에 `checkAndRecordRateLimit(uid,
"fitting")` 1회만 호출**하고, 루프 안의 개별 Gemini 호출은 **기존
`"image"` 카운트를 그대로 유지**(실제 Gemini 비용은 여전히 호출
횟수만큼 나가므로 비용 가시성 자체는 유지해야 함) — 다만
`imageLimit`은 순차 호출 배수를 흡수할 만큼 올린다.

**구체 값 제안**(실측 아님, 계산 — 구현 전 재검토 필요):
- `fittingLimit = 6`/시간 — 기존 `imageLimit = 20`을 "3벌 피팅
  기준" 나눈 값과 비슷한 자릿수, 정상 사용(한 세션에 코디 여러
  벌 시도)엔 여유롭고 남용은 여전히 막음.
- `imageLimit`을 20 → **32**로 상향 — `fittingLimit = 6` ×
  최대 아이템 수(코디보드 슬롯 상한, §6 "코디보드 슬롯 구조" 절
  근거로 최대 9장이 아니라 실사용 분포 상 3~5벌이 보통이므로
  6×5=30에 여유를 조금 더한 값. **9장까지 실제로 쓰는 사용자가
  있다면 6×9=54가 필요** — 코디보드 실사용 아이템 수 분포를
  확인 안 하고 이 문서에서 값만 제안하는 것이므로, 구현 전에
  실제 분포(또는 최소 슬롯 상한)를 다시 확인해야 한다.
- 순수 텍스트/서명 경로는 안 바뀌므로 `textLimit`/`signLimit`은
  그대로.

**대안(기각, 기록만)**: `imageLimit`을 안 건드리고 `fittingLimit`만
따로 둬서 순차 호출은 `"image"` 카운트를 아예 안 먹게(피팅 전용
콜러블 안에서는 `"image"` 카운트를 건너뛰고 `"fitting"`만 셈) 하는
안도 검토했으나, 그러면 순차 경로를 통하지 않는(이론상 미래에
생길 수 있는) 다른 이미지 모델 소비 경로와 비용 계측이 분리돼
전체 이미지 비용을 한 곳에서 못 보게 된다 — `"image"` 카운트는
유지하고 상한값만 올리는 쪽이 더 단순하고 계측 일관성이 있다.

## e. 실패 처리

**중간 단계 실패 시 전체 실패로 본다 — 부분 결과를 쓰지 않는다.**
근거: 4장(§3 "폴백 원칙", `functions_bg_removal/main.py`가 인용하는
것과 같은 결)은 "실패해도 이전 단계 산출물(원본)은 그대로 유효한
상태로 남긴다"는 원칙이지, "일부만 처리된 결과를 성공으로
보여준다"는 뜻이 아니다. 3벌 중 신발 단계에서만 실패했다고 상의+
하의만 입힌 사진을 "가상 피팅 결과"로 보여주면 사용자가 요청한
조합과 다른 걸 성공으로 오인한다 — `fitting_cache`에도 최종 조합
키로만 쓰기 때문에(아래 f) 부분 결과를 캐시할 방법도 마땅치 않다.

**구체 동작**: 루프 중 한 단계라도 예외가 나면 그 시점에서 루프를
멈추고 예외를 그대로 던진다(`_withRetry`가 지금처럼 바깥에서
받음). **재시도 단위는 전체 루프가 아니라 실패한 단계 하나만** —
`_withRetry`를 루프 바깥이 아니라 **루프 안, 단계별로** 감싸는
방향을 제안한다(3단계 중 2단계까지 성공했는데 3단계 실패로 전체를
처음부터 다시 하면 이미 성공한 1·2단계 호출 비용이 낭비되고
소요시간도 2배 가까이 늘어남 — 순차 구조의 장점을 재시도 설계가
못 살리는 셈). 다만 이러면 "몇 번째 재시도인지"가 단계마다
달라져 전체 시한 설계(h)가 복잡해지므로, 두 방식(전체 재시도 vs
단계별 재시도) 중 무엇을 쓸지는 **구현 시 결정 사항으로 남기고
이 문서에서 확정하지 않는다** — h에서 두 경우 다 계산해둔다.

## f. 캐시

**캐시 키는 기존대로 최종 조합 기준 유지**(`sha256(전신id:정렬된
옷id들)`, 순서 안 타는 정렬 때문에 옷을 어느 순서로 입혔든 같은
조합이면 같은 키 — 이건 그대로 맞다, 순차 여부와 무관하게 사용자가
보는 최종 결과물이 같은 조합이면 캐시 히트가 나야 함).

**중간 결과 캐시는 하지 않는다 — 이번 버전 범위 밖으로 명시.**
"같은 상의로 여러 하의를 시도하면 1단계(상의 단계) 결과를 재사용할
수 있다"는 아이디어 자체는 맞지만:
- 캐시 키 체계를 "부분 조합"까지 확장해야 함(지금은 완성된
  `clothingItemIds` 집합 전체에 대한 키 하나뿐 — 부분집합 키까지
  두면 `fitting_ownership_policy.ts`/`fitting_cache_key.ts` 양쪽
  다 손대야 하고 Dart↔TS 교차 검증 테스트도 다시 설계해야 함).
- 순서 의존성이 생김 — 상의를 먼저 입힌 뒤 하의를 바꾼 경우와
  하의를 먼저 입힌 뒤 상의를 바꾼 경우가 지금 제안(b, 순서 고정)
  대로면 항상 같은 순서라 문제 없지만, 순서를 사용자가 바꿀 수
  있게 되는 순간 "부분 캐시 히트"의 이미지가 실제로 지금 만들려는
  최종본과 같은 경로로 만들어진 게 맞는지 검증이 필요해짐.
- 지금 3회 재현 실험에서 이미 단일 단계도 76.2초 스파이크가
  나온 걸 보면(위 재현성 결과), 부분 캐시가 있어도 신규 단계
  호출 자체의 지연 위험은 안 줄어듦 — 이득 대비 복잡도가 이번
  범위에서는 안 맞는다고 판단.

## g. 되돌릴 수단

기존 `SERVER_FITTING_CACHE`(`lib/services/gemini_service.dart`,
`bool.fromEnvironment`, 기본 false) 플래그와 같은 패턴으로
**`SEQUENTIAL_FITTING`** dart-define 플래그를 신설, 기본 **false**
(기존 일괄 방식 유지). `generateFittingImage()` 안에서:

```
if (sequentialFittingEnabled) {
  // 새 순차 루프
} else {
  // 기존 한 번에 호출 (지금 코드 그대로, 한 글자도 안 바꿈)
}
```

**`SERVER_FITTING_CACHE`와의 관계**: 둘은 직교하는 축이다 —
순차냐 일괄이냐(요청을 몇 번 나누는가)와 서버가 캐시를 대신
쓰느냐(성공 즉시 서버가 `fitting_cache`에 쓰는가)는 별개 결정.
순차 루프의 **마지막 단계**만 서버 캐시 경로(`_callFittingProxy`,
`generateFittingImage` 콜러블)를 타게 하고 중간 단계는 항상
`_callProxyText`(캐시 불필요 — 중간 결과는 캐시 대상이 아님, 위
f 참고)를 쓰는 조합을 제안 — 이러면 두 플래그를 곱한 4가지 조합
중 실제로 쓰는 건 "순차 켬 + 마지막 단계만 서버캐시"와 "순차
꺼짐(기존)" 둘뿐이라 매트릭스가 커지지 않는다.

## h. 클라이언트 시한

**핵심 문제**: 재현성 확인에서 단일 "옷 1벌 추가" 단계가 76.2초까지
나왔다. 그동안 이 축의 관측(A군 3회 + 직접 호출 다수, 총
~18건)은 전부 9.5~19.4초였으므로 기존 `_callProxyText`의 60초
시한은 넉넉해 보였지만, 이번 1건이 표본에 들어오면서 "옷 1벌
단계도 60초를 넘을 수 있다"는 게 실측으로 확인됐다 — 60초를
그대로 단계별 시한으로 쓰면 이번 같은 스파이크에서 그 단계가
실패한다.

**단계별 시한 제안**: 기존 60초를 유지하되(76.2초는 60초를
넘었으므로 이번 스파이크는 이 값으로도 못 막았을 것 — 더 늘리는
게 정답인지, 늘려도 "얼마나"인지는 표본이 1건뿐이라 근거가
약하다), **단계별 재시도(위 e에서 제안한 방향)와 묶어서 판단**:
한 단계가 60초에 걸려도 `_withRetry`가 그 단계만 즉시 재시도하면
(기존 `_withRetry`의 "타임아웃 → 무조건 1회 재시도" 동작 그대로),
1벌 구간 재시도가 다시 스파이크를 맞을 확률은 낮을 것(정정 3의
분포상 1벌 구간 자체가 원래 저산포이므로 연속 스파이크 확률은
더 낮음 — 다만 이것도 표본 1건으로는 확정 못 함).

**전체 시한**: 단계 수 × (단계별 시한 + 재시도 여유)를 그대로
합산하면 3벌 기준 최악 `3 × (60+60) = 360초` — 사용자를 6분 기다리게
하는 건 "빠르게 만드는 방법을 찾는다"는 애초 목적과 어긋난다.
**제안: 전체 시한은 별도로 두지 않고, 진행 표시(c)로 "지금 몇
단계인지"를 계속 보여줘 사용자가 직접 기다릴지 판단하게 한다** —
숫자로 강제로 끊는 것보다, 정상 케이스(대부분 30~50초대, 위 표
참고)에서는 어차피 훨씬 빨리 끝나고, 스파이크가 나더라도 "지금
2/3단계, 오래 걸리는 중"이라는 정보 자체가 사용자에게 유용하다는
판단(다만 이것도 실기기로 검증 안 된 UX 가설 — 구현 후 실제
반응을 봐야 함). 강제 상한이 꼭 필요하다면 **너무 짧지 않게**
(예: 총 240초 정도, 76.2초 스파이크가 한 단계에서 났을 때 나머지
정상 단계들과 합쳐도 여유가 남는 값) 두는 안을 대안으로 남긴다 —
확정은 구현 시.
