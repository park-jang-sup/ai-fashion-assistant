# 작업 지시서 — 심사위원 실행 경로 확보 (F′단계, 개정)

대상 저장소: `park-jang-sup/ai-fashion-assistant`
선행: D단계(ownerUid 격리)·E단계(Google 승격) 완료·검증 끝

---

## 0. 배경 — F의 대상이 바뀌었다

원래 F단계는 "실사용자에게 배포해 데이터를 수집한다"였다. 참가자 모집이
불가능해지면서 그 목표는 폐기됐고, **APK를 실행할 유일한 사람은 심사위원**이
되었다.

그런데 D단계가 그 경로를 막았다.

```
심사위원: APK 설치 → Google 로그인 → 새 uid
        → wardrobeStream(uid): where('ownerUid' == 새 uid)
        → 0건 → 텅 빈 앱
```

격리 이전에는 전역 옷장이라 누가 로그인해도 118벌이 보였다. 지금은 안 보인다.
**시제품 가점 3점이 걸린 APK가 "아무것도 안 되는 앱"으로 보인다.**

이 작업의 목적은 하나다 — **처음 켠 사람이 30초 안에 이 앱이 무엇을 하는지
보게 만드는 것.**

# F′.1 — 데모 옷장

## F′.1.1 무엇을 넣는가 — 118벌 전부

일부를 골라 넣지 않는다. **현재 옷장 118벌을 그대로 넣는다.**

이유는 셋이다.

1. **문서의 수치와 화면이 일치해야 한다.** 사업계획서와 논문의 모든 수치가
   118벌(속성 보유 87벌) 기준이다 — 커버리지 12.6%→33.3%, 표1~15, "모집단
   87벌". 화면에 12벌짜리 데모가 뜨면 문서가 말하는 대상과 눈앞의 앱이 다른
   물건이 된다.
2. **카테고리·격식 분포가 자동으로 해결된다.** 일부만 고르면 상의가 하나도
   안 들어가거나 특정 TPO 태그가 조합 불가로 빠지는 사고가 난다.
3. **포멀 신발 부재는 큐레이션으로 못 고친다.** 옷장에 아예 없다(표5, 필터
   순도 0.00). 몇 벌을 고르든 결혼식·면접·경조사에서 부재 안내가 뜬다. 그건
   큐레이션 실패가 아니라 옷장의 성질이고, 논문 5.8.4의 부재 인지 기능이
   실제로 작동하는 장면이다.

**제외는 검토해도 좋다.** 특정 아이템을 빼고 싶으면 다음 절의 스크립트에서
제외 목록으로 처리한다. 이건 큐레이션이 아니라 단순 제외라 판단 비용이 없다.

## F′.1.2 전달 방식 — 읽기 전용 `demo_wardrobe` 컬렉션

asset JSON은 쓰지 않는다. 512차원 임베딩이 아이템당 6~7KB라 **APK에 1MB 가까이
붙고**, 데모 세트를 갱신할 때마다 재빌드가 필요하다.

`firestore.rules`에 블록을 추가한다.

```
// 데모 옷장 — 심사·시연용 공개 읽기 전용 세트.
// 앱은 읽기만 하고, 채우는 것은 tools/seed_demo_wardrobe 스크립트로만 한다.
// write를 막아 사용자 데이터(users/{uid}, ownerUid 격리)와 컬렉션 수준에서
// 분리한다 — D단계에서 전역 옷장을 없앤 취지를 훼손하지 않으면서 데모
// 경로만 여는 구조.
match /demo_wardrobe/{itemId} {
  allow read: if request.auth != null;
  allow write: if false;
}
```

`allow write: if false`가 핵심이다. 앱 코드에서 이 컬렉션에 쓰는 경로가
있으면 안 된다.

**이미지는 복제하지 않는다.** `storage.rules`가 `wardrobe_images`·
`wardrobe_cutouts`를 `request.auth != null` read로 열어두고 있으므로, 기존
문서의 `imageUrl`·`cutoutImageUrl`을 그대로 재사용하면 인증된 새 계정에서도
로드된다.

> 이 성질에 의존한다는 점을 규칙 파일과 시드 코드 양쪽에 주석으로 남길 것.
> 나중에 Storage를 사용자별로 조이면 데모 이미지가 함께 깨진다.

## F′.1.3 채우기 — `tools/seed_demo_wardrobe/`

`tools/backfill_owner_uid/`의 규약을 그대로 따른다.

- 서비스 계정 키는 저장소 밖 경로만(`--credentials` 또는 환경변수)
- **기본 동작은 dry-run**, 실제 쓰기는 `--apply` 명시
- `--exclude <itemId>` 를 여러 번 받아 제외 처리

동작:

1. `wardrobe`에서 `ownerUid == <본인 uid>` 인 문서를 읽는다
2. 제외 목록을 걸러낸다
3. 각 문서에서 `ownerUid`를 **제거**하고 나머지 필드(`imageUrl`,
   `cutoutImageUrl`, `category`, `subCategory`, `attributes`, `size`,
   `embedding`, `createdAt`)를 `demo_wardrobe`에 복사한다
4. 마지막에 개수와 카테고리별 분포, `attributes` 보유 수, `embedding` 보유
   수를 출력한다

4번의 출력이 **사업계획서에 그대로 들어갈 수치**다. 문서와 화면이 같은
모집단이라는 근거가 된다.

## F′.1.4 앱 쪽 — 버튼과 시드

### 후크 위치

`lib/screens/wardrobe_screen.dart:813`의 `_buildEmptyState()`. `items.isEmpty`
일 때만 렌더링되므로(700~701행) 시드 후에는 버튼이 자연히 사라진다.

- 문구: **"데모 옷장 불러오기"** (샘플이 아니라 데모다 — 118벌 전량이다)
- 부연: "내 옷을 등록하기 전에 기능을 먼저 확인할 수 있어요"

### 시드 메서드

`addWardrobeItem`은 `attributes`와 `embedding`을 받지 않는다. 아이템당 두 번
쓰기는 낭비이고 중간 실패 시 반쪽 문서가 남는다. 전용 메서드를 만든다.

```dart
// 데모 옷장을 현재 사용자에게 복사한다.
// demo_wardrobe를 읽어 ownerUid만 갈아끼워 wardrobe에 쓴다.
static Future<int> seedDemoWardrobe(String uid)
```

구현 시 지킬 것:

- **문서 id는 새로 발급**한다. `demo_wardrobe`의 id를 그대로 쓰면 두 번째
  심사위원이 시드할 때 충돌한다
- 각 문서에 **`isDemo: true`** 를 기록한다
- `WriteBatch`로 묶는다. 118건은 Firestore 배치 상한(500)에 여유롭게 들어가고,
  전부 성공하거나 전부 실패하므로 반쪽 옷장이 생기지 않는다
- `createdAt`은 원본 값을 그대로 옮긴다. `serverTimestamp()`로 한 번에 쓰면
  118벌이 **전부 같은 시각**이 되어 정렬이 임의가 된다 — 동점 정렬이 순회
  순서로 갈리는 문제는 이 프로젝트가 5.8.5·5.10.2에서 이미 겪었다

### `isDemo` 플래그를 붙이는 이유

1. 심사위원이 자기 옷을 넣고 싶을 때 데모만 골라 지울 수 있다
2. F′.3 지표 집계에서 제외해 본인 데이터 수치가 오염되지 않는다
3. 데모 세트를 갱신할 때 이전 것을 찾아낼 수 있다

### 로딩 상태를 반드시 둘 것

`demo_wardrobe` 118건을 읽으면 임베딩 때문에 **약 1MB가 내려온다.** 모바일
회선에서 수 초가 걸린다. 진행 표시 없이 두면 심사위원이 "버튼이 안 먹는다"고
판단한다.

- 버튼을 누르면 즉시 로딩 상태로 잠근다(연타 방지 겸용)
- 진행 문구를 띄운다
- 실패하면 조용히 넘기지 말고 재시도 가능한 안내를 낸다 — 이 경로는 폴백이
  "아무것도 하지 않음"이면 안 된다. 심사위원이 빈 화면에 갇힌다

## F′.1.5 데모 옷장 비우기 (권장)

설정 화면에 **"데모 옷장 비우기"**를 둔다. `isDemo == true`인 문서만 골라
삭제한다(`WriteBatch`로 묶을 것).

없으면 **한 번 불러온 뒤 되돌릴 방법이 없다.** 필요한 상황이 셋이다.

1. 심사위원이 빈 상태(F′.2.2에서 확인하는 그 화면)를 다시 보고 싶을 때
2. 자기 옷을 등록해 데모와 **비교**하고 싶을 때 — F′.2.4의 컷아웃 품질 차이가
   여기서 드러난다
3. 시연 촬영에서 "처음 켠 상태"를 다시 만들어야 할 때

삭제 대상을 `isDemo == true`로 한정하는 것이 중요하다. 옷장 전체를 지우는
버튼이 되면 사용자가 직접 등록한 옷까지 날아간다. **확인 다이얼로그를 둘 것.**

# F′.2 — 신규 계정 완주 검증

**이 단계가 F′의 진짜 목적이다.** 지금까지 모든 검증은 옷장 118벌·이력 다수인
본인 계정에서만 이뤄졌다. 심사위원의 조건은 전혀 다르다.

## F′.2.1 반드시 새 구글 계정으로 할 것

본인 계정으로 확인하면 아무 의미가 없다. 새 구글 계정(또는 에뮬레이터 + 다른
계정)으로 **릴리스 APK를 처음 설치한 상태**에서 시작한다.

## F′.2.2 0벌 상태를 먼저 본다 — 버튼을 누르기 전에

**데모를 넣기 전 상태가 더 위험하다.** 논문 5.8.1에 "현 데이터 118벌에서 도달
불가"로 기록한 shortfall 분기가 **여기서 처음 실행될 수 있다.** 한 번도 돌아본
적 없는 코드가 심사위원 화면에서 처음 도는 상황이다.

확인 항목:

- 홈 화면이 깨지지 않고 `_EmptyCard`가 정상 표시되는가(`home_screen.dart:191`)
- 옷장 탭의 빈 상태와 데모 버튼이 보이는가
- AI 피팅 탭이 옷 0벌에서 크래시하지 않는가
- 캘린더에 일정을 넣고 백그라운드를 수동 실행했을 때 **조용히 아무 일도
  안 일어나는가**(폴백 원칙) — 크래시나 빈 추천 카드가 뜨면 안 된다
- 활동 로그에 무엇이 남는가

## F′.2.3 시드 후 완주

1. 데모 버튼 → 118벌이 뜬다(로딩 표시 정상)
2. 옷장 탭에서 아이템 상세 진입 → 속성·치수·"비슷한 옷" 섹션이 렌더링된다
3. 캘린더에 **내일 일정**을 하나 등록한다
4. 설정 → 백그라운드 즉시 실행 → **홈에 추천 카드가 뜬다**
5. 추천 이유 문구가 정상이고, 필요 시 `optionalNote`/`fallbackNote` 배지가 뜬다
6. AI 피팅을 1회 실행해 결과가 나오고, **코디보드에 컷아웃이 정상 배치된다**
7. 설정 → 지연 실행(30초) → 앱 종료 → **잠금화면 알림**

4번이 핵심이다. **추천 카드가 뜨면 격리·시드·추천 파이프라인이 신규 계정에서
끝까지 이어졌다는 뜻이다.**

## F′.2.4 알려진 위험 — 심사위원이 자기 옷을 직접 찍어 올리는 경우

현재 옷장 118벌은 플랫폼 제품 사진이라 배경이 깔끔해 **컷아웃이 잘 되고
코디보드에 예쁘게 들어간다.** 반면 직접 찍은 사진은 사람 몸이 함께 찍히거나
옷걸이에 걸린 상태여서 **배경 제거가 잘 되지 않는다.**

심사위원이 호기심에 자기 옷을 촬영해 등록하면 그 결과를 보게 된다. 이번
범위에서 고칠 수 있는 문제가 아니므로 **확인만 하고 기록해 둘 것** — 실제로
얼마나 나쁘게 나오는지, 등록 자체는 정상 완료되는지. 사업계획서의 한계
항목이자 향후 과제가 된다.

## ✅ F′.2 관문

| | 항목 |
|---|---|
| 1 | 새 계정 0벌 상태에서 5개 탭 전부 크래시 없음 |
| 2 | 데모 시드 후 118벌 정상 표시, `isDemo: true` 기록 확인 |
| 3 | 신규 계정에서 **추천 카드 생성** |
| 4 | 신규 계정에서 **잠금화면 알림** |
| 5 | 본인 계정 옷장 118벌이 **그대로**(데모 시드가 본인 데이터에 영향 없음) |
| 6 | 시드 중 로딩 표시가 뜨고, 연타해도 중복 생성되지 않음 |
| 7 | **데모 비우기** → 빈 상태로 돌아가고, 직접 등록한 옷은 남아 있다 |

5번을 빠뜨리지 말 것. 시드 로직이 uid를 잘못 잡으면 본인 옷장에 데모가 섞인다.

# F′.3 — 지표 집계

사용자가 한 명이어도 **사업계획서에 넣을 수치는 산출 가능하다.**
`tools/user_study_report/`에 스크립트를 두고, `isDemo: true`는 **전부 제외**한다.

| 지표 | 산출 |
|---|---|
| 옷장 규모·구성 | 총 벌 수, 카테고리별 분포, 격식 분포 |
| 속성 추출 성공률 | `attributes != null` 비율 |
| 임베딩 보유율 | `embedding != null` 비율 |
| 옷장 커버리지 | 표9와 같은 방식으로 실데이터 산출 |
| 추천 채택률 | `userChoice == accepted` / 응답 있는 추천 |
| 백그라운드 발화 간격 | `agent_meta`의 시계열 |

**마지막 항목은 `lastInvokedAt` 패치가 선행되어야 한다.** 가드에 걸려 조기
반환한 실행은 `agent_meta`에 아무것도 남기지 않으므로, 지금 상태로는 발화
이력을 모을 수 없다. 30분이면 되고, 켜두면 8/28까지 4주치가 **손대지 않아도**
쌓인다. **F′.1보다 먼저 넣을 것.**

## 금지 사항

- 데모 세트를 **일부만 골라 넣지 말 것.** 118벌 전량이 기본이고, 빼는 것만
  `--exclude`로 처리한다
- 데모 데이터를 **asset JSON으로 넣지 말 것.** APK가 1MB 무거워지고 갱신에
  재빌드가 필요하다
- 앱 코드에서 `demo_wardrobe`에 **쓰지 말 것.** 규칙이 막고 있고, 채우는 것은
  스크립트 전용이다
