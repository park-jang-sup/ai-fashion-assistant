## 0. 목표와 범위

지금 앱의 에이전트는 **정해진 순서**(일정 감지 → 예보 → 조합 → 자기평가 → 저장)로 움직인다. 이 트랙은 사용자가 **말로 부탁하면 모델이 스스로 어떤 도구를 어떤 순서로 쓸지 정하고**, 그 과정이 화면에 보이게 한다. 심사위원이 한 번 눌러 보고 "에이전트"임을 알 수 있어야 한다.

- 홈에 "AI에게 부탁하기" 입력과 예시 버튼 3개
- 전용 화면에서 단계가 한 줄씩 실시간으로 보인다(생각 한 문장 → 쓴 도구 → 결과 요약)
- 도구는 읽기 5개, 쓰기 1개(일정 등록). 쓰기는 사용자 확인을 받은 뒤에만 실행
- 등록한 일정은 기존 선제 추천이 이어받는다(예보가 바뀌면 다시 준비)

**서버는 바꾸지 않는다.** 도구 실행은 전부 앱 안에서 한다(§2-1).

범위 밖: 가상 피팅을 도구로 부르는 것, 옷 삭제·수정 도구, 여러 요청에 걸친 대화 기억, 음성 입력, 주간 플랜 변경.

## 2. 설계

### 2-1. 도구 호출 방식

서버가 도구 호출 필드를 막고 있고(§1-1) 그 방어를 풀지 않는다. 그래서 **모델이 매 단계 JSON 한 개로 "다음에 쓸 도구"를 말하고, 앱이 그 도구를 직접 실행해 결과를 다음 요청의 글에 붙이는 방식**으로 만든다. 기존 텍스트 프록시를 그대로 쓴다.

- 요청 하나 = contents 1개, text part 1개(지침 + 도구 설명 + 오늘 날짜 + 사용자 요청 + 지금까지의 단계 기록)
- `generationConfig`: `responseMimeType: application/json`, `temperature: 0.2`, `maxOutputTokens: 800`, `thinkingConfig.thinkingBudget: 0`
- 모델 출력 규약(한 단계에 정확히 하나):

```json
{"thought": "사용자에게 보일 한 문장", "action": "도구 이름", "args": { }}
```

- 단계마다 `withTextModelFallback`으로 호출한다(§1-3). 응답에 코드 펜스가 붙어 와도 읽을 수 있게 기존 JSON 파서를 쓴다.
- 앱은 출력을 검증한다: JSON인지, `action`이 아래 7개 중 하나인지, `args`가 형식에 맞는지(날짜는 `YYYY-MM-DD`, 상황 태그는 9개 중 하나, 카테고리는 5개 중 하나). 어긋나면 그 사실을 관찰로 돌려주고 한 번 더 기회를 준다. 두 번 연속 어긋나면 끝낸다.
- 모델 호출은 **요청 하나에 최대 6회**. 6회에 `finish`가 안 나오면 앱이 "여기까지 확인했어요"와 마지막 결과를 보여 주고 끝낸다.
- 단계당 시한 20초, 요청 전체 90초. 호출량 초과가 나면 재시도하지 않고 안내하고 끝낸다.
- 관찰(도구 결과)은 한 건에 1,500자 이하로 줄여 붙인다. 전체 글이 30,000자를 넘지 않게 한다.

### 2-2. 도구

모두 로그인한 사용자 본인의 데이터만 다룬다. 모델 출력은 아래 함수의 인자로만 쓰이고, 다른 경로로 실행되지 않는다. 도구가 실패하면(예보 조회 실패, 옷장이 비어 있음 등) 앱이 멈추지 않고 실패 사실을 관찰로 돌려준다.

| 도구 | 인자 | 하는 일 | 돌려주는 것 |
|---|---|---|---|
| `get_calendar` | `from`, `to` (최대 14일) | 일정 조회 | 날짜별 일정(상황, 예정/기록)과 그 날짜에 준비된 추천의 요약 |
| `get_weather` | `from`, `to` | 예보 조회 | 날짜별 최고·최저·강수확률, 기온대(더움/온화/선선/추움), 비 여부. 7일 밖은 "예보 범위 밖". 가정 예보면 그 표시 |
| `search_wardrobe` | `category?`, `keyword?` | 옷장 조회 | 인자가 없으면 종류별 벌수. 있으면 일치 벌수와 최대 8벌(종류·색·앞쪽 태그 3개·격식) |
| `preview_outfit` | `date`, `tpo` | `matchForWeather` 1순위 조합 미리 보기. **모델 호출 없음, 저장 없음** | 조합(종류별 색·종류), 날씨 문구, 격식 차선 여부 |
| `add_plan` | `date`, `tpo` | **쓰기.** 예정 일정을 등록하고 그 일정의 코디를 준비한다(§2-3) | 등록 여부, 저장된 추천의 조합·점수·문구, 또는 준비하지 못한 이유 |
| `ask_user` | `question` | 사용자에게 되묻는다. 요청 하나에 1회까지 | 사용자의 답 |
| `finish` | `answer` | 끝낸다 | — |

### 2-3. `add_plan` (유일한 쓰기)

- 모델이 `add_plan`을 내면 앱은 실행하지 않고 **확인 카드**를 띄운다: "11/20(금) [모임] 일정을 등록하고 코디를 준비할까요?" + [등록] [취소].
  - [취소]면 "사용자가 취소함"을 관찰로 돌려준다. 같은 요청 안에서 `add_plan`은 다시 실행하지 않는다.
- 같은 날짜에 예정 일정이 이미 있으면 새로 넣지 않고 그 사실을 관찰로 돌려준다.
- 날짜는 오늘부터 60일 안만 받는다. 과거 날짜는 거절한다.
- 등록 뒤 코디 준비는 **기존 준비 경로(§1-5)를 그대로 쓴다.** 자기평가, 추천 저장, 활동 내역, 홈 카드가 평소와 같게 동작해야 한다. `_proactiveInFlight`와 겹치지 않게 한다.
  - 날짜가 예보 범위(오늘 포함 7일) 안이면 바로 준비한다. 기존 준비 경로를 3일 밖 날짜에 안전하게 쓸 수 없으면, 3일 안만 바로 준비하도록 줄이고 그 사실을 보고한다.
  - 예보 범위 밖이면 등록만 하고 "코디는 일정이 가까워지면 예보를 보고 준비해요"를 관찰로 돌려준다.
- 일정의 `source` 값은 기존 필드의 뜻에 맞는 것을 쓴다. 맞는 값이 없으면 새 필드를 `firestore.rules` 변경 없이 추가하고 보고한다.

### 2-4. 프롬프트

Dart 빌더 함수 하나로 만든다(순수 함수 + 골든 파일). 담을 것:

- 역할: 사용자의 옷장·일정·예보를 도구로 확인해 코디를 돕는 비서
- 오늘 날짜와 요일(기기 현지 시각), 상황 태그 9개와 각 격식
- 도구 7개의 이름·인자·돌려주는 것
- 규칙
  - 출력은 규약의 JSON 하나뿐. 한국어. `thought`는 한 문장
  - 옷은 **도구 결과에 나온 것만** 말한다. 없는 옷을 지어내지 않는다
  - `add_plan`은 사용자가 준비·등록을 부탁했을 때만 쓴다. 묻기만 한 요청에는 쓰지 않는다
  - 날짜("금요일", "내일", "다음 주 수요일")는 `YYYY-MM-DD`로 풀어 쓴다. 날짜나 상황을 알 수 없으면 `ask_user`를 한 번 쓴다
  - 옷·일정·날씨와 무관한 요청은 도구를 쓰지 않고 `finish`로 할 수 있는 일을 안내한다
  - 확인할 것이 끝나면 바로 `finish`한다
- 지금까지의 단계 기록(생각·도구·인자·결과)을 순서대로

분석 프롬프트 3종과 그 골든 6개, 자기평가 프롬프트는 바꾸지 않는다.

### 2-5. 화면

**홈**: 날씨 줄과 추천 코디 카드 사이에 "AI에게 부탁하기" 카드를 둔다. 한 줄 입력과 예시 버튼 3개. 카드는 낮게 만든다(입력 한 줄 + 가로로 넘기는 버튼 줄) — 추천 코디 카드가 첫 화면에서 밀려나지 않아야 한다.

| 예시 버튼 | 보여 주려는 것 |
|---|---|
| 금요일 저녁 모임에 입을 옷 준비해줘 | 일정·예보 확인 → 미리 보기 → 확인 후 등록 |
| 내일 비 오면 뭐 입지? | 예보 → 미리 보기 → 답만 한다(등록 없음) |
| 겨울 아우터 뭐 있는지 보고 가장 추운 날 입을 것 골라줘 | 옷장 조회 → 주간 예보 → 미리 보기 |

**전용 화면**(입력하거나 예시를 누르면 열리고 바로 시작):

- 맨 위에 사용자의 요청
- 단계 목록: 단계마다 아이콘과 도구의 한국어 이름("일정 확인", "예보 확인", "옷장 조회", "코디 미리 보기", "일정 등록", "질문"), 생각 한 문장, 결과 한 줄. 진행 중인 단계에는 진행 표시
- `add_plan` 확인 카드, `ask_user` 질문과 답 입력
- 마지막 답 카드: 글 + 조합이 있으면 옷 사진(기존 이미지 위젯). [캘린더에서 보기]. 추천 카드에서 피팅룸으로 보내는 기존 경로를 그대로 쓸 수 있으면 [피팅룸에서 입어 보기]도 넣고, 새 배선이 필요하면 뺀다
- [새로 부탁하기]
- 뒤로 나가면 진행 중인 요청을 멈춘다. 확인을 받지 않은 쓰기는 실행되지 않는다
- 글자 크기를 키운 기기에서도 버튼이 가려지지 않아야 한다

**활동 내역**: 요청 시작("AI에게 부탁: …"), 도구마다 한 줄, 끝난 답의 첫 문장을 남긴다. 한 요청은 같은 `relatedDocId`로 묶는다.

**가이드**: 4쪽에 "홈의 'AI에게 부탁하기'에 말로 부탁할 수도 있어요" 한 문장을 넣는다.

**마스코트**(2026-11-14 추가):
- 사용자가 저장소에 넣어 둔 `agent_mascot.png`(512px 정사각형)를 앱 자산으로 등록한다. 기존 자산 폴더 관례가 있으면 그것을 따르고, 없으면 `assets/images/`로 옮긴다. 파일이 보이지 않으면 위치를 묻는다.
- 쓰는 곳은 세 군데: 홈 "AI에게 부탁하기" 카드 왼쪽, 전용 화면 맨 위, 단계의 생각 문장 옆(작게). 모두 원형으로 잘라 쓴다.
- 앱의 색, 글꼴, 앱 아이콘, 앱 이름, 다른 화면은 바꾸지 않는다.
- 이미지를 불러오지 못해도 화면이 깨지지 않게 기본 아이콘으로 대체한다.

## 10. 진입 방식과 기록(2026-11-14)

실기기 확인에서 나온 요청 두 가지: (1) 지난 대화를 다시 볼 수 없다. (2) 홈 카드 대신, 가상 피팅 때 뜨는 둥근 진행 표시처럼 어디서나 보이는 버튼으로 바꾼다.

**A. 떠 있는 마스코트 버튼**
- 홈의 "AI에게 부탁하기" 카드를 없애고 홈을 이전 구성으로 되돌린다.
- 주요 탭 화면 위에 원형 마스코트 버튼을 띄운다. 누르면 전용 화면이 열린다. 로그인 화면, 첫 실행 가이드, 전용 화면 안에서는 띄우지 않는다.
- 탭마다 주요 버튼(피팅룸의 분석 버튼 등)과 기존 가상 피팅 진행 표시를 가리지 않는 자리에 둔다. 가리는 탭이 있으면 그 탭에서만 위치를 옮긴다. 탭별 위치를 보고한다.
- 처음에는 버튼 옆에 "AI에게 부탁하기" 말풍선을 잠깐 보여 준다. 한 번 누른 뒤에는 보여 주지 않는다.
- 예시 버튼 3개는 전용 화면의 첫 상태(인사말 + 예시 + 입력)로 옮긴다.

**B. 화면을 닫아도 이어지는 진행**
- 부탁의 진행 상태를 화면이 아니라 앱 수준의 컨트롤러가 갖는다(가상 피팅 작업 컨트롤러와 같은 방식).
- 화면을 닫아도 진행은 계속된다. 진행 중에는 버튼에 진행 고리를, 사용자 차례(확인·질문)이거나 답이 나왔으면 점을 보여 준다. 버튼을 누르면 그 대화가 그대로 다시 열린다.
- 화면에 [멈추기]를 둔다. "뒤로 나가면 멈춘다"는 동작은 없앤다.
- add_plan은 지금처럼 확인 카드에서 [등록]을 눌러야만 실행된다. 화면이 닫혀 있는 동안에는 실행되지 않고 기다린다.
- 한 번에 부탁 하나만 진행한다. 진행 중에 새 부탁을 하려 하면 멈출지 묻는다.
- 단계당 20초, 요청 전체 90초 시한과 모델 호출 6회 상한은 그대로다(사용자 차례에서 기다리는 시간은 세지 않는다).

**C. 지난 부탁 기록**
- 부탁이 끝나면(답, 멈춤, 실패 모두) 요청 문장, 단계별 요약, 답 전문, 조합이 있으면 그 옷, 시각을 저장한다.
- 전용 화면에 "지난 부탁"을 두고 최근 20건을 보여 준다. 누르면 그 대화를 읽기 전용으로 다시 보여 준다.
- 저장 위치는 firestore.rules를 바꾸지 않고 쓸 수 있는 곳으로 정한다. 새 색인이 필요한 조회는 쓰지 않는다. 어디에 어떻게 저장했는지 보고한다. 활동 내역 화면의 기존 표시는 달라지지 않아야 한다.

**D. 함께 고칠 것**

- 가이드 4쪽 문장을 새 진입 방식에 맞게 고친다.
