# 작업 지시서 — 서버 접근 통제 강화 트랙 (task_hardening_v2)

## 0. 이 문서 자체의 위치 — 착수 시점이 아니라 S1 완료 후에 쓰였다

이 트랙의 S1(인스턴스 상한)은 이 지시서 없이 대화로만 진행되어 이미 코드에
반영되었다(`functions/src/index.ts`, 9개 함수 `maxInstances` 설정 완료).
즉 이 문서는 착수 시점의 사전 지시서가 아니라 **S1 완료 후에 그 결과를
기록하고 S2 이후를 사전 등록하기 위해 작성되었다.**

이 저장소의 작업 원칙 2번("판정 기준을 결과 보기 전에 정한다", 논문
6.5.1절)은 S1 구간에 한해 **지켜지지 않았다.** 이 사실을 숨기지 않고
여기 적는다 — S1의 값(9개 함수 각각의 `maxInstances`)은 결과를 관측하기
전에 서면으로 고정된 적이 없고, 대화 중 그 자리에서 정해졌다. S2부터는
착수 전에 판정 기준이 이 문서에 고정되므로, **트랙 안에서도 구간별로
근거의 강도가 다르다.** 이후 이 트랙을 인용할 때 S1과 S2 이후를 같은
증거 수준으로 취급하지 말 것.

## 1. 트랙의 범위와 순서 근거

### 대상 3건

1. **인스턴스 상한 부재** (S1) — `functions/`(TypeScript) 9개 함수 중
   어느 것에도 `maxInstances`가 없었다.
2. **App Check 미강제** (S2) — 클라이언트는 `activate()`하지만
   (`main.dart:57`) 서버 어느 함수도 그 검증을 강제하지 않는다
   (`functions/src/` 전체에 `enforceAppCheck` 0건, grep으로 확인).
3. **프록시 요청 본문 무검증** (S3) — `callGeminiText`가 `requestBody`를
   가공 없이 그대로 중계한다(설계 의도, `gemini_service.dart` A-1 주석
   참고). 형태 검증이 없다.

**[정정 2026-08-10] 위 세 항목의 서술 "서버 함수"는 실제로는 `functions/`
(TypeScript, 9개)만을 가리켰다.** §2의 4)(콘솔 대조) 과정에서, 배포된
함수 목록에 `bg_removal_on_upload`(별도 코드베이스
`functions_bg_removal/`, Python)가 포함되어 있고 콘솔에 최대 인스턴스
**`0/20`**으로 표시됨을 확인했다. `functions_bg_removal/main.py:119-127`
의 `@storage_fn.on_object_finalized` 데코레이터를 대조한 결과
`region`/`memory`/`timeout_sec`/`min_instances`만 있고 **`max_instances`
인자가 없다** — 즉 콘솔에 보이는 `20`이라는 값의 출처가 이 코드가
아니다. 런타임 기본값인지 과거 콘솔에서 수동으로 설정된 값인지는
**미확인으로 남긴다.**

이 정정의 의미: 이 트랙은 범위를 **"functions/ 디렉터리"**로 잡았지만,
실제 공격면(및 이번 항목이 다루는 자원 소비 문제의 대상)은 **"배포된
함수 전체"**였다. 범위 정의가 위협 모델을 따라간 것이 아니라 저장소
구조(코드베이스가 둘로 나뉘어 있다는 사실)를 따라간 것이었고,
`functions_bg_removal`이 별도 코드베이스로 분리돼 있다는 사실 자체가
그 사각을 만들었다 — 논문 5.15절("[이관 층위] 옮기는 과정에서 드러난
것")이 기록한 계열과 같다: 옮기는 과정에서(여기서는 배경 제거 기능을
Python 서버로 분리 이전한 과정에서) 검토 단위가 갈라진다. **이번
트랙에서는 `bg_removal_on_upload`의 `max_instances`를 고치지 않는다**
— 값의 출처가 미확인인 채로 손대면 무엇을 바꿨는지 스스로 모르게
된다. 이 항목 자체는 이번 트랙의 대상 3건에 속하지 않으므로(S1은
`functions/`로 범위가 이미 확정된 채 완료됨), 출처 규명은 등록만 하고
이번 트랙에서는 별도로 착수하지 않는다.

**[정정 2026-08-10, 범위 정정 3차] S2는 착수부터 "서버 함수"를
범위로 잡았으나, App Check의 실제 적용 단위는 함수가 아니라
서비스다.** §3-1-1의 API 탭 확인 결과, Firestore와 Storage 역시
App Check가 미적용 상태임이 드러났다 — 이 트랙은 처음부터 이
둘을 범위에 넣은 적이 없었다.

의미: 논문 3.12절이 설계한 `firestore.rules`/`storage.rules`는
"요청자가 누구인가"(auth)는 검증하지만 "요청이 정말 우리 앱에서
왔는가"(app)는 검증하지 않는다. 익명 인증만 통과하면 규칙 평가가
시작되고, 앱 밖에서 SDK로 직접 접근하는 경로가 열려 있다. 이는
3.12.5절이 "실제 사용자 권한 토큰의 직접 호출"로 검증한 내용과
**모순되지 않는다** — 그 검증은 권한 축(auth)이었고 이것은 출처
축(app)이다. 두 축이 독립이라는 점이 지금까지 이 문서 어디에도
명시되지 않았다.

**범위 정정 이력(발견 순서 보존):**

- **1차** — `functions/` 디렉터리 기준으로 잡아
  `bg_removal_on_upload`를 누락(§1, 위 문단).
- **3차** — "서버 함수" 기준으로 잡아 Firestore/Storage를 누락
  (이번).

(2차에 해당하는 항목은 없다. 번호는 발견 **순서**를 보존하기 위한
것이며 무언가 비어 있는 것이 아니라 애초에 둘뿐이다 — 다음 사람이
"2차는 어디 갔나"를 찾지 않도록 이 사실을 여기 명시한다.)

두 번 모두 범위가 **위협 모델이 아니라 우리가 코드를 조직한 단위를
따라갔다.** 1차는 코드베이스 분리(TypeScript/Python)가 원인이었고,
3차는 "서버 = 함수"라는 암묵적 등식이 원인이다 — Firestore/Storage는
"함수"가 아니므로 범위를 "서버 함수"로 정의한 순간부터 시야 밖에
있었다.

### 순서 기준 — "되돌리기 비용"

분량이나 위험도가 아니라 **잘못 켰을 때 되돌리는 비용**으로 순서를
정한다.

- **S1** — 되돌릴 일이 사실상 없다. 값을 지우고 재배포하면 그만이고,
  실패 방향이 "느려짐"이지 "막힘"이 아니다(9개 함수 옵션 추가 시 이미
  기록한 판단).
- **S2** — **잘못 켜면 앱이 전면 정지한다.** App Check를 강제(enforce)로
  전환했는데 클라이언트 쪽 공급자 설정이나 디버그 토큰 등록이 어긋나면,
  모든 서버 함수 호출이 일제히 거부된다 — 텍스트 분석도, 가상 피팅도,
  옷장 화면 진입(서명 URL)도 전부 막힌다. 6개 onCall 함수가 전부 같은
  강제 스위치 아래 있으므로 실패가 국소화되지 않는다.
- **S3** — 잘못 켜면 **일부 기능만 무성(無聲) 정지한다.** 스키마 검증이
  과도하게 엄격하면 특정 요청 형태(예: 특정 옵션 조합)만 조용히 거부되고
  나머지 경로는 정상이므로, 장애 범위가 S2보다 좁고 원인 추적도 상대적으로
  쉽다.

즉 순서는 위험이 큰 것을 먼저 처리하는 것이 아니라, **가장 되돌리기 쉬운
것부터 실행해 트랙 자체의 절차(계측 → 사전 등록 → 실행 → 검증)를
저위험 구간에서 먼저 검증한 뒤, 되돌리기 비용이 큰 구간(S2)으로 넘어가는
순서다.**

### 논문과의 관계

세 항목 모두 현재 `DOT_paper_rev8.md` 7.1절에 **독립 항목으로 등록되어
있지 않다.** App Check 미강제는 개정 5판에서 "요청 검증 강제와 동시 실행
상한이 다음 방어선이다"(5.13.5절 인용, 7.1절 원문)로 방향만 언급되었을
뿐 판정 가능한 항목으로 존재한 적이 없다. 7.1절 갱신은 이 트랙 종료 시
**S5**에서 일괄 처리한다 — 트랙 중간에 절반만 반영하면 무엇이 "완료"고
무엇이 "진행 중"인지 논문 스냅샷과 저장소 상태가 어긋난다.

근거(코드 주석으로도 남김, `functions/src/index.ts`의 `callGeminiText`
바로 위):

- 현재 사용자 규모는 n=1이고, 동시 호출이 나오는 유일한 경로(옷 N벌
  순차 합성 = 호출 N회)도 클라이언트가 직렬로 돈다 — 정상 사용에서
  동시 인스턴스가 2를 넘을 일이 없다.
- 따라서 이 값들은 **"정상 사용의 상한"이 아니라 "비정상 사용(버그·
  남용)의 천장"**이다. 실사용자가 붙으면 반드시 재산정해야 한다.
  **[정정 2026-08-10] 실사용자 유입 전에 아래 [규명됨] 결함(재시도
  증폭)을 먼저 닫아야 한다** — 상한에 닿는 시점이 곧 이 결함이 처음
  발동하는 시점이고, 그때는 이미 호출량이 상한 근처라 증폭이 가장
  아픈 구간이다.
- `generateFittingImage`만 5로 낮은 이유: `timeoutSeconds`가 320이라
  인스턴스 하나가 점유하는 시간이 길고, 상류(Gemini) 호출 비용까지
  곱해진다 — 같은 남용 시도라도 이 함수에서 열어두는 동시 창이 더 비싸다.

### 배포 후 확인 항목

- 배포 로그에 함수 삭제(`delete`) 라인이 없을 것 — 옵션 추가만으로
  함수 자체가 재생성되며 삭제를 거치지는 않아야 정상이다.
- Firebase 콘솔 함수 목록에서 배포 전후 함수 개수가 그대로일 것(9개
  함수 전부 갱신이지 증감이 아니다).
- **옷 2벌 이상으로 가상 피팅 1회 완주.** 옷 1벌로는 이 배포를
  검증하지 못한다 — `generateFittingImage`가 9개 함수 중 가장 낮은
  값(5)이고, 순차 합성 루프가 이 함수를 반복 호출하는 유일한 경로이기
  때문이다(옷 1벌이면 이 함수가 1회만 불려 값 자체가 관측 대상이 되지

### 규명된 결함과 남은 미확인 — 다음 세션으로 이월

**[정정 2026-08-10]** 아래 항목은 원래 "미확인"으로 통째로 등록했으나,
직전 대조에서 재시도 증폭 **경로가 존재함 자체는 코드로 규명되었다.**
"확인해봐야 안다"와 "이 조건만 성립하면 발동한다"는 다음 사람이 이
문서를 읽을 때 완전히 다른 작업으로 이어지므로 구분해 둔다.

**[규명됨] 상한에 걸린 요청이 폴백 재시도로 호출을 두 번 쓰는 경로가
코드에 존재한다.**

`_mapProxyException`(`gemini_service.dart:232-253`)은 서버가
`deadline-exceeded` 코드로 실패를 돌려주면 이를 `TimeoutException`으로
재구성한다. `withTextModelFallback`(같은 파일 76-91행)은
`TimeoutException`을 잡으면 무조건 대체 모델로 **한 번 더** 호출한다.
즉 서버가 `deadline-exceeded`로 응답하는 조건이 성립하기만 하면, **상한에
걸린 요청이 호출을 두 번 쓴다** — 인스턴스 상한을 둔 목적(값싼 거부의
무제한 반복을 막는 것)과 정반대 방향이다.

이는 논문 5.21.6절이 이미 등록한 "재시도가 실제 API 비용을 두 번 쓴다"와
같은 계열이지만, 원인이 다르다 — 그쪽은 **업스트림(Gemini) 오류**가
원인이고, 이쪽은 **우리가 스스로 건 상한 자체**가 원인이다. 방어
장치가 자기 자신을 증폭시키는 형태다.

**[미확인] `maxInstances` 초과 시 GCF(Cloud Run 기반 Functions v2)가
실제로 반환하는 오류 코드.**

- `deadline-exceeded` 계열이면 위 [규명됨] 경로가 그대로 발동한다.
- `resource-exhausted` 계열이면 `_mapProxyException`이 이를
  `RateLimitExceededException`으로 재구성하므로(같은 파일 235-237행)
  `GeminiApiException.isRetryable` 판정 자체를 타지 않는다 — 이 경우
  증폭은 일어나지 않는다. 다만 이 분류가 실제로 맞는지는 별도 확인이
  필요하다.

n=1 규모에서는 `maxInstances`에 실제로 부딪힐 일이 없으므로 이 오류
코드를 실측할 기회가 없었다 — 그래서 이 부분만 미확인으로 남는다.
**실사용자가 유입되어 처음으로 상한에 부딪히는 순간이 이 경로를 처음
실측할 수 있는 시점이다.** S2 이후에도 여전히 미확인이면, 착수
조건(n>1)이 충족되는 시점에 별도 계측으로 닫아야 한다.

이번 정정에서는 코드를 고치지 않는다 — S2 트랙 진행 중이고, 이
결함의 수정은 별도 축이다. 여기서는 등록만 한다.

### H-A 정정 — "토큰 미등록"이 아니라 "앱 자체가 미등록"

**기존 가설**: "디버그 공급자가 만든 토큰이 콘솔에 등록되지 않아
교환 실패." 방향은 맞았으나 **한 층 얕았다.** 문제는 토큰이
등록되지 않은 것이 아니라 **앱 자체가 App Check에 등록되지
않았다.** 앱이 등록되지 않은 상태에서는 디버그 공급자가 토큰을
교환할 대상 자체가 존재하지 않는다 — 토큰 등록 여부를 따지는 것은
그 다음 단계의 질문이었다.

**이로써 §3-1의 VALID 0 / INVALID 110 / MISSING 37이 전부
설명된다.** 앱이 등록되지 않았으므로 `activate()`가 만드는 어떤
토큰도 서버가 유효한 것으로 검증할 방법이 없다 — 포그라운드
(`INVALID`, activate는 호출되지만 산출물이 무효)든 백그라운드
(`MISSING`, activate 자체가 없음)든 결과는 실패로 수렴하고, 실패의
구체적 형태(디코딩 불가/부재)만 경로에 따라 갈린다.

**논문 5.13.5절과의 연결 — 이 트랙의 핵심 발견.** 개정 5판 5.13.5절
("검증기가 켜져 있지 않았다")은 "공급자 설정 이전에 요청 검증
서비스(App Check) 자체가 이 프로젝트에서 한 번도 활성화된 적이
없었음"을 기록했다. 개정 5·6·7·8판을 거치는 동안 **이 상태가 한
번도 바뀌지 않았다.** 그 사이 클라이언트는 계속 `activate()`를
호출했고, 서버는 계속 무효 토큰을 받아 통과시켰으며, 강제하는
지점이 없어 어떤 증상도 나타나지 않았다.

이는 5.13 계열(선언과 실제의 불일치)의 새 사례이되 성격이 다르다 —
기존 사례들(5.13.1~5.13.4)은 "선언된 방어가 실제로는 다른 것에
의해 이루어지고 있었다"는 형태였다면, 이번은 **선언된 방어가
아무것도 하고 있지 않았고, 그것을 알 수단이 구조적으로 없었다.**
검증 계층은 강제되지 않으면 자신의 고장도 보고하지 않는다.

**아울러 이 항목이 논문 7.1절 미해결 목록에 없었다는 사실도
기록한다.** 5.13.5절이 본문 서술에 그치고 7.1절의 한계 목록으로
승격되지 않아, 개정 6·7·8판 세 판에 걸친 한계 갱신에서 매번 시야
밖이었다 — 이번 S2 트랙이 처음으로 이 항목을 목록화하는 계기가
된다(S5에서 7.1절 갱신 시 반영).

  제약: Play 배포(또는 최소한 Play의 내부 테스트 트랙)를 전제로 한다.
  APK 사이드로드 중심의 현재 배포 방식(`docs/HANDOFF.md`: "App
  Distribution 배포 — 심사위원에게 파일로 전달한다")에서 Play
  Integrity가 실제로 성립하는지 **미확인.**
- **경로 2 — 디버그 공급자를 유지하고 디버그 토큰을 콘솔에 수동
  등록.** 제약: 토큰이 설치본마다 다르므로 재설치할 때마다 수동
  등록이 필요하다. 이 저장소는 릴리스 빌드를 반복 설치하는 개발
  패턴이고(논문 5.11.4절, 익명 식별자가 하루에 넷으로 갈린 이력이
  같은 패턴에서 나왔다), 그 패턴과 정면으로 충돌한다.

선택 기준은 **"어떤 방식으로 배포하는가"**이며, 이것은 논문 7.2절
로드맵 16번(실사용자 수용 조건)과 같은 축이다 — 심사위원 배포가
APK 파일 전달로 확정되어 있는 한 경로 1의 전제(Play 배포)가 성립하지
않을 수 있고, 반대로 향후 Play 배포로 전환한다면 경로 2의 제약
(재설치마다 수동 등록)이 오히려 감당 불가능해진다. 이 연결을
여기 적어 두는 이유는, 이 결정이 App Check 하나의 문제가 아니라
배포 방식 자체에 대한 결정과 얽혀 있음을 다음에 이 절을 읽는
사람이 놓치지 않게 하기 위해서다.

### 3-1-2. 층 구조 정정 — "강제 지점 두 층" 전제가 서비스마다 다르다

이 트랙은 App Check 강제에 두 층(콘솔 적용 + 코드
`enforceAppCheck`)이 있다고 전제해 왔다. **이 전제는 Functions에
대해서만 맞고, Firestore/Storage에 대해서는 틀렸다** — 위 API 탭
확인 결과가 그 근거다.

| 서비스 | 콘솔 토글 | 코드 스위치 | 강제 지점 |
|---|---|---|---|
| Functions | 없음(안내 링크만) | `enforceAppCheck`(있음, 현재 0건) | **코드가 유일한 스위치** |
| Firestore / Storage | 있음("적용" 전환) | 없음 | **콘솔이 유일한 스위치** |

즉 서비스마다 강제 지점의 위치 자체가 다르다. 정정된 요구 조건:

- **Functions** → 앱 등록 + `enforceAppCheck: true`(코드 변경 필요).
- **Firestore/Storage** → 앱 등록 + 콘솔에서 "적용" 전환(코드 변경
  없음).

공통 선행 조건은 **"앱 등록"**이며, §3-1-1의 확인 결과대로 현재
미충족이다.

### 3-2. S2-a 계측 설계

**6개 onCall 함수**(`callGeminiText`, `generateFittingImage`,
`beginFittingAttempt`, `getSignedImageUrls`, `sendTestPush`,
`triggerScheduledCheckTest`)에 `[appCheck] fn=<함수명> uid=<uid>
hasApp=<true/false>` 형태의 로그를 심는다. `request.app`의 존재 여부로
`hasApp`을 판정한다(강제하지 않은 상태에서도 `request.app`은 토큰이
왔으면 채워진다 — onCall의 App Check 컨텍스트는 강제 여부와 무관하게
관측 가능하다).

**onSchedule 2개(`scheduledProactiveCheck`, `sweepStorageTokens`) +
onObjectFinalized 1개(`revokeTokenOnUpload`)는 계측 대상이 아니다.**
이유: 이 셋은 공개 HTTP 엔드포인트가 없다 — `onSchedule`은 Firebase가
내부적으로 만드는 Pub/Sub 트리거이고 `onObjectFinalized`는 Storage
이벤트 트리거다. App Check는 클라이언트가 직접 호출하는 요청(콜러블·
HTTP)의 신원을 검증하는 장치이므로, 애초에 클라이언트가 호출하지 않는
이 세 함수에는 App Check 개념 자체가 적용되지 않는다.

**`functions_bg_removal/bg_removal_on_upload`도 같은 이유(Storage
이벤트 트리거, 공개 엔드포인트 없음)로 계측 대상이 아니다.** 다만
이 함수는 §1이 정정한 대로 별도 코드베이스(Python)에 있어 검토 단위가
갈라진다 — App Check 적용 여부 판단 자체는 위와 동일하게 성립하므로
이번 S2-a에서는 손대지 않되, "함께 검토했는지"를 명시적으로 남기기
위해 제외 사유만 여기 함께 적는다.

### 3-3. 사전 등록 판정 기준 — 원 기준과 정정을 둘 다 남긴다

**원 기준(정정 전, 이 문서 작성 이전에 대화로 등록됨):**

> 경로 (a)~(f) 전 경로에서 `hasApp=true` 100%.

**정정 사유:**

`background_agent.dart:156-160`이 백그라운드 아이솔레이트에서 App
Check `activate()`를 의도적으로 생략하고 있음을 코드로 확인했다
(§3-1). 경로 (f)(백그라운드)는 activate 자체가 없으므로 App Check
토큰이 생성되지 않고, 따라서 **반드시 `hasApp=false`로 나온다.** 원
기준은 이 사실과 원리적으로 동시 충족이 불가능하다.

결과를 보고 기준을 완화하는 것이 아니라, **기준이 잰다고 선언한 것과
실제로 재는 것이 데이터 수집 이전에 달랐음을 발견한 정정이다** — 논문
5.17.1절("사전 등록한 기준이 데이터 상한과 모순이었다")과 같은 형태.

**정정된 기준 — 축을 둘로 나눈다:**

**[축 1] 포그라운드 경로 (a)~(e)**

| 경로 | 진입점 |
|---|---|
| (a) 옷 등록 → 속성 추출 | `callGeminiText` |
| (b) 사이즈표 OCR | `callGeminiText` |
| (c) 코디 분석(스트리밍) | `callGeminiText`(스트림) |
| (d) 가상 피팅(옷 2벌 이상) | `beginFittingAttempt` + `generateFittingImage` |
| (e) 옷장 화면 진입 | `getSignedImageUrls` |

기준: `hasApp=true` 100%. 하나라도 `false`면 원인 규명 전까지 S2-b(강제
전환) 금지. 여기서 `false`가 나오면 그건 예상 밖이고, 그걸 잡아내는 것이
이 계측의 원래 목적이다.

**[축 2] 백그라운드 경로 (f)**

기준: `hasApp=false`가 **최소 1회 관측될 것.**

참(true)이 아니라 거짓(false)이 기준이라는 점에 주의한다. 이 축에서
재는 것은 App Check 상태가 아니라 **계측 장치가 백그라운드 경로에
도달하는가**다.

- `false`가 1회 이상 관측 → 배선 확인 완료, S2-a-2로 진행.
- 아무 로그도 없음 → 백그라운드 미발화인지 로그 미배선인지 미확정.
  이 상태로는 S2-a-2로 넘어가지 않는다(고친 뒤의 침묵을 성공으로
  오독하게 된다 — 논문 5.11.7절 "관측 장치의 잔여 사각"과 같은 계열).
- `true`가 나옴 → 코드 읽기(§3-1)가 틀린 것이다. 그 경우 원인
  재규명이 우선이며 S2-a-2는 보류한다.

**두 축의 판정은 독립이다.** 축 1이 통과해도 축 2가 미확정이면 S2-b로
가지 않는다 — 강제 전환의 위험이 가장 큰 경로가 바로 (f)이기
때문이다(강제로 전환된 순간 activate 자체가 없는 (f)는 무조건 거부당해
백그라운드 자율 실행 전체가 조용히 멈춘다).

### 3-3-1. `false`의 해석 규칙 (2026-08-10 등록, 같은 날 3상태로 정정)

**위 축1·축2의 기준값(`hasApp=true` 100% / `hasApp=false` 최소 1회)은
그대로 둔다.** 결과를 예상했다고 해서 기준을 완화하지 않는다 — 이
조항은 정확히 지금 같은 상황(축1이 실패할 가능성이 높아 보이는
상황)에서 S2-b를 막으라고 등록된 것이고, 지금 그렇게 발동하는 것이
정상 동작이다.

**[정정 2026-08-10, 같은 날 두 번째] 처음 등록한 (i)/(ii) 두 상태
구분은 불완전했다.** `evidence_appcheck_2026-08-09.md` 163~165행에서
`app:"MISSING"`이 확인되었을 때 이미 별도 사례로 적어뒀으나, 그때는
그 함의를 축2 기준에까지 반영하지 않았다. 다시 집계해 보니 실제
상태는 프레임워크 기준으로 **셋**이다:

| `verifications.app` | 우리 `hasApp` | 의미 |
|---|---|---|
| `VALID` | `true` | 정상 — App Check 토큰이 실제로 검증됨 |
| `INVALID` | `false` | 토큰은 왔으나 유효한 JWT로 디코딩되지 않음 |
| `MISSING` | `false` | 토큰 자체가 오지 않음 |

`request.app != null` 하나로 판정하는 우리 계측은 `INVALID`와
`MISSING`을 **똑같이** `hasApp=false`로 뭉갠다. 그런데 이 둘은 원인도
대응도 다르다:

- **`MISSING`** → 그 호출 경로에서 `activate()`가 아예 호출되지 않았다는
  뜻이다. **축2가 원래 잡으려던 것이 정확히 이것**이다(백그라운드
  아이솔레이트는 `activate()`를 생략하므로).
- **`INVALID`** → `activate()`는 호출됐으나 attestation이 유효한 토큰을
  산출하지 못했다는 뜻이다. 공급자 등록·기기 무결성·디버그 토큰
  미등록 등이 후보이며, **백그라운드 여부와 무관하다** — 배선 이전
  증거(위 "배선 이전 증거" 절)의 110건이 이미 포그라운드 경로
  (`callGeminiText`/`getSignedImageUrls`/`beginFittingAttempt`)에서
  발생한 것으로 확인됐다.

**따라서 §3-3 축2의 원래 기준("경로 (f)에서 hasApp=false 최소 1회")은
`MISSING`을 기대하고 등록했지만, `INVALID`로도 충족되어 버린다** —
축2가 재려던 것과 실제로 재는 것이 다시 한번 어긋난다. 이는 5.17.1절
(사전 등록 기준의 자기 모순), §3-3의 원 기준 정정(원리적으로 불가능한
100% true)에 이어 **이 트랙에서 세 번째로 나온 같은 형태의 문제다**
— 등록해 둔 판정 조건이 값의 원인까지는 구분하지 못했다.

**정정된 축2 기준:**

> 경로 (f)에서 `hasApp=false`가 관측되고, **같은 시각대 프레임워크
> 로그의 `verifications.app`이 `MISSING`일 것.**

`INVALID`로 나오면 축2는 **미충족**이다 — 그건 백그라운드 특유의
문제가 아니라 포그라운드와 공유하는 문제이기 때문에, 이 값만으로는
"백그라운드 아이솔레이트가 activate를 생략한다"는 가설을 지지하는
증거가 되지 못한다. 축1 기준(`hasApp=true` 100%)은 이번 정정과
무관하게 그대로 둔다.

**참고로, 배선 이전 증거를 3상태로 다시 집계한 결과가 이미 이
방향의 근거를 일부 보여준다**(아래 §3-2 "배선 이전 증거" 절의 표
참고) — `getSignedImageUrls`는 `MISSING`이 0건인 반면
`callGeminiText`/`beginFittingAttempt`에는 `MISSING`이 존재하고,
`agent_planner.dart:722-723`이 `callGeminiText`를 호출하며 이 경로가
`background_agent.dart`의 `runProactiveCheck`를 통해 백그라운드
아이솔레이트에서도 실행됨을 코드로 확인했다. 다만 이는 **S2-a
계측(`[appCheck] fn=...`) 배선 이전 시점**의 간접 정황일 뿐,
축2의 정정된 기준을 직접 충족시키는 것은 아니다 — 정정된 기준을
직접 충족하려면 우리 계측 로그와 같은 시각대 프레임워크 로그를
실기기 (a)~(e) 실행 이후에 대조해야 한다.

**이것은 계측 설계의 결함이다.** `request.app`만으로는 우리가 알고자
한 것("토큰이 왔는가")을 온전히 재지 못하며, 지금 그 구분을 대신
해주고 있는 것은 우리 계측이 아니라 프레임워크 로그다. **다음 계측
개정 시 반영할 항목으로 등록만 한다** — 진입점 표시(`src=fg|bg`)와
`hasApp` 대신 3상태(`VALID`/`INVALID`/`MISSING`)를 직접 기록하는 값으로
바꾸는 것. **이번 커밋에서는 고치지 않는다.** 관측 개시 직전에
계측을 바꾸면 무엇을 쟀는지 알 수 없게 된다(개정 6판에서 무효화된
실측과 같은 형태의 오염 회피, S2-a 작업 3에서 이미 적용한 원칙과
동일).

### 3-3-2. `beginFittingAttempt`의 `MISSING` 7건 — 경쟁 가설로 등록 (실행 전 사전 등록)

이전 절(§3-3-1)은 `beginFittingAttempt`의 `MISSING` 7건을 "미해결"로
남겼다. 다시 보니 그건 가설이 하나(H1)뿐이어서 안 맞았던 것이지,
데이터가 부족한 게 아니다 — **경쟁 가설을 둘로 등록**한다.

**H1(아이솔레이트 가설).** 백그라운드 아이솔레이트에서 호출되는
경로는 `activate()`가 없어(§3-1) `MISSING`이 나온다.

- 예측: `callGeminiText`(백그라운드에서도 호출됨, §3-3-1) 높음 /
  `getSignedImageUrls`(포그라운드 전용) 0 / `beginFittingAttempt`
  (포그라운드 전용, 아래 참고) 0.
- **실측과 어긋난다.** `beginFittingAttempt`도 `MISSING` 7건이
  나왔다(`docs/evidence_appcheck_2026-08-09_full.md` 192~198행).

**H2(콜드스타트 타이밍 가설).** App Check 토큰 취득은 비동기다 —
`activate()` 호출 직후 곧바로 토큰이 준비되는 것이 아니라 SDK가
백그라운드에서 attestation을 교환한 뒤 채워진다. 앱 실행 직후,
토큰이 아직 준비되기 전에 나가는 호출은 `MISSING`(토큰 필드 자체가
비어 있음)이 되고, 그 이후의 호출은 토큰은 있지만 교환에 실패한
상태라 `INVALID`가 된다.

- 예측: 실행 직후 호출이 몰리는 경로일수록 `MISSING` 비율이 높다.
- `_beginFittingAttempt()`(`gemini_service.dart:150-159`, 405행에서
  호출)는 `AgentPlanner`/`background_agent.dart` 어디에서도 불리지
  않는 **포그라운드 전용** 호출이다(코드 확인 — `agent_planner.dart`에
  `beginFittingAttempt` 문자열 자체가 없다). **H1로는 설명되지
  않지만 H2로는 설명된다** — 사용자가 앱을 막 켜고 바로 피팅을
  시작하면, 아직 토큰이 준비되기 전에 이 호출이 나갈 수 있다.
- 정황(`docs/evidence_appcheck_2026-08-09_full.md`의 재집계에서
  새로 확인): `beginFittingAttempt`의 `MISSING` 7건은
  2026-08-09T15:56:13.6~15:56:17.9, **약 4.4초 안에 전부 몰려
  있다.** `beginFittingAttempt`는 순차 피팅 1회당 한 번만 불리므로
  (코드 주석 확인), 이 7건은 짧은 시간에 몰린 여러 번의 호출이다 —
  H2와 방향은 맞지만, 이것만으로 "콜드스타트 직후"였는지 "이미 켜져
  있던 앱에서 반복 시도"였는지는 구분되지 않는다.

### 호출 횟수 결함 여부 확인 (2026-08-10, 코드 + 로그, 실행 불필요)

사람이 4.4초에 피팅을 7번 개시할 수는 없으므로, 이 7건이 "사용자
조작 7회"가 아니라 "한 번의 시도에서 나온 다중 호출"(호출 횟수
결함)일 가능성을 먼저 배제해야 H2 해석이 성립한다.
`rate_limit.ts`/코드 주석은 "`beginFittingAttempt`는 피팅 시도
하나당 정확히 1회만 센다"고 선언한다 — 이 선언을 코드 읽기와
전수 로그 대조로 확인했다.

1. **호출 위치 — 루프 바깥.** `gemini_service.dart:405`의
   `_beginFittingAttempt()` 호출은 `_generateFittingImageSequential()`
   안에서 순차 루프(`for (var step = 0; ...)`, 416행) **시작 전**에
   있다(395-410행). 옷 N벌이어도 이 호출은 1회다.
2. **재시도 경로 — 다시 안 불린다.** 단계별 재시도
   `_stepWithRetry`(471-483행)는 이미지 생성 호출
   (`_callFittingProxy`/`_callProxyText`)만 감싸며,
   `_beginFittingAttempt`는 그 범위 밖(405행, 루프 밖)에 있어
   재시도로 인해 다시 불릴 수 없다.
3. **UI/재구성 가드 — 이중으로 있다.** 컨트롤러
   (`fitting_job_controller.dart:244`)는 `if (isGeneratingFitting ||
   ...) return;`으로 재진입을 막고, 화면
   (`fitting_room_screen.dart:307-310`)의 `_canGenerateFitting`도
   `!widget.jobController.isBusy`로 같은 상태를 한 번 더 검사한다.
   컨트롤러는 `main.dart:174`에서 앱 생명주기 동안 단 하나만
   생성되므로(`final FittingJobController _fittingJob =
   FittingJobController()`) 화면 재구성이 새 인스턴스를 만들어
   가드를 우회하지도 않는다. 다만 `isGeneratingFitting`은
   `finally`(316-317행)에서 항상 `false`로 풀리므로, **한 시도가
   끝난 뒤 사용자가 다시 누르는 것은 막지 않는다** — 이 가드는
   "동시 중복"만 막지 "빠른 연속 재시도"는 막지 않는다.
4. **같은 4.4초 구간의 `callGeminiText` 건수 — 0건.** 전수 원본
   로그(`raw_functions_log.txt`, 1869줄)에서 2026-08-09T15:56:13~18
   구간을 대조한 결과, `beginfittingattempt` 7건 사이에
   `callgeminitext` 라인이 **하나도 없다.** 대신 마지막 줄이
   ```
   2026-08-09T15:56:17.927662Z ? beginfittingattempt: [rateLimit] 초과 uid=BDDOIl08EhXnHu6oz6Zro47EtMw1 kind=fitting bucket=2026080915
   ```
   이며, `functions/src/index.ts:166`의 `fittingLimit: 6`과 정확히
   일치한다 — 6번째까지 통과, **7번째에 상한 초과.** 서버의
   `fittingCount` 카운터가 실제로 6에서 걸렸다는 것은, 이 7건이
   서버에서 개별적으로 집계된 **7번의 진짜 콜러블 호출**이었다는
   뜻이다 — 클라이언트가 같은 요청 하나를 재전송하는 버그였다면
   카운터가 설정값과 정확히 일치하는 지점에서 걸릴 이유가 없다.

**판정: "시도당 정확히 1회" 선언이 성립한다.** 항목 1·2가 코드로,
항목 3이 가드 구조로, 항목 4가 서버 카운터 동작으로 서로 다른
층위에서 같은 결론을 가리킨다. 4.4초 7건은 **App Check와 무관한
별개 결함이 아니라, 사용자(또는 테스터)가 실제로 7번 시도를
개시한 것**이다 — `callGeminiText`가 0건인 것으로 보아 각 시도가
이미지 생성 단계(루프 진입 후 첫 호출)에 닿기도 전에 실패했을
가능성이 높고(예: 사용자 사진 다운로드 단계에서의 실패), 실패가
빠르고 조용했다면 사용자가 "다시 시도" 버튼을 연타했다는 시나리오와
들어맞는다 — 정확한 실패 지점은 이 확인의 범위 밖으로 남긴다.
**MISSING 원인 분석은 §3-3-2 H2 그대로 진행한다.**

**부수 확인 — 논문 7.1절 "fittingLimit=6" 서술에 대한 영향 없음.**
이 절이 지적한 것("그 소진이 정상 사용이 아니라 중복 호출이었을
수 있다")은 이번 확인으로 **기각된다** — 소비는 정확히 시도 수만큼
이루어졌다. 7.1절의 "`fittingLimit=6`이 실사용·시연에 충분한지 아직
관측되지 않았다"는 결론은 전제가 바뀌지 않았으므로 그대로 유효하다.

**두 가설은 배타적이지 않다 — 둘 다 참일 수 있다** (`MISSING` 37건이
두 원인의 혼합일 수 있다). 현재 데이터로는 분리되지 않으며, 이는
논문 5.21.2절이 등록한 "상관된 두 변수 사이의 교란을 통제하지 않은
것"과 같은 형태다 — 함수 정체성(포그라운드/백그라운드)과 호출 시점
(콜드스타트 직후/이후)이 지금까지의 관측에서는 서로 얽혀 있어 갈라
보지 못했다.

**판별 설계(실기기 (a)~(e) 실행 시 함께 수행한다) — 이 기준을 실행
전에 사전 등록한다:**

- **조건 A** — 앱을 콜드스타트한 직후 **5초 이내**에 (a)(옷 등록 →
  속성 추출, `callGeminiText`) 실행.
- **조건 B** — 앱 실행 후 **60초 대기**한 뒤 (a) 실행.
- H2가 참이면: 조건 A에서 `MISSING`, 조건 B에서 `INVALID`가
  나온다(토큰이 준비될 시간을 줬으므로 최소한 "토큰 필드는 채워진"
  상태가 되고, 그 토큰 자체가 유효한지는 여전히 §3-1-1의 H-A에
  달려 있다).
- 두 조건 모두 `INVALID`로 나오면 H2는 기각되고, `MISSING`의 원인은
  H1 단독이거나 이 문서에 아직 없는 제3의 원인이다.
- 두 조건 모두 `MISSING`으로 나오면 H2도 기각된다(시간을 줘도
  안 바뀌면 타이밍 문제가 아니다) — 이 경우도 제3의 원인 후보를
  다시 찾아야 한다.

이 판별은 §3-3-3(가칭, 실행 후 결과 기록)으로 이어진다 — 결과는
실기기 (a)~(e) 실행 이후에 이 절 바로 아래 추가한다.

### 3-4. S2-a-3 — 포그라운드 토큰 고장 규명·수정 (2026-08-10 신설, S2-a-2보다 앞으로)

**[정정 2026-08-10] 트랙 순서를 재편한다.**

- 기존 순서: S2-a(계측) → S2-a-2(백그라운드 activate) → S2-b(강제)
- **변경 순서: S2-a(계측, 완료) → S2-a-3(포그라운드 토큰 고장 규명·
  수정) → S2-a-2(백그라운드 activate) → S2-b(강제)**

**변경 사유**: 포그라운드가 한 번도 유효한 토큰을 내지 못한 상태에서
(§3-1, `INVALID` 110건·`VALID` 0건) 백그라운드 `activate()`를
먼저 추가해도, 그 결과는 `MISSING`이 `INVALID`로 바뀌는 것뿐이다 —
축2가 잡으려던 "activate 부재" 문제는 실재하지만, 그건 **두 번째
층**이다. 첫 번째 층(포그라운드조차 유효한 토큰을 못 만든다, §3-1-1
H-A)을 닫지 않은 채 두 번째 층을 먼저 손대면, S2-a-2 완료 후에도
여전히 강제 전환이 위험한 상태(§3-6-1)가 그대로 남는다.

**이 단계의 내용은 §3-1-1의 검증 체크리스트(4항목)와 그 결과에 따른
수정 경로 선택으로 구성된다** — 별도로 새로 적지 않고 §3-1-1을
그대로 가리킨다. S2-a-3 완료 조건: §3-1-1의 4개 확인 항목에 답이
채워지고, 그 답에 따라 경로 1 또는 경로 2 중 하나가 적용되어
`INVALID` 110건과 같은 실패가 재현되지 않음을 실측으로 확인.

**§3-3 축1의 기준(`hasApp=true` 100%)은 유지한다 — 다만 현재 그
기준이 충족 불가능한 상태임을 명시한다.** 이는 논문 5.17.1절·§3-3
정정·§3-3-1에 이어 이 트랙에서 **네 번째로 나온 "재려던 것과 실제로
재는 것이 다른" 형태**이나, 앞의 셋과 성격이 다르다 — 앞의 셋은
**기준 자체가 틀렸던** 경우(원리적으로 충족 불가능하게 등록됐거나,
값이 무엇을 재는지 불완전하게 정의됨)였고, 이번은 **기준은 맞고
시스템이 그 기준에 미달한** 경우다. 그래서 **기준을 고치지 않는다**
— S2-a-3이 닫아야 할 것은 판정 기준이 아니라 시스템의 실패
그 자체다.

### 3-6. S2-b — 강제(enforce) 전환

### 3-6-1. 위험도 재평가 (2026-08-10) — 계측 단계 분리가 이미 값을 회수했다

**이 관측(§3-2 "배선 이전 증거", §3-3-1)이 없었다면 어떤 일이
벌어졌을지를 기록해 둔다.** `enforceAppCheck: true`로 바로 전환했다면,
백그라운드 경로(축2, 원래 위험하다고 알고 있던 곳)만이 아니라
**포그라운드를 포함한 모든 서버 호출이 즉시 실패**했을 것이다 —
`callGeminiText`/`getSignedImageUrls`/`beginFittingAttempt`가 이미
디코딩 불가능한 토큰을 보내고 있었으므로, 강제 전환은 이 셋을
`enforceAppCheck`가 그대로 거부하게 만들 뿐이었다. 롤백 경로가
재배포뿐이므로(아래 참고), 재배포가 끝날 때까지 **앱이 전면 사용
불가** 상태였을 것이다.

즉 §1이 정한 순서 근거("저위험 구간(S1)에서 절차를 먼저 검증한 뒤
되돌리기 비용이 큰 구간(S2)으로 넘어간다")와, S2 안에서도 계측(S2-a)을
강제(S2-b)보다 먼저 분리해 둔 판단이, 정확히 이 지점에서 값을
회수했다. 계측이 없었다면 이 실패는 강제 전환 **이후**에야, 그것도
"모든 호출이 한꺼번에 죽는다"는 형태로만 발견됐을 것이다.

**S2-b의 전제 조건에 한 줄을 명시적으로 추가한다.** 기존 전제는
"축1 `hasApp=true` 100%"였고 그것으로 충분하다고 보았으나, `false`가

**`true`의 의미도 함께 명시해 두어야 한다** — 축1이 100% `true`로
나온다는 것은 "activate가 호출됐다"가 아니라 "서버가 디코딩 가능한
유효한 토큰을 실제로 검증했다"는 뜻이어야 하고, 그 둘이 다르다는
것을 지금 알게 됐다.

- **전제 조건**: S2-a-3(§3-4) 완료, 축 1·축 2 둘 다 확정, S2-a-2(§3-5)

### 3-7. 후속 항목 — Firestore/Storage의 App Check 적용 (S2-b 이후, 이번 트랙에서 착수하지 않음)

§1의 범위 정정 3차(§3-1-2)에서 등록한 대로, Firestore와 Storage도
App Check 미적용 상태다. **Functions보다 위험도가 낮지 않다** —
오히려 데이터에 직접 접근하는 경로다. 선행 조건이 Functions와
같으므로(앱 등록, §3-1-2), 순서상 Functions(S2-b) 뒤에 둔다.

**되돌리기 비용의 비대칭을 기록한다:**

| 서비스 | 강제 전환 방법 | 롤백 |
|---|---|---|
| Firestore/Storage | 콘솔 토글 | **즉시 가능**(토글을 되돌리면 끝) |
| Functions | 코드 배포 | 재배포 필요, **롤백 중에도 앱 전면 정지**(§3-6의 "롤백 경로가 재배포뿐" 참고) |

이 트랙의 순서 기준이 애초에 "되돌리기 비용"이었으므로(§1), 이
비대칭은 **S2-b 착수 순서를 재검토할 근거가 될 수 있다** — 되돌리기
쉬운 쪽(Firestore/Storage)을 먼저 켜서 절차를 저위험 구간에서 한 번
더 검증한 뒤 Functions로 넘어가는 편이, §1이 이미 채택한 논리(S1로
저위험 구간에서 절차를 먼저 검증)와 일관될 수 있다. **다만 지금
순서를 바꾸지는 않는다** — 근거로 기록만 하고, §3-1-1의 경로
결정(경로 1/경로 2) 이후에 함께 판단한다.

### 6-1. `sweepStorageTokens` 24시간 미발화

### 관측 (콘솔, 요청 24시간 열, 2026-08-10)

| 함수 | 스케줄 | 24시간 요청 수 |
|---|---|---|
| `scheduledProactiveCheck` | every 3 hours | 7회 |
| `sweepStorageTokens` | every 24 hours | **0회** |

### 대조의 의미

같은 `onSchedule`이고 같은 리전(`asia-northeast3`)인데 한쪽만 0이다.
즉 **`onSchedule` 인프라 자체는 작동한다**(`scheduledProactiveCheck`가
3시간 주기에 맞게 7회 찍혔다 — 24시간 ÷ 3시간 = 8회 기대치에 근접).
문제는 `sweepStorageTokens`에 한정된다. `every 24 hours`라면 어떤
24시간 관측 창에도 최소 1회는 잡혀야 한다(관측 창 경계에 정확히 걸린
경우는 제외).

### 논문과의 관계 — "안 쟀다"에서 "쟀더니 0"으로

이는 논문 7.1절 "배포된 주기 작업의 미검증"(5.18.6절)의 **첫 실측이다.**
기존 서술은 "토큰 스윕의 로직은 로컬 실행으로 검증했으나, 배포된 스케줄
작업 자체는 아직 한 번도 발화하지 않았다"였고, 이는 **관측 부재**였다
— 발화했는지 안 했는지 잰 적이 없다는 뜻이다. 지금은 24시간 관측
창에서 0회라는 **관측이 있다.** "안 쟀다"에서 "쟀더니 0"으로
등급이 올라간다 — 후자는 원인 규명이 가능한 상태이고, 전자는
그렇지 않았다.

### 확인 방향 (후보, 전부 사용자만 할 수 있는 확인)

- [ ] Cloud Scheduler 콘솔에 `sweepStorageTokens`에 대응하는 잡이
      실제로 생성되어 있는가.
- [ ] 그 잡의 마지막 실행 시각과 상태(성공/실패/미실행)가 무엇인가.
- [ ] 로그에 `[sweepStorageTokens] scanned=.. revoked=..` 라인이
      있는가(있다면 실행은 됐으나 콘솔 요청 수 집계에서만 빠진
      것이고, 없다면 실행 자체가 안 된 것이다 — 원인의 층위가
      달라진다).

### 6-2. 준비 단계 안전망 부재 — 수동 재시도가 호출량 예산을 태운다는 실측 흔적

### 배경 — `beginFittingAttempt` 4.4초 7건 확인 과정에서 나온 부산물

앞선 "호출 횟수 결함 여부 확인"(§3-3-2)에서, 같은 4.4초 구간의

상류 이미지 모델 호출에 닿기도 전에 끝났다는 뜻이다.

### 논문과의 관계 — 5.19절 "준비 단계의 안전망 부재"의 실측 형태

이는 논문 7.1절 "개정 7판에서 새로 규명된 미해결 결함" 첫 항목
(=5.19절 "준비 단계의 안전망 부재")과 정합한다:

> **준비 단계의 안전망 부재** — 상류 모델 호출 앞단의 이미지
> 다운로드가 4장의 3중 안전망 어디에도 감싸이지 않아, 일시적 실패가
> 곧바로 사용자 실패로 노출된다. 관측 당시 사용자가 수동 재시도로
> 해소하였다.

이번 로그(2026-08-09T15:56:13.6~17.9)는 원 서술의 "사용자가 수동
재시도로 해소하였다"는 문장이 실제로 어떤 형태였는지를 처음으로
수치로 보여준다 — **4.4초에 7회.**

### 새로 드러난 것 — 원 서술에 없던 상호작용

**수동 재시도가 `fittingLimit`(6/시간, `functions/src/index.ts:166`)를
소진시킨다.** 이번 구간의 7번째 시도에서
`[rateLimit] 초과 ... kind=fitting`이 실제로 발생했다(§3-3-2 확인
참고). 즉 이 결함은 실패에서 그치지 않고 **정상 사용의 예산을
태운다.** 사용자 관점에서는 "실패해서 다시 눌렀더니 이제 상한에
걸려 아예 못 한다"가 된다 — 실패 한 번이 재시도를 통해 최대 6번의
정상 시도 기회를 대신 소모할 수 있다는 뜻이다.

**이 상호작용은 어느 쪽 항목에도 기록되어 있지 않다.** 5.19절
(안전망 부재)은 호출량 상한을 다루지 않고, 3.11.6절/3.14.5절
(호출량 상한 설계)은 실패 재시도가 예산을 먹는 경로를 다루지 않는다
— 두 설계가 각각은 타당하나, 맞물리는 지점이 검토되지 않았다.
논문 5.8.8절("독립적이라 가정한 두 정책이 실제로는 의존 관계였던"
사례, 매칭 정책의 무채색 보너스와 최근 노출 감점 사이에서 관측)과
같은 형태이며, 이번엔 **신뢰성 설계(3중 안전망)와 비용 통제 설계
(호출량 상한) 사이**에서 나타났다는 점이 다르다.

### 미확정으로 남기는 것

7회 시도가 정확히 어느 지점에서 실패했는지는 이번 확인 범위 밖이다.
준비 단계(사용자 사진 다운로드, `_downloadViaResolverOrFallback`)가
유력하나 로그로 확정하지 않았다 — 확정하려면 그 구간의 클라이언트
로그가 필요하며, 현재 남아 있지 않다. **추정을 결론으로 적지
않는다**(논문 5.21.2절 계열 — 검증 불가능한 근거로 가설을 확정하지
