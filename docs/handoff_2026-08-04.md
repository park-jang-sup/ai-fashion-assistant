## 2. 확정된 설계와 그 근거

### 서버 이전 — 왜, 그리고 엔진을 포팅하지 않는 이유

F'.3 계측이 드러낸 것: 로컬 카운터(OS 발화) 19 / `invokeCount`(uid+meta
도달) 10 — 차이 9. 인증 복원 이전에 죽은 실행이 있었다는 뜻. 서버가
한 번에 닫는 것: 인증 복원 실패·Gemini 키 노출·앱 종료 시 알림
미도달·iOS 미지원·로그 드레인 유예 장치.

**엔진(`OutfitMatcher`/`TpoMatchPolicy`/`OutfitSelfEvaluator`/색상
택소노미)은 어느 단계에서도 TypeScript로 포팅하지 않는다.** 옮기면
140개 테스트가 안 따라오고(검증된 Dart와 실행되는 TS가 갈림), 정책
변경마다 두 곳을 고쳐야 한다. 서버는 트리거·인증·키·알림만 가져간다.

### A단계 — 프록시 구조

- `callGeminiText`(Callable, `asia-northeast3`)가 model/requestBody를
  가공 없이 중계하는 범용 함수. 텍스트(A-1)·이미지(A-2) 둘 다 이
  함수 하나로 처리 — 이미지 전용 함수를 새로 안 만들었다(엔진 포팅
  최소화와 같은 판단). 함수 이름이 "Text"인데 이미지도 처리하는 이유는
  `index.ts` 상단 주석에 남김.
- **반드시 `onCall`+`request.auth` 검사.** `onRequest`면 누구나 쓰는
  무료 Gemini 게이트웨이가 된다(키를 빼내는 수고를 없애줘 지금보다
  나쁨). 미인증은 `unauthenticated`로 즉시 거부 — 401 실측 완료.
- **모델 선택·폴백 재시도는 클라이언트에 남긴다.** 서버가 폴백까지
  하면 `FormatException` 판정(`_parseJsonObject`가 잘린 응답 감지)이
  서버·클라이언트 두 벌이 된다.
- **예외 매핑은 서버가 성격별로 구분해 명시적으로 던져야 한다** —
  프레임워크의 디테일 없는 `internal` 뭉갬은 클라이언트의
  `withTextModelFallback` 세 갈래(`TimeoutException`/
  `GeminiApiException(isRetryable)`/`FormatException`) 중 아무 데도
  안 걸린다. 컨벤션: 본문 전송 중 연결 끊김 → `data-loss`, 200인데
  비유효 JSON → `internal`+`{reason:invalid-json}`, 업스트림 실제 오류
  → `internal`+`{upstreamStatus,upstreamMessage}`. 새 코드/reason 추가
  시 클라이언트 `gemini_service.dart`의 `_mapProxyException`도 같은
  커밋에서 확장해야 한다 — 서버만 고치면 클라이언트가 모르는 코드라
  똑같이 무력화된다.
- **ALLOWED_MODELS 화이트리스트**에 `gemini-3.1-flash-lite`(폴백)·
  `gemini-3.1-flash-image`(이미지) 등록. 모델 교체 시 클라이언트
  `_textModel`과 서버 `ALLOWED_MODELS`를 **같은 커밋**에서 바꿔야
  한다 — 하나만 바꾸면 폴백 경로가 `invalid-argument`로 전부 거부.

### B단계 — FCM 토큰/채널/탭 경로

- 토큰은 `users/{uid}/fcm_tokens/{token}` 컬렉션(문서 id=토큰 문자열
  자체라 중복 저장 자연 방지), `onTokenRefresh` 구독으로 갱신 대응.
  다기기 대비 컬렉션 구조(단일 필드 아님).
- **알림 채널을 로컬 알림과 통일**(`agent_recommendation`) — 안 그러면
  설정이 둘로 갈린다. 기존 로컬 알림 경로는 지우지 않고 유지(서버
  푸시와 도달률을 비교해야 함).
- **탭 수신 경로가 `isColdStart`로 이원화된다** — 이게 오늘까지도
  중요한 설계다:
  - `getInitialMessage()`(콜드스타트) → `runProactiveCheck` 호출
    **생략**(`AppShell.initState()`가 앱 진입 시 이미 선제 체크를
    돌기 때문 — `main.dart:188`).
  - `onMessageOpenedApp`(백그라운드 탭, 앱이 살아있는 상태) →
    `runProactiveCheck` 호출 **유지**(`initState()`가 다시 안 도는
    유일한 경로 — `AppShell`은 백그라운드→포그라운드 복귀만으로는
    재마운트 안 됨, `WidgetsBindingObserver` 같은 lifecycle 훅도 없음).
  - 락을 걸지 않은 이유(사용자 명시 지시): 어느 쪽이 막힐지가 타이밍에
    달려 "서버 푸시가 완주로 이어진 비율"이라는 계측 자체가 왜곡된다.
    `isColdStart`로 애초에 한쪽만 부르면 경합 자체가 안 생긴다.
  - **계측 필드도 갈린다**: `serverTapCount`/`serverTapAt`은 두 경로
    공통 기록. `serverTapLastRunAt`은 **백그라운드 탭 경로만** 기록
    (콜드스타트는 `runProactiveCheck`를 직접 안 부르므로 완주 시각을
    못 잡음). **`lastRunAt`(WorkManager 전용 필드)으로 콜드스타트
    경로의 완주 여부를 판정할 수 없다** — 결과물(추천 문서 생성
    여부)로만 확인 가능.

### C단계 — 스케줄러 판정 범위와 계측 필드 분리

- **서버는 "추천 없는 날짜"만 트리거한다.** 예보 변화 재계획 판정
  (`shouldReplanForWeather`)은 클라이언트에 그대로 둔다 — 서버에
  복제하면 임계값 로직이 서버·클라이언트 두 벌로 갈린다(엔진 포팅
  금지와 같은 원칙의 축소판). 판정 기준은 클라이언트의
  `recommendationForDateSilently`(`targetDate==date &&
  dismissed==false`)와 완전히 동일해야 한다 — **`userChoice==null`
  조건을 넣으면 안 된다.** Firestore의 `where('field','==',null)`은
  필드가 명시적으로 null로 저장된 문서만 매치하고 필드가 아예 없는
  문서는 매치 안 한다(`recommendation_entry.dart`가 null이면 필드
  자체를 안 씀) — 이 조건을 넣었다가 "미확인 추천 없음" 상시 오판정
  버그를 냈었다(수정·검증 완료).
- **계측 3단 깔때기를 깨지 않는다** — 로컬 카운터(OS 발화) →
  `invokeCount`·`invocationLog`(uid+meta 도달) → `lastRunAt`(완주) 3층
  구조에 t0부터 표본이 쌓이는 중. 서버 발화는 `agent_meta`의 **별도
  필드**(`serverInvokeCount`/`serverInvocationLog`/`serverLastRunAt`)에
  기록 — 기존 필드와 절대 안 섞는다. 트랜잭션으로 감싸 RMW 경합 제거
  (검증 단계의 짧은 간격 수동 호출이 자연 3시간 주기보다 경합
  가능성이 훨씬 높아 필요).
- **자동/수동 판별법**: `scheduledProactiveCheck`(자동)는
  `getActiveUids()`로 모든 uid를 한 함수 실행 안에서 순회하며
  기록하므로 uid들의 로그 시각이 **1초 이내로 붙어서 찍힌다.**
  `triggerScheduledCheckTest`(수동)는 호출한 uid 하나만 기록해 짝이
  없다. **Cloud Functions 로그의 "Starting new instance" 라인은 쓰지
  말 것** — 인스턴스가 웜 상태면 이 라인 자체가 안 찍혀 발화 횟수를
  과소 집계한다. Firestore 로그 짝짓기만 신뢰할 것.
- 락을 안 건 이유(함정 8 대응, 사용자 명시 지시): 경합 폭이 짧고
  최악의 경우가 "같은 날짜 추천 두 개"뿐이라 락을 걸면 락에 막혀
  스킵된 실행을 계측에 어떻게 셀지가 애매해져 표본 해석이 깨진다.

나타남). 1번 후보만이 아니라 2·3번 후보·미채택 동점자도 섞는다(천장

아래 참고)**: 절대비율(+5%p) 임계값은 실측 n으로 검산해 통계적으로
무의미함을 확인하고 폐기(n=9에서 5%p=0.45건, 우연히 벗어날 확률
100%; n=150으로도 22.1%). **대체 — 쌍대비교(부호검정/sign test).**
`current`와 제안 정책이 다른 조합을 고른 경우(discordant pairs)만
모아 그 안에서 제안 정책이 "입겠다" 판정을 받은 비율을 본다. **나아짐
기준: 양측 부호검정 p<0.10 그리고 방향이 ≥70%.** `p<0.05`가 아니라
`p<0.10`인 이유: discordant n=15~20(반나절 라벨링 예산 안에서 현실적
규모)에서 p<0.05를 넘으려면 승률 80%대가 필요해 진짜 개선을 놓칠
위험(false negative)이 크다고 판단 — **이 문단 자체가 결과를 보기
전에 기준을 정했다는 사전 합의의 증거**(`task_formality_policy_ab.md`가
겪은 "기준 없이 결과부터 본" 실패를 반복하지 않기 위함).

**discordant 모수 확장**: `findCandidateMatches` 트리거를 추가 — 실측
결과 트리거 87개(속성 있는 전 아이템) 전부(100%)가 상위 3후보 동점이라
트리거 자체 선별은 병목이 아니다. 카테고리×색상 층화로 다양성만
확보하면 된다(희소 색상 우선 가중).

**블라인드 라벨링**: 라벨링 화면에 "이건 어느 정책이 고른 조합인지"를
절대 안 보여준다 — 안 그러면 무의식적으로 정책을 편들게 된다. 정책
매핑은 라벨링 종료 후 별도 파일(`combo_policy_map.json`, 라벨링 UI가

**도구**: `tools/eval_harness/` 독립 디렉터리(프로덕션 코드에 일회성
저자 도구를 안 얹는다). 로컬 웹페이지, `tools/export_for_kaggle/output/

`tools/eval_harness/labels.json`(개인 데이터라 `.gitignore` 대상,


## 4. 살아있는 함정 (원본 §5 형식, 상태 표시 포함)

### 지금도 반드시 지켜야 할 것

1. **프록시는 반드시 `onCall`+`request.auth` 검사.** `onRequest`로
   만들면 인증 없는 무료 Gemini 게이트웨이가 된다 — 키를 빼내는 수고를
   없애줘 지금보다 나쁘다. (A-1·B·C 전부 이 패턴 — 지켜지고 있음.)
2. **스트리밍 응답 상한은 10MB**(non-streaming 32MB와 다름). 이미지를
   스트리밍으로 보내지 말 것 — 지금 이미지는 non-streaming 경로라
   해당 없지만, 향후 스트리밍 확장 시 주의.
3. **`shouldReplanForWeather`를 서버에 복제하지 말 것.** 서버는
   `existing==null`인 날짜만 트리거하고 예보 변화 재계획 판정은
   클라이언트에 남긴다 — 넘어가고 싶어지면 멈추고 사람에게 물을 것.
4. **계측 3단 깔때기를 깨지 말 것.** 기존 WorkManager 경로(`invokeCount`

   필드에만 기록한다.
5. **스케줄러가 `users`를 통째로 순회하지 않게 구조를 열어둘 것.**
   지금은 uid 5개(실사용 3개)뿐이라 무해하지만, 나중에 조용히
   비싸진다. 처리량 상한·최근 활동 기준 축소는 지금 구현 안 함, 자리만

### 새로 발견한 것 (2026-08-02~08-04)

10. **Firestore `where('field','==',null)`은 필드가 명시적으로 null인
    문서만 매치하고, 필드가 아예 없는 문서는 매치 안 한다.**

11. **`getInitialMessage()`가 이미 소비한 메시지를 이후의 무관한

    재현 조건 불충족으로 필터 작동 자체는 **미검증**.

    판정하면 틀린다.
13. **uid 착각 — 이 프로젝트는 uid가 최소 5개다**(본인/심사/유령
    계정 2개/이탈 세션 2개, §8 표 참고). Firestore 콘솔에서 아무 uid나
    보고 "비어있다"고 판단하기 전에 logcat의 `FirebaseAuth: Notifying
    id token listeners about user ( uid )`로 실제 로그인 uid부터 확인할
    것 — **이 프로젝트에서 최소 두 번(§2-12, §2-15) 실제로 이 착각이
    일어났다.**
14. **`fitting_cache`가 이미지 프록시 실기기 검증을 가릴 수 있다.**
    같은 사용자·같은 옷 조합이면 캐시가 응답해 서버 미경유로 착각할
    수 있다. "다시 분석" 버튼은 텍스트만 재실행해 우회 안 됨 —
    "새로 생성하기"(`forceRegenerate:true`) 버튼을 쓰거나, 가장
    확실하게는 한 번도 안 써본 옷 조합으로 검증할 것(캐시 키가
    SHA256(사용자 사진+정렬된 옷 id들)이라 새 조합이면 캐시 자체가
    없음).
15. **Doze/절전 최적화로 인한 FCM 지연** — 화면이 꺼져 있을 때만
    알림 도달이 지연되는 패턴 실측(토큰·FCM 경로 자체는 정상, 화면
    보는 상태에서 재발송하면 즉시 도달). `android.priority` 지정
    여부는 조사만 하고 판단 보류 중(사용자 지시, 코드 미변경).
16. **`toKstDateString`/`kstMidnight` — 서버 런타임 시각(UTC)과
    calendar/recommendations의 날짜(KST 자정 정규화)를 맞추려면 +9시간
    고정 오프셋 변환이 필요하다.** `Date.toISOString()`을 그대로 쓰면
    날짜가 하루 당겨진다(KST 8/2 00:00 = UTC 8/1 15:00) — 실측으로
    확인된 버그, 수정 완료.
17. **`cloud_functions` 스트리밍 청크(`Chunk.partialData`)는
    `Map<Object?, Object?>`로 온다.** `as Map<String, dynamic>` 캐스트가
    실기기에서 항상 실패 — `Map<String, dynamic>.from(x as Map)`으로
    변환.
18. **`cloud_functions`는 `^5.4.1`로 고정, 6.x 올리지 말 것.** 6.x는
    `firebase_core` 4.x 세대라 core/firestore/auth/storage/app_check

19. **`google-services` 플러그인이 꺼져 있으면 App Check 문제가 조용히

    App Check SDK가 네트워크 호출 자체를 안 나가 문제가 안 보인다 —
    플러그인 켜서 초기화가 완전해져야 실제 상태가 드러난다.
20. **이 저장소 릴리스 빌드에서 `debugPrint`는 찍힌다**(이전 판의

### 최우선 — F'.3 표본 계정 문제

`BDDOIl08EhXnHu6oz6Zro47EtMw1`(본인 계정, `task_server_v1.md`가 인용한
"로컬 카운터 19 / `invokeCount` 10" 원본 t0 기준선 그 계정)의
`invokeCount`(WorkManager 자연 발화)가 **2026-07-31 이후 `10`에서 한
번도 안 늘었다**(`lastRunAt=2026-07-31T00:43:43Z` 그대로). 원인은
단순 — 최근 며칠간 실기기가 계속 심사 계정(`yPyw4DC2gkPXQ97i7c1h9JJdrgY2`)
으로 로그인된 상태였다(logcat `FirebaseAuth` 로그로 재확인). 심사
계정의 `invokeCount`는 `33`, `lastRunAt=2026-08-03T19:17:46Z`로 정상
축적 중이다. **표본이 사라진 게 아니라 계정이 바뀌었다 — 단 두
계정은 서로 다른 t0에서 출발한 별개 카운터라 이어 붙일 수 없다.**
(`serverInvokeCount`는 스케줄러가 `users` 전체를 순회해 기록하므로
로그인 상태와 무관하게 계속 쌓인다 — 끊긴 건 `invokeCount` 쪽뿐.)

선택지 세 가지, 결론은 사용자 판단:
1. **심사 계정을 새 기준으로 삼고 t0를 재정의한다.** 논문에 이미
   인용된 "t0=2026-07-31 09:09:13, 로컬 19/invokeCount 10"이 본인
   계정 기준이라, 재정의하면 그 인용을 정정하거나 각주로 계정 전환을
   설명해야 한다. 심사 계정은 4주 표본을 8/28까지 새로 채워야 해서
   원래 목표한 기간을 못 채울 수 있다.
2. **본인 계정으로 다시 로그인해 원래 표본을 이어간다.** t0 기준선은
   그대로 살지만, **심사 계정 쪽 축적이 그 순간부터 멈춘다** — 심사
   계정 표본(현재까지 쌓인 것)은 8/3까지의 부분 표본으로 굳어진다.
   또한 실기기 검증(오늘 C단계 검증처럼 심사 계정으로 실행해야 하는
   작업)을 할 때마다 다시 계정을 전환해야 해 운영 부담이 늘어난다.
3. **두 계정을 별개 표본으로 취급하고 둘 다 보고한다.** 논문에 "본인
   계정 표본(t0~7/31, ~4일)"과 "심사 계정 표본(8/1~, 진행 중)"을
   따로 제시 — 인위적 개입이 없다는 장점이 있지만, 표본이 쪼개져
   각각의 통계적 힘이 약해진다.

## 11. 유지해야 할 프로젝트 원칙

- **측정 없이 고치지 않는다.** 결함을 발견하면 먼저 그 수정의 효과를
  측정할 장치를 만든다.
- **판정 기준을 결과 보기 전에 정한다.** 정했다는 사실 자체를 문서에
  남긴다(§2 하네스 판정 기준의 `p<0.10` 근거 문단이 실제 사례).
- **폴백 방향은 항상 "아무것도 하지 않음"**(예보 조회 실패 시 재계획
  안 함, 사유 불명 시 배지 미표시, 벡터 없으면 섹션 미렌더링, 해상도
  없는 신호는 억지로 안 만든다 — §2 7-a 결론과 같은 결).
- **유사도 ≠ 궁합.** 코사인은 "닮음"이므로 궁합 판정에 직접 쓰지
  않는다 — 단 (b) 유형(정책이 실제로 못 보는 정보가 있는 경우)에서
  "결정론적 축이 놓친 정보의 회수"로 쓰는 것은 예외적으로 정당화됨
  (§2 참고, 이 예외의 조건을 벗어나면(=동점 밖에서 순위가 바뀌면)
  즉시 과도 신호로 취급).
- 임베딩 매칭에 **절대 임계값 금지**, 상대 순위(top-N)만. 코사인
  수치를 사용자에게 노출하지 않는다.
- **안 한 것을 했다고 쓰지 않는다**(논문·문서 공통). 이 원칙을
  스스로 어긴 걸 로그 대조로 잡아낸 사례가 여럿 있다(§2-12류 자기
  정정) — 정정 경위 자체도 기록에 남긴다.
- **검증 목적으로 실데이터(옷·추천 이력) 삭제 금지** — 판정 로직을
  순수 함수로 분리하고 합성 데이터로 테스트한다.
- **블라인드 라벨링**(신규, 하네스 설계에서 나온 원칙) — 사람이
  라벨을 매길 때 정책 출처를 안 보여준다. 측정자가 측정 대상에
  개입하지 않게 하는, "측정 없이 고치지 않는다"의 연장.
- 논문은 "프로젝트 일기"에 가까운 기록물 — **논문 서술에 맞춰 코드를
  수정하지 않는다.** 우선순위는 실제 성능 향상.
- 주석은 "무엇을"이 아니라 **"왜 이렇게"**.
- **단계마다 커밋 하나, 단계마다 검증.** 백그라운드 에이전트를
  A/B/C로 쪼갠 것이 릴리스 전용 결함 2건을 잡아냈고, 문서 갱신도
  같은 원칙으로 쪼개 커밋했다.
- **엔진(`OutfitMatcher` 이하)은 포팅하지 않는다.** 서버는 트리거·
  인증·키·알림만 가져간다 — 어느 단계에서도 이 경계를 넘지 않았다.
- **논문에 인용한 심볼은 저장소에 대조한다.** `grep -rn "심볼\b" lib/
  test/`(단어 경계 필수).
- **firebase deploy / flutter build / adb install은 실행 전 사용자
  확인.** `adb install` 실패해도 uninstall 금지.
