작성 2026-08-08, **[착수 승인 2026-08-08] 96d61f2 배제 확정 후 3+1
착수 승인됨 — 구현 진행 중.** 근거: `handoff_2026-08-07.md` §4 "업스트림
이미지 생성이 55초를 넘겨 실패"(실측 확정 항목) — 원인이 업스트림(Gemini
이미지 모델) 지연으로 좁혀졌고, 우리가 못 고치는 지연을 견디는 설계로
조치 성격이 바뀌었다. 이 문서는 그 조치안 중 "3. 서버 측 캐시 쓰기"와
"1. 클라이언트 시한 조정(소폭)"을 함께 넣는 설계 지시서다. **배포와

서버가 이미지 모델 응답을 받는 즉시 스스로 Storage 업로드 +
`fitting_cache` 기록까지 마치도록 옮기고, 클라이언트 시한은 소폭만
올려 병행한다. 오늘 관측(§4)상 서버는 이미 10번 중 9번(90%) 성공하고
있으므로, "한 번 실패 화면을 보고 다시 들어가면 즉시 뜬다"는 효과가
클라이언트 코드를 거의 안 건드리고도 나온다.

## 0. 구조 판단 — 프록시 예외(a) vs 전용 콜러블(b)

**결론: (b) 전용 콜러블 신설이 맞다.** 코드로 검토한 근거:

1. **`callGeminiText`는 지금 진짜로 모델 불문 중계다.** `functions/src/index.ts:209`부터
   추적하면 `ALLOWED_MODELS`에 있는 어떤 모델이든 `requestBody`를
   가공 없이 그대로 넘기고, 응답도 원본 그대로 돌려준다(주석: "서버는
   `requestBody`를 가공 없이 그대로 중계"). 이 원칙 덕에 논문 5.16이
   기록한 사례 — 신규 텍스트 모델 교체를 검토했다가 파라미터 계약
   회귀를 배포 전에 잡은 것 — 가 **서버 코드 변경 없이** 가능했다.
   `callGeminiText` 안에 "이 응답이 이미지 모델 성공이면 Storage에
   올리고 Firestore에 쓴다" 같은 분기를 넣는 순간, 이 함수는 더 이상
   모델 불문이 아니게 되고 다음번 모델 교체 검증 때 이 분기까지
   같이 살펴봐야 한다 — 5.16이 확보한 이점이 깎인다.
2. **가상 피팅은 이미 성격이 다른 호출이다.** 유일하게 이미지 개수가
   가변(코디보드 슬롯 수만큼), 유일하게 결과를 캐시해야 하고, 유일하게
   응답이 100초대(다른 호출은 텍스트 6.7~9.9초, §4 상관분석 참고)다.
   같은 함수 안에서 "보통 10초 안에 끝나는 호출들"과 "가끔 300초까지
   가는 호출"이 같은 `timeoutSeconds`·같은 인스턴스 풀을 공유하는 것
   자체가 이미 어색하다(지금은 어쩔 수 없이 같이 쓰고 있음).
3. **4번(백그라운드+FCM) 확장 시 프록시가 무관해진다.** 피팅 전용
   함수를 비동기(트리거 기반)로 바꾸는 건 그 함수 하나의 문제지만,
   `callGeminiText`가 피팅을 겸하고 있었다면 텍스트 분석·속성
   추출·사이즈표 OCR까지 전부 영향권에 들어간다.

**(a)가 나을 수 있는 유일한 지점**: 인증 검사·호출량 상한
(`checkAndRecordRateLimit`)·업스트림 fetch(`fetchUpstream`)·abort
계측·에러 매핑을 통째로 다시 써야 한다는 비용. 이건 구조 판단을
뒤집을 이유는 아니고, **공유 헬퍼로 뽑아 중복을 줄이는 것**으로
해결한다(아래 1절).

## 1. 신설 함수 — `generateFittingImage`

`functions/src/index.ts`에 새 `onCall` export를 추가한다. 클라이언트
쪽 메서드명(`GeminiService.generateFittingImage`)과 이름이 같지만
계층이 다르므로(서비스 vs 서버 콜러블) 충돌 아님 — 오히려 대응
관계가 명확해짐.

### 1.1 공유 헬퍼로 뽑을 것 (중복 방지)
- `fetchUpstream`(이미 함수) — 그대로 재사용.
- 인증 검사·`checkAndRecordRateLimit` 호출 — 지금 `callGeminiText`
  본문에 인라인돼 있는 걸 작은 헬퍼로 뽑아 양쪽이 같은 걸 쓰게 한다.
- reqId·시작/완료 로그 포맷 — 상관 키 규약을 통일해야 두 함수의 로그를
  같은 방식으로 대조할 수 있다(§4의 계측 설계와 동일 원칙).

### 1.2 요청 계약
```
{
  userPhotoId: string,
  clothingItemIds: string[],
  requestBody: {...}   // 지금 client가 만드는 것과 동일(base64 포함)
}
```
클라이언트는 이미지 다운로드·base64 인코딩·프롬프트 조립을 지금과
똑같이 client에서 한다(`GeminiService.generateFittingImage` 내부
로직 불변) — **바뀌는 건 호출 대상 함수명과, 페이로드에
`userPhotoId`/`clothingItemIds` 두 필드를 추가하는 것뿐**이다. 이미
클라이언트가 들고 있는 값이라 새로 조회할 필요 없음.

### 1.3 캐시 키 — 서버가 재계산한다 (클라이언트 값 신뢰 안 함)

**원칙(3.12.2와 동일): 클라이언트가 만든 결과물을 받지 않고, 식별자를
받아 서버가 직접 계산·검증한다.** 지금 `_buildFittingCacheKey`
(`fitting_job_controller.dart:285`)는:
```dart
sha256(userPhoto.id + ':' + sortedClothingIds.join(','))
```
이 로직을 `functions/src/fitting_cache_key.ts`(신규, 순수 함수)로
그대로 미러링한다:
```ts
export function buildFittingCacheKey(userPhotoId: string, clothingItemIds: string[]): string {
  const sorted = [...clothingItemIds].sort();
  return sha256(`${userPhotoId}:${sorted.join(',')}`);
}
```
**정합성 고정 — 착수 시 첫 커밋에 포함할 것**: Dart 쪽에서 알려진
입력(예: `userPhotoId='TEST_U'`, `clothingItemIds=['b','a']`)으로
해시를 한 번 뽑아 고정 벡터로 삼고, `fitting_cache_key.test.ts`가
같은 입력에 같은 해시를 내는지 단위 테스트로 고정한다. **이 테스트
없이는 착수하지 않는다** — 어긋나면 캐시가 영원히 미스가 되는데,
그 실패는 겉으로 "그냥 좀 느리네" 정도로만 보여서 알아채기 어렵다.

### 1.4 소유권 검증 — `signed_url_policy.ts`와 같은 패턴

`decideSignedUrlAccess`처럼 **Admin SDK 읽기와 판정 로직을 분리한
순수 함수**로 만든다(`fitting_ownership_policy.ts`, 신규):
- `userPhotoId`·`clothingItemIds`에 대응하는 `wardrobe` 문서를 전부
  읽는다(배치 조회, `getSignedImageUrls`와 같은 방식).
- 각 문서의 `ownerUid === request.auth.uid`인지 검사(`wardrobe`
  정책과 동일 — `demo_wardrobe`는 이 흐름에 안 들어옴, 가상 피팅은
  본인 옷장 아이템만 대상이므로).
- 하나라도 불일치·미존재면 `permission-denied`로 거부하고 **캐시
  키도 계산하지 않는다**(신뢰 안 되는 id로 캐시를 오염시키지 않기
  위해 — 검증이 먼저, 계산이 나중).

### 1.5 처리 순서
1. 인증 검사 → 소유권 검증(1.4) → 캐시 키 계산(1.3, 검증 통과 후에만).
2. `checkAndRecordRateLimit(uid, 'image')` — 기존과 같은 카운터
   재사용(새 쿼터를 만들지 않음, 상한 이원화로 인한 우회 방지).
3. `fetchUpstream` 호출(기존 `UPSTREAM_TIMEOUT_MS` 그대로 재사용).
4. 성공 시: 이미지 바이트 추출 → **서버가 직접**
   `StorageService.uploadFittingResult`에 대응하는 로직으로
   Storage 업로드 → `fitting_cache` 문서 쓰기(`ownerUid` 포함,
   `createdAt`은 `serverTimestamp()`) → **원본 Gemini 응답 그대로
   클라이언트에 반환**(클라이언트의 기존 파싱/표시 코드는 안 건드림
   — `_extractImageFromResponse`가 그대로 동작).
5. 클라이언트가 이 응답을 실제로 받으면, 기존 `_cacheFittingResultSilently`가
   다시 한 번 같은 경로에 업로드+캐시 쓰기를 시도한다(중복). **이번
   범위에서는 이 중복을 그대로 둔다** — `uploadFittingResult`가
   같은 cacheKey 경로에 덮어쓰는 구조라 멱등이고, 비용도 작다.
   클라이언트가 서버 응답의 캐시 여부를 읽어 자기 쓰기를 건너뛰게
   하는 최적화는 **범위 밖(나중 후보)**로 남긴다 — 지금 범위를
   "호출 대상 이름 + 필드 2개 추가"로 최소화하는 게 우선.

## 2. 클라이언트 시한 — 150초, 3과 함께만

**표본 갱신(96d61f2 배제 테스트 4건 포함, 서버 300초 상한 배포 이후
총 10건)**: 75.5 / 78.6 / 79.0 / 79.7 / 94.3 / 110.8 / 114.2 / 133.4 /
139.4초(성공 9건) + 300초+(실패 1건). 중앙값 약 102.6초(정렬된
10건의 5·6번째 평균) — 표본이 늘면서 이전 추정(6건 기준)보다
중앙값이 올라갔다.

| 임계값 | 잡히는 성공 | 비율 |
|---|---|---|
| 90초 | 75.5/78.6/79.0/79.7초 (4건) | 40% |
| 120초 | 위 + 94.3/110.8/114.2초 (7건) | 70% |
| **150초** | 위 + 133.4/139.4초 (9건, 성공 전부) | **90%** |
| 180초 | 150초와 동일(9건) | 90%(150초 대비 이득 없음) |
| (모든 값) | 44fb3bdc(300초+ 실패)는 어떤 값으로도 못 잡음 | — |

**150초를 제안으로 올린다(이전 제안 120초=67%에서 상향)** — 150초와
180초가 커버율이 같은데(둘 다 성공 9건 전부, 90%) 180초는 사용자가
30초를 더 기다리기만 하고 얻는 게 없다. 120초는 표본이 늘면서
커버율이 67%→70%로 사실상 그대로라 상향 근거가 약하다. **비용**:
150초는 사용자가 최대 2분 30초 스피너를 본다는 뜻 — 여전히 크다.
1절(서버 캐시)이 같이 들어가야만 이 비용이 정당화된다(놓친 나머지
10%는 재진입에서 회수되므로). 3 없이 1만 단독으로 넣는 건 이번
설계에서 제외.

## 3. 착수 전 확인

### 3.1 3.11절 원칙 저촉 여부
**결론: "추천 엔진은 옮기지 않는다"는 경계는 안 건드린다.** 이 변경은
가상 피팅의 *결과 저장*을 옮기는 것이지 *무엇을 추천할지 결정하는*
로직이 아니다 — 결정(어느 옷을 코디보드에 놓을지)은 여전히 클라이언트에
있다. 다만 3.11이 정의한 경계 기준이 "분량이 아니라 검증의 소재지"였다는
점에서, **"이 결과를 저장해도 되는가"의 검증 소재지가 클라이언트(암묵적
신뢰)에서 서버(명시적 소유권 검사, 1.4절)로 옮겨간다**는 건 사실이다 —
이미 서버가 쥐고 있던 "자격증명 프록시" 역할이 "결과 확정(저장)"까지
넓어지는 것으로 본다. **논문 rev8 재료로 등록**(아래 4절).

### 3.2 되돌릴 수단
- **서버**: `generateFittingImage`는 순수 추가(additive)다 —
  `callGeminiText`는 한 글자도 안 바뀐다. 문제가 생기면 클라이언트가
  이 함수를 안 부르게만 하면 되고, 함수 자체 삭제는 정리 차원의
  선택 사항이지 필수 아님.
- **클라이언트**: 호출 대상을 바꾸는 순간부터는 되돌리려면 클라이언트도
  다시 빌드·배포해야 한다(서버만 되돌려선 안 됨 — 존재하지 않는 함수를
  부르게 되므로). **`SIGNED_URLS` dart-define과 같은 컴파일타임
  플래그**(`--dart-define=SERVER_FITTING_CACHE=false`)로 경로를
  가르는 걸 제안한다 — 다만 이것도 빌드 자체는 필요하다(런타임
  즉시 킬스위치가 아님, `image_url_resolver.dart`의 `signedUrlsEnabled`
  주석이 이미 같은 한계를 명시해둔 전례가 있다). **즉시 킬스위치가
  필요하면 Remote Config 같은 런타임 설정층 추가가 별도로 필요하다 —
  이번 범위에 넣을지는 검토 대상으로 남긴다(비용 대비 필요성 낮아
  보임 — 서버 쪽은 항상 안전하므로 최악의 경우도 "느린 캐시 미스"지
  기능 정지가 아님).**

## 4. 논문 rev8 재료 (핸드오프에만 기록, 논문 원문은 이번에 안 고침)
- 3.11절 "서버 계층 도입"의 경계가 "결과 확정(저장)"까지 넓어진
  사례로 등록 후보. 기준 문장("경계는 분량이 아니라 검증의 소재지")을
  그대로 적용해, 저장 여부 검증의 소재지가 클라이언트→서버로 이동했음을
  기록.
- §4의 "업스트림 이미지 생성이 55초를 넘겨 실패"가 이 설계의 직접
  동기라는 점도 같이 남긴다(원인이 우리가 못 고치는 지연이라는 게
  확정되면서 조치 성격이 "버그 수정"에서 "지연을 견디는 설계"로
  바뀐 경위).

## 5. 손대면 안 되는 것
- `callGeminiText`의 기존 동작(모델 불문 중계) — 한 글자도 안 바꾼다.
- `UPSTREAM_TIMEOUT_MS`/`onCall timeoutSeconds`(300s/320s, 측정용
  임시값) — 이 작업과 무관, 되돌릴 조건은 별도(§4 참고).
- 재시도 정책(`_withRetry`) — 조치안 "2. 재시도 정책 재설계"(헤지드
  리트라이 등)는 **[하향 2026-08-08] "후순위"가 아니라 "근거 없음"으로
  내린다.** 그 안의 유일한 근거는 "재시도가 첫 시도보다 체계적으로
  빠르다"는 관측(두 세션: 300초+→78.6초, 139.4초→75.5초)이었는데,
  96d61f2 배제 테스트 4건에서 정반대가 나왔다(94.3초→114.2초,
  79.7초→133.4초 — 둘 다 재시도가 더 느림). 표본 6쌍 전체로 보면
  재시도 소요시간은 첫 시도와 무관하게 산포한다 — "재시도가 빠르다"는
  패턴은 우연이었다. 헤지드 리트라이를 도입할 근거 자체가 사라졌으므로
  이번 3+1 범위에도, 다음 후보로도 올리지 않는다(재검토하려면 새
  근거가 있어야 함).
- `fitting_cache`의 캐시 키 체계(SHA-256, 입력 형식) — 그대로 미러링만
  한다, 바꾸지 않는다.

1. **Dart↔TS 캐시 키 일치 테스트 — 착수 필수조건.** 1.3절의
