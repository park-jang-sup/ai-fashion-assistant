# 작업 지시서 — 서버 이전 (task_server_v1)

`docs/task_hardening_v1.md`(작업 1~4)는 **완료·검증·푸시까지 종료**됐다. 이 문서는 그 다음 단계다.

## 0. 왜 서버로 가는가

지금 자율 실행은 기기의 WorkManager가 트리거한다. F′.3 계측이 드러낸 사실:

- **로컬 카운터(OS 발화) 19 / `invokeCount`(uid+meta 도달) 10 — 차이 9.** 이 9건은 인증 복원 이전에 죽었고, 계측을 넣기 전에는 **관측조차 불가능한 구간**이었다.
- 이 숫자를 **비율로 환산하지 말 것.** 9건 중 4건은 지연 실행 후 일부러 로그아웃해 만든 것이고 나머지도 수동 트리거가 섞였다. 지금 말할 수 있는 것은 "이 구간이 0이 아니다"까지이며, 서버 이전의 근거로는 그것으로 충분하다. 자연 발생 비율은 t0(2026-07-31 09:09:13)부터 4주가 지나야 나온다.

서버로 옮기면 한 번에 닫히는 것들:

| 지금 문제 | 서버가 닫는 방식 |
|---|---|
| 아이솔레이트 재초기화·인증 복원 실패 | Admin SDK는 uid를 인자로 받는다 — 복원할 인증이 없음 |
| Gemini 키가 APK에 문자열로 실림 | 키가 서버 환경변수로 이동 |
| 앱이 죽어 있으면 알림 도달 불가 | FCM 푸시 |
| iOS 미지원(Background Fetch 재량) | 서버 스케줄러가 플랫폼 무관 |
| 로그 드레인 3초 대기 등 유예 장치 | 함수는 반환할 때까지 살아 있음 |

## ⚠ 사전 조건 — 먼저 확인하고 시작할 것

**Cloud Functions는 Blaze(종량제) 요금제가 필요하다.** 현재 프로젝트가 Spark라면 A단계부터 막힌다. 실사용량은 무료 한도 안에 들어갈 가능성이 높지만 **결제 수단 등록 자체가 전제**다.

이 확인은 사용자만 할 수 있다. Claude Code는 **콘솔에서 요금제를 바꾸려 하지 말고**, 배포가 요금제 문제로 실패하면 멈추고 보고한다.

## 사전 조건

Blaze(종량제) 요금제 — **이미 활성화됨.** Cloud Functions 배포에 걸림돌 없음.

## 범위 밖 (건드리지 말 것)

- **추천 엔진(`OutfitMatcher`, `TpoMatchPolicy`, `OutfitSelfEvaluator`, 색상 분류)의 TypeScript 포팅** — 아래 "왜 전면 포팅을 하지 않는가" 참조. **이 지시서 어디에서도 이 코드를 다른 언어로 다시 쓰지 않는다.**
- Storage 경로 격리 / `demo_images/` 분리 — 다운로드 토큰이 규칙을 우회한다는 실측 이후 우선순위가 내려갔다. 서버 이전 뒤로 미룸.
- 평가 하네스, 임베딩 다양성 타이브레이크, 축 B — 이후 작업.
- App Check 프로바이더 변경, R8, `tflite_flutter` 제거, split-per-abi.
- 상태 관리 라이브러리 도입, 화면 파일 분할, 서비스 인스턴스화.

## 왜 전면 포팅을 하지 않는가

`AgentPlanner.runProactiveCheck`는 100행이지만, 그 안의 `_prepareRecommendationFor`가 240행이고 다시 `OutfitMatcher`(정적 메서드 32개)·`GeminiService`·`OutfitSelfEvaluator`·색상 택소노미를 부른다. 전부 옮기면 **핵심 로직이 Dart와 TypeScript 두 벌로 갈린다.**

그러면 이렇게 된다:

- **140개 테스트가 따라오지 않는다.** 테스트는 Dart 순수 함수를 검증하는데, 실제로 도는 것은 TS 사본이 된다. 지금까지 이 저장소가 쌓아온 검증이 통째로 무효가 되는 게 아니라 — 더 나쁘게 — **검증된 코드와 실행되는 코드가 달라진다.**
- 정책을 하나 바꿀 때마다 두 곳을 고쳐야 하고, 어긋나면 조용히 어긋난다.
- 4주 안에 끝날 분량이 아니다.

그래서 **엔진은 Dart 클라이언트에 그대로 두고, 서버는 "트리거·인증·키·알림"만 가져간다.** 단계가 올라갈수록 서버가 하는 일이 늘지만, 어느 단계에서 멈춰도 그 자체로 완결이다.

---

## 공통 규칙

- **A → B → C 순서로, 단계마다 커밋 하나.** 이 저장소는 백그라운드 에이전트를 A/B/C로 쪼갠 것이 실제로 값을 했다(릴리스 전용 결함 2건을 단계별로 격리해서 잡음).
- **단계마다 사용자 검증을 받고 다음으로 넘어간다.** 한 세션에서 A와 B를 이어 하지 않는다.
- 주석은 한국어로, "무엇을"이 아니라 **"왜 이렇게"**를 적는다.
- Dart 쪽 변경 후에는 `flutter analyze`(**이슈 0건이 현재 기준선**)와 `flutter test`(140개)를 돌린다. 줄어들면 완료가 아니다.
- 폴백 방향은 항상 **"아무것도 하지 않음"**.
- **`firebase deploy` / `flutter build` / `adb install`은 실행 전에 사용자 확인을 받는다.** `adb install`이 실패해도 **uninstall 금지** — F′.3 발화 표본(t0부터 8/28까지)이 리셋된다.

# A단계 — Gemini 프록시 (키 회수)

## 왜 이것부터인가

파이프라인과 무관하게 독립적이고, 지금 남아 있는 보안 항목 중 가장 큰 것을 닫는다. `lib/config/env.dart`를 `.gitignore`에 넣은 것은 **저장소 유출**만 막는다. 키는 `Env.geminiApiKey`로 6곳에서 URL 쿼리에 붙어 컴파일되므로 **배포 APK의 `libapp.so`에 문자열로 남는다.** 심사위원에게 APK를 직접 배포하는 상황에서 이건 이론적 위험이 아니다.

## ⚠ 함정 1 — 프록시가 새로운 무방비 엔드포인트가 된다

인증 없는 HTTP 함수로 만들면 **누구나 호출 가능한 무료 Gemini 게이트웨이**가 된다. 키를 APK에서 빼내는 수고를 없애주는 셈이라 지금보다 나쁘다.

**반드시 `onCall`(Callable) 함수로 만들고 `request.auth`를 검사한다.** 미인증 요청은 `unauthenticated`로 즉시 거부. `onRequest`를 쓰지 말 것.

## ⚠ 함정 2 — 이미지 페이로드

가상 피팅은 사람 사진 + 옷 이미지를 base64로 실어 보낸다. 요청·응답이 수 MB가 되고, Callable 함수에는 페이로드 상한과 타임아웃이 있다.

**A단계에서는 텍스트 계열 호출만 옮긴다** — 속성 추출, 스타일링 설명, 자기 평가, 주간 플랜. **이미지 합성(`_imageModel` 경로)은 클라이언트에 그대로 둔다.** 이미지 경로 이전은 별도 판단이 필요하고, 텍스트만 옮겨도 키 노출은 동일하게 닫힌다(키는 하나이므로 — **단, 클라이언트에 이미지 경로가 남아 있는 한 키도 남는다**).

**따라서 A단계의 목표를 정확히 적는다: "텍스트 경로의 키 사용을 없앤다"이지 "APK에서 키를 제거한다"가 아니다.** 키 제거는 이미지 경로까지 옮겨야 완성된다. 이 사실을 커밋 메시지와 주석에 명시하고, 완료 보고에서 "키가 APK에서 사라졌다"고 쓰지 말 것.

## ⚠ 함정 3 — 모델 폴백 로직의 위치

`GeminiService.withTextModelFallback`은 `TimeoutException`·`GeminiApiException(isRetryable)`·`FormatException`을 잡아 `gemini-3.1-flash-lite`로 갈아탄다. 이 분기는 **서버로 함께 옮긴다** — 클라이언트에 남기면 재시도마다 왕복이 두 배가 되고, 서버는 예외 종류를 그대로 볼 수 있지만 클라이언트는 Callable 에러로 뭉개진 것만 본다.

`gemini_api_exception.dart`의 `isRetryable` 판정 기준(503·429·타임아웃)을 서버에서 동등하게 재현할 것. **이건 "엔진 포팅"이 아니라 HTTP 상태 코드 분기이므로 위 금지 사항에 해당하지 않는다.**

## 바꿀 것

1. `functions/` 디렉터리 신설 (TypeScript, Node 20+). `firebase.json`에 `functions` 블록 추가.
2. `callGeminiText` Callable 함수 — 모델명·프롬프트·이미지(선택, 속성 추출용 소형 이미지)를 받아 Gemini에 중계. 키는 함수 환경변수(`defineSecret` 또는 `.env`). **`request.auth == null`이면 거부.**
3. `lib/services/gemini_service.dart` — 텍스트 계열 호출 6곳 중 이미지 합성을 제외한 것들이 `Env.geminiApiKey` 대신 Callable을 타도록 변경. `cloud_functions` 패키지 추가.
4. `lib/config/env.example.dart`와 CI는 그대로 둔다 — 이미지 경로가 아직 키를 쓴다.

## 검증

- `flutter analyze` 0건 / `flutter test` 140개.
- 에뮬레이터 또는 배포 후 실기기에서: 옷 등록(속성 추출) → 추천 카드의 스타일링 설명 → 가상 피팅(이미지 경로, 여전히 클라이언트) 각각 정상.
- **미인증 거부 확인** — 로그아웃 상태에서 함수를 부르면 `unauthenticated`가 나야 한다. 이걸 안 보면 함정 1을 놓친다.
- 함수 로그에서 폴백 모델 전환이 실제로 일어나는지(강제로 유발하기 어려우면 "미검증"으로 보고).

## 커밋

`feat: Gemini 텍스트 호출을 Cloud Functions 프록시로 이전 (A단계)`

# B단계 — FCM 인프라

## 왜 별도 단계인가

파이프라인과 무관하게 **"서버가 이 기기에 알림을 보낼 수 있는가"만** 검증한다. C단계에서 이게 안 되면 원인이 스케줄러인지 푸시인지 구분이 안 된다. A단계 때와 같은 이유로 쪼갠다.

## ⚠ 함정 4 — `google-services` 플러그인이 주석 처리되어 있다

`android/app/build.gradle.kts`에서 `id("com.google.gms.google-services")`가 **주석 상태**다(`google-services.json`은 이미 있는데도). 지금은 `firebase_options.dart`로 프로그래매틱 초기화라 동작하지만, **FCM은 이 플러그인이 생성하는 리소스에 의존하는 부분이 있다.**

주석을 푸는 순간 빌드가 깨질 수 있다(플러그인이 `google-services.json`을 엄격하게 검증한다). **B단계에서 이 항목을 반드시 먼저 확인하고, 푼 뒤 릴리스 빌드가 통과하는지부터 본다.** 여기서 막히면 진행하지 말고 보고할 것.

## ⚠ 함정 5 — 토큰은 갱신된다

FCM 등록 토큰은 앱 재설치·데이터 삭제·주기적 갱신으로 바뀐다. 한 번 저장하고 끝내면 조용히 도달하지 않게 된다. `onTokenRefresh`를 구독해 `users/{uid}/fcm_tokens/`에 갱신 저장할 것. **여러 기기를 대비해 단일 필드가 아니라 컬렉션으로.**

## ⚠ 함정 6 — 기존 로컬 알림과 충돌

이미 `notification_service.dart`(A단계 산출물, 로컬 알림)가 있고 채널이 만들어져 있다. FCM 알림이 **같은 채널을 재사용**하도록 맞추지 않으면 알림 설정이 둘로 갈린다. 기존 채널 ID를 그대로 쓸 것.

또한 **로컬 알림 경로를 지우지 않는다.** C단계에서 서버 푸시와 기기 로컬 알림의 도달률을 비교할 수 있어야 한다.

## 바꿀 것

1. `firebase_messaging` 추가, 권한 요청(Android 13+ POST_NOTIFICATIONS는 이미 있음 — 확인할 것).
2. 토큰 등록·갱신 → `users/{uid}/fcm_tokens/{token}`. `firestore.rules`에 본인만 read/write 규칙 추가.
3. 서버에 테스트용 Callable — 호출하면 그 uid의 모든 토큰으로 푸시. **스케줄러는 아직 만들지 않는다.**
4. 설정 화면 진단 섹션에 "FCM 테스트 푸시" 버튼 (기존 "테스트 알림 보내기" 옆에).

## 검증

- 앱을 **완전히 종료한 상태**에서 테스트 푸시가 잠금화면에 뜨는지. 앱이 떠 있을 때만 되는 건 통과가 아니다.
- 토큰이 Firestore에 저장됐는지 콘솔 확인.
- 기존 로컬 알림("테스트 알림 보내기")이 여전히 동작하는지 — 회귀 확인.

# C단계 — 서버 스케줄러가 트리거를 가져간다

## 이 단계가 실제로 하는 일

Cloud Scheduler가 주기적으로 함수를 깨우고, 함수는 **"이 사용자에게 지금 추천이 필요한가"만 판단**해서 FCM으로 알린다. 판단에 필요한 것은 전부 Firestore 읽기와 날씨 HTTP 호출이라 **엔진 포팅 없이 TypeScript로 가능하다**:

- `calendar_entries`에서 오늘~+3일의 `isPlanned == true` 조회
- 해당 날짜에 이미 추천이 있는지(`recommendations`, `userChoice == null`)
- 예보 변화 판정 — `shouldReplanForWeather`의 임계값(강수확률·기온차 `_tempDiffThreshold = 5.0`)과 날짜당 상한 2회

**엔진(`OutfitMatcher` 이하)은 부르지 않는다.** 조합 생성은 클라이언트가 깨어났을 때 기존 경로 그대로 한다.

## ⚠ 함정 7 — `shouldReplanForWeather`가 두 곳에 생긴다

위 판정 로직을 서버에 쓰면 Dart 원본과 TS 사본이 갈린다 — 이 지시서가 금지한 바로 그 상황의 축소판이다.

**대응:** 서버는 **"추천이 없는 날짜"만** 트리거한다. 예보 변화에 의한 재계획 판정은 **클라이언트에 그대로 둔다.** 서버가 하는 판단을 `existing == null`로 좁히면 임계값 로직을 복제할 필요가 없고, 재계획은 앱이 깨어났을 때 기존 경로가 처리한다.

이걸 지키면 서버 코드가 수십 줄로 끝난다. 넘어가고 싶어지면 **멈추고 보고할 것** — 복제가 정당한지는 사람이 판단한다.

## ⚠ 함정 8 — 계측 3단 깔때기를 깨지 말 것

지금 신뢰성 측정은 **로컬 카운터(OS 발화) → `invokeCount`·`invocationLog`(uid+meta 도달) → `lastRunAt` 갱신(완주)** 3층으로 되어 있고, t0부터 표본이 쌓이는 중이다. 논문 3.4.5·5.12의 근거다.

**기존 WorkManager 경로를 제거하지 않는다.** 서버 트리거를 **추가**하고, 서버 발화는 `agent_meta`의 **별도 필드**(예: `serverInvokeCount`, `serverInvocationLog`)에 기록한다. 기존 필드에 섞으면 4주 표본이 오염되고, "기기 실행 vs 서버 실행" 비교라는 이 단계의 가장 값진 산출물이 사라진다.

이 비교표는 발표 자료에 그대로 들어갈 수 있다.

## ⚠ 함정 9 — 스케줄러가 전 사용자를 순회한다

지금 사용자는 2명(본인·심사 계정)이지만, 함수가 `users` 컬렉션을 통째로 순회하는 구조로 짜면 나중에 조용히 비싸진다. 처리량 상한(`maxPlans` 같은)을 서버에도 두고, 순회 대상을 **최근 활동 기준으로 좁힐 수 있게** 설계할 것. 지금 구현할 필요는 없고 구조만 열어둔다.

## 바꿀 것

1. Cloud Scheduler + 스케줄 함수(주기는 기존 WorkManager와 같은 3시간부터 시작).
2. 각 uid에 대해 "추천 없는 예정일"이 있으면 FCM 푸시 + `agent_meta`에 서버 계측 기록.
3. 클라이언트는 푸시 수신 시 기존 `runProactiveCheck` 경로를 태운다(새 파이프라인을 만들지 않는다).

## 검증

- 스케줄 함수가 실제로 주기 발화하는지(Cloud Functions 로그).
- 앱 완전 종료 상태에서 푸시 → 탭 → 추천 생성까지 이어지는지. **이것이 논문에 "아직 미관측"으로 적어둔 무개입 end-to-end의 서버 버전이다.**
- `agent_meta`에서 기존 필드와 서버 필드가 섞이지 않았는지.

## 사용자만 할 수 있는 일 (Claude Code가 하지 말 것)

1. **Blaze 요금제 확인·전환.**
2. **`firebase deploy`** — 배포 전 `firebase use`로 활성 프로젝트 확인(오배포 전례). `--only functions`는 배포마다 비용·시간이 든다.
