### 천장 2 — 엔진의 서버 재배치 (미착수, 착수 조건 미관측)

지금 백그라운드 에이전트는 "앱이 죽어 있어도 준비가 **시작**된다"까지만 증명됐고, 완결에는 사용자의 탭이 필요하다. `handoff`가 정한 D단계 착수 조건은 **"푸시는 도달했는데 파이프라인이 완주하지 않는다"가 관측되는 것**이며, 아직 관측되지 않았다.

착수하게 되면 제안된 경로는 "TS로 포팅"이 아니라 **Dart 엔진을 Dart인 채로 Cloud Run에 올리는 것**이다 — 140종 테스트가 검증하는 그 코드가 서버에서 실행되므로 "테스트가 다른 것을 검증하게 된다"는 금지 사유가 소멸한다. 다만 이건 `handoff §2`가 "설계조차 하지 말라"고 못 박은 D단계의 변형이므로, 착수 전에 그 금지의 취지와 이 방식의 차이를 사용자가 확인해야 한다.

## 2. 작업 원칙 (이 프로젝트 고유 — 반드시 지킬 것)

이 원칙들은 전부 사고를 겪고 만들어진 것이다. 논문 6.5절이 정식화하고 있다.

### 측정과 판정

1. **고치기 전에 재는 장치를 먼저 만든다.** 측정 하네스 우선 원칙.
2. **판정 기준을 결과 보기 전에 등록한다.** 등록 사실 자체를 커밋한다. 결과를 보고 기준을 만들면 사후 정당화가 된다.
3. **확인 항목은 지점 단위로 열거한다.** "전 화면 정상" 같은 문구는 24곳 중 1곳만 봐도 참이 되어 통과 신호만 만든다. 실제로 그 사고가 났다.
4. **관문은 변경 전후로 두 번 수행한다.** 변경 전 기준선이 없으면 발견된 이상의 원인을 가릴 수 없다.
5. **중단 규칙을 사전 등록한다.** 특히 "설명 가능하니 계속 진행"을 명시적으로 배제한다 — 이 판단이 두 번 사고를 만들었다.
6. **공허한 검증을 식별한다.** 비교 대상이 0이면 "통과"가 아니라 "성립 불가"로 기록한다.
7. **추정을 실측으로 포장하지 않는다.** 로컬 실측으로 클라우드를 추정하지 않는다(1.29초 → 68초 사례).

### 되돌리기

8. **되돌릴 수 없는 작업 앞에 되돌릴 수단을 먼저 만든다.** 백필·회수 도구에 manifest 기반 롤백을 붙였고, 실제 사고 당일 244건 복원에 썼다.
9. **검증되기 전에 안전망을 걷지 않는다.** 킬 스위치는 기본 꺼짐으로 도입하고, 레거시 폴백은 새 경로가 검증될 때까지 남긴다.
10. **삭제·회수류 작업은 대상을 참조하는 코드와 문서를 전수 확인한 뒤에만 실행한다.** 과거 문서의 "미참조" 서술을 믿고 파일 9개를 지웠다가 27개 문서가 참조 중임이 드러나 영구 소실됐다.

### 기록

11. **원문을 지우지 않고 정정 블록을 덧붙인다.** 무엇을 몰랐는지가 기록의 일부다.
12. **실측치에는 재현 코드를 함께 남긴다.** 수치만 남고 계산 코드가 없어 역산해야 했던 전례가 있다.
13. **안 한 것을 했다고 쓰지 않는다.** "실기기 미확인 — 단위 테스트로 갈음" 같은 한정을 그대로 적는다.
14. **인용하는 근거가 실제로 같은 사례인지 확인한다.** 릴리스 크래시의 원인 귀속이 다른 버그의 이슈를 인용하고 있었고, 그 위에서 로드맵 방향이 두 판 동안 유지됐다.

### 검증 실무

15. **릴리스 빌드로 검증한다.** 릴리스 전용 결함을 세 번 겪었다.
16. **클라이언트 코드 수정 후 실기기 확인 전에, 설치된 APK가 그 수정을 포함하는지 확인한다.** 커밋 시각과 `adb shell dumpsys package`의 `lastUpdateTime` 대조. 재빌드 누락으로 "고쳤는데 안 고쳐졌다"가 두 번 발생했다.
17. **규칙은 읽는 것이 아니라 두드려서 확인한다.** 접근 규칙의 의도가 실제로 성립하는지는 일반 사용자 권한으로 직접 호출해봐야 안다.
18. **작업 단위를 쪼갠다.** 배포 미지수와 배선 미지수를 한 단계에 섞지 않는다.

### 절대 금지

- 실데이터 삭제 금지. `adb uninstall` 금지(로컬 카운터·WorkManager 예약이 날아가 F'.3 계측 표본이 리셋된다).
- 엔진(매칭·색상·핏 예측) 포팅 금지 — 천장 2의 착수 조건이 관측되기 전까지.
- `flutter build` / `firebase deploy` / `adb install`은 실행 전 사용자 확인.

### 서명 URL 이행 (천장 1-2)

이미지 접근을 영구 토큰 URL에서 **만료 있는 서명 주소**로 교체. 기존 250건 토큰 회수 완료, 신규 업로드는 트리거(1.16초 내 제거)와 일 1회 스윕으로 처리.

- **1차 시도는 실패했다.** 배선이 24곳 중 1곳만 된 상태로 회수해 앱 이미지 표시가 대부분 정지 → 244건 전량 롤백 → A-5(25곳 배선)·A-6(예외 안전성) 후 재시도.
- **파일 9개 영구 소실 사고.** 과거 문서의 "앱 미참조" 서술을 믿고 삭제했으나 27개 문서가 참조 중. 확인 도구(`tools/audit_image_refs`)는 이미 저장소에 있었고 쓰지 않았을 뿐이다. 버킷 버전 관리가 꺼져 있어 복구 불가.
- 서명 요청 단위는 **경로가 아니라 문서 식별자** — 유출 주소에서 경로를 뽑아 재발급하는 루프를 차단.
- 클라이언트는 다운로드 토큰을 **지울 수 없다**(400 거부, 서버 전용 키)는 것을 실측으로 확정.

- **재사용할 산출물**(전부 `tools/embedding_spike/cloud_run_spike/`에 남아 있음, 스파이크 함수 자체는 삭제했지만 로컬 파일은 안 지움): `main.py`의 전처리(`_preprocess`, `CLIPImageProcessor` 로직을 torchvision 직접 호출로 이식)·추론 코드, `export_onnx.py`(ONNX 변환, SHA-256 포함), 5건 픽스처 기반 코사인 유사도 파리티 검증 하네스(§9/§11/§14). `@core.init` 우회 패턴(§18)도 그대로 재사용 가능.
- **열린 항목(등록만, 미해결)**: ONNX 모델의 재현성(`export_onnx.py`를 다시 돌렸을 때 같은 해시가 나오는지 미검증), Kaggle 노트북(`kaggle_embedding_comparison.ipynb`)이 쓰는 `transformers` API가 향후 버전업으로 깨질 가능성, `tools/export_for_kaggle/export.py`의 `DEFAULT_BUCKET` 값이 낡았다는 기존 결함(§1에서 이미 지적, 안 고침).
- **정리 상태**: 스파이크 함수·`firebase.json` 항목 롤백 완료·확인됨. **Artifact Registry 이미지는 서비스 계정 403 + `gcloud` 부재로 삭제·확인 둘 다 못 함 — 사용자가 콘솔에서 직접 처리해야 한다**(경로: Artifact Registry → `asia-northeast3` → `gcf-artifacts` → `embedding-coldstart-spike` 포함 이미지). 다음 달 초(2026-09) 청구 확인도 후속 항목으로 남아 있다.

**[보류, 2026-08-13] 로드맵 5번 자체를 보류한다 — `task_embedding_impl_v1.md`(본 구현 설계, 커밋 `f35ec3a`)까지 만든 뒤 사용자가 착수를 접었다.** 설계 문서는 지우지 않고 문서 서두에 `[보류]` 블록으로 근거·재개 조건·재사용 산출물을 남겨 뒀다. 근거 요약(전체는 그 문서 참고):

- 유일한 소비처("비슷한 옷" 시트)가 `embedding==null`을 정상 처리하도록 이미 설계돼 있어, 없어도 화면이 안 깨진다.
- **임베딩(유사도)과 코디 추천(어울림)은 다른 축이다** — 옷장에 더할 옷을 고르는 문제엔 유사도가 잘못된 축.
- **"상점 옷 연결의 전제 조건"이라는 이전 판단을 정정** — 속성 추출 + 기존 `OutfitMatcher`(격식·색 조화·톤온톤)로도 상점 옷 매칭이 가능하고, 오히려 그 편이 "어울림"에 더 맞는다.
- 옷장이 유동적이라 벡터 수명이 짧다 — 백필해도 결측이 다시 쌓인다.
- 에이전트 서사(자율 실행·자기 평가·자가 수리)에 기여가 없다.

**유일하게 남는 명분**: "비슷한 옷 = 중복 구매 방지" 프레이밍은 유사도가 맞는 문제이지만, **상점 카탈로그가 있어야 성립한다.** **재개 조건: 외부 카탈로그 데이터 소스가 확보된 시점.** 그 전에는 로드맵 5번을 다시 열 근거가 없다 — 다음 세션은 이 항목을 기본 후보로 다루지 말 것(아래 §6에 다음 축 후보 별도 등록, 로드맵 5번은 그 후보에 없다).

### (F) 주간 플랜의 옷장 규모 간접 상한 — [신규, 2026-08-13] 착수하지 않음, 후보 제시만

**로드맵 5번(실시간 임베딩) 보류(위 (C))에 따라 새로 제시하는
후보 중 하나.** `functions/src/request_shape.ts:218`의
`maxTotalTextChars: 30_000`(요청 페이로드 텍스트 총량 상한,
**Gemini API 자체 한도가 아니라 이 저장소가 자체로 건 가드**,
추정치 기반 — 실측이 아니라 "부분 확정"으로 표시돼 있음)을 주간
플랜(`agent_planner.dart:724-726`, 옷장 전체를 한 줄씩 프롬프트에
싣는 `catalog` 구성)이 넘으면 `HttpsError("invalid-argument",
"허용되지 않은 요청 형식입니다.")`로 실패한다

**피해 크기 — 확실하다.** 2026-08-11 실기기 실측(`task_hardening_

**52.8%**. 결측 임베딩(로드맵 5번, 보류된 것)과 달리 **사용자가
정상적으로 옷을 등록하기만 해도 언젠가 도달하는 상한**이고,
실패 메시지(`허용되지 않은 요청 형식입니다`)는 원인이 옷장
크기라는 걸 사용자에게 전혀 알려주지 않는다 — 겪으면 원인을
알 방법이 없는 실패다. 재검토 트리거("실측이 상한의 70%를
넘으면 재검토", 같은 문서:1731-1734)가 이미 등록돼 있으나 아직
안 넘어 재검토가 안 된 상태.

**[정정, 2026-08-14, task_weekly_plan_scale_v1.md 1단계(c)]** 위에서
인용한 `허용되지 않은 요청 형식입니다`는 **서버가 실제로 보내는
문구로는 정확하지만, 그 시점 사용자 화면에 실제로 뜨던 문구는

원문·`violations`을 전부 버리고 **완전히 다른 문구**("플랜
생성에 실패했어요. 잠시 후 다시 시도해주세요")로 바꿔치기하고
있었다 — 원인 불명 정도가 아니라 "재시도하면 될 수도 있다"는
**틀린 방향**의 안내였다(구조적 실패는 재시도해도 반복된다).
**우선순위도 재배치됐다** — 사용자 결정으로 상한 조정(F-1)보다
이 에러 문구 문제(F-2)를 먼저 다뤘다: 범용 catch는 상한 도달
여부와 무관하게 **모든 주간 플랜 실패**에 이미 걸리고 있어
당장 영향 중이었던 반면, 상한 도달은 현재의 2.16배(약 303벌)가
필요해 아직 멀었기 때문이다. **[해소, 2026-08-14]** 위 §4 결함표
"주간 플랜 에러 문구가 구조적 실패를 일시적 실패로 오도" 행
참고 — 원인별 분류·문구·계측을 갖췄다.

**수정 비용**: 상한 자체 조정(추정치 기반 배수를 다시 검토해야
함)은 근거를 다시 세우는 작업이라 중간 규모. 근본 해법(옷장
규모에 비례하지 않는 프롬프트 구성 — 요약·발췌 등)은 설계가
더 필요해 규모가 있다. **최소 완화책**(상한 근접 시 사용자에게
원인을 알리는 오류 메시지로 바꾸는 정도)은 상대적으로 저비용.

**측정 가능 여부 — 높음.** `request_shape.ts`에 이미 계측
인프라(`totalTextChars`, `text_too_long` 위반 플래그)가 있고,
118벌 기준 실측도 이미 확보돼 있다 — 재현·회귀 확인이 쉬운
축이다.

**[진행 상황, 2026-08-14]** 최소 완화책(에러 문구)은 해소됐다

근거와 접근 계측 설계는 위 §4 "주간 플랜 옷장 규모 상한" 행 참고.
근본 해법은 여전히 후보만(미착수). **인계**: 며칠 뒤

미수정(`task_hardening_v2.md`). 착수하지 않는다 — 후보 제시만.

### (G) 폴백 후보의 최종 추천 우위(Δ=9.85) — [신규, 2026-08-13] 착수하지 않음, 후보 제시만

**이미 §4(165행)에 등록된 결함을 다시 후보로 올린다** — 등록
당시("이번엔 고치지 않는다") 다음 우선순위가 실시간 임베딩이었는데
그게 이번에 보류됐으므로((C) 참고) 순서가 비었다.

`OutfitSelfEvaluator`의 최종 추천 선택(`outfit_self_evaluator.
dart:242-246`, `bestMatch`)이 순수 점수 비교만 한다 —
`judgeCandidate`(판정 경로, 이미 폴백 모델 점수 할인 처리됨)와
달리 **모델 출처(주 모델 `gemini-3.5-flash` vs 폴백
`gemini-3.1-flash-lite`)를 전혀 안 본다.** 통계적으로 확정된
격차: **Δ=9.85**(95% CI [7.05, 12.65], Welch t=-7.15, df=33.38,
p≈3.2×10⁻⁸, `task_selfeval_validity_v1.md`) — 폴백 모델이 점수를
체계적으로 더 후하게 준다는 뜻이라, 폴백 후보가 섞이면 최종
추천에서 구조적으로 유리해진다.

**피해 크기 — 이미 배포된 동작, 매 추천에 영향.** 능동 추천(새
옷)과 선제 추천/주간 플랜(TPO) 둘 다 이 선택 로직을
공유한다(`outfit_self_evaluator.dart:89`). 플래그로 막혀 있지
않다 — `withTextModelFallback`이 주 모델 실패 시 자동으로
폴백을 쓰므로, 폴백이 섞일 때마다 이 편향이 실제 추천 결과에
그대로 반영된다.

**[정정, 2026-08-14, task_selfeval_bestmatch_v1.md 1단계(c)]** 위
"매 추천에 영향"은 부정확했다 — 실측(agent_logs의
`candidate_evaluated` 이벤트 154건, 2026-07-25~08-13, 약 3주)에서
`verdictWithheld=true`(자기평가 경로에서 폴백이 응답한 사례)는
**0건**이었다. 정확히는 "폴백이 걸릴 때만 영향이고, 이 3주간
자기평가 경로에서 폴백이 한 번도 안 걸렸다"이다. **그럼에도
(F)보다 먼저 착수한 근거**: `task_selfeval_validity_v1.md` §6-가가
2026-08-12에 별도 측정 하네스로 5분 3초 구간 동안 텍스트 모델
1차 시도 20건 중 12건(60%)이 폴백으로 튄 사례를 실측해 뒀다 —
그 앞뒤 8/1~8/11 구간은 줄곧 0~4.9%였고 이 상승은 그 짧은 창에만
몰려 있었다(원인은 미확정: 외부 수요 급증 vs 하네스의 연속 호출
자체가 유발했을 가능성, 구분 안 됨 — 자기평가 경로의 호출이
아니라 같은 프록시(`callGeminiText`)를 쓰는 별도 측정 하네스의
호출이었다는 점도 함께 밝힌다). 즉 **평시엔 관측 0이지만
업스트림이 아플 때는 몰아서 튀며, 그 순간이 정확히 이 결함이
작동하는 조건과 겹친다** — 무작위로 희소한 게 아니라 실패가
집중되는 구간에 결함도 함께 집중되는 구조이므로, 희소성만으로
후순위로 미루지 않는다는 것이 오늘(2026-08-14)의 결정이다.

**수정 비용 — 상대적으로 국소적.** 판정 경로(`judgeCandidate`)가
이미 같은 문제(모델 출처 무시)를 푼 패턴이 있다 — 같은 할인
로직을 `bestMatch` 선택에도 적용하면 될 가능성이 높다. 다만
"할인 폭을 어떻게 정할지"(판정 경로와 같은 값을 쓸지, 다시
측정할지)는 별도 결정이 필요하다.

**측정 가능 여부 — 높음.** 이미 통계적으로 확정된 수치(Welch
t 검정, N=20/조건)가 있고, 수정 전/후 대조도 같은 방법론을
재사용하면 된다.

**상태**: 등록만, 실제 추천 코드에 그대로 남아 있다. 착수하지
않는다 — 후보 제시만.

**결정은 사용자에게 넘긴다** — (F)(G) 중 무엇을 다음으로 삼을지,
아니면 §4의 다른 결함이나 다른 로드맵 항목을 먼저 볼지는 여기서
정하지 않는다.
