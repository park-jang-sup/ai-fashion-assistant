## 2. 배경 — 왜 배타 구조가 두 결함을 상충시키는가

`findForTpo` 현재 흐름(outfit_matcher.dart 603~636행 기준):

```
scored  = topPerCategory(score > 0)      // 격식+무채색보너스 통과분
hasCore = required(상의·하의) ⊆ scored
hasCore → 조합은 scored에서만          → isFallback=false
!hasCore → 조합은 relaxed(전부)에서만   → isFallback=true
```

- 조합 재료의 출처가 **조합 전체 단위**로 scored 아니면 relaxed다.
- 게이팅 off(현행): 격식 미달 무채색이 0+1=1 > 0으로 scored 통과 → 오염.
- 게이팅 on(neutralGating): 포멀 태그에서 신발 전원 score 0 → scored에서
  신발 키 자체가 소멸 → hasCore는 상·하의로 성립하므로 조합은 scored에서
  만들어지고 **신발 없는 조합이 정상 경로로 출하**된다.

즉 결함의 뿌리는 보너스 값이 아니라 **출처 선택의 단위**다.

## 3. 설계

### 3-1. 새 정책 축: `fillOptionalFromRelaxed` (이름은 구현 시 재검토 가능)

`TpoMatchPolicy`에 `final bool fillOptionalFromRelaxed`(기본 false) 추가.
프리셋 `perCategoryFill = TpoMatchPolicy(gateNeutralBonus: true,
fillOptionalFromRelaxed: true)` — **이 축은 게이팅과 세트로만 의미가
있으므로** 프리셋은 묶되, 귀속 분리를 위해 단독 프리셋
`fillOnly = TpoMatchPolicy(fillOptionalFromRelaxed: true)`도 둔다
(forceEnumerated/enumeratedOnly와 같은 취지 — 축이 숨으면 귀속이 죽는다).

### 3-2. 동작 (플래그 on일 때만)

```
scored  = topPerCategory(score > 0)                  // 기존과 동일
hasCore = required ⊆ scored                          // 기존과 동일
hasCore인 경우:
  combosSource = scored의 얕은 복사
  for cat in policy.optionalCategories:
    if cat ∉ combosSource && cat ∈ relaxed:
      combosSource[cat] = relaxed[cat]                // 카테고리 단위 보충
      filledFromRelaxed.add(cat)
  combos = buildCombos(combosSource)
  optionalMissing = optionalMissingFrom(combosSource) ∪ filledFromRelaxed
  isFallback = false                                  // 필수는 진짜 적합이므로
!hasCore 경로: 기존과 동일(relaxed 전체 + isFallback=true)
```

주의점 셋.

- **relaxed 보충분의 내부 순서는 "게이팅 안 한 점수"로 매긴다.** 보충
  집합 안에서는 전원이 격식 미달이므로, 무채색 +1이 "무난한 차선 우선"
  이라는 원래 취지대로 작동하는 유일한 자리다. 구현상: 보충 채움용
  rankScore는 ungated 공식을 쓴다(게이팅은 scored 진입 판정에만 적용).
  이것이 이 재설계의 핵심 한 줄이다 — **보너스를 지우는 게 아니라
  필터에서 순서로 강등한다.**
- **`optionalMissing`의 의미 확장은 상위호환이다.** 기존 의미(풀에
  있으나 순도 0)와 새 의미(scored에 없어 relaxed에서 보충)는 사용자
  관점에서 같은 안내("이 카테고리는 격식에 딱 맞는 게 없어 차선으로
  채웠어요")로 수렴한다. 배지 문구는 그대로 재사용하고, 리포트에서만
  두 발생 경로를 분리 집계한다(표16).
- **required 카테고리는 보충하지 않는다.** 필수가 scored에 없으면 기존
  relaxed 전체 경로(isFallback=true)가 이미 정답이다. 보충은
  optionalCategories 한정 — 이래야 isFallback의 기존 의미(필수 격식
  미달)가 한 비트도 안 바뀐다.

### 3-3. 전이성·결정론 체크 (211bb94의 교훈 선반영)

보충 채움은 **정렬이 아니라 집합 선택**이므로 비교자 전이성 문제는 없다.
다만 relaxed 보충분과 scored 잔존분이 한 조합 생성기에 섞여 들어가므로,
`_buildCombosFromRanked`의 skeleton 정렬(우선순위→최고점)에서 보충
카테고리의 최고점이 ungated 점수라는 것이 **skeleton 경쟁의 동점 구도를
바꿀 수 있다**. maxSkeletonCategories=4라 4개 카테고리 전원이 들어가는
현행에서는 실해가 없지만, skeleton3 프리셋과 조합되면 다르다 — 표16에서
skeleton 구성 변화를 함께 찍는다.

## 4. 측정 — 코드보다 먼저 커밋할 것

`test/tpo_policy_report_test.dart`에 4개 표 추가(기존 번호 이어 표16~19).
전부 기존 컨벤션(로컬 items.json 없으면 skip, print 마크다운) 준수.

- **표16 — 재설계 A/B 골격**: 9태그 × {current, neutralGating,
  perCategoryFill}에 대해 (a) 1번 후보의 신발/아우터 포함 여부,
  (b) isFallback, (c) optionalMissing 발생 경로별(기존 순도0 / 신규 보충)
  건수, (d) 1번 후보 아이템의 진짜 적합 비율(조합 순도).
  **핵심 대조**: neutralGating 단독에서 신발이 사라지는 태그 수 vs
  perCategoryFill에서 0이 되는지.
- **표17 — 색상 변별력 회복**: 조합 순도가 오른 상태에서
  pairwiseColor를 다시 켰을 때(perCategoryFill+pairwiseColor) 1번 후보
  변화가 표8의 0/9에서 움직이는지. 5.8.8 "실효화 전제조건" 주장의 실측.
- **표18 — 커버리지 영향**: 표9/표14와 같은 방식으로 perCategoryFill의
  커버리지(현행 33.3% 대비). 보충 채움이 relaxed에서 끌어오는 아이템이
  기존 미노출군인지도 분리 집계.
- **표19 — recency 상호작용**: perCategoryFill × {0.0, 0.4} 감점 2×2.
  5.8.8이 경고한 의존 관계의 재설계판 — 보충 집합 내 순서에 recency가
  개입하는지, isFallback 발화가 감점에 따라 달라지는지(달라지면 안 된다

리포트 재현 코드는 이 표들 자체다(함정 28 원칙 — 수치는 저장소의
코드로 재현 가능해야 한다).

## 5. 사전 등록 — 라벨·판정 (결과 확인 전 확정, 이 절 수정 금지)

### 5-1. 구조 판정 (결정론, 라벨 불요)

기본값 전환의 **필요조건** 네 가지. 표16~19 확인 전에 등록한다.

1. 신발 포함률: perCategoryFill에서 9/9 유지 (neutralGating 단독의
   소멸이 재현되면 그 수치도 기록).
2. isFallback: 9태그 전부 current와 동일 (0/9 유지 — 재설계는 필수
   카테고리 판정을 건드리지 않으므로 달라지면 구현 결함이다).
3. 조합 순도(표16-d): current 대비 하락 없음, 포멀 3태그에서 상승.
4. 커버리지(표18): 33.3%에서 유의미한 하락 없음(-2%p 이내).

하나라도 미충족이면 **활성화하지 않고** 미충족 수치를 기록한다.

**[갱신 2026-08-06]** M2 완료 후 미리보기 실측(포멀 3태그 조합순도
0.75→0.75, 무변화)에서 조건 3 후반과 표18 기준선 불일치가 드러나 아래로
갱신한다. 원문(위 1~4)은 삭제하지 않고 이 블록이 그 위에 적용된다.

- **조건 3 개정**: "포멀 3태그에서 상승" 요구를 삭제하고 "조합 순도
  current 대비 하락 없음(전체 평균·태그별 모두)"만 남긴다. 근거: 포멀
  신발 보유 0벌(논문 5.14.2의 데이터 상한)이라 신발 슬롯 자체가 genuine
  적합을 낼 수 없고, 순도가 오르는 유일한 경로는 조건 1이 금지하는
  "카테고리를 통째로 뺀다"뿐이다 — 조건 1(포함 유지)과 원 조건 3 후반
  (순도 상승)이 동시 충족 불가능하게 오정의돼 있었다.
- **조건 4 프로토콜 명시**: 표18은 표14와 동일한 순차 누적 방식(9태그를
  정해진 순서대로 처리하며 앞선 태그의 1번 후보를 recentItemIds에
  누적)으로 계산한 값을 33.3%와 비교한다. 태그마다 독립 호출(recentItemIds
  없음)하는 방식의 수치는 별도 행으로 병기하되 33.3% 대조의 기준으로는
  쓰지 않는다 — 두 방식이 같은 정책·같은 옷장에서도 2.6배(12.6%
  vs 33.3%) 차이가 나, 방식을 못 박지 않으면 조건 4가 어느 수치와도
  비교 가능해져 사실상 무의미해진다.
- **조건 5 신설**: current↔perCategoryFill의 1번 후보 아이템 시그니처
  diff를 9태그 × {독립 호출, 순차 누적} 전부(18칸)에서 센다. 전 칸이
  diff 0이면 두 정책의 1번 후보가 완전히 같다는 뜻이므로 M4(블라인드
  라벨링)의 discordant 모수가 0이 되어 라벨링 자체가 공허하다 — 이
  경우 M4는 생략하고, 기본값 전환 여부는 구조 판정(조건 1·2·3·4)만으로
  사람이 판단한다.

### 5-2. 라벨 판정 (사람, 블라인드)

구조 판정 통과 시에만 진행. 7-b 인프라(tools/eval_harness) 재사용.

- **비교 단위**: 7-b와 동일하게 같은 (태그, 슬롯)의 1위 후보 쌍.
  단, 이번 재설계는 **카테고리 출현 자체가 갈리는** 쌍(현행에 신발이
  없고 재설계에 있는 경우)을 만든다. 이 쌍은 아이템 대 아이템 비교가
  불가능하므로 **별도 층**으로 분리해 "신발이 있는 조합 vs 없는 조합"
  중 어느 쪽을 입겠는가로 묻는다(조합 단위 비교가 정당한 유일한 경우 —
  슬롯이 하나만 다르기 때문).
- **판정 기준**: discordant 모수를 먼저 재고(표16에서 산출), n 확정 후
  7-b와 같은 절차로 임계 등록(양측 정확 이항검정, α와 방향 임계는 모수
  확정 시점에 위음성 논증과 함께 기록 — 7-b가 p<0.10/70%를 n=21에서
  도출한 것과 같은 방식, **라벨 착수 전**).
- **블라인드**: pairs.json에 정책 정보 배제, policy_map.json 사후 결합,
  좌우·순서 시드 무작위 — 기존 index.html 그대로.

### 5-3. 사전 등록하는 우려 (주시 항목)

- 보충 채움이 "격식 상황에 캐주얼 신발"을 **정상 경로(isFallback=false)**
  로 출하한다 — 이것이 개악인지의 최종 심급이 5-2 라벨이다. 다만
  현행도 같은 신발을 무채색 보너스로 출하하고 있으므로(표3: 포멀 신발
  22/22 구제), 라벨이 가를 것은 "출하 여부"가 아니라 "안내 문구가 붙은
  출하가 더 나은가"다.
- optionalMissing 배지의 발화 빈도가 크게 늘면(포멀 3태그 × 신발은
  확정 발화) 배지 피로 문제가 생길 수 있다 — 발화 수를 표16-c로 세고,
  문구·표시 정책은 별도 판단으로 넘긴다(이 작업 범위 밖).
