   `[STREAM-FALLBACK]` 안전장치가 매번 비스트리밍으로 강제 전환시키고 있었다.

### 2-9. A-1 프록시 하드닝 + 미검증 항목 2개 처리 (같은 날 후속 세션) — A-1 종결

미인증 거부는 검증 완료, 스트리밍 점진성은 조사 끝에 **미검증으로 종결**
(원인 미확정, 재조사 보류 — 아래 참고). 이걸로 A-1을 닫는다.

커밋: `5fa335a`.

**한 것 — `functions/src/index.ts`의 미포착 예외 4곳을 성격별로 분리해 던짐**
(전부 프레임워크의 디테일 없는 `internal`로 뭉개지던 지점들):

| 지점 | 성격 | 매핑 |
|---|---|---|
| 비스트리밍 `upstream.text()` 실패 | 본문 전송 중 연결 끊김 | `data-loss` |
| 스트리밍 `reader.read()` 실패 | 본문 전송 중 연결 끊김 | `data-loss` |
| 비스트리밍 `JSON.parse(text)` 실패(200인데 본문이 JSON 아님) | 응답 형식 문제 | `internal` + `{reason: invalid-json}` |
| SSE 청크 `JSON.parse(jsonStr)` 실패 | 응답 형식 문제 | `internal` + `{reason: invalid-json}` |

클라이언트 `gemini_service.dart`의 `_mapProxyException`도 함께 확장했다
(같은 커밋 — 서버만 고치면 새 코드/reason을 받을 곳이 없어 그대로
`FirebaseFunctionsException`으로 전파되고 `withTextModelFallback`의 세
갈래 중 아무 데도 안 걸린다):

- `data-loss` → `GeminiApiException(503, ...)`으로 재구성. 실제로 Gemini가
  503을 준 건 아니지만 "지금은 실패해도 재시도하면 될 수 있는 일시적 문제"라는
  성격이 같아 기존 `isRetryable` 판정에 태워 대체 모델로 넘어가게 한다.
- `details.reason == 'invalid-json'` → `FormatException`으로 재구성. 직접
  호출 시절 `_parseJsonObject`가 던지던 것과 같은 성격("1차 모델 응답이
  깨지거나 잘림")이므로 `withTextModelFallback`의 세 번째 갈래를 그대로 탄다.

스트리밍 경로(③④)의 실제 착지점은 어차피 `fitting_job_controller.dart`의
`catch (e)` → `[STREAM-FALLBACK]` → 비스트리밍 전체 재시도라 코드 선택의
실효는 크지 않지만, 로그에 원인(연결 문제 vs 형식 문제)이 남게 했다.

**검증됨:**

- `flutter analyze` 0건 / `flutter test` 140개. `functions`는 `npx tsc --noEmit` 통과(린트 스크립트 없음).
- **미인증 거부(지시서 함정 1)** — 인증 헤더 없이 `callGeminiText`를 직접
  호출해 실측:
  ```

  {"error":{"message":"로그인이 필요합니다.","status":"UNAUTHENTICATED"}}
  ```

**스트리밍 점진성 — 미검증으로 조사 종료:**

- **추가 후(재배포·재실측)** 2회: 243ms / 255ms

### 2-10. Gemini 3.6 Flash 교체 검토 — 하지 않기로 결정(2026-08-01)

3.6-flash는 `thinkingConfig.thinkingBudget: 0`을 HTTP 400으로 거부한다(단순
프롬프트로 격리 확인). 이 저장소는 3곳에서 이 설정을 쓴다(`extractAttributes`
800 / `extractSizeFromChart` 800 / `planWeeklyOutfits` 2000). thinking을 끌 수
없으면 같은 `maxOutputTokens` 예산을 thinking과 출력이 나눠 쓰는데, 실측
결과 thinking 소모가 386~766토큰으로 호출마다 크게 튄다(동일 이미지·설정
5회, 출력은 58~61로 안정). 800에서 1회 잘림(thinking 766) → FormatException
→ 폴백. 900~1600에서는 완결됐으나 편차 상단이 재현되면 900도 위험하다. 즉
상한을 올려 흡수하려면 요청당 토큰이 늘어 교체 동기 자체가 뒤집힌다.
`gemini-3.5-flash` + `thinkingBudget: 0`은 이 변수를 0으로 고정해 예산이
결정적이다. **성능이 아니라 안정성 때문에 유지한다.**

참고: 스타일링 분석 경로(`thinkingConfig` 미사용, 3000토큰)는 3.6에서
형식이 완전히 일치했고 thinking도 3.5보다 적게 썼다(1374 vs 2224, 단일
샘플). 이 경로만 따로 옮기는 것은 이론상 가능하나, 모델이 두 개로 갈리면
폴백·화이트리스트·검증이 전부 두 배가 되므로 하지 않는다.

폴백(`gemini-3.1-flash-lite` → `gemini-3.5-flash-lite`) 교체도 보류.
`gemini-3.5-flash-lite`가 `thinkingBudget: 0`을 받는지 미확인이며, 폴백
경로 3곳이 모두 이 설정을 쓴다. 폴백이 400으로 죽으면 안전망이 필요한
순간에 함께 무너진다. 현재 `gemini-3.1-flash-lite`는 실측 기록이 있다
(주간 플랜 55초 타임아웃 뒤 3.249초 200 완주, JSON 파싱 통과 — §2-8).

**나중에 같은 유혹을 느끼더라도 재조사하지 말 것** — 위 실측이 근거다.
3.6-flash 자체가 사양 변경(새 모델·새 기능)되어 `thinkingBudget: 0`을
다시 받아들이게 되지 않는 한 결론은 바뀌지 않는다.

바뀌었다** — 다만 두 계정의 `invokeCount`는 서로 다른 t0에서 출발한
별개 카운터라 이어 붙일 수 없다.

**선택지만 적어둔다, 결론은 내지 않는다** (논문 서술과 직결되는 판단이라
사용자가 결정):
1. 심사 계정을 새 기준으로 삼고 t0를 재정의한다.
2. 본인 계정으로 다시 로그인해 원래 표본을 이어간다 — 그러면 심사 계정
   쪽 축적이 거기서 멈춘다.
3. 두 계정을 별개 표본으로 취급하고 둘 다 보고한다.

`serverInvokeCount`(서버 계측)는 두 계정 다 스케줄러가 `users` 전체를
순회하며 매 사이클 기록하므로 로그인 상태와 무관하게 계속 쌓인다 — 끊긴
건 **`invokeCount`(기기 WorkManager 자연 발화, 로그인된 계정에서만
발생)** 쪽뿐이라는 점도 판단 시 참고할 것.

**[2] 8/7 등록 → 자동 발화에서 `successCount` 확인.** 사용자가 judge
계정으로 8/7 일정(`tpoTag=면접`) 등록 → Firestore `serverInvocationLog`를
20초 간격으로 폴링하며 대기(수동 호출 없이) → 다음 3시간 주기(8/4 03:46
UTC = 12:46 KST)에 자연 발화:

지금까지 `successCount`가 찍힌 사례는 전부 수동 호출
(`triggerScheduledCheckTest`, §2-13·§2-14)이었다 — **자연 발화에서 이
필드가 실제로 채워지는 걸 오늘 처음 확인했다.** 계측 공백 수정(§2-13 버그

**[검증 2] 백그라운드 탭(`onMessageOpenedApp`) — 통과.** 위 푸시를 받고

중 남은 건 `messageId` dedup 필터(§2-13 버그 4) 하나뿐.

**dedup 필터 — 미검증으로 남긴다, 억지 재현은 하지 않는다.** 재현 조건
(§2-13에서 가설로 남긴 "탭 직후 다른 실행 없이 바로 `adb install -r`")이
오늘도 자연 발생하지 않았다. 코드(`messageId` 파일 기반 dedup, 읽기/쓰기
실패 시 폴백은 "필터링 안 함")는 이미 배포돼 있고 최악의 경우도 필터
없음과 동일해 해가 없다. 인위적으로 재현하려면 탭 직후 즉시 재설치를
해야 하는데, 그러면 방금 만든 8/7 검증 결과(추천 문서·계측값)를 다시
흔드는 조작이라 하지 않는다 — 투자 대비 회수가 없다고 판단해 미검증인
채로 종결한다.

**표본 집계 시 주의 (누적, 4주 표본 해석 때 반드시 볼 것):**
- `serverInvokeCount`에는 수동 호출분이 섞여 있다. judge 계정 기준 8/2에
  8건, 8/3에 1건이 수동(`triggerScheduledCheckTest`, §2-13·§2-14
  재확인용 + [2] 조건 확인용). 8/4(오늘)는 수동 호출을 하지 않아 신규
  수동 0건.
- `serverTapCount`는 2026-08-02 이전 값에 오염분이 포함된다
  (`getInitialMessage()` 재소비,
  [firebase/flutterfire#10768](https://github.com/firebase/flutterfire/issues/10768)
  — §2-13 참고). dedup 필터 도입(2026-08-02) 이후 값만 신뢰하거나
  `serverInvocationLog`(서버가 실제로 보낸 횟수)와 대조해서 볼 것.

**D단계 판단 — 지금 시점엔 착수 불필요로 보인다, 최종 판단은 4주 표본
이후.** `task_server_v1.md`의 D단계 조건은 "푸시는 도달했는데 파이프라인이
완주하지 않는다"가 데이터로 확인될 때만이다. 오늘까지 관측된 것은 정확히
그 반대다 — 콜드스타트 탭([검증 1], §2-14)과 백그라운드 탭([검증 2], 위)
양쪽 다 푸시 도달 → 탭 → `runProactiveCheck` 완주 → 추천 생성까지 끊김
없이 이어졌다. 지금 근거로는 D가 필요하다는 신호가 없다 — 단, 이건 실기기로
손에 꼽을 만큼 확인한 결과지 4주 자연 표본으로 확인한 게 아니다. **최종
판단은 t0부터 4주 표본(§0 참고)이 쌓인 뒤로 미룬다.**

### 2-16. 신발 카테고리 격식 판정 무력화 — 평가 하네스 설계 조사 중 발견 (2026-08-04)

**하네스 설계와 무관한, 엔진 자체의 발견이라 별도로 남긴다.** 평가 하네스
(b) 표본 설계를 위해 실제 옷장(103벌)으로 태그×카테고리 동점 규모를
전수 실측하던 중 나왔다 — 조사만 했고 코드는 손대지 않았다.

**실측 — 신발만 9개 태그 전부에서 동점 100%다:**

| 태그 | 상의 동점률 | 하의 동점률 | 아우터 동점률 | 신발 동점률 |
|---|---|---|---|---|
| 출근/데이트/모임 | 13% | 24% | 5% | **100%** |
| 결혼식/면접/경조사 | 14% | 29% | 6% | **100%** |
| 여행/운동/일상 | 71% | 57% | 75% | **100%** |

상의·하의·아우터는 태그(포멀 성격)에 따라 5~75%로 갈리는데(무채색 편중과
옷장 스타일 분포가 만든 자연스러운 패턴), **신발만 태그와 무관하게 항상
100%다.** 질적으로 다른 상태.

**원인 — 정책 버그가 아니라 실데이터가 그렇다.** `gemini_service.dart`의
속성 추출 프롬프트(592행)는 카테고리 구분이 없는 단일 프롬프트라 신발만
다르게 취급하는 코드가 없음을 먼저 확인했다. 신발 22벌의 실제 태그를
전부 열어보니 **22벌 전부 스니커즈·러닝화·샌들·어글리슈즈뿐이고 로퍼·
옥스포드·구두 등 격식 있는 신발이 단 하나도 없다.** `formality` 100%
"캐주얼", `isNeutralColor` 100% true도 이 태그와 정확히 일치하고, `users`
프로필의 `preferredStyles: ["캐주얼"]`과도 일관된다(상의/하의/아우터는
포멀 0벌이지만 세미포멀은 각각 4/5/1벌 있어 신발만 완전 균일하다는 대조로
확정). **결론: 이 사람은 격식 있는 신발을 실제로 한 켤레도 안 갖고 있다 —
정책이 신발 속성을 잘못 읽는 게 아니라, 읽을 다양성 자체가 데이터에 없다.**

**부수 관측 — 옷↔옷 궁합 경로(`findCandidateMatches`)도 동일 패턴.**
트리거 87개(속성 있는 전 아이템) 전부(100%)가 상위 3후보 동점이었다.
신발에 국한된 문제가 아니라 이 옷장의 무채색 편중이 TPO 매칭·궁합 매칭
두 경로 모두에서 판별력을 거의 없애고 있다는 뜻 — 지금은 기록만 하고
손대지 않는다.

**영향 범위**: 평가 하네스 설계(§b 이후)에 참고용으로만 쓴다 — 신발
카테고리는 어떤 정책을 넣어도 동점 구조 자체가 안 바뀔 가능성이 높다는
뜻이라, 신발이 낀 조합의 라벨은 "이 정책이 신발을 잘 골랐는가"를 검증하는
용도로는 약하다.

### 2-17. 평가 하네스 판정 기준 — 라벨링 착수 전 사전 합의 (2026-08-04)

**평가 하네스(로드맵 7번, §7 이후 로드맵 — 실제 위치는 이제 아래 §3 참고)
설계 조사 (a)~(e) 진행 중 확정한 판정 기준. 라벨은 아직 한 건도 안 붙였다
— 순서가 중요하다(`task_formality_policy_ab.md`의 실패를 반복하지 않기
위해).**

당초 제안한 "동점 집합 내 절대 비율 +5%p"를 실측 n으로 검산한 결과 전량
기각됐다 — 동점 집합의 실제 결정 지점(TPO 태그)은 9개뿐이라 n=9에서 5%p는
0.45건(≒0건)이고, 이항분포로 우연히 ±5%p 벗어날 확률이 n=9에서 100%,
n=150(라벨링 목표 전체)으로도 22.1%였다(양측, p0=0.5 정확계산). **절대
비율 임계값은 이 규모에서 통계적으로 무의미해 폐기한다.**

**대체 — 쌍대비교(부호검정/sign test)로 확정:**

- 판정 대상: `TpoMatchPolicy.current`와 제안 정책(임베딩 타이브레이크)이
  **다른 조합을 고른 경우만** 필터링(discordant pairs).
- 하나의 숫자: 그 안에서 제안 정책이 "입겠다" 라벨을 받은 비율.
- **나아짐의 기준(사전 합의, 결과 확인 전): 양측 부호검정 `p<0.10`이고
  방향이 우연(50%)보다 뚜렷이 유리(≥70%)한 경우.** `p<0.05`가 아니라
  `p<0.10`인 이유를 여기 명시한다 — discordant n=15~20 규모(반나절
  라벨링 예산 안에서 현실적으로 확보 가능한 범위)에서 `p<0.05`를 넘으려면
  승률 80% 이상이 필요한데(실측: discordant 15/승12=80%→p=2.1%,
  15/승11=73%→p=11.8%), 이건 요구하는 효과크기가 너무 커서 진짜 개선을
  놓칠(false negative) 위험이 크다고 판단했다. `p<0.10`은 완화이지 결과를
  보고 정한 게 아니다 — **이 문단 자체가 그 사전 합의의 증거로 남긴 것**이다.
- 동점 밖(비동점 슬롯)에서 1번 후보가 바뀌면 즉시 과도 신호로 취급
  (`task_formality_policy_ab.md` §4의 "과도 신호" 패턴 재사용).
- discordant 모수를 9(TPO 태그)보다 키우기 위해 `findCandidateMatches`
  트리거 기반 조합을 추가로 쓴다 — 실측 결과 트리거 87개(속성 있는 전
  아이템) **전부(100%)가 상위 3후보 동점**이라(§2-16 "부수 관측" 참고)
  트리거 선별 자체는 병목이 아니고, 카테고리·속성 다양성 확보만 신경
  쓰면 된다.

**아직 안 정한 것**: 라벨링 도구·저장 경로((c) 나머지), discordant 트리거
구체적 선정 목록, 라벨링 세션 분할(무작위 순서·세션당 40~50개·10%
재검사로 신뢰도 측정하는 방향까지는 합의, 세부 구현 미정).

### 2-18. 로드맵 7번 재정의 — 스코어링 해상도가 타이브레이크 전제를 깬다 (2026-08-04)

**근거 — 실측 세 가지.**

판정이 아니라 동점 집합 안의 순서에만 쓴다"였고, 이건 동점이 드물고
국소적이라는 전제 위에서만 "유사도≠궁합" 원칙과 충돌하지 않는다. 그런데
scored 항목의 절반(신발은 전부)이 이미 동점이면, 그 51%(신발 100%) 구간에서
**현재 TPO 점수는 최종 선택에 기여하는 정보량이 0이고 코사인만 정보를
준다.** 코드 경로 라벨은 여전히 "동점 시 타이브레이크"지만, 실제 정보
기여도로 보면 **그 구간에서 코사인이 궁합을 판정하는 것과 동일한 효과를
낸다** — 이 저장소가 명시적으로 금지해온 바로 그 상태.

**하네스 해석 문제.** 이 상태에서 7-b(평가 하네스)를 먼저 돌리면,
discordant pair(정책 A/B가 다른 조합을 고른 경우)의 상당수가 "원래도
무의미했던 동점이 다른 무의미한 방식(코사인)으로 깨진 것"일 수 있어,
부호검정이 유의하게 나와도 "타이브레이크가 좋다"인지 "해상도가 낮아 아무
재배열이나 그럴듯해 보인다"인지 구분이 안 된다. **7-a가 7-b보다 먼저인
이유가 이것.**

**§7(이후 로드맵, `handoff_2026-08-01.md`와 별개로 사용자가 관리하는
문서)의 원래 표(5/7/8)에서 5번·8번은 이 판단과 무관하게 그대로 유효하다
— 바뀐 건 7번의 내용뿐이다.**

**7-a 조사 결과(같은 날, 조사만·코드 미작성). 1번 답을 조사하다가 최초
초안이 틀렸다는 걸 발견해 정정했다 — 그 경위까지 남긴다.**

1. **해상도를 올릴 데이터 근거가 있는가 — 있다, 단 처음 생각보다 복잡하다.**
   `ClothingAttributes`(`color/style/pattern/formality/fit/tags` 6종) 중
   `TpoMatchPolicy`의 후보 생성 스코어링(`OutfitMatcher.findForTpo`/
   `findCandidateMatches`)이 실제로 쓰는 건 여전히 `formality`와 `color`
   (무채색 여부)뿐임을 확인(`lib/services/outfit_matcher.dart` 전수 grep,
   `style`·`fit`·`tags` 참조 0건). **정정 — `pattern`은 완전 미사용이
   아니다**: 색상 궁합 점수(`_colorScore`)에서 "같은 색상군+같은 밝기인데
   패턴이 다르면 애매한 깔맞춤 감점을 면제"하는 좁은 용도로 쓰인다(363~365행,
   747e9a9 커밋). 일반 스코어링 축은 아니고 예외 처리 하나뿐.
   **더 중요한 정정 — `style`은 "미구현"이 아니라 "다른 곳에서 이미
   쓰이고 있다".** `OutfitSelfEvaluator`(자기평가 루프, 후보 생성 *이후*
   단계)가 Gemini에게 매 후보를 `[격식적합]/[색상조화]/[스타일통일]`
   세 축으로 1~100점 채점시킨다(`gemini_service.dart:741-743`) — 즉
   style은 이미 파이프라인에 들어와 있다, 다만 ① `OutfitMatcher`의
   결정론적 후보 *생성·1차 정렬*이 아니라 ② Gemini의 LLM 판단으로 후보
   *생성 이후*에 평가되는 자리다. `fit`·`tags`는 `lib/` 전체(서비스·
   상수 레이어)에서 모델 필드 선언 외엔 참조가 0건 — 이 둘만 진짜
   미사용이다.
2. **formality 3단계·무채색 2단계 자체를 세분화할 근거는 약하다(원래
   판단 유지).** `formality`는 캐주얼/세미포멀/포멀 3종만 존재하는
   Enum이고 데이터도 이 3종뿐이라 더 잘게 쪼갤 원본이 없다 — 포화 상태.
   무채색도 이진 축이 자연스러워 세분화 여지가 적다.
3. **`style`을 `OutfitMatcher`의 결정론적 스코어링에 새로 넣으면
   해상도가 오르긴 하겠지만, 이미 있는 [스타일통일] Gemini 평가와
   같은 신호를 두 번 쓰는 셈이라는 게 이번에 드러난 새 논점이다.**
   정확한 distinct-값 증가폭은 style을 점수식에 넣어 재계산해야
   나온다(코드 변경 없이 시뮬레이션만으로 가능 — 다음 조사 항목으로
   남긴다). 단 "안 쓰던 신호를 쓴다"가 아니라 "다른 자리(LLM 후처리)에서
   쓰던 신호를 앞자리(결정론적 사전 필터)로 옮기거나 중복시킨다"는
   프레이밍이 더 정확하다 — 후자로 가면 self-evaluator의 [스타일통일]
   점수와 새 결정론적 style 점수가 서로 다른 answer를 낼 때 어느 쪽을
   따를지도 같이 정해야 한다.
4. **7-a·7-b 순서가 다시 얽히는 문제 — 판단은 유지, 근거는 위 3번으로
   더 분명해졌다.** 해상도만 올리고 라벨 검증을 안 하면 "세분화됐다"와
   "그 세분화가 실제 선호와 맞다"의 간극이 다시 생긴다
   (`task_formality_policy_ab.md`가 겪은 함정과 같은 모양). **7-a는
   "해상도가 오르는가"(라벨 불필요, 순수 계산)까지만 검증하고, "그
   방향이 옳은가"는 7-b(하네스)로 넘긴다** — 하네스 설계((a)~(c))는
   그대로 재사용 가능(대상이 "임베딩 타이브레이크"에서 "확장된
   스코어링"으로 바뀔 뿐). **이 판단이 맞는지, 그리고 self-evaluator와의
   신호 중복을 어떻게 풀지는 사용자가 확정할 것 — 여기서는 조사 결과만
   제시.**

### 2-19. 7-a 계속 — style 보류 결정 + 해상도 재조사 + 동점 그룹 코사인 실측 (2026-08-04)

**판단(사용자) — style을 `OutfitMatcher` 결정론적 스코어링 앞단으로
옮기지 않는다.** 근거: ① 지금 구조가 "후보 생성(결정론적, 격식·색상) →
후보 평가(Gemini, `[스타일통일]`·`[색상조화]`·`[격식적합]`)"로 역할이
갈려 있는데, style을 앞단에 넣으면 같은 신호가 이중 가중된다. ② 자기평가는
**조합 전체**를 보고, 후보 생성은 **아이템 단위**다 — "이 상의의 style"과
"이 조합의 스타일 통일감"은 다른 질문이라, 앞단에 넣으면 후자를 전자로
근사하게 돼 정보 손실이 생긴다.

**style이 막혀 나머지 후보를 재조사(조사만, 코드 미작성):**

**1. formality 3단계 세분화 여지 — 없다, 데이터 상한 확정.** 전체
카테고리 합산 formality 분포 실측: **캐주얼 76 / 세미포멀 10 / 포멀 0(!)
/ null 1.** 옷장 전체(103벌)에 **포멀 아이템이 단 한 벌도 없다.**
`legacyFormalityFitScore`의 diff는 이론상 0/1/2 세 값이지만, 아이템
rank가 실질적으로 {0,1} 두 값만 존재해 어떤 태그를 기준으로 삼아도 diff는
사실상 2종류만 실현된다. **이건 정책 문제가 아니라 데이터 상한이다** —
formality 축을 아무리 정교하게 다듬어도 이 옷장에서는 못 늘어난다.

**2. 무채색 보너스 3단계(무채색/저채도/고채도) — 데이터가 지지하지
않는다.** `color_taxonomy.dart`엔 이미 family(9종 유채색군)·brightness
(밝기 3단)·temperature 축이 있어 이론적으로는 세분화 여지가 있어
보이지만, 실제 옷장 색상 분포를 보면 **전체 87벌(4개 아웃핏 카테고리) 중
유채색은 11벌(13%)뿐**이고 그 11벌도 6개 family(브라운·블루·스카이블루·
옐로우·핑크·와인)에 흩어져 family당 1~4벌이다. 동점 덩어리의 실체는
76벌짜리 **무채색** 버킷 쪽인데, 무채색을 더 쪼개려면(예: "블랙이 베이지
보다 더 격식 있어 보인다") 현재 택소노미에 없는 새 축을 발명해야 한다 —
데이터가 이미 뒷받침하는 세분화가 아니라 만들어 넣는 세분화라는 점에서
1번과 성격이 다르다.

**3. fit·tags — fit은 상관 없음(반직관적, 실측으로 기각), tags는
필터링 없이는 노이즈가 더 많다.**
- `fit`×`formality` 교차표: 오버사이즈 36벌 중 세미포멀 4벌(11%),
  레귤러 43벌 중 세미포멀 6벌(14%) — **거의 같은 비율.** "슬림/레귤러가
  더 격식 있어 보인다"는 직관과 달리 이 옷장에서는 fit이 formality를
  전혀 가르지 못한다 — 상관 가설 기각.
- (부수 발견, 별건) `fit` 값에 `"레귤러"`와 `"레ギュラー"`(카타카나
  섞인 오타/인코딩 글리치로 보임)가 별개 문자열로 3벌 섞여 있다 —
  fit을 문자열 키로 그대로 쓰면 조용히 값이 갈린다. 지금은 기록만.
- `tags` 원본 샘플을 직접 읽어보니 계절("여름"/"봄가을"/"사계절")·
  소재("린넨혼방"/"울혼방") 같은 **TPO와 무관한 태그**와, "셔츠"/
  "슬랙스"/"트레이닝팬츠"처럼 **격식과 plausible하게 연관된 태그**가
  섞여 있다. 지적하신 대로 "린넨이라서"는 계절이지 TPO가 아니다 — 쓰려면
  전체 tags를 그대로 넣지 말고 격식 연관 키워드만 큐레이션한 부분집합이
  필요하다(설계 작업이 더 든다는 뜻, 지금은 목록만 확인).

**4. 동점 그룹 내부 코사인 유사도 실측 — 균질하지도, 균일하게 판별
실패도 아니다. 규모에 따라 갈린다.**

`embeddings.json`(FashionCLIP 512-dim, 103벌)으로 각 (태그,카테고리)
동점 그룹의 내부 평균 코사인 유사도를, 같은 카테고리 내 무작위 쌍
베이스라인과 대조했다:

| 그룹 | 동점벌수 | 그룹내 평균코사인 | 카테고리 랜덤베이스라인 | 차이 |

| 포멀·세미포멀 계열 상의(출근/데이트/모임/결혼식/면접/경조사) | 3 | 0.7390 | 0.5524 | **+0.1867** |

**해석 — 두 가지 다른 상태가 섞여 있다:**
- **작은 동점 그룹(포멀 계열, 3~5벌)**: 랜덤보다 뚜렷이 유사(+0.13~

  가능해서 우열이 무의미하다"는 해석과 맞아떨어진다.
- **큰 동점 그룹(캐주얼 계열 12~17벌, 그리고 신발 22벌 전부)**:
  랜덤과 거의 같거나(캐주얼 계열, +0.01~0.03) **정확히 같다(신발,
  -0.0008 — 통계적으로 무차별).** 이건 "옷장이 균질해서"가 아니라
  **"임베딩으로는 뚜렷이 다른 신발들인데 지금 정책(격식+무채색만 봄)이
  전혀 못 가른다"는 뜻이다** — §2-16에서 확인한 "신발 22벌이 격식

  시각적으로 다양하다")는 서로 다른 층위의 사실이라 모순이 아니다.
  라벨(카테고리형 속성)이 균일해도 임베딩(시각 정보)은 다양할 수 있다.

**요약 — 51% 동점 중 일부는 "진짜 대체 가능"(정보 손실 없음), 일부는
"정책이 못 봄"(정보 손실 있음), 그리고 그 비중이 그룹 크기·태그 성격에
따라 갈린다는 게 실측으로 확인됐다.** 신발이 가장 극단적으로 후자 쪽에
있다. 결론은 내지 않는다 — 이 데이터를 근거로 7-a의 다음 방향(해상도를
어디에 얼마나 투자할지, 혹은 안 할지)은 사용자가 판단한다.

### 2-20. 7-a 종료 — 결론 세 가지 + 7-b 재설계 (2026-08-04)

**결론 1 — 스코어링 해상도는 올리지 않는다.** §2-19의 조사 다섯 갈래
전부가 부정적이었다:

| 후보 | 판정 | 근거 |
|---|---|---|
| formality 세분화 | 불가 | 포멀 0벌 — 데이터가 정한 상한, 정책 문제 아님 |
| 무채색 3단계 | 불가 | 유채색 11벌뿐, 76벌 무채색 버킷을 쪼갤 축이 택소노미에 없음 |
| fit 추가 | 불가 | formality와 상관관계 실측 기각(오버사이즈 11% vs 레귤러 14%, 사실상 동일) |
| tags 추가 | 보류 | 계절·소재 노이즈와 격식 연관 키워드가 섞여 큐레이션 없이는 사용 불가 |
| style 추가 | 배제 | §2-19 — self-evaluator(`[스타일통일]`)와 신호 중복, 아이템 단위/조합 단위 질문이 다름 |

**남은 세분화 여지가 없다 — 없는 신호를 억지로 만들어내지 않는다.**
`task_server_v1.md`류 지시서가 반복해온 "폴백은 아무것도 하지 않음"
원칙과 같은 결의 판단.

**결론 2 — 동점의 성격이 둘로 갈린다. 이번 조사의 핵심 발견.**

- **(a) 실제 대체 가능** — 포멀계열 소형 그룹(3~5벌), 임베딩 유사도가
  랜덤 대비 **+0.13~+0.19**. 정책이 못 가르는 게 아니라 진짜 닮은
  옷들이다 — 무작위 선택이 정당하고 타이브레이크가 불필요한 영역.
- **(b) 판별 실패** — 신발 22벌(9개 태그 전부 동점), 임베딩 유사도가
  랜덤 대비 **-0.001**(무차별). 격식·색상 라벨은 균일하지만
  FashionCLIP은 서로 다르게 본다 — 구분 가능한 정보가 실재하는데
  정책이 그 정보를 안 보고 있는 영역.

**결론 3 — 임베딩 타이브레이크는 정당하다, 단 근거가 바뀐다.**
원래 근거("동점 안의 순서만 정하므로 유사도≠궁합과 충돌 안 함")는
동점이 드물다는 전제에 기대고 있었는데, 51% 동점 상태에서는 이 논리가
약했다(§2-18). **새 근거: (b) 유형에서 임베딩은 격식·색상 축이 못 보는
정보를 실제로 갖고 있다는 것이 실측으로 확인됐다.** 즉 타이브레이크는
"무작위를 대체하는 것"이 아니라 **"결정론적 축이 놓친 정보를 보조
축으로 회수하는 것"**이다 — 궁합을 코사인이 새로 판정하는 게 아니라,
이미 있는데 못 보던 정보를 드러내는 것이라는 재정식화. 단 **(a)
유형에서는 여전히 무의미하다** — 진짜 닮은 옷들 사이의 코사인 순서는
노이즈이므로, 거기서 순서를 바꾸는 건 정보 회수가 아니라 그냥 잡음
주입이다.

**다음 — 7-b(평가 하네스) 재설계, (a)/(b) 층 분리. 라벨링 착수 전
사전 확정(§2-17과 같은 원칙 — 결과 본 뒤 기준을 바꾸지 않는다):**

- 라벨링 대상을 **(a) 유형과 (b) 유형에서 각각 별도로** 뽑는다(기존
  discordant-pair 설계에 층 하나 추가 — 표본 크기·부호검정 설계
  자체는 §2-17 그대로 재사용, 유형별로 따로 집계할 뿐).
- 판정도 유형별로 따로 낸다 — 하나의 숫자가 아니라 (a)용 하나,
  (b)용 하나.
- **기대(사전 등록):**
  - **(b)에서는 proposed(임베딩 타이브레이크)가 이겨야 한다** —
    §2-17의 부호검정 기준(`p<0.10`, 방향 ≥70%) 그대로 적용.
  - **(a)에서는 차이가 없어야 한다.** proposed가 (a)에서도 유의하게
    이기면, 그건 "정보 회수"가 아니라 **코사인이 궁합을 판정하고
    있다는 신호** — 즉시 과도 신호로 잡는다. §2-17의 "동점 밖에서
    1번 후보가 바뀌면 과도 신호"와 같은 성격의 안전장치를 동점 안에서도
    하나 더 두는 것.
- discordant 모수 확장(§2-17의 `findCandidateMatches` 트리거 방식)도

## 4. 반드시 알아야 할 함정 (누적)

이전 판의 4-1~4-8 전부 유효 — **단 4-5는 정정 필요, 4-16 참고.**

### 4-9. Firebase CLI `--only storage:rules`는 문법이 틀렸다

Firestore는 `firestore:rules`처럼 콜론 뒤에 하위 리소스를 쓰지만, Storage는
콜론 뒤가 **배포 타깃 이름**이다. `firebase deploy --only storage`(콜론 없이)가
맞는 문법.

### 4-10. `firebase functions:artifacts:setpolicy`의 기본 리전은 `us-central1`

함수를 다른 리전(이 프로젝트는 `asia-northeast3`)에 배포했으면
`--location asia-northeast3`를 명시해야 한다. 안 그러면 "리포지토리가 없다"고
엉뚱한 리전을 보고한다.

### 4-11. Cloud Functions Callable의 예외 매핑은 서버가 명시해야 한다

`fetch`가 예외(어보트·네트워크 실패)를 던지고 안 잡으면 Functions 프레임워크가
디테일 없는 `internal`로 뭉갠다. 클라이언트가 원인별로 다르게 처리(타임아웃→폴백,
인증 실패→그대로 전파 등)해야 한다면, 서버에서 반드시 `HttpsError(code, message,
details)`로 명시적으로 던져야 한다 — 이번 A-1에서 실제로 겪은 버그.

**추가(2026-08-01 후속 하드닝, §2-9):** "예외를 안 잡는 지점을 잡아서 전부
`internal`로 던지는 것"은 이 함정을 절반만 고친 것이다. 클라이언트의
`withTextModelFallback`은 `TimeoutException`/`GeminiApiException(isRetryable)`/
`FormatException` 세 갈래로만 재시도를 판단하므로, 서버가 뭉뚱그린 `internal`을
던지면 여전히 아무 갈래에도 안 걸려 폴백이 무력화된다. **성격이 다른 실패는
다른 코드/details로 구분해서 던져야** 클라이언트가 골라 받는다 — 이 저장소가
정한 컨벤션:
- 본문 전송 중 연결 끊김(바디를 다 못 읽음) → `HttpsError("data-loss", ...)`
- 200인데 본문이 유효 JSON이 아님(응답 형식 문제) → `HttpsError("internal", ..., {reason: "invalid-json"})`
- 업스트림이 실제 오류 상태를 준 경우 → `HttpsError("internal", ..., {upstreamStatus, upstreamMessage})`(기존 컨벤션)

새 코드/reason을 추가할 때는 **클라이언트 `gemini_service.dart`의
`_mapProxyException`도 같은 커밋에서 함께 확장**해야 한다. 서버만 고치면
클라이언트가 그 코드를 모르는 채로 그냥 `FirebaseFunctionsException`을
전파해 아무 갈래에도 안 걸리는 건 마찬가지다.

### 4-12. `cloud_functions` 스트리밍 청크는 `Map<Object?, Object?>`로 온다

플랫폼 채널을 거친 `Chunk.partialData`를 `as Map<String, dynamic>`으로 캐스트하면
런타임에 항상 실패한다. `Map<String, dynamic>.from(x as Map)`으로 변환할 것.
`jsonEncode`는 이 문제가 없다(키의 런타임 타입만 봄).

### 4-13. `cloud_functions`는 `^5.4.1`로 고정, 6.x 올리지 말 것

6.x는 `firebase_core` 4.x 세대와 짝이라(pub BoM 기준) 올리면
core/firestore/auth/storage/app_check 전부 메이저 업그레이드가 딸려온다.
5.4.1부터 스트리밍 Callable(`.stream()`)이 있어 지금 세대로 충분하다.

### 4-14. adb 경로

이 개발 환경엔 `adb`가 PATH에 없다. 전체 경로:
`C:\Users\hse09\AppData\Local\Android\Sdk\platform-tools\adb.exe`

### 4-15. `google-services` 플러그인이 꺼져 있으면 App Check 문제가 조용히 숨는다

플러그인을 안 켠 상태(A-1·A-2 내내)에서는 `Firebase.initializeApp()`이
`firebase_options.dart`로 프로그래매틱하게만 되고, App Check SDK는 아예
네트워크 호출을 안 나갔다 — 그래서 "GCP 프로젝트에서 App Check API가
한 번도 활성화된 적 없다"는 사실이 안 보였다. B단계에서 플러그인을 켜자
Firebase 초기화가 정상화되고 App Check가 실제로 호출을 시도하면서 처음
드러남(§2-8 정정 참고). **교훈**: Firebase 하위 기능(App Check 등)의
문제 유무는 초기화 경로가 완전한 상태에서만 정확히 관측된다 — 프로그래매틱
초기화만으로 "일단 앱은 켜지니 문제없다"고 판단하면 이런 종류의 잠복
결함을 놓칠 수 있다.

### 4-16. 정정 — `debugPrint`는 이 프로젝트 릴리스 빌드에서 찍힌다

이전 판(4-5)의 "릴리스에서 `debugPrint`가 안 찍힌다"는 **이 저장소의 현재
빌드 설정 기준으로 부정확하다.** B단계 FCM 진단(§2-12) 중 릴리스 APK의
logcat에서 `[FCM-DIAG]`·`[PLAN]`·`[WEATHER]`·`[TIMING]` 태그 `debugPrint`
출력이 전부 정상적으로 찍히는 것을 실측으로 확인했다.

**근거**: `android/app/build.gradle.kts`의 `release` 빌드 타입에
`isMinifyEnabled`(R8/ProGuard)가 **설정돼 있지 않다**(기본값 false) —
로그를 지우는 축소·난독화가 안 걸린다. Flutter SDK의 `debugPrint`
구현(`packages/flutter/lib/src/foundation/print.dart`) 자체도
`kReleaseMode`/`kDebugMode`로 게이팅되어 있지 않다 — 기본값
`debugPrintThrottled`는 빌드 모드와 무관하게 항상 출력한다. 앱 코드에서
`debugPrint = ...`로 재정의해 무음 처리한 곳도 없다(grep 확인, 0건).

**4-5가 왜 틀렸다고 기록됐는지는 확인 못 함** — 다른 세대의 빌드 설정
(R8 활성화 등)에서 실제로 관측됐던 것일 수도 있고, 애초에 오기였을 수도
있다. **지금 확실한 것은 이 저장소의 현재 설정(R8 꺼짐)에서는 찍힌다는
것.** 나중에 R8/minify를 켜면(로드맵에 후보로 남아 있음) 이 결론이
다시 뒤집힐 수 있으니, 그때 다시 확인할 것.

**결론 — 진단 로그(`[FCM-DIAG]` 등)는 지우지 않고 남긴다.** 이번이
"조용한 실패"를 관측할 유일한 수단이었다 — 함수 로그·firestore 규칙·
SHA-1·API 활성화 전부 정상인데 원인을 못 찾다가, 결국 이 로그들로
"어디까지 갔는지"를 구분해 좁혔다. 같은 종류의 조용한 실패가 재발하면
같은 로그가 다시 필요해진다.
