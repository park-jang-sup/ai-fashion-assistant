### 2-9. A-1 프록시 하드닝 + 미검증 항목 2개 처리 (같은 날 후속 세션) — A-1 종결

미인증 거부는 검증 완료, 스트리밍 점진성은 조사 끝에 **미검증으로 종결**
(원인 미확정, 재조사 보류 — 아래 참고). 이걸로 A-1을 닫는다.

커밋: `5fa335a`.

**한 것 — `functions/src/index.ts`의 미포착 예외 4곳을 성격별로 분리해 던짐**
(전부 프레임워크의 디테일 없는 `internal`로 뭉개지던 지점들):

| 지점 | 성격 | 매핑 |
|---|---|---|
| 비스트리밍 `upstream.text()` 실패 | 본문 전송 중 연결 끊김 | `data-loss` |
| 스트리밍 `reader.read()` 실패 | 본문 전송 중 연결 끊김 | `data-loss` |
| 비스트리밍 `JSON.parse(text)` 실패(200인데 본문이 JSON 아님) | 응답 형식 문제 | `internal` + `{reason: invalid-json}` |
| SSE 청크 `JSON.parse(jsonStr)` 실패 | 응답 형식 문제 | `internal` + `{reason: invalid-json}` |

클라이언트 `gemini_service.dart`의 `_mapProxyException`도 함께 확장했다
(같은 커밋 — 서버만 고치면 새 코드/reason을 받을 곳이 없어 그대로
`FirebaseFunctionsException`으로 전파되고 `withTextModelFallback`의 세
갈래 중 아무 데도 안 걸린다):

- `data-loss` → `GeminiApiException(503, ...)`으로 재구성. 실제로 Gemini가
  503을 준 건 아니지만 "지금은 실패해도 재시도하면 될 수 있는 일시적 문제"라는
  성격이 같아 기존 `isRetryable` 판정에 태워 대체 모델로 넘어가게 한다.
- `details.reason == 'invalid-json'` → `FormatException`으로 재구성. 직접
  호출 시절 `_parseJsonObject`가 던지던 것과 같은 성격("1차 모델 응답이
  깨지거나 잘림")이므로 `withTextModelFallback`의 세 번째 갈래를 그대로 탄다.

스트리밍 경로(③④)의 실제 착지점은 어차피 `fitting_job_controller.dart`의
`catch (e)` → `[STREAM-FALLBACK]` → 비스트리밍 전체 재시도라 코드 선택의
실효는 크지 않지만, 로그에 원인(연결 문제 vs 형식 문제)이 남게 했다.

**검증됨:**

- `flutter analyze` 0건 / `flutter test` 140개. `functions`는 `npx tsc --noEmit` 통과(린트 스크립트 없음).
- **미인증 거부(지시서 함정 1)** — 인증 헤더 없이 `callGeminiText`를 직접
  호출해 실측:
  ```
  HTTP/1.1 401 Unauthorized
  {"error":{"message":"로그인이 필요합니다.","status":"UNAUTHENTICATED"}}
  ```
  서버 코드(`request.auth == null` → `unauthenticated`)가 실제로 동작함을
  확인. A-1 완료 보고 때 "미검증"으로 남아 있던 유일한 실검증 수단이 이것.

**스트리밍 점진성 — 미검증으로 조사 종료:**

최초에 "확인됨"으로 보고했으나 오류였다. `STREAM-FALLBACK` 0건은
"스트리밍 경로가 예외 없이 끝까지 돌았다"만 증명하지 "청크가 실제로
점진적으로 도착했다"는 증명이 아니다. 화면도 파서를 거쳐 게이지·카드로
재조립되는 구조([점수]/[분위기점수]/[분위기] 세 줄이 다 와야 게이지 하나가
그려짐)라 육안 판별 자체가 불가능하다고 확인됨 — 그래서 판정은
`[TIMING] 2) 첫 응답까지`/`3) 전체 생성 완료` 간격으로만 했다.

- **`Accept-Encoding: identity` 추가 전** 3회: 240ms / 206ms / 222ms
- **추가 후(재배포·재실측)** 2회: 243ms / 255ms

**사실상 동일하다 — 헤더는 효과가 없었다.** 커밋 `ca7c1b0`의 코드 주석은
"헤더 누락이 원인이고 고쳐졌다"는 취지로 쓰여 있었는데, 이건 사실이

서버 `sendChunk` 호출 시각을 `console.log`로 남기면 청크가 몇 번에 나눠

### 2-10. Gemini 3.6 Flash 교체 검토 — 하지 않기로 결정(2026-08-01)

3.6-flash는 `thinkingConfig.thinkingBudget: 0`을 HTTP 400으로 거부한다(단순
프롬프트로 격리 확인). 이 저장소는 3곳에서 이 설정을 쓴다(`extractAttributes`
800 / `extractSizeFromChart` 800 / `planWeeklyOutfits` 2000). thinking을 끌 수
없으면 같은 `maxOutputTokens` 예산을 thinking과 출력이 나눠 쓰는데, 실측
결과 thinking 소모가 386~766토큰으로 호출마다 크게 튄다(동일 이미지·설정
5회, 출력은 58~61로 안정). 800에서 1회 잘림(thinking 766) → FormatException
→ 폴백. 900~1600에서는 완결됐으나 편차 상단이 재현되면 900도 위험하다. 즉
상한을 올려 흡수하려면 요청당 토큰이 늘어 교체 동기 자체가 뒤집힌다.
`gemini-3.5-flash` + `thinkingBudget: 0`은 이 변수를 0으로 고정해 예산이
결정적이다. **성능이 아니라 안정성 때문에 유지한다.**

참고: 스타일링 분석 경로(`thinkingConfig` 미사용, 3000토큰)는 3.6에서
형식이 완전히 일치했고 thinking도 3.5보다 적게 썼다(1374 vs 2224, 단일
샘플). 이 경로만 따로 옮기는 것은 이론상 가능하나, 모델이 두 개로 갈리면
폴백·화이트리스트·검증이 전부 두 배가 되므로 하지 않는다.

폴백(`gemini-3.1-flash-lite` → `gemini-3.5-flash-lite`) 교체도 보류.
`gemini-3.5-flash-lite`가 `thinkingBudget: 0`을 받는지 미확인이며, 폴백
경로 3곳이 모두 이 설정을 쓴다. 폴백이 400으로 죽으면 안전망이 필요한
순간에 함께 무너진다. 현재 `gemini-3.1-flash-lite`는 실측 기록이 있다
(주간 플랜 55초 타임아웃 뒤 3.249초 200 완주, JSON 파싱 통과 — §2-8).

**나중에 같은 유혹을 느끼더라도 재조사하지 말 것** — 위 실측이 근거다.
3.6-flash 자체가 사양 변경(새 모델·새 기능)되어 `thinkingBudget: 0`을
다시 받아들이게 되지 않는 한 결론은 바뀌지 않는다.

## 4. 반드시 알아야 할 함정 (누적)

이전 판의 4-1~4-8 전부 유효 — **단 4-5는 정정 필요, 4-16 참고.**

### 4-9. Firebase CLI `--only storage:rules`는 문법이 틀렸다

Firestore는 `firestore:rules`처럼 콜론 뒤에 하위 리소스를 쓰지만, Storage는
콜론 뒤가 **배포 타깃 이름**이다. `firebase deploy --only storage`(콜론 없이)가
맞는 문법.

### 4-10. `firebase functions:artifacts:setpolicy`의 기본 리전은 `us-central1`

함수를 다른 리전(이 프로젝트는 `asia-northeast3`)에 배포했으면
`--location asia-northeast3`를 명시해야 한다. 안 그러면 "리포지토리가 없다"고
엉뚱한 리전을 보고한다.

### 4-11. Cloud Functions Callable의 예외 매핑은 서버가 명시해야 한다

`fetch`가 예외(어보트·네트워크 실패)를 던지고 안 잡으면 Functions 프레임워크가
디테일 없는 `internal`로 뭉갠다. 클라이언트가 원인별로 다르게 처리(타임아웃→폴백,
인증 실패→그대로 전파 등)해야 한다면, 서버에서 반드시 `HttpsError(code, message,
details)`로 명시적으로 던져야 한다 — 이번 A-1에서 실제로 겪은 버그.

**추가(2026-08-01 후속 하드닝, §2-9):** "예외를 안 잡는 지점을 잡아서 전부
`internal`로 던지는 것"은 이 함정을 절반만 고친 것이다. 클라이언트의
`withTextModelFallback`은 `TimeoutException`/`GeminiApiException(isRetryable)`/
`FormatException` 세 갈래로만 재시도를 판단하므로, 서버가 뭉뚱그린 `internal`을
던지면 여전히 아무 갈래에도 안 걸려 폴백이 무력화된다. **성격이 다른 실패는
다른 코드/details로 구분해서 던져야** 클라이언트가 골라 받는다 — 이 저장소가
정한 컨벤션:
- 본문 전송 중 연결 끊김(바디를 다 못 읽음) → `HttpsError("data-loss", ...)`
- 200인데 본문이 유효 JSON이 아님(응답 형식 문제) → `HttpsError("internal", ..., {reason: "invalid-json"})`
- 업스트림이 실제 오류 상태를 준 경우 → `HttpsError("internal", ..., {upstreamStatus, upstreamMessage})`(기존 컨벤션)

새 코드/reason을 추가할 때는 **클라이언트 `gemini_service.dart`의
`_mapProxyException`도 같은 커밋에서 함께 확장**해야 한다. 서버만 고치면
클라이언트가 그 코드를 모르는 채로 그냥 `FirebaseFunctionsException`을
전파해 아무 갈래에도 안 걸리는 건 마찬가지다.

### 4-12. `cloud_functions` 스트리밍 청크는 `Map<Object?, Object?>`로 온다

플랫폼 채널을 거친 `Chunk.partialData`를 `as Map<String, dynamic>`으로 캐스트하면
런타임에 항상 실패한다. `Map<String, dynamic>.from(x as Map)`으로 변환할 것.
`jsonEncode`는 이 문제가 없다(키의 런타임 타입만 봄).

### 4-13. `cloud_functions`는 `^5.4.1`로 고정, 6.x 올리지 말 것

6.x는 `firebase_core` 4.x 세대와 짝이라(pub BoM 기준) 올리면
core/firestore/auth/storage/app_check 전부 메이저 업그레이드가 딸려온다.
5.4.1부터 스트리밍 Callable(`.stream()`)이 있어 지금 세대로 충분하다.

### 4-15. `google-services` 플러그인이 꺼져 있으면 App Check 문제가 조용히 숨는다

플러그인을 안 켠 상태(A-1·A-2 내내)에서는 `Firebase.initializeApp()`이
`firebase_options.dart`로 프로그래매틱하게만 되고, App Check SDK는 아예
네트워크 호출을 안 나갔다 — 그래서 "GCP 프로젝트에서 App Check API가
한 번도 활성화된 적 없다"는 사실이 안 보였다. B단계에서 플러그인을 켜자
Firebase 초기화가 정상화되고 App Check가 실제로 호출을 시도하면서 처음
드러남(§2-8 정정 참고). **교훈**: Firebase 하위 기능(App Check 등)의
문제 유무는 초기화 경로가 완전한 상태에서만 정확히 관측된다 — 프로그래매틱
초기화만으로 "일단 앱은 켜지니 문제없다"고 판단하면 이런 종류의 잠복
결함을 놓칠 수 있다.

### 4-16. 정정 — `debugPrint`는 이 프로젝트 릴리스 빌드에서 찍힌다

이전 판(4-5)의 "릴리스에서 `debugPrint`가 안 찍힌다"는 **이 저장소의 현재
빌드 설정 기준으로 부정확하다.** B단계 FCM 진단(§2-12) 중 릴리스 APK의
logcat에서 `[FCM-DIAG]`·`[PLAN]`·`[WEATHER]`·`[TIMING]` 태그 `debugPrint`
출력이 전부 정상적으로 찍히는 것을 실측으로 확인했다.

**근거**: `android/app/build.gradle.kts`의 `release` 빌드 타입에
`isMinifyEnabled`(R8/ProGuard)가 **설정돼 있지 않다**(기본값 false) —
로그를 지우는 축소·난독화가 안 걸린다. Flutter SDK의 `debugPrint`
구현(`packages/flutter/lib/src/foundation/print.dart`) 자체도
`kReleaseMode`/`kDebugMode`로 게이팅되어 있지 않다 — 기본값
`debugPrintThrottled`는 빌드 모드와 무관하게 항상 출력한다. 앱 코드에서
`debugPrint = ...`로 재정의해 무음 처리한 곳도 없다(grep 확인, 0건).

**4-5가 왜 틀렸다고 기록됐는지는 확인 못 함** — 다른 세대의 빌드 설정
(R8 활성화 등)에서 실제로 관측됐던 것일 수도 있고, 애초에 오기였을 수도
있다. **지금 확실한 것은 이 저장소의 현재 설정(R8 꺼짐)에서는 찍힌다는
것.** 나중에 R8/minify를 켜면(로드맵에 후보로 남아 있음) 이 결론이
다시 뒤집힐 수 있으니, 그때 다시 확인할 것.

**결론 — 진단 로그(`[FCM-DIAG]` 등)는 지우지 않고 남긴다.** 이번이
"조용한 실패"를 관측할 유일한 수단이었다 — 함수 로그·firestore 규칙·
SHA-1·API 활성화 전부 정상인데 원인을 못 찾다가, 결국 이 로그들로
"어디까지 갔는지"를 구분해 좁혔다. 같은 종류의 조용한 실패가 재발하면
같은 로그가 다시 필요해진다.

## 7. 이어받은 직후 할 일

```bash
git clone https://github.com/park-jang-sup/ai-fashion-assistant
cd ai-fashion-assistant
git remote -v          # personal이어야 함, origin 아님
flutter pub get
flutter test            # 140개 통과 확인
flutter analyze         # 0건
git log --oneline -10
firebase use             # ai-fashion-assistant-personal 확인
firebase functions:list  # callGeminiText, asia-northeast3, nodejs20 확인
```

그다음 **C단계(Cloud Scheduler 서버 트리거) 착수 전에** 확인할 것:
- App Check enforcement가 여전히 꺼져 있는지(콘솔) — 켜져 있으면 릴리스
  키스토어 정리가 먼저다.
- 데이터 확인 시 uid를 먼저 확인할 것(§2-12 교훈) — 이 프로젝트는 본인
  계정과 심사 계정 둘이 공존한다. Firestore 콘솔에서 아무 uid나 보고
  "비어 있다"고 판단하기 전에 logcat의 `FirebaseAuth: Notifying id
  token listeners about user ( uid )`로 실제 로그인된 uid부터 확인.
- (참고, 급하지 않음) `functions/`가 아직 CI 컴파일 체크 대상이 아니다
  (`tsc --noEmit`이 로컬에서만 돎) — A-2·B 둘 다 미루고 넘어왔다, C에서
  손댈 김에 같이 넣을지 판단.
- C단계 "앱 완전 종료 상태" 검증은 §2-12의 서버 대 서버 직접 호출
  방법(커스텀 토큰 → ID 토큰 교환 → Bearer POST)을 그대로 재사용 가능.
