## 2. 설계

### 0. 하네스 구조 정리

에이전트를 둘러싼 틀(하네스)을 여섯 층으로 나누고, 코드의 경계를 그에 맞춘다. 새 기능(A~F)은 이 틀 위에 얹는다.

| 층 | 하는 일 | 지금 위치 |
|---|---|---|
| 맥락 구성 | 모델에 줄 글을 만든다: 날짜표, 프로필, 스타일 원칙, 대화 요약, 현재 코디 | `ask_prompt.dart` |
| 도구 등록부 | 도구마다 이름, 인자 형식과 검증, 실행 함수, 화면용 이름과 문장, 턴당 횟수 상한, 쓰기 여부와 확인 필요 여부, 시한을 한 곳에 정의한다 | 지금은 프롬프트 글·`validateAskReply`·엔진의 분기에 흩어져 있다 |
| 루프 | 모델 호출 → 출력 검증 → 도구 실행 → 관찰 붙이기. 호출 상한, 시한, 대체 모델 | `ask_engine.dart` |
| 안전장치 | 확인 카드, 횟수 상한, 옷 번호와 날짜 범위 검증. 모델의 말이 아니라 엔진이 강제한다 | `ask_engine.dart`, `ask_controller.dart` |
| 기억 | 대화 안(현재 코디, 이전 턴 요약)과 대화 밖(착장 기록, 추천 반응, 대화 내역) | `ask_controller.dart`, `ask_history.dart` |
| 평가 | 가짜 모델 단위 테스트, 프로브의 사전 고정 기준 | `test/`, `tools/text_probe/` |

- **도구 등록부를 만든다.** 프롬프트의 도구 설명, 출력 검증, 엔진의 한도·확인 처리가 등록부 한 곳에서 나오게 한다. 도구를 더하거나 고칠 때 한 곳만 바꾸면 되게 하는 것이 목적이다.
- **동작은 바뀌지 않아야 한다.** 등록부로 옮긴 직후, 새 도구를 넣기 전에 에이전트 프롬프트 골든 2개와 기존 테스트가 그대로 통과하는지 확인하고 커밋한다.
- 이 정리에 쓰는 시간은 1시간까지다. 넘으면 지금 구조 위에서 A~F를 진행하고 그 사실을 보고한다.
- 작업이 끝나면 실행 기록에 "하네스 구성 요약"을 남긴다: 층별 구현 위치, 도구 표(이름·인자·한도·쓰기 여부), 안전장치 목록. 기획서에 쓸 자료다.

### A. 날짜표

- 프롬프트에 **오늘부터 14일의 날짜표**를 넣는다. 줄마다 날짜, 요일, 그 날짜를 가리키는 말을 적는다.
  - 가리키는 말: 오늘·내일·모레·글피, "이번 주 ○요일" / "다음 주 ○요일" / "다다음 주 ○요일"(한 주는 월~일), 주말 여부
- **표는 부탁할 때마다 기기의 현재 날짜로 새로 만든다.** 날짜를 코드나 프롬프트에 고정해 적지 않는다.
- 규칙을 바꾼다: 날짜 표현은 날짜표에서 찾아 쓴다. 표에 없는 날짜(14일 밖, "크리스마스" 등)는 표를 기준으로 세거나, 확실하지 않으면 `ask_user`로 날짜를 묻는다.
- `add_plan` 확인 카드에 요일과 가리키는 말을 함께 보여 준다(예: "11/16(월) · 다음 주 월요일").
- 순수 함수로 만들고 테스트로 고정한다: 오늘이 월~일 각각인 경우, 월말과 연말을 넘는 경우.

### B. 답의 품질

1. **사용자용 문장과 모델용 문장을 나눈다.** 도구는 모델에 줄 관찰과 화면에 보일 한 줄을 따로 돌려준다. 화면·대화 내역·활동 내역에는 화면용 한 줄만 쓴다. 막힌 호출, 형식 오류, 내부 안내("남은 호출", 제한 안내)는 화면에 보이지 않거나 "이미 확인한 내용으로 이어갈게요"처럼 사용자 말로 바꾼다.
2. **옷장 요약 도구** `get_wardrobe_profile {}`: 한 번에 옷장 전체를 요약한다.
   - 종류별 벌수, 종류마다 계절 분포(여름 / 간절기 / 가을·겨울 / 한겨울용)와 격식 분포, 많은 색 상위, 많은 스타일 태그 상위, 한겨울용 아우터 목록
   - 빈 부분(계산으로 낸다): 지금 기온대에 맞는 옷이 3벌 미만인 종류, 격식별로 0벌인 종류
   - "전신"은 세지 않는다. 1,500자 상한
3. **옷장 조회 제한을 바꾼다.** `search_wardrobe`는 한 번의 사용자 말(턴)에 3회까지, 같은 인자의 반복은 실행하지 않는다. 막혔을 때 모델에는 이유를 알려 주되 화면에는 보이지 않는다(1번).
4. **답 형식**(`finish`의 `answer`): 첫 줄은 결론 한 문장. 그 아래에 이유나 항목을 "- "로 시작하는 짧은 줄 2~5개. 필요하면 마지막에 다음에 할 수 있는 일을 한 줄. 굵은 글씨 같은 꾸밈은 쓰지 않는다. 화면은 줄바꿈과 "- " 항목을 그대로 살려 보여 준다.
5. **내부 사정을 말하지 않는다.** 도구 이름, 호출 횟수, 한도, 오류 문구를 답에 쓰지 않는다. 확인하지 못한 것이 있으면 "~은 아직 확인하지 못했어요"처럼 쓴다.
6. **구매 제안을 허용한다.** 규칙 "옷은 도구 결과에 나온 것만 말한다"를 아래로 바꾼다.
   - 사용자가 **가진 옷**으로 말하는 것은 도구 결과에 나온 옷뿐이다.
   - 옷장에 없는 옷은 "구매 제안:"으로 구분해서만 말한다. 사용자가 살 옷을 물었거나, 상황에 맞는 옷이 옷장에 없을 때 쓴다.
   - 제안은 종류·색·소재 수준까지다. 브랜드, 가격, 판매처, 링크는 쓰지 않는다.
7. **사용자 프로필**을 프롬프트에 한 줄로 넣는다(있는 항목만): 키, 체형, 퍼스널 컬러, 선호 스타일.
8. **스타일 원칙**을 프롬프트에 넣는다. 아래 문구를 그대로 쓴다. 외부 글이나 영상의 문장을 프롬프트에 옮겨 적지 않는다.

```
[스타일 원칙] 코디를 고르거나 조언할 때의 기준이다. 원칙을 늘어놓지 말고, 해당하는 것만 이유로 짧게 쓴다.
- 코디는 따로 떨어진 옷을 색으로 이어 한 벌처럼 보이게 하는 일이다. "이 옷에 무슨 색"보다 "이 옷을 나머지와 어떻게 잇나"로 본다.
- 같은 색 계열로 맞출 때는 밝기 차이를 분명히 둔다. 비슷한 밝기끼리는 밋밋하다.
- 다른 색을 섞을 때는 분위기(밝기·선명함)가 비슷한 색끼리 맞춘다.
- 한 착장의 색은 세 가지 이내로 한다(흰색·회색·검정은 세지 않는다).
- 색이 서로 부딪히면 그중 한두 벌을 흰색·회색·검정으로 바꿔 정리한다.
- 핏은 체형의 장점을 살리고 단점을 가리는 쪽으로 고르고, 위아래 실루엣의 균형을 본다.
- 겹쳐 입을 때는 안쪽에서 바깥쪽으로 갈수록 품이 넉넉해지게 한다.
- 퍼스널 컬러가 있으면 얼굴에 가까운 상의·겉옷 색에 먼저 반영한다.
- 옷장에 무채색이 많으면 그것을 바탕으로 삼고, 색이나 질감이 있는 옷 한 벌로 변화를 준다.
- 구매를 제안할 때는 색뿐 아니라 소재와 만듦새(천연 소재 비중, 박음질·단추·지퍼)도 함께 말한다.
```

### C. 조합 도구 확장 (`preview_outfit`)

인자를 늘린다. 조합 로직과 점수는 바꾸지 않고, `matchForWeather`에 넘기는 옷 목록을 거르는 방식으로만 구현한다(기온대 규칙과 같은 방식).

| 인자 | 뜻 |
|---|---|
| `date`, `tpo` | 지금과 같다 |
| `count` (1~5, 기본 1) | 서로 다른 조합을 여러 개 낸다. 앞 조합의 상의·아우터를 빼고 다시 돌리는 식으로 만든다. 만들 수 있는 만큼만 낸다 |
| `style` (선택) | 스타일 글자(예: "스트릿"). 상의·하의·아우터 각각, 태그에 그 글자가 든 옷이 있으면 그 종류는 그 옷들로 좁힌다. 없으면 좁히지 않는다. 좁혔는지 결과에 적는다 |
| `keep` (선택) | 그대로 둘 옷의 번호 목록. 그 종류는 그 옷으로 고정한다. 이렇게 지정한 옷은 기온대 규칙으로 빼지 않는다 |
| `exclude` (선택) | 빼고 고를 옷의 번호 목록 |
| `adjust` (선택) | "더 따뜻하게" 또는 "더 가볍게". 기온대를 한 단계 옮겨 고른다 |

- **옷 번호**: 도구 결과에 나오는 옷마다 대화 안에서만 쓰는 짧은 번호를 붙인다(예: `#12`). `keep`·`exclude`와 E의 피팅이 이 번호를 쓴다. 번호와 실제 옷의 대응은 엔진이 갖고, 없는 번호가 오면 형식 오류로 돌려준다.
- **예보 범위 밖 날짜**: 예보가 없으면 오늘 예보의 기온대를 대신 쓰고, 그 사실을 결과에 적는다("예보 범위 밖이라 오늘 기온대 기준").
- 결과에는 조합마다 번호가 붙은 옷 목록, 날씨 문구, 격식 차선 여부를 적는다.

### D. 이어지는 대화

- 대화 하나는 여러 턴(사용자 말 → 단계들 → 답)으로 이뤄진다. 답이 나온 뒤에도 입력창이 남아 이어서 말할 수 있다.
- 프롬프트에는 이전 턴을 줄여서 넣는다: 사용자 말, 답, 그리고 **[현재 코디]**(마지막으로 보여 준 조합을 옷 번호와 함께). 이전 턴의 단계와 관찰은 넣지 않는다. 28,000자 상한은 그대로다.
- "다시 추천해줘", "자켓만 바꿔 줘", "더 따뜻하게"는 [현재 코디]를 기준으로 `preview_outfit`의 `exclude`·`keep`·`adjust`를 써서 푼다.
- 상한: 턴마다 모델 호출 6회(지금과 같다), `ask_user`는 턴마다 1회, 대화 하나는 10턴. 10턴을 넘으면 새 대화를 시작하라고 안내한다.
- 여러 대화에 걸친 기억은 없다. [새 대화]를 누르면 처음부터다.
- 대화 내역 한 건은 대화 전체(모든 턴)다. v1 형식으로 저장된 기록은 한 턴짜리 대화로 읽어 보여 준다. 기록에는 사진 자체를 넣지 않고(주소나 키만), 답은 턴마다 2,000자까지만 저장한다.

### E. 가상 피팅 도구 (`try_on`)

- `try_on {"outfit": [옷 번호들]}`: 그 조합을 코디보드에 올리고 가상 피팅을 실행한다. 기존 경로(§1-6)를 그대로 쓴다. 결과 사진은 대화 안에 보여 주고, 누르면 크게 본다.
- 전신 사진은 앱에서 지금 선택된 것을 쓴다. 선택된 사진이 없으면 실행하지 않고 그 사실을 돌려준다.
- 사용자가 입은 모습을 보여 달라고 했을 때만 쓴다(프롬프트 규칙). **엔진도 막는다**: 턴마다 1회, 다른 피팅이 진행 중이면 실행하지 않는다.
- 피팅 상한(시간당 6회) 초과와 실패는 재시도하지 않고 사용자 말로 알린다.
- 이 도구가 기다리는 시간(최대 120초)은 단계 시한과 요청 전체 시한에 세지 않는다.
- 확인 카드는 띄우지 않는다. 사용자가 직접 부탁한 일이고, 되돌릴 수 없는 변경이 아니다.
- 코디보드에 있던 조합은 이 조합으로 바뀐다. 결과를 돌려줄 때 그 사실을 함께 알려, 답에 "코디보드에도 올려 두었어요"가 들어가게 한다.

### F. 착장 기록 읽기와 데모용 예시

1. 도구 `get_style_history {}`: 최근 60일의 착장 기록과 추천 반응을 요약한다.
   - 자주 입은 옷 상위 5벌(번호 포함), 자주 입은 색과 격식, 상황별 가장 최근 착장 1건, 추천을 그대로 입은 횟수와 다르게 입은 횟수, 60일 동안 기록에 없는 옷의 수와 예시 5벌
   - 기록이 없으면 "아직 착장 기록이 없어요"를 돌려준다.
2. `preview_outfit`에 인자 `unworn_first`(선택, 참/거짓)를 더한다. 참이면 종류마다 최근 60일 기록에 없는 옷으로 좁힌다(그런 옷이 있는 종류만).
3. **데모용 예시 착장**: 데모 옷장 불러오기가 성공하면 지난 14일 안에 예시 착장 기록 6건을 넣는다(`isDemo`). 상황을 섞고, 조합은 기존 매칭으로 만든다. 불러올 때마다 결과가 같아야 한다. "예시" 표시를 붙이고, "데모 옷장 비우기"가 함께 지운다. `firestore.rules`는 바꾸지 않는다.
   - 이 기록 때문에 내일 예시 일정의 추천이 달라지는지 확인해 보고한다.

### G. 화면

- 대화 화면: 턴이 위에서 아래로 쌓이고 입력창은 아래에 남는다. 진행 중 단계, 확인 카드, 질문, 답 카드, 피팅 사진이 그 안에 들어간다. [새 대화], [멈추기], [대화 내역].
- 첫 상태의 예시 버튼을 바꾼다: "금요일 저녁 모임 옷 골라서 입혀 봐줘", "내일 뭐 입지?", "내 옷장에 부족한 옷 알려줘", "요즘 안 입은 옷으로 코디해줘".
- "지난 부탁"을 "대화 내역"으로 바꾼다. 한 건 삭제와 모두 삭제를 넣는다(지우기 전에 한 번 묻는다).
- 떠 있는 버튼을 끌어서 옮길 수 있게 한다. 화면 밖이나 하단 탭 위로 나가지 않게 하고, 놓으면 가까운 좌우 가장자리에 붙는다. 옮긴 자리는 계정별로 기기에 저장하고 모든 탭에 쓴다. 옮긴 적이 없으면 지금의 탭별 자리를 쓴다.
- 가이드 4쪽 문장은 지금 것을 유지한다.

### H. 음성 입력 (선택)

- 입력창에 마이크 버튼을 둔다. 누르면 한국어로 받아써 입력창에 넣는다(보내기는 사용자가 누른다). 권한이 없거나 기기가 지원하지 않으면 버튼을 숨긴다.
- **다른 부분의 APK 확인이 끝난 뒤에, 커밋과 빌드를 따로 한다.** 1시간 안에 빌드가 되지 않거나 기존 기능에 영향이 보이면 되돌리고 보고한다.

**진행 규칙**: 안전 기준이 모두 100%면 그 밖의 기준이 미달이어도 미달로 기록하고 화면 작업으로 넘어간다. 다시 실행 2회를 다 쓰고도 안전 기준이 하나라도 미달이면 넘어가지 말고 보고하고 멈춘다.

프로브 실행은 사용자가 자기 터미널에서 한다. 실행 명령을 알려 주고 기다린다. 구현하지 못해 뺀 부분의 시나리오는 빼고, 뺀 사실을 적는다.

## 4. 작업 순서

부분마다 커밋 1개.

1. §1 대조
2. 하네스 구조 정리(§2-0. 동작 변화 없음을 확인하고 커밋. 1시간 한도)
3. A 날짜표
4. B 답의 품질(문장 분리, 옷장 요약 도구, 조회 제한, 답 형식, 구매 제안, 프로필, 스타일 원칙)
5. C 조합 도구 확장과 옷 번호
6. D 이어지는 대화(엔진·컨트롤러·프롬프트)
7. E 가상 피팅 도구
8. F 착장 기록 도구, 데모용 예시 착장
9. 프로브 T7 준비 → 사용자 실행 → 판정 보고. **여기서 한 번 멈춘다**
10. G 화면 → `flutter analyze`, `flutter test` → **멈추고 보고**(APK 빌드는 승인 후)
11. H 음성 입력(승인 후, 따로)

시간이 모자라면 뺄 순서: H → F의 데모용 예시 착장 → F 전체 → G의 버튼 옮기기 → C의 `count`(1개만 내게 둔다). A·B·D·E는 빼지 않는다.

## 5. 문서에 남길 한계

- 한 턴이 텍스트 호출을 최대 6회 쓴다. 시간당 60회 상한 안에서 10~15턴쯤 이어 말하면 상한에 닿을 수 있다. 상한 값은 바꾸지 않는다
- 가상 피팅은 시간당 6회다
- 대화 사이의 기억은 없다. 착장 기록과 추천 반응만 다음 대화에 쓰인다
- 예보는 7일까지다. 그 밖의 날짜는 오늘 기온대를 기준으로 고른다

## 7. 실기기 확인 항목

- 날짜: "다음 주 월요일", "모레", "이번 주 일요일"로 일정 등록을 부탁해 확인 카드의 날짜를 본다

## 8. 금지 사항
