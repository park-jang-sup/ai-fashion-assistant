## 1. 배포 장애물 — 로컬 배포 검사 10초 타임아웃

**문제**: `firebase deploy`가 실제 배포 전에 로컬에서 함수를
한 번 임포트해보는 "discovery" 단계를 거치는데, 여기 **10초
제한**이 있다. `torch`/`torchvision`/`onnxruntime`을 모듈 스코프에
그대로 두자 이 단계에서 실패했다: `Error: User code failed to
load. Cannot determine backend specification. Timeout after
10000`.

**원인 확인**: `firebase-debug.log`를 직접 읽어 원인을 좁혔다 —
`venv/Scripts/activate.bat`가 없어서 뜬 1차 실패, venv를 만든
뒤엔 Flask 기반 로컬 discovery 서버가 무거운 임포트 자체를
10초 안에 못 끝내서 뜬 2차 실패. **이건 실제 Cloud Run 콜드스타트가
아니라 별도의 로컬 전용 제한**이라는 걸 확인한 게 중요했다 — 잘못
알았으면 측정 대상 자체를 오해할 뻔했다.

**해결**: Firebase 공식 문서(`firebase.google.com/docs/functions/
tips`)가 권장하는 `firebase_functions.core.init` 훅으로 무거운
초기화를 감쌌다 — 이 데코레이터는 "인스턴스당 1회, 함수 코드
실행 전"에 돌도록 문서화돼 있고, **로컬 discovery 단계에서는
아예 호출되지 않는다**(그 함수 자체가 로컬에선 안 불림). 이걸로
로컬 10초 제한을 완전히 피했다.

**부작용(나중에 §3에서 발견)**: 이 수정이 "콜드스타트"의 정의
자체를 바꿔놨다 — 아래 3절 참고.

커밋: `b1dc67e`, `81e1c36`.

## 3. 핵심 발견 — `startup_latencies`가 아니라 `request_latencies`를 봐야 한다

**문제**: GCP 공식 콜드스타트 지표(`run.googleapis.com/container/
startup_latencies`)를 먼저 봤더니 **870~1410ms대**로 나와, 우리
자체 측정(12~20초)과 **자릿수 자체가 달랐다**. 처음엔 계측 오류로
의심했다.

**원인 규명**: 1절의 `@core.init` 우회가 원인이었다.
`startup_latencies`는 **컨테이너가 트래픽을 받을 준비가 될
때까지**(HTTP 서버가 포트를 리슨하기까지)만 잰다. 무거운 초기화를
`@core.init`으로 옮긴 결과 컨테이너 자체는 빠르게 "준비 완료"
상태가 되고, **무거운 초기화는 첫 요청이 실제로 들어왔을 때
그 요청 처리의 일부로 실행된다** — 우리가 재려던 비용이
`startup_latencies`가 아니라 **`request_latencies`(요청 처리
시간)** 쪽으로 넘어가 있었다. 로컬 10초 제한을 피하려고 쓴
수정이 GCP가 "콜드스타트"를 어느 지표에 기록하는지도 함께
바꿔놓은 것.

**대조 결과**: `request_latencies`로 다시 보니 우리 자체 측정과
정확히 맞아떨어졌다(19,574.2ms vs 20.089s, 8,331.2ms vs 8.408~
9.006s 등, 오차는 대부분 네트워크 왕복). **우리 계측 자체는
신뢰할 수 있다는 걸 GCP 공식 지표로 교차검증한 것**이 이 절의
핵심 성과 — "콜드스타트를 어느 지표로 볼 것인가"라는 질문이 새로
생겼다는 것도 함께 등록했다.

커밋: `3f2b328`.

## 4. 웜 이상 — "웜"인데 왜 7~9초인가

로컬(§14 하네스, 완전히 새 프로세스마다 1회 로드)에서는 웜 추론이
~0.04~0.24초로 사실상 즉시였다. 그런데 클라우드에서 **같은
리비전에 대한 2~4번째 호출도 7.7~9.0초**로, 최초 호출(19.57초)
보다는 짧지만 로컬의 "거의 0"에는 전혀 못 미쳤다. `@core.init`은
"인스턴스당 1회"로 문서화돼 있는데, 응답 본문의 `importTorchSeconds`
등 값이 2~4번째 호출에서도 계속 2~3초대로 찍혔다 — 이게 진짜
초기화 재실행인지 확신이 없는 채로 이 절을 마쳤다(§19 시점엔
"원인은 조사하지 않는다"는 지시가 있어 등록만 하고 넘어갔다).

**함의**: 상시 인스턴스(`min_instances=1`, 월 $56)를 쓰는 이유는
보통 "콜드스타트를 없애 모든 요청이 빠르게 응답하게 한다"인데,
이 관측대로면 **상시 인스턴스를 켜도 매 요청이 여전히 7~9초일 수
있다** — $56을 내고 얻는 게 "콜드스타트 제거"가 아니라 "19초를
8초로 줄이는 것"뿐일 수 있다는 뜻이라, 사용자에게 min_instances
결정을 넘기면서 이 불확실성을 그대로 표기했다.

커밋: `3f2b328`.

## 5. 웜 이상 원인 규명 — 무료 진단으로 부분 규명

다음 세션(같은 날 이어짐)에서 사용자가 "API 호출 없이 무료
수단부터 소진하라"고 명시적으로 지시해 재조사했다.

**(a) "웜"이 진짜 웜이었는가 — `instance_count` 지표로 확인**:
Cloud Monitoring `container/instance_count`를 07:39~08:03Z 구간
1분 단위로 조회했다. `active+idle` 합이 이 구간 내내 **한 번도
0으로 안 떨어졌다** — 즉 컨테이너 인스턴스는 4번째 호출까지(그
이후 마커 재배포로 다음 리비전이 뜰 때까지) 한 번도 안 죽었다.
**"매번 새 인스턴스" 가설은 이 지표로 기각.**

**(b) 그런데 세션·모델이 요청마다 다시 로드되는가 — 이미 받은
응답 자체가 답이었다**: §2의 표를 다시 보면 `moduleTotalSeconds`가
2~4번째 호출에서 **7.753 / 8.368 / 7.724로 서로 다르다.**
`@core.init`이 정말 1회만 돌았다면 이 값은 1번째 호출이 써넣은
19.075를 그대로 반복 출력해야 하는데, 매번 다른 값이 나왔다는
것 자체가 **`_initialize()`가 실제로 반복 실행됐다는 직접
증거**다.

**코드 배선은 SDK 소스에서 직접 확인 — 결함 아님**:
`firebase_functions/core.py`(venv에 실제 설치된 패키지)를 읽어
`_did_init`이라는 프로세스 전역 bool 가드로 "1회만" 실행되게
짜여 있음을 확인했고, `https_fn.py:435`에서 `on_request`가 실제로
이 가드를 우리 핸들러에 씌우는 것도 확인했다 — **`main.py`의
사용법 자체는 문서·SDK 소스와 정확히 일치, 코드 결함이 아니다.**
남는 설명은 `functions_framework`의 gunicorn 서빙 계층
(`WORKERS` 환경변수 기본값 1이지만 배포 컨테이너의 실제 값은
확인 불가) — **추정만 가능하고 확정은 못 했다.**

**로그 경로도 확인 — 애초에 볼 게 없었다**: `firebase functions:log`
를 다시 돌려도 감사 로그(CreateFunction/UpdateFunction) 6줄만
나왔다. 이유는 권한 문제가 아니라 **`main.py`에 애초에 `print()`/
`logging` 호출이 하나도 없어서**였다 — 이 경로는 코드 수정 없이는
막다른 길임을 확인.

**더 싼 진단 후보(재배포 없이) 사전 등록**: gunicorn 워커 가설이
맞다면 워커가 N개일 때 처음 N번의 호출은 매번 새 워커라 느리고
그 이후는 급격히 빨라져야 한다 — 8~10회 연속 호출로 이 전환점의
유무를 보는 반증 가능한 예측을 등록해 뒀다(실행 안 함, 승인
대기 상태로 남김).

커밋: `ac3df60`, `b5a8649`.

## 6. 판정 기준 자체가 틀렸다 — 5초/20초 문턱 재검토

여기가 이 세션에서 방향이 가장 크게 꺾인 지점이다.

**5초/20초 문턱의 출처를 다시 찾았다**: `task_background_removal_
v1.md:470-472`가 원출처였다 — "콜드스타트가 사용자 체감상 허용
범위(**기준값은 사용자 판단** — 예: 수 초~10초대는 **"업로드
중" 스피너로 자연스럽게 가려짐**, 그 이상이면 문제)". 즉 이
문턱은 (1) 측정이 아니라 임의 판단이었고, (2) **"사용자가 스피너를
보며 기다린다"는 전제 위에서만 성립**했다.

**핵심 질문으로 코드를 다시 봤다 — 이 지연을 누가 기다리는가?**
Explore 에이전트로 전체 소비 경로를 조사하고 핵심 지점은 직접
재확인했다:
- 임베딩 벡터를 읽는 곳은 앱 전체에서 **"비슷한 옷" 액션 시트
  하나뿐**(`wardrobe_screen.dart:255-260`) — 사용자가 **나중에,
  임의 시점에, 스스로 카드를 눌러야만** 열린다. 코드 주석 자체가
  "embedding이 없으면 섹션 자체를 렌더링하지 않는다"고 돼 있다
  — `null`을 정상 상태로 이미 설계해 뒀다.
- 등록 플로우(`wardrobe_screen.dart:659-719`) 안에서도 "업로드
  (동기, 스피너 있음)"와 "속성 추출(`unawaited`로 명시적 비동기)"
  이 이미 나뉘어 있다.
- **배경 제거의 실제 프로덕션 배포도 비동기였다**: 클라이언트
  동기 배경 제거 코드는 존재하지만 릴리스에선 꺼져 있고
  (`_kOnDeviceBgRemovalEnabled=false`, 네이티브 크래시 때문),
  실제로 도는 건 `functions_bg_removal/main.py`의 Storage 트리거
  기반 완전 비동기 함수(`min_instances=0`)다 — **배경 제거는
  68초 콜드스타트(로컬 대비 53배)로도 아무 문제 없이 운영
  중이다**, 지켜보는 사용자가 없기 때문.

**결론**: 5초/20초 문턱이 전제한 "스피너로 지켜보는 사용자"가
이 기능엔 없다. **초 단위 지연 요구사항 자체가 적용 대상을
잃는다.** 새 요구사항은 "등록 후 N초 안"이 아니라 **"사용자가
다음에 그 카드를 누르기 전까지"**(분~시간 단위 여유)로 대체했다.
`[정정]` 블록으로 등록(원문은 §7/§13(c)/§19에 그대로 남김).

**min_instances 재정리**: `min_instances=0`으로 충분, 상시
인스턴스($56/월)를 쓸 근거가 사라진다. §5의 "웜 이상"은 이제
성능 문제가 아니라 **비용 축으로만** 남는다(아래 7절).

커밋: `3dd1af2`.

## 10. 본 구현 설계 (`task_embedding_impl_v1.md`)

조사 트랙 종결 후 사용자가 결측 46벌 백필을 **범위 안으로
되돌리며** 본 구현 설계를 지시했다. 코드는 작성하지 않고 설계만
문서화.

**아키텍처 — 공유 본체 + 진입점 2개**(§5의 "계산부를 트리거와
분리" 제약을 실제로 값하게 만듦):
- `_compute_embedding` / `_write_embedding` / `_record_metric`을
  공유 본체로 두고,
- **진입점 1** `embedding_on_upload`(Storage 트리거, 신규 등록) —
  배경 제거와 똑같은 메타데이터 계약(`wardrobeDocId`/`ownerUid`/
  `category`) 재사용.
- **진입점 2** `embedding_backfill_batch`(관리자 배치, 기존 결측
  분) — 스파이크가 이미 쓴 IAM invoker 제한 패턴 재사용, 공개
  엔드포인트 아님. 60초 타임아웃 안에서 시간 예산(예: 45초)만큼만
  처리하고 나머지는 다음 호출이 자연히 처리(멱등 — 이미
  `embedding`이 있으면 스킵).

**이미지 소스 결정**: 컷아웃/원본 혼용(기존 관례) 대신 **원본으로
통일** — 배경 제거가 같은 이벤트를 독립 트리거로 받아 순서
보장이 없어 신규 등록 시점엔 컷아웃이 없을 확률이 높고, 신규·
백필 간 이미지 소스가 갈리면 파리티가 조용히 깨질 수 있어서.
승인 단계에서 뒤집을 수 있는 기본값으로만 등록.

**실패 처리**: 배경 제거 선례(`functions_bg_removal/main.py`)를
직접 읽고 대조 — try/except 전체 감싸기·재시도 없음·등록 자체는
안 깨짐은 그대로 가져오되, `print()`에만 남기던 실패 로그를
**Firestore `embedding_metrics` 컬렉션**으로 보강(릴리스에서도
조회 가능하게).

**계측 설계**: `embedding_metrics`에 성공/실패, 소요시간 세부
(`moduleTotalSeconds` 포함), 모델 해시를 기록 — **5절의 웜 이상
비용 축을 스파이크 재측정 없이 이 계측이 며칠 쌓이면 답할 수
있게** 설계.

**재현성**: 배포 전 `export_onnx.py` 해시 재대조 절차 + 런타임에
모델 해시를 매 기록에 실어 사후 감사 가능하게.

**판정 기준 5개 사전 등록**, 범위 밖(외부 카탈로그 엔드포인트,
양자화, 기존 배치 파이프라인 수정 등) 명시.

## 11. 보류 결정 — 설계 직후 트랙 전체를 접었다

설계를 마친 직후, 사용자가 더 근본적인 문제를 제기해 **트랙
전체를 보류**했다. 설계 문서는 지우지 않고 서두에 `[보류]` 블록만
추가.

**보류 근거(다섯 가지)**:
1. 벡터의 유일한 소비처는 수동 탭으로 열리는 "비슷한 옷" 시트
   하나이고, `null`이면 숨겨지도록 이미 설계돼 있다(6절에서 이미
   확인된 사실 — 그때는 min_instances 판정에만 썼는데, 이번엔
   "애초에 이 기능이 필요한가"로 같은 사실이 다시 쓰였다).
2. **임베딩은 "비슷함"을 재는데, 코디 추천은 "어울림"을
   필요로 한다** — 다르고 때로 반대다. 옷장에 더할 옷을 고르는
   문제에서 시각적 유사도는 애초에 잘못된 축.
3. **"상점 옷 연결의 전제 조건"이라는 이 트랙의 앞선 판단을
   정정** — 속성 추출 + 기존 `OutfitMatcher`(격식·색 조화·
   톤온톤)만으로도 상점 옷 매칭이 가능하고, 오히려 그 편이
   "어울림"에 더 맞는다.
4. 옷장이 유동적이라 벡터 수명이 짧다 — 지금 46벌을 채워도
   결측은 다시 쌓인다(일회성 비용이 아니라 계속 갚는 빚).
5. 에이전트 서사(자율 실행·자기 평가·자가 수리)에 기여가 없다.

**유일하게 살아남는 명분과 순서**: "비슷한 옷 = 중복 구매 방지"
프레이밍("비슷한 거 이미 갖고 계세요")은 유사도가 정확히 맞는
문제다(어울림이 아니라 진짜 비슷함을 묻는 질문이라서). **다만
상점 카탈로그가 있어야 성립한다** — 비교할 "살 수 있는 옷"이
없으면 그 말 자체가 성립 안 함. **재개 조건: 외부 카탈로그
데이터 소스가 확보된 시점.** 그 전엔 다시 열 근거가 없다.

**재개 시 바로 꺼내 쓸 산출물**: ONNX 변환 스크립트
(`export_onnx.py`, 해시 포함), 전처리 코드와 그 안의 두 원인
(**antialias 누락**, **`int()` 절삭** — 반올림 아님), 파리티
하네스와 5건 픽스처(기준 ≥0.9999997), 실행 위치 판정과 근거,
콜드스타트·비용 실측, 웜 이상 관측(원인 미확정).

커밋: `bd12815`(설계 문서 보류 표시 + handoff 갱신).

계열)에 쓸 만한 사례들을 등록만 해 둔다(논문 파일은 수정 안
함):

1. **측정 인프라를 바꾸면 측정 대상의 정의도 같이 바뀔 수
   있다** — `@core.init`으로 10초 로컬 제한을 피한 수정이
   GCP의 "콜드스타트" 공식 지표(`startup_latencies`)를 무의미하게
   만들고 실제 비용을 `request_latencies`로 이동시켰다(3절). 우회
   수정 하나가 계측 정합성 자체를 바꾼 사례.
2. **다른 맥락에서 가져온 판정 기준은 전제까지 같이 옮겨야
   한다** — 5초/20초 문턱을 배경 제거에서 그대로 가져왔지만,
   그 문턱이 성립하는 전제("사용자가 스피너를 보며 기다린다")를
   확인 안 하고 재사용했다가 뒤늦게(6절) 전제 자체가 이번
   기능엔 안 맞음을 발견했다.
3. **누적 그래프와 일별 그래프를 혼동하면 없는 이상 신호를
   본다** — "곡선이 안 내려온다"는 누적 그래프의 정의상 당연한
   현상이었는데 이상 신호로 오독했다(8절). "봤어야 할 건 절대값이
   아니라 기울기."
4. **무료 진단 먼저 원칙이 실제로 절반의 답을 냈다** — 웜
   이상의 원인을 API 호출 없이(GCP 지표 재해석 + SDK 소스 직접
   읽기) 부분 규명했다(5절) — 완전한 답은 못 냈지만, 유료
   재측정 없이 "코드 결함은 아니다"까지는 확정할 수 있었다.
5. **"이 지연을 누가 기다리는가"라는 질문이 기술 수치보다
   먼저 와야 한다** — 요구사항(N초)을 기술 실측에서 역산하지
   않고 실제 소비 경로(코드)에서 도출하니 판정 자체가 뒤집혔다
   (6절). 기술 수치는 요구사항이 이미 정해진 뒤에나 의미가 있다.
