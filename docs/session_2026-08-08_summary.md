# 작업 정리 (2026-08-08 세션 — 가상 피팅 실패 진단 + 계측 도입)

이 세션 전체를 관통한 질문은 하나였다: **가상 피팅이 왜, 어떤 계정에서
실패하는가.** 여러 가설(회색 옷, 컷아웃 배경 제거, 심사용 계정 전신
사진 부재, 특정 이미지 문제, 페이로드 초과, 무한 로딩=5.19.2)을 순서대로
세우고 데이터로 하나씩 배제해나가, 마지막엔 **실제 업스트림(Gemini
이미지 모델) 응답이 정상보다 훨씬 느리다(실측 110.8초)**는 확정 수치까지
도달했다. 커밋 8건(`e34d45d`~`eb1ee48`), 전부 완료·배포까지 반영.

## 1. 코디보드 슬롯 구조 오인 정정

**문제**: 이전 세션에서 `fitting_room_screen.dart:1576`의 `allCategories`
(5개 카테고리)를 가상 피팅 슬롯으로 잘못 인용 → 페이로드 상한 근거
계산이 "6장, 1.5배 여유"로 틀리게 나가 있었다.

**어떻게 파악**: 사용자가 실제 화면에서 보이는 슬롯 수(7개, 아우터는
조건부 렌더링이라 안 보일 때가 있음)를 근거로 재조사를 요청. 코드
추적 결과 `1576`은 `_matchStyleRecommendations`(스타일 추천 카드용
지역 변수)일 뿐, 실제 코디보드는 `outfit_board.dart`의
`outfitBoardSlots` 상수(8슬롯: 아우터·상의·하의·신발·모자·가방·시계·
팔찌)였다.

**결과(정확한 수치)**:
- 실제 최대 이미지 수 = **9장**(코디보드 8슬롯 + 전신 1) — 6장 아님.
- 이론상 최악 페이로드 = raw 9×1,384,759B=12.46MB → base64 **15.85MB**.
- 배포된 상한(16MB) 대비 여유 = **약 1.01배**(1.5배 아니었음), 차이는
  약 153KB뿐.
- `subCategory` 실측 분포: 모자 10 / 가방 1 / 시계 1 / 팔찌 0.
- 상한 값 자체(16MB)는 이번에 변경하지 않음 — 주석만 정정
  (`functions/src/payload_limit.ts`).

커밋: `875d78a`.

## 2. `seed_demo_wardrobe/seed.py` — 삭제 반영 기능 추가

**문제**: 도구가 `wardrobe` → `demo_wardrobe` upsert만 하고, 원본에서
지워진 문서를 `demo_wardrobe`에서 정리하지 않았다 — 손상된 원본 문서가
데모 세트에 고아로 남는 구조적 원인.

**추가한 것**: `find_stale_demo_docs()`로 원본에 없는 `demo_wardrobe`
문서를 찾아 삭제 후보로 표시. 안전장치:
- **Storage 파일은 절대 안 건드림**(Firestore 문서만) — 과거 공유
  Storage 구조 때문에 전신 12건을 영구 손실한 전례(`task_signed_urls_v1.md`
  §8-3)를 코드 주석으로 명시.
- 삭제 비율이 `--max-delete-ratio`(기본 **20%**, 제안값)를 넘으면
  `--apply` 전체를 중단.
- 삭제 전 `manifests/`에 JSON 백업(문서 전문), 롤백 기능은 없음.
- dry-run 실행 결과(이 시점): **삭제 대상 0건**(정상 — 아직 원본을
  안 지웠으므로).

커밋: `e8443b7`.

## 3. 손상 문서 6건 확인·처리

**문제**: `imagePath`가 버킷 루트 파일을 가리키거나 아예 없는 문서
(원본 소실, 폴더 규칙 이전 잔재) 총 **6건**을 두 컬렉션(`wardrobe`,
`demo_wardrobe`)·두 계정(본인, 심사용) 전수 스캔으로 확정.

**어떻게 파악**: `imagePath` 필드 유무만 보면 놓치는 문서가 많다는 걸
발견(심사용 계정·`demo_wardrobe`는 애초에 이 필드가 없는 설계) —
`signed_url_policy.ts`의 `pathFromDownloadUrl` 로직을 그대로 Python으로
복제해 **`imagePath ?? imageUrl에서 역산한 경로`** 기준으로 재스캔해야
전수 확인이 된다는 방법론을 이번에 확립(향후 재사용 가능하도록 handoff에
별도 기록).

**처리**: 본인 계정 1건(`PoE3BNsOerVgEMtDdQzf`)은 콘솔에서 개별 삭제.
심사용 계정 5건은 "데모 옷장 비우기 → 불러오기"로 일괄 갱신(개별 삭제
대신 전량 재구성). **최종 카운트: 본인 wardrobe 113 / demo_wardrobe
113 / 심사용 wardrobe 113 — 전부 일치**(118 → 113은 손상 5건이 양쪽에서
같이 빠졌기 때문).

커밋: `875f0bd`.

## 4. "무한 로딩" 오진단 → 정정 → 실제 원인 확정 (이 세션의 핵심)

### 4.1 최초 관측과 오판
심사용 계정에서 데모 재시드로 전신 사진 3장을 확보한 뒤 가상 피팅을
실행 → 사용자 보고가 처음엔 불명확했고, 로그상 `callGeminiText`
(model=`gemini-3.1-flash-image`) 호출이 `10:12:49Z`와 `10:13:45Z`
(56초 간격, requestBytes **329,867B** 동일)에 두 번 찍힌 뒤 **12분+
로그 침묵**만 보여 "무한 로딩 = 논문 5.19.2(시한이 걸리지 않는 호출)
재현"으로 잠정 결론 내렸다.

### 4.2 정정
사용자가 실제로 기다려 확인한 결과: **무한 로딩이 아니라 약 2분 뒤
에러 메시지**였다. 56초 간격은 클라이언트 60초 타임아웃이 아니라 서버
`fetchUpstream`의 **55초 `AbortController`**가 2회 연속(최초 시도 +
`_withRetry` 1회 재시도) 발동한 것으로 재해석 — 5.19.2는 재현 절차
없음 상태로 되돌림.

### 4.3 계측 부재 확인 및 추가
문제: 실패 시 서버 로그에 완료·실패 흔적이 전혀 안 남아, "55초를
넘겼다"를 로그의 침묵으로 추론할 수밖에 없었다. `callGeminiText`에
**상관 키(reqId) 기반 시작/완료 로그**와 **55초 abort 발동 시점 자체를
찍는 로그**를 추가해 배포(커밋 `d3f2cf5`).

### 4.4 배제된 가설들 (정확한 수치)
- **페이로드 문제 아님**: 실패 3세션 requestBytes 각각 329,867B /
  310,863B / 177,199B — 전부 9장 상한(15.85MB)과 무관한 소규모.
- **계정 특유 가설 약화**: 본인 계정도 같은 날(8/8) 동일 패턴으로
  **4회 연속 실패**(14:20:57Z, 14:21:53Z, 14:31:03Z, 14:31:58Z, 매번
  elapsedMs **55,036~56,055**에서 abort).
- **특정 이미지 가설 — 확정 불가로 결론**: requestBytes 역산으로 조합을
  좁혀봤으나, 탐색 공간(옷 아이템 110개, 2개 조합 시 5,995쌍)이 커질수록
  우연히 정확히 일치하는 조합이 나오는 통계적 함정을 확인(같은 옷
  아이템이 서로 다른 두 시도의 "완전 일치" 후보로 겹쳐 나옴) — 억지로
  좁히지 않고 "특정 안 됨"으로 보고.
- **텍스트 경로는 정상**: 같은 세션의 코디 분석(텍스트 모델) 호출은
  두 번 다 **6.7초**만에 성공(responseBytes 9,569B / 10,260B) — 이미지
  모델만 느림을 숫자로 확인.
- **모델 자체는 유효**: Gemini API `ListModels`로 직접 확인—
  `gemini-3.1-flash-image`(Nano Banana 2) 존재, Stable, 폐기 없음.
  `ALLOWED_MODELS`엔 대체 이미지 모델 없음(교체 안 함).

### 4.5 측정용 시한 상향 → 실제 소요시간 확정
55초 한도로는 "55초 이상"까지만 알 수 있어 실제 소요시간을 영원히
측정할 수 없다는 판단 하에, **측정 목적으로만** 서버 시한을 상향:
- `UPSTREAM_TIMEOUT_MS`: 55,000 → **300,000**(5분)
- `onCall timeoutSeconds`: 60 → **320**
- 원래 값·되돌릴 조건("업스트림 소요시간 분포를 확보한 시점")을 주석에
  명시(커밋 `dfcd795`, 배포 완료).

**실측 결과(최초 성공 측정)**: 본인 계정 재시도 요청
(`reqId=90ad4194`, requestBytes=496,695) — **110.8초(elapsedMs=110,810)
만에 success, upstreamStatus=200, responseBytes=2,941,335**. 55초
한도가 실제 소요시간의 정확히 절반 지점에서 매번 잘라내고 있었던
것으로 확인.

**단, 사용자 체감은 그대로 실패**: 클라이언트 `HttpsCallableOptions`는
여전히 60초라, 서버가 110.8초 걸려 응답할 무렵엔 클라이언트가 이미
60초에 `DEADLINE_EXCEEDED`를 띄운 뒤였다(사용자 실기기 확인 +
`fitting_cache`에 해당 시각 신규 기록 없음으로 교차검증).

**최종 결론**: 페이로드·계정 특유·특정 이미지 전부 배제/약화되고,
**"이미지 모델 자체가 정상(실측 12.7~37.8초대) 대비 훨씬 느리게(실측
110.8초) 응답한다"는 업스트림 지연**으로 원인이 좁혀졌다. **왜
느려졌는지(모델 저하 vs 특정 조건)는 여전히 미규명** — 다음 세션
과제로 handoff에 등록.

커밋: `d3f2cf5`, `dfcd795`, `eb1ee48`.

## 5. 등록만 하고 고치지 않은 것 (의도적)

- **재시도 정책**: `_withRetry`가 55초 실패를 백오프 없이 동일
  페이로드로 즉시 재시도 — 실패할 확률이 높은 상황에서 대기시간·업스트림
  비용을 실질 2배로 만든다. 지금 고치면 다음 재현 관측이 바뀌므로
  이번 세션에서는 등록만 함.
- **클라이언트 60초 타임아웃**: 서버는 300초로 늘렸지만 클라이언트는
  그대로 — 사용자 체감 실패는 아직 해소되지 않았다. 다음 판단(분포를
  더 볼지, 클라이언트도 늘릴지)은 이후 세션 과제.
