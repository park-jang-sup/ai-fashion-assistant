# 가상 피팅 품질 판별·개선 v1 — 지시서

작성 2026-08-31. 개정 2차(검토 6건 반영: forceRegenerate·집합
원복·예산·슬롯 8·커버리지·2안). 개정 3차(접두사
슬롯 표·유효 실행 정의·0단계 관문·교차 실행). **개정 4차
(2026-08-31)** — fittingOrder 인용 정정(액세서리 포함 5원소),
달성 불가 지시("액세서리 입력 순서 고정") 삭제, 슬롯 표를 코드
실동작(7벌에서 모자 뒤 2단계)에 맞게 교체 + 5벌 vs 7벌 보조
관측 축 추가. **[착수 승인 완료, 2026-08-31]** 아래 판정 기준의 굵은
값들은 문서 끝 체크리스트에서 사용자가 확정했다 — 확정 후에는
결과를 보고 바꾸지 않는다(6.5.1 규칙).

## 배경 — 왜 이 트랙인가

가상 피팅 품질 저하가 체감되고 있고, 코디보드 슬롯 축소(8→4~5)가
검토되고 있다. 그런데 축소는 **H-1(누적 손실)이 참일 때만 효과가
있는 베팅**이다 — H-3(카테고리 고유 난이도)이 참이면 단계를 줄여도
액세서리를 포함하는 한 품질은 돌아오지 않는다. 두 가설의 판별
실험(접두사 집합 재실행)은 `task_hardening_v2.md` §6-3에 설계
완료·착수 가능 상태로 등록되어 있다(handoff_2026-08-15 §2 표
27번). **판별 없이 축소부터 하는 것을 이 지시서로 막는다.**

이 트랙은 5단계다: 계측 선행(0) → 판별 실험(1) → 보드-피팅
분리(2) → thinking_level A/B(3) → 액세서리 일괄 프로브(4).
Nano Banana Pro 전환(5)은 선택 항목으로만 등록한다.

각 단계는 커밋 분리, `flutter analyze`/`flutter test`/`npx tsc
--noEmit` 통과 후 다음 단계. **배포(firebase deploy)는 단계마다
사용자 승인 후 수동.**

## 0단계 — 단계 로그에 카테고리 추가 (계측 선행)

handoff_2026-08-15 §2 표 26번의 3번 항목. §6-3이 명시한 판별
실험의 **선결 조건**이다 — 이것 없이는 1단계 결과를 시간 축으로
해석할 수 없다.

- `callGeminiText`의 구조화 로그(`[callGeminiText] start/done`)에
  그 단계가 입힌 **카테고리**를 함께 남긴다.
- 카테고리는 클라이언트가 안다(`onProgress` 콜백이 이미 받는 값,
  `gemini_service.dart:435` 부근).
- **새 필드는 callable 데이터 래퍼의 형제 키**(`model`·`requestBody`
  옆)로 싣는다 — `evaluateRequestShape`는 `requestBody`만 검사하므로
  통과하고, `requestBody`를 안 건드리니 **프롬프트·모델 입력 불변**이
  구조적으로 보장된다.
- **관문: 배포 후 실기기 피팅 1회에서 카테고리가 포함된 서버 로그
  실측 1건.** 형제 키는 `evaluateRequestShape`에 도달하지 않으므로
  단위 테스트로는 아무것도 검증되지 않는다 — 형제 키를 읽어 로그로
  옮기는 배선은 index.ts 계층이고, 그 계층은 이 저장소의 미검증
  계층이다(논문 7.1 "검증 체계 비대칭"). "코드가 그렇게 되어
  있다"가 아니라 "실제로 남더라"를 관문으로 삼는다. 이 관문은
  배포를 포함하므로 0단계 배포 승인이 선행된다.
- **커버리지 조건**: 이 로그는 `serverFittingCacheEnabled=false`
  (현재 기본값)일 때만 전 단계를 커버한다 — 플래그가 켜지면 마지막
  단계가 `generateFittingImage`로 빠져 로그가 빈다. **1단계 실험은
  플래그 off 상태로만 실행한다**를 여기서 함께 고정한다.
- 이 커밋은 로그만 바꾼다. 다른 어떤 동작도 바꾸지 않는다.

## 1단계 — 접두사 집합 판별 실험 (H-1 vs H-3)

설계는 `task_hardening_v2.md` §6-3 원문을 따른다. 여기서는 집합
정의·실행 절차·예산을 고정한다.

### 접두사의 정의 — 슬롯 집합의 접두사다 (렌더링 순서의 접두사가 아니다)

`_generateFittingImageSequential`은 입력 순서와 무관하게
`fittingOrder = ['상의', '하의', '아우터', '신발', '액세서리']`
(`gemini_service.dart:40` — **액세서리가 목록 안에 있다**)로
재정렬한다. 모자·가방·시계는 전부 최상위 `category`가
'액세서리'(subCategory로만 구분, `wardrobe_item.dart:10`)이고
`clothingNames`에는 이 최상위 category가 실리므로
(`fitting_job_controller.dart:283`), 셋은 4번 인덱스에서 동률이
된다. 동률은 입력 인덱스 비교(`a.compareTo(b)`,
`gemini_service.dart:408`)로 안정 처리되고, 입력 목록은
`selectedItems.values` — 사용자가 슬롯을 채운 순서가 아니라
**main.dart 맵 선언 순서**(아우터·상의·하의·신발·**모자·가방·
시계**·팔찌, `main.dart:190-198`)다. 따라서:

- **액세서리 내 렌더링 순서는 코드가 고정한다(모자→가방→시계).
  실험자가 제어하지 않으며, 제어하려고 코드를 바꾸지 않는다** —
  측정 대상 자체를 바꾸는 것이고 과거 관측(같은 코드로 실행됨)과의
  비교도 깨진다.
- 렌더링 순서로 접두사를 자르면 짧은 집합에서 모자가 빠져
  H-3("접두사에 모자를 포함시켜 검증", §6-3 원문)이 검증 불가가
  된다. 집합은 아래 표로 고정한다:

| 집합 | 슬롯 구성 | 모자 앞 단계 | 모자 뒤 단계 |
|---|---|---|---|
| 3벌 | 상의·하의·**모자** | 2 | 0 |
| 4벌 | + 신발 | 3 | 0 |
| 5벌 | + 아우터 | 4 | 0 |
| 7벌 | + 가방·시계 | 4 | **2** |

- **판별의 주 축은 3→4→5벌이다** — 모자가 마지막 단계이고 앞
  단계 수만 2/3/4로 변하는 깨끗한 통제.
- **5벌 vs 7벌은 보조 관측 축이다** — 모자 앞 단계 수는 4로
  동일하고, "이미 얹힌 모자 위로 후속 재생성 2회가 지나가는"
  효과만 분리된다(누적 손실의 다른 얼굴 — 선반영 부위의 후속
  붕괴). **주 판정에는 쓰지 않고 해석 각주로만 기록한다** —
  사전 등록 판정 축을 늘리는 것이 아니다. 과거 7벌 관측도 정확히
  이 구조로 실행됐으므로 비교 가능성이 유지된다.
- 아이템은 과거 관측(2026-08-11, 내림차순 4회)과 같은 것을 쓴다.
  과거 실행의 집합 구성이 이 표와 다른 것으로 확인되면 **이 표가
  정본**이고, 차이를 결과 해석 시 명시한다.

### 실험 절차

- **유효 실행 = 캐시 미스 실행(`isFittingFromCache == false`).**
  기본 경로는 생성 전에 `fitting_cache`를 조회해 히트 시 생성 없이
  반환한다(`fitting_job_controller.dart:261` 부근) — 캐시 히트는
  모델 호출 없는 실행이라 시간·품질 데이터 전부 무효이며, 겉으로는
  "빨라진 것처럼" 보여 발견도 늦는다. 1회분의 신규 조합은 캐시
  미스라 기본 경로가 곧 유효 실행이다. **캐시 히트가 뜨면(2회분
  부터) 재생성 버튼(`forceRegenerate: true`,
  `fitting_room_screen.dart:1252` — `hasRealFittingResult`일 때만
  노출)으로 재실행한다.** 매 실행의 캐시 미스 여부를 기록에 남긴다.
- 각 집합 1회 실행 = 1회분. **최소 2회분 반복**(단일 관측 판정
  금지 — 개정 5판의 추론 토큰 386~766 산포 사례).
- **집합 실행 순서는 회분마다 기록한다.** 1회분은 과거 관측과 직접
  비교되도록 내림차순(7→5→4→3), 2회분은 오름차순(3→4→5→7)으로
  돌려 실행 순서 효과 유무를 병행 관측한다(§6-3의 순서 효과 경고
  대응).
- 관측 항목: (a) 접두사별 모자(동일 아이템)의 품질(육안, 원본
  대조), (b) 부위별 붕괴 정도와 합성 순서의 상관(§6-3이 H-1 직접
  겨냥 항목으로 등록한 것), (c) 단계별 시간(0단계 로그로 카테고리
  매칭).
- **품질 판정 자료는 같은 배율의 부위별 크롭으로 남기고, 확대
  조건(배율·크롭 범위)을 함께 기록한다.** §6-3 원문: 지난 관측에서
  확대 조건 미기록으로 정정이 두 번 발생했다("모델이 상반신만
  생성했다"는 관측이 크롭 탓으로 판명). 전체 프레임 원본도 별도
  보존한다.

### 판정 기준 (실행 전 고정)

- **H-1 지지**: 모자 품질이 **3벌>4벌>5벌로 단조 악화**(앞 단계
  수 2→3→4와 동행) **그리고** 부위별 붕괴 정도가 합성 순서
  (뒤일수록 심함)와 상관.
- **H-3 지지**: 3~4벌 집합에서도 모자 자리 품질 저하 유지
  **그리고** 붕괴가 순서와 무관하게 특정 카테고리에 고정.
- 혼재 시: 두 축을 분리 기록하고 축소 결정은 보류, 2단계(분리)만
  진행한다 — 분리는 어느 가설이 맞아도 유효하다.

### 호출 예산 (사전 고정)

1회분 = image **19콜**(7+5+4+3) + fitting 4콜. 상한은 image
32/시간, fitting 6/시간(`index.ts` RATE_LIMIT_CONFIG 실측 확인).

- **1회분 = 시간 창 하나.** 2회분 연속(38콜)은 image 상한을
  넘으므로 회분 사이에 창 경계를 둔다. 창 안 여유는 32−19=13콜 —
  업스트림 "high demand" 재시도(재시도 1건 = image +1, 검증 세션
  3회 중 2회 발생 이력)를 흡수할 수 있는 폭이다.
- **재시도 누적으로 창 안 image 소진이 32에 닿으면 그 회분은
  폐기하고 다음 창에서 재실행한다** — 429 이후의 시간·품질 측정은
  오염으로 간주한다(사전 등록).
- 상한을 올리지 않는 것이 기본이다. 3회분 이상이 필요해져 일정상
  불가피할 때만 `fittingLimit`/`imageLimit`을 임시 상향한다 —
  UPSTREAM_TIMEOUT_MS 임시 상향 때와 같은 형식: 상향 값·사유·
  **복원 조건(실험 종료 커밋에서 원복)**을 이 문서에 추기하고,
  원복 커밋까지가 실험의 일부다.

## 2단계 — 보드-피팅 분리 (판별 결과와 무관하게 진행)

코디보드는 **8슬롯**(아우터·상의·하의·신발·모자·가방·시계·팔찌,
`main.dart:189` 부근) 유지. **피팅 렌더링만 코어 4개(아우터·상의·
하의·신발)로 캡**하고, 액세서리는 결과 화면에 텍스트/썸네일로
병기한다.

- **캐시 키에는 실제 렌더링된 아이템 id만 넘긴다.**
  `buildFittingCacheKey`가 `sorted(clothingItemIds)` 해시이므로
  (functions/src/fitting_cache_key.ts:18-21 확인), 보드 8개 id를
  그대로 넘기면 같은 코어 4개 + 액세서리만 다른 보드들이 캐시를
  못 맞춘다. 클라이언트 쪽 캐시 키 계산(crypto 동일 알고리즘)도
  같은 커밋에서 같은 목록을 쓰게 한다 — 어긋나면 서버/클라이언트
  캐시가 서로 다른 키를 만든다.
- `beginFittingAttempt`·rate limit 의미는 불변("피팅 시도 1회 =
  1콜") — 렌더링 아이템 수가 줄면 image 콜만 자연 감소한다.
- 캡은 상수로 두되 **되돌릴 수단**을 남긴다(순차 합성 §g와 같은
  패턴 — dart-define 또는 단일 상수).
- 1단계에서 H-1이 지지되고 사용자가 승인하면, 이후 "액세서리
  풀 렌더링"을 유료 옵션 후보로 로드맵에만 등록한다(이번 트랙
  범위 아님).

## 3단계 — thinking_level A/B

`gemini_service.dart`의 이미지 생성 두 호출(369·448행 부근)은
현재 `responseModalities`만 설정 — 문서 기준 gemini-3.1-flash-image의
thinking_level 기본값은 minimal이고 high가 지원된다.

### (a) 파라미터 수용 단독 검증 — A/B보다 먼저

이 저장소는 모델 파라미터 계약 회귀를 이미 겪었다(개정 5판).
**high A/B에 들어가기 전에**, 이미지 모델이 이 파라미터 조합
(`generationConfig.thinkingConfig.thinkingLevel` — REST 필드명이
텍스트 계열의 `thinkingBudget`과 다를 수 있으므로 400 응답 시
공식 REST 레퍼런스로 필드명부터 확정)을 실제로 수용하는지 옷
1벌 호출 1회로 단독 확인한다. 수용 실패 시 이 단계 전체를 접고
결과만 기록한다.

서버는 수정 불필요 — `request_shape.ts`는 top-level 키와 part
키만 검사하고 `generationConfig` 내부는 검사하지 않는다(코드
확인됨). 단, 이 사실을 근거로 쓰지 말고 (a) 검증 때 실제 통과를
함께 확인한다.

### (b) 판정 기준 — 품질·지연 2축, 실행 전 고정

이 트랙의 고통 축이 애초에 지연이었다. 단일 축 판정 금지.

- 측정: 같은 조합으로 minimal/high 각 **3회**, **교차 실행
  (m→h→m→h→m→h) + 실행 순서 기록** — 연속 실행(m 3연속 → h
  3연속)은 업스트림 상태의 시간 변동이 조건과 교란된다(1단계
  순서 효과 대응과 같은 결). 전부 캐시 미스 실행(1단계와 같은
  기준·같은 확인 절차). fitting 6콜 = 한 시간 창 소진 — 다른
  피팅 작업과 겹치지 않는 시간에 실행.
- **채택 조건(제안값, 사용자 확정 필요)**: 육안 품질이 3회 중
  2회 이상 우위 **그리고** 단계당 소요 중앙값 증가 **+15초
  이하** **그리고** 60초 초과 스파이크 발생률이 minimal 대비
  증가하지 않음.
- 채택 시 적용 범위도 사전 결정. **1안**: 문제 카테고리 단계만
  high(1단계 판별 결과가 대상을 알려준다). **2안**: 문제
  카테고리가 2단계 이후 렌더링 대상 밖(액세서리)이면 1안은 적용할
  단계가 존재하지 않는다 — 이 경우 **마지막 단계만 high**로
  대체한다. §6-3이 H-3 부분 지지 + 문제 카테고리 후보로 모자를
  이미 지목하고 있으므로 2안이 실제 경로가 될 가능성이 높다.

## 4단계 — 액세서리 일괄 합성 프로브

**이것은 회귀 구간 재진입 실험이다.** "이미지 여러 장 한 요청"은
정확히 60~300초 회귀가 관측된 조건이다. 목적은 소형 아이템
(시계·팔찌·모자·가방)이 같은 문턱을 밟는지의 1회 확인이지,
기능 구현이 아니다.

- 형태 검증은 통과한다 — `request_shape.ts` 상한이 inlineData
  9(전신 1 + 슬롯 8)로 잡혀 있어 "중간 결과 1 + 액세서리 3~4"는
  범위 내(코드 확인됨). 서버 수정 없이 클라이언트 임시 경로로만,
  캐시 미스 실행으로 한다.
- **탈출 기준(사전 고정)**: 프로브 1회에서 소요 **60초 이상**이
  나오면 즉시 접고 결과만 기록한다. 재시도·반복 금지 — 회귀
  구간에 예산을 태우지 않는다.
- 60초 미만이면 2회만 추가해 재현성을 보고, 성립 시 "코어 4
  순차 + 액세서리 일괄 1"의 5단계 구조를 별도 지시서 후보로
  등록한다(이번 트랙에서 구현하지 않는다).

## 5단계 (선택, 별도 승인) — Nano Banana Pro 시험

착수하지 않는다. 등록만 한다. 착수 시 반드시 지킬 것:

- `ALLOWED_MODELS`(index.ts)와 **`kindForModel`(payload_limit.ts)을
  같은 커밋에서** 바꾼다. `kindForModel`은 현재
  `model === "gemini-3.1-flash-image"` 문자열 완전 일치라(코드
  확인됨), Pro 모델명을 추가하지 않으면 이미지 페이로드가 text
  상한으로 판정되어 **첫 호출부터 조용히 거부**된다 — 폴백만
  죽는 게 아니라 경로 전체가 죽는다.
- 클라이언트 `_imageModel`과 서버 화이트리스트를 같은 커밋에서
  바꾼다(기존 규칙).
- 적용 범위 1안: 마지막 단계만 Pro, 또는 재생성 요청 시만 Pro.
  비용·지연 실측 전 전면 적용 금지.

## 금지 사항

- **1단계 접두사를 렌더링 순서로 자르지 않는다.** 집합 구성은
  본문의 슬롯 표가 정본이다 — 렌더링 순서로 자르면 짧은 집합에서
  모자가 빠져 H-3이 조용히 검증 불가가 된다.
- **액세서리 렌더링 순서를 바꾸려고 코드(fittingOrder·맵 선언
  순서·동률 처리)를 수정하지 않는다** — 측정 대상 변경이자 과거
  관측과의 비교 파괴다.
- **캐시 히트 실행을 유효 데이터로 쓰지 않는다.** 매 실행
  `isFittingFromCache == false` 확인을 기록에 남긴다(1·3·4단계
  공통).
- **판별(1단계) 전에 슬롯 수·렌더링 캡 이외의 품질 대응을
  선반영하지 않는다.** 특히 프롬프트 수정 금지 — 실험 중 프롬프트가
  바뀌면 접두사 간 비교가 무효가 된다.
- 판정 기준을 결과를 본 뒤 바꾸지 않는다. 바꿔야 한다면 사유를
  적고 해당 회분을 폐기 후 재실행한다.
- 실패·스파이크를 인위로 유발하지 않는다.
- 1단계 실험 중 `serverFittingCacheEnabled`를 켜지 않는다(0단계
  커버리지 조건).
- 상한(`fittingLimit`·`imageLimit`) 상향은 1단계 예산 절의 절차
  없이 하지 않는다. 상향했다면 원복 커밋 없이 트랙을 닫지 않는다.
- 배포는 단계마다 사용자 승인 후 수동. CI는 컴파일·테스트 검증만.
- 이 문서의 실측 서술(행 번호·상수 값)과 저장소가 어긋나면
  저장소가 옳다 — 어긋남을 발견하면 이 문서에 정정 블록을 추가한다.
