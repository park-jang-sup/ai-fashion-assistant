# 배경 제거 재개 — 서버 이관 (v1)

작성 2026-08-06. 전제: 이건 버그 수정이 아니라 런타임 교체다. 원인은
앱 코드 밖(onnxruntime-android 네이티브)에 있고, 우리 쪽 코드/설정으로
고칠 수 없다는 실무적 결론은 유효하다(§0 참고 — 다만 "어떤 버그인지"의
근거는 부정확했다는 게 이번 조사에서 드러났다).

## 0. 방향 결정 근거 (2026-08-06, (B) 서버 이관 채택)

1. **(C) 조사가 원인 규명 자체를 흔들었다.** 스파이크 노트
   (`docs/tflite_background_removal_spike_notes.md`)가 인용한
   `microsoft/onnxruntime#12679`는 우리 버그가 아니었다 — 실제
   원인은 tree-ensemble 모델의 feature_id 인덱스 초과(SIGSEGV)로,
   JNI와 무관하다. 진짜 관련 있는 JNI pending-exception 수정
   (`#11451`+PR`#12516`)은 2022-09-09에 이미 머지돼 onnxruntime
   1.13.0부터 포함됐는데, 우리는 그보다 한참 뒤인 1.23.0에서 크래시를
   재현했다 — "업스트림이 언젠가 고칠 것"이라는 기대 자체가 성립하지
   않는다. 1.23.0 이후 1.28.0까지 릴리스 노트 전수 확인 결과 관련
   수정 없음. 상세 경위는 스파이크 노트와
   `docs/handoff_2026-08-04.md`의 정정 블록(2026-08-06) 참고. 논문
   5.7절도 같은 부정확한 근거를 인용 중 — rev8 논문 세션에서 정정
   필요(지금은 메모만).
2. **(A, 온디바이스 TFLite 교체)는 리스크가 중첩된다.** 도메인이 맞는
   모델(U²-Net 계열)은 공식 TFLite 완성본이 없어 자체 변환이 새
   미지수이고, 변환에 성공해도 마스크 품질 유지가 별개 검증이다.
   완성 TFLite 바이너리가 있는 모델(MediaPipe Selfie Segmentation)은
   인물 전용이라 우리 사진(사람 없는 단독 의류 촬영)에 도메인이 안
   맞는다. 조사 상세는 이전 턴의 비교표 참고(이 문서에는 요약만).
3. **(B, 서버 이관)의 미지수가 가장 적다.** rembg/U²-Net을 서버에서
   Python으로 돌리는 건 업계에서 널리 검증된 경로이고, C-4b에서 만든
   `onObjectFinalized` 업로드 트리거 패턴을 그대로 재사용할 수 있다
   (`functions/src/index.ts`의 `revokeTokenOnUpload`가 이미 실기기
   검증까지 끝난 선례).

**비용/로드맵 불일치는 여전히 유효한 트레이드오프다** — 무료였던
처리가 건당 서버 비용으로 바뀌고, 로드맵이 원래 그렸던 "온디바이스
교체" 방향과 반대다(로드맵 13번 원문은 이 저장소에서 확인 못 함,
사용자 언급을 그대로 인용). 이 트레이드오프를 감수하고 (B)로
진행한다는 것이 이번 결정이다 — 되돌리기 어려운 결정은 아니다(§7
참고, 트리거 하나 삭제로 원복 가능).

### 1-4. 리뷰 결함 1 — 전신 사진에 컷아웃 생성 (수정 완료, 2026-08-07)

**증상**: 클라이언트는 `category != '전신'`일 때만 배경 제거를
시도하는데(`wardrobe_screen.dart:587`), 트리거(`functions_bg_removal/
main.py`)는 애초에 조회를 안 하는 설계(§1-3)라 카테고리를 판정할
수단이 없어 전신 사진에도 컷아웃을 만들고 있었다. `SignedNetworkImage`가
`cutoutImageUrl ?? imageUrl` 순으로 우선 컷아웃을 표시하므로(§3),
옷장 카드와 피팅룸 Step 1의 전신 기준 이미지 표시가 의도치 않게
바뀐다. u2netp는 인물 매팅 모델이 아니라 품질도 보장 안 됨.

**수정**: 업로드 커스텀 메타데이터에 `category`를 추가해(§1-3의
`wardrobeDocId`/`ownerUid`와 같은 자리) 트리거가 조회 없이 판정할
수 있게 했다.

- `storage_service.dart`의 `uploadWardrobeImage`에 `required String
  category` 파라미터 추가, `customMetadata`에 `'category': category`
  포함.
- `wardrobe_screen.dart` 호출부에서 이미 선택된 `category`를 그대로
  전달.
- `functions_bg_removal/main.py`: `wardrobeDocId`/`ownerUid`와 함께
  `category`도 메타데이터 완전성 검사에 포함(셋 중 하나라도 없으면
  §1-3 7항과 동일하게 처리 대상 제외 + 로그만). `category == '전신'`이면
  즉시 반환(로그 남김). **Firestore 조회로 판정하지 않는다** — 이
  설계의 전제(문서가 아직 없을 수 있음, §1-3)를 그대로 지킨다.

### 1-5. 리뷰 결함 2 — 디버그 빌드에서 컷아웃 이중 생성 ((b) 채택·구현 완료, 2026-08-07)

**증상**: `wardrobe_screen.dart:201`의 `if (kReleaseMode) return;`은
release에서만 온디바이스 배경 제거 초기화를 막는다. 디버그 빌드에서는
`_isBgRemoverReady`가 true가 되어 클라이언트가 자체 컷아웃을 만들어
`uploadWardrobeCutout`으로 올리고, **동시에** 서버 트리거도 같은
`wardrobeDocId`에 대해 독립적으로 컷아웃을 만들어 `doc_ref.set(...,
merge=True)`로 `cutoutPath`/`cutoutImageUrl`을 쓴다. 두 쓰기 다 같은
필드를 갱신하므로 나중에 도착한 쪽이 이기고, 진 쪽이 올린 Storage
파일은 어느 문서에서도 참조되지 않는 고아로 남는다 — §1-3에서 언급한
기존 고아 유형(5.18.3, 5.19.4)과 같은 구조가 새 경로에서 재생산되는
것. release에서는 클라이언트 쪽이 애초에 안 돌아 충돌이 없다.

**방향 비교**(결정은 사용자 몫, 코드 변경 없음):

| 방향 | 내용 | 장점 | 단점 |
|---|---|---|---|
| (a) 클라이언트 배경 제거 경로 완전 제거 | `image_background_remover`/온디바이스 초기화·호출 코드를 디버그 포함 전부 삭제 | 이중 생성 구조 자체가 없어짐, 코드 단순화 | §6에서 이미 "서버 경로가 검증되기 전에는 아무것도 제거하지 않는다"는 원칙을 세워둔 상태 — 서버가 아직 실기기 미검증인 지금 되돌릴 안전망(클라이언트 경로)을 먼저 없애는 셈. 서버에 새 결함이 나오면 롤백 수단이 `functions:delete`뿐이고, 그 사이 컷아웃이 전혀 안 생기는 공백 발생 |
| (b) 디버그에서도 클라이언트 경로를 끄고 서버만 쓰게(플래그 하나) | `kReleaseMode` 대신 별도 상수(예: `_useOnDeviceBgRemoval = false`)로 온디바이스 초기화 자체를 막되, 코드/의존성은 유지 | 이중 생성 즉시 해소, 클라이언트 코드는 그대로 남아 있어 되돌리기 쉬움(상수 하나 뒤집으면 복구), §6 원칙("아무것도 제거하지 않는다")과 충돌 없음 | 디버그에서 온디바이스 경로 자체를 비교 검증할 수단이 당분간 사라짐(§6이 이미 "디버그에서는 비교용으로 당분간 남겨둘 수도 있다"고 언급한 용도가 없어짐) |
| (c) 클라이언트/서버 어느 쪽이 썼는지 구분해 서버 쓰기만 우선시키는 조율 | 예: 서버 쓰기에 `cutoutSource: 'server_v1'` 마커(§5에서 이미 제안된 필드)를 달고, 클라이언트는 디버그에서 컷아웃을 **올리지 않고 로컬 미리보기로만** 쓰거나, 문서에 이미 `cutoutSource`가 있으면 클라이언트 쓰기를 건너뜀 | 디버그에서 온디바이스 결과를 여전히 눈으로 비교해볼 수 있음(파일 업로드는 안 하고 미리보기만) | 구현 범위가 (b)보다 크다(§5의 스키마 변경을 앞당겨 결정해야 함, 이 문서 §5는 "제안만"이라고 못박아 둔 상태) — 이번 리뷰 대응치고 과함 |

**결정: (b) 채택**(사용자, 2026-08-07). 구현:

- `wardrobe_screen.dart`의 `_initBackgroundRemover()` 진입부를
  `if (kReleaseMode) return;`에서 `if (!_kOnDeviceBgRemovalEnabled)
  return;`로 교체 — **명시적 상수 하나**(`const bool
  _kOnDeviceBgRemovalEnabled = false;`, 파일 상단)로 디버그·릴리스를
  동일하게 끈다. release 전용 분기였던 게 release에서만 재현되는
  결함(온디바이스 배경 제거 크래시 자체가 그 사례)을 디버그 검증이
  못 잡는 전례를 반복하지 않기 위함 — 디버그가 릴리스와 다른 경로를
  타면 "디버그에서 됐다"가 릴리스 동작을 보증하지 못한다.
- `image_background_remover` 의존성과 `_isBgRemoverReady`/
  `_removeBackgroundWithPreview`/온디바이스 ONNX 초기화 코드는
  **그대로 둔다** — 지우지 않는다. 플래그가 꺼진 상태에서
  `_isBgRemoverReady`는 초기값 `false`에서 절대 바뀌지 않고(그
  값을 `true`로 바꾸는 유일한 지점이 `_initBackgroundRemover()`
  안, 위 조기 반환 뒤에 있음), 업로드 시점의
  `category != '전신' && _isBgRemoverReady` 판정이 항상 거짓이 되어
  `cutoutBytes`가 `null`로 남는다 — `StorageService
  .uploadWardrobeCutout()` 호출부(`if (cutoutBytes != null) {...}`)
  자체가 도달 불가능해진다. 서명 URL 이행에서 킬 스위치를 기본
  꺼짐으로 두고 회수 후에도 레거시 폴백을 남긴 것과 같은 원칙 —
  서버 경로가 실기기 검증을 통과하기 전에는 되돌아갈 곳을 남긴다.
- **한시적 장치임을 코드 주석에 명시**(`_kOnDeviceBgRemovalEnabled`
  선언부): 최종 상태는 이 플래그가 아니라 (a) — 서버 경로가 실기기
  검증을 통과하면 온디바이스 초기화/호출 코드와
  `image_background_remover` 의존성 자체를 걷어낸다. 그때까지는
  서버에 새 결함이 나왔을 때 돌아갈 안전망으로 남겨둔다.

**남은 계획(이 문서에 등록)**: 서버 경로(`functions_bg_removal`)가
배포되어 실기기 검증(§4 체크리스트)을 통과하면, 다음 별도 승인
단계에서 (a)로 전환 — `_kOnDeviceBgRemovalEnabled`와 그 판정부,
`_isBgRemoverReady`/`_removeBackgroundWithPreview`/온디바이스 ONNX
초기화 코드, `image_background_remover`/`tflite_flutter`(§6에서
이미 별도 판단 대상으로 남겨둔 것) 의존성을 함께 제거한다. 지금
단계에서는 실행하지 않는다.

### 1-6. 미해결로 등록 — "파일은 있고 문서는 없거나 바닥 상태" (구현 안 함, 기록만)

코드 리뷰 Q3에서 확인된 유형: 클라이언트가 `uploadWardrobeImage`
이후 ~ `addWardrobeItem` 이전 사이 종료되면, Storage에는 원본(및
트리거가 이미 돌았다면 컷아웃까지)이 남고 Firestore에는 문서가
아예 없거나 `cutoutPath`/`cutoutImageUrl`만 있는 바닥 문서가 남는다
(`ownerUid`가 없어 `wardrobeStream`엔 절대 안 뜬다 — 사용자에게
안 보이는 채로 조용히 쌓임). §1-3에서 언급한 "문서만 있고 파일 없음"
(5.18.3/5.19.4)의 **반대 방향** 고아 유형이다.

발생 조건이 좁아(업로드 완료~문서 생성 사이의 짧은 창에서 앱 강제
종료) 지금 정리 도구를 새로 만들지 않는다 — 기존 `tools/
delete_orphaned_docs/`는 반대 방향(문서만 있음)을 다루는 도구라
범위 밖이다. 필요해지면 이 반대 방향 유형과 묶어 한 도구로 다룰 수
있다는 점만 남겨둔다.

**실측 1건 관측(2026-08-07)**: 이 유형이 이론이 아니라 실재함을
확인했다. `bg_removal_on_upload` 배포 직후 실측 1·2 시도 과정에서
`wardrobe_images/1e25aec129df4ff55c3574a38350fadc.jpg`
(`timeCreated` 2026-08-07T06:27:10Z)가 업로드됐으나, `imagePath`가
이 경로인 `wardrobe` 문서가 존재하지 않는다(읽기 전용으로 확인,
Firestore `where('imagePath', '==', ...)` 매칭 0건). 앞선 두 건
(`9131b52d...`, `bfc95961...`)은 정상적으로 문서가 붙었고 이 건만
빠졌다는 점에서, 등록 흐름 도중 이탈·취소(예: 카테고리/치수 선택
바텀시트를 닫거나 앱을 벗어남)로 `uploadWardrobeImage` 완료 후
`addWardrobeItem` 전에 흐름이 끊긴 것으로 추정 — §1-6 위 문단에서
설계 단계에 예견한 정확히 그 창이다. **손대지 않았다**(읽기만, 파일

### 1-1. 트리거 신설

`storage_fn.on_object_finalized(region=..., memory=..., min_instances=0)`
로 `wardrobe_images/` 업로드를 감지한다(`bucket`은 명시하지 않음 —
배포 시 Firebase 설정에서 자동 주입되는 걸 `revokeTokenOnUpload`와
동일하게 그대로 따름).

**반드시 `wardrobe_images/`로만 스코프를 제한한다** —
`wardrobe_cutouts/`·`fitting_results/`까지 받으면 이 함수 자신이
`wardrobe_cutouts/`에 쓴 결과가 다시 자기 트리거를 발화시켜
**무한 루프**가 된다(`revokeTokenOnUpload`는 메타데이터만 패치해
`finalized` 이벤트를 새로 만들지 않으므로 이 문제가 없지만, 이
함수는 새 오브젝트를 생성하므로 스코프 제한이 안전을 위한 필수
조건이다). Eventarc 필터(`bucket`)만으로는 프리픽스를 못 거르므로,
**함수 코드 진입부에서 `event.data.name.startswith('wardrobe_images/')`
아니면 즉시 return**하는 이중 방어를 둔다(설정 실수로 필터가
느슨해져도 코드가 막는다 — `revokeTokenOnUpload`의
`isTokenRevocablePath()`와 같은 패턴).

### 1-2. `revokeTokenOnUpload`와의 상호작용

같은 `google.cloud.storage.object.v1.finalized` 이벤트를 두
함수(Node `revokeTokenOnUpload`, Python 신규 함수)가 **각자 독립된
Eventarc 트리거로 동시에 받는다** — GCP는 이걸 순서 보장 없이
병렬로 전달한다. 실제로 겹치는 지점과 안전성 확인:

- **원본(`wardrobe_images/`) 업로드**: 두 함수 다 반응한다.
  `revokeTokenOnUpload`는 그 경로의 토큰만 지운다(파일 읽기는 안
  함). 신규 함수는 Admin SDK로 그 파일을 **읽어야** 한다 — Admin
  SDK는 토큰 유무와 무관하게 접근 가능하므로(토큰은 클라이언트용
  서명 없는 다운로드 URL 메커니즘일 뿐, Admin SDK 읽기는 IAM 기반)
  `revokeTokenOnUpload`가 먼저 토큰을 지우든 나중에 지우든 신규
  함수의 원본 읽기에는 영향이 없다. **순서 무관 — 안전.**
- **신규 함수가 쓰는 `wardrobe_cutouts/{path}`**: 이 쓰기 자체가 새
  `finalized` 이벤트를 만들어 `revokeTokenOnUpload`를 다시 발화시킨다
  — **이건 버그가 아니라 기존 설계 그대로다**(클라이언트가 직접
  올리던 컷아웃도 지금까지 똑같이 이 경로를 탔다). 새로 생긴 위험
  없음.
- **결론**: 두 함수는 서로 락이나 순서 조율이 필요 없다 — 겹치는
  범위가 "같은 파일을 서로 다른 목적으로 각자 처리"뿐이고 상호
  배타적 자원이 없다. 명시적으로 확인해야 하는 유일한 조건은 위의
  "무한 루프 방지 스코프 제한"뿐이다.

### 1-3. Firestore 문서 연결 — 메타데이터 전달 (확정, 2026-08-06)

`revokeTokenOnUpload`는 경로만 알면 되지만, 이 함수는 **어느
`wardrobe` 문서에 `cutoutImageUrl`/`cutoutPath`를 써야 하는지**
알아야 한다. 폴링도 클라이언트 순서 반전도 아닌 **제3안 — 업로드
메타데이터로 문서 식별자를 직접 전달**하는 방식으로 확정한다.

**설계**:

1. 클라이언트가 업로드 *전에* Firestore 문서 ID를 미리 확보한다 —
   `_db.collection('wardrobe').doc()`로 서버 왕복 없이 클라이언트
   쪽에서 새 ID를 할당(쓰기 아님, ID 생성만).
2. `StorageService.uploadWardrobeImage()`가 `SettableMetadata
   .customMetadata`에 `{wardrobeDocId: <위 ID>, ownerUid: <uid>}`를
   실어 업로드한다.
3. `FirestoreService.addWardrobeItem()`은 `.add()`(자동 ID) 대신
   `.doc(<위 ID>).set({...}, SetOptions(merge: true))`로 **같은
   ID**를 쓴다.
4. 트리거는 `event.data.metadata['wardrobeDocId']`를 읽어 조회 없이
   바로 그 문서를 대상으로 삼는다 — `db.collection('wardrobe')
   .doc(wardrobeDocId).set({cutoutPath, cutoutImageUrl}, merge=True)`.
   **트리거도 반드시 merge를 쓴다** — 클라이언트의 3번 쓰기와 서버의
   4번 쓰기 중 어느 쪽이 먼저 도착하든(순서 보장 없음) merge라서
   서로 덮어쓰지 않는다. 이게 이 설계의 핵심 — **레이스가 남아있는
   게 아니라 애초에 레이스가 성립하지 않는다**(두 쓰기가 서로 다른
   필드만 건드리고 양쪽 다 upsert이므로 순서 무관).
5. `ownerUid`는 방어용 — 트리거가 대상 문서를 쓰기 전에 문서의
   `ownerUid`(존재한다면)가 메타데이터의 `ownerUid`와 일치하는지
   대조한다. `storage.rules`가 `wardrobe_images/`에 소유자 검사
   없이 `allow write: if request.auth != null`만 요구하므로, 이
   대조 없이는 임의의 인증된 클라이언트가 `wardrobeDocId`를
   조작해 **다른 사용자의 문서에 컷아웃을 주입**할 수 있다 —
   메타데이터를 신뢰하되 소유권만은 서버가 다시 확인한다.
6. `demo_wardrobe`는 대상이 아니다 — 데모 옷장은
   `seedDemoWardrobe()`(`firestore_service.dart`)가 기존 `wardrobe`
   컷아웃을 복사해 채우는 것이라(코드 확인됨) 이 트리거를 거치는
   신규 업로드 자체가 없다.
7. **메타데이터가 없는 업로드는 처리 대상에서 제외하고 로그만
   남긴다** — 레거시 경로(이 기능 배포 전 업로드)나 다른
   클라이언트가 `wardrobeDocId`를 안 실었을 가능성을 놓고 경로
   기반으로 문서를 추측하지 않는다. 그 이미지는 그냥 컷아웃 없는
   원본으로 남는다(§3의 폴백 원칙과 동일).

**이 방식을 택한 근거**: 폴링(가)은 대기 시간을 임의로 정해야 하고,
초과 시 "컷아웃은 생겼는데 참조하는 문서가 없는" **세 번째 유형의
고아**를 구조적으로 만든다 — 이 저장소는 이미 두 유형의 고아를
겪었다(5.18.3, 5.19.4). 메타데이터 전달은 애초에 그런 실패 모드
자체가 없다(문서 참조가 항상 확정적으로 존재 — 클라이언트가 그
ID로 문서를 만들 것이 보장되어 있고, 순서만 불확실할 뿐 존재
자체는 불확실하지 않다). 그리고 이 원리는 서명 URL 이행 3.12.2가
"서명 대상을 경로가 아니라 문서 식별자로 결정한다"고 잡은 것과
같은 원리다 — 여기서도 "이미지가 어디 있는지"가 아니라 "이 이미지가
어느 문서 소유인지"를 업로드 시점에 명시적으로 실어 보낸다.

클라이언트 변경 범위(구현 시): `StorageService.uploadWardrobeImage`
시그니처에 `wardrobeDocId`/`ownerUid` 파라미터 추가,
`FirestoreService.addWardrobeItem`을 `.add()`→
`.doc(id).set(merge:true)`로 변경, 호출부(`wardrobe_screen.dart:612`)
에서 ID를 미리 뽑아 두 호출에 같이 넘기도록 조정. 업로드 순서
자체(putFile → addWardrobeItem)는 안 바꾼다 — `docs/
task_signed_urls_v1.md` §9 사고의 교훈("업로드 순서를 함부로 안
바꾼다")을 그대로 지킨다, ID를 미리 할당하는 것과 쓰기 순서를
바꾸는 것은 다른 문제다.

## 2. 모델 후보와 호스팅 판단

### 2-1. 모델 후보 — u2netp 우선

조사 1순위였던 경량판 **u2netp(4.7MB)를 먼저 품질 평가**한다 —
전체 u2net(176MB)의 1/37 크기라 호스팅 부담(컨테이너 크기·콜드스타트·
메모리)이 크게 줄어든다. u2netp는 아키텍처가 u2net과 동일하고
En.5 FeatureMap 채널 수만 512→64로 줄인 경량 변형이라(§1단계 조사
결과) 상당수 실사용 사례에서 품질 저하가 크지 않다고 알려져 있으나,
**우리 옷 사진(행거/평면 단독 촬영)에 대한 실제 마스크 품질은 아직
확인 안 됨** — 구현 스파이크의 첫 단계로 검증한다. 미달이면 그때
full u2net(176MB)으로 전환 — **처음부터 176MB를 기본값으로 잡지
않는다.**

### 2-2. 호스팅 판단 — Cloud Functions vs Cloud Run

**추정하지 않고 확인된 수치만 근거로 삼는다.**

| 항목 | 값 | 출처 |
|---|---|---|
| rembg 기본 모델(u2net.onnx, full) 크기 | 176MB | rembg가 `~/.u2net/`에 내려받는 실측 배포 파일(HuggingFace 미러 다수에서 동일 크기 확인) |
| rembg 경량 모델(u2netp.onnx) 크기 | 4.7MB | 동일 출처 — §2-1 우선 후보 |
| rembg 자체 의존성(onnxruntime 등 포함) | 약 400MB | rembg 배포 문서 |
| Cloud Functions(2nd gen) 메모리 상한 | 최대 32GiB, 128MB 단위로 설정 가능 | Firebase Functions 공식 quotas 문서 |
| Cloud Functions(2nd gen) 이벤트 트리거 타임아웃 상한 | **540초(9분)** — HTTP는 60분이지만 Storage 트리거는 이벤트 트리거 분류 | Firebase Functions 공식 quotas 문서 |
| Python 런타임 스토리지 트리거 지원 | `firebase_functions.storage_fn.on_object_finalized()` 존재, Node의 `onObjectFinalized`와 동일 이벤트 모델 | Firebase 공식 문서 |
| 여러 코드베이스(Node+Python 공존) | `firebase.json`의 `functions`를 배열로 바꿔 `codebase`별 `source`/런타임 분리 — Firebase 공식 기능(멀티 코드베이스) | Firebase 공식 문서 |

**메모리·타임아웃 상한만 놓고 보면 Cloud Functions(2nd gen, Python)로
충분히 들어간다** — u2netp 기준(4.7MB 모델 + 400MB 의존성)은 물론
full u2net(176MB 모델)을 쓰게 되더라도 32GiB 상한에 비하면 여유가
크고, 단일 이미지 추론(수 초 단위로 알려짐 — 아래 참고)은 540초
상한에 크게 못 미친다.

**확인 안 된 것, 그래서 결정을 못 내리는 부분**: **콜드스타트
지연시간.** 검색으로 찾은 "~10초 추론(모델 로드 포함)" 수치는 출처
불명확한 블로그 단편이고, 우리 환경(asia-northeast3, Cloud
Functions 2nd gen, 실제 컨테이너 빌드)에서 실측한 값이 아니다 —
이 트랙에서 "추정을 실측으로 확인하지 않아 세 번 틀렸다"는 교훈을
그대로 반복하지 않는다. 사용자 2명, 업로드 빈도가 낮은 앱 특성상
인스턴스가 자주 0으로 스케일다운될 것이므로 콜드스타트가 상시
경로가 된다 — 이게 무시 못 할 크기면 사용자 체감 지연(등록 후 컷아웃이
뜨기까지의 시간)이 문제 된다. u2netp를 먼저 쓰는 이유 중 하나도
이것 — 모델이 작을수록 콜드스타트 중 로드 시간이 줄어들 가능성이
높다(다만 이것도 실측 전까지는 가능성일 뿐).

**공통 전제 — 후보에서 이미 제외된 구성**: 호스팅을 Cloud
Functions로 하든 Cloud Run으로 하든, **매 요청마다 모델 파일을
Storage 등에서 새로 내려받아 로드하는 구성은 애초에 후보가 아니다**
— 176MB(또는 4.7MB)를 매 요청 I/O로 왕복시키는 건 콜드스타트보다
더 나쁜, 항상 발생하는 지연이다. 모델은 **컨테이너 이미지에
번들링**한다(빌드 시점에 이미지 안에 모델 파일 포함) — Cloud
Functions/Cloud Run 둘 다 컨테이너 기반 배포이므로 방식은 동일
하다.

**결정 규칙(구현 착수 시 첫 스파이크로 확정)**:
1. u2netp를 컨테이너에 번들링한 최소 기능(모델 로드 + 추론 1회 +
   결과 저장) Python Cloud Function을 실제 배포한다.
2. 콜드스타트(배포 직후 첫 호출) 3회, 웜스타트(연속 호출) 3회를
   실측해 초 단위로 기록한다.
3. 콜드스타트가 사용자 체감상 허용 범위(기준값은 사용자 판단 —
   예: 수 초~10초대는 "업로드 중" 스피너로 자연스럽게 가려짐,
   그 이상이면 문제)를 넘으면 **Cloud Run으로 전환**한다. 이때
   Cloud Run 쪽 구성은 다음 두 가지를 함께 적용한다 — 어느 하나만
   으로는 의미가 없다:
   - **최소 인스턴스 1**(`min instances=1`)로 콜드스타트를 원천
     제거. 상시 비용 발생이 트레이드오프 — 이 비용 자체가 §0의
     "무료였던 처리가 건당 비용으로 바뀐다"는 트레이드오프를
     인스턴스 상시 가동 비용으로 구체화한 것이다.
   - **컨테이너 내 모델 번들링**(위 공통 전제) — `min
     instances=1`이어도 요청마다 모델을 다시 로드/다운로드하는
     구성이면 상시 가동의 이점이 없다.
4. 이 실측 전에는 Cloud Functions/Cloud Run 둘 중 하나로 확정하지
   않는다.

### 2-3. 최종 결정 — u2netp + Cloud Run 최소 인스턴스 0 (2026-08-06)

**모델: u2netp.** 근거는 15건 표본이 아니라 **신발 22벌 전수
재평가**다(도메인 안에서 유일하게 결함이 몰린 카테고리이므로 전수
확인 대상으로 삼음, `tools/bg_removal_spike/` `--category 신발
--tag shoes_full`). 결과: u2netp 명확한 실패 3/22(kC0gwb —
신발끈 반투명화, MBbsBN·NBUt3T — 흰색-on-흰색 반투명) + 경미한
결함 1/22(Z0HlgPZ — 앞코 옅은 반투명 패치) = **4/22(18%)**. u2net
(full)은 **0/22** — 세 실패 전부 해소(2건은 완전 해소, 1건은 미세
잔여만). 사전 등록한 판정 기준(5벌 이상 실패 → full 채택, 2벌 이하
→ u2netp 유지, 3~4벌 → 콜드스타트/비용이 결정)의 **세 번째 구간**에
해당해, 아래 비용·콜드스타트 실측이 결정한다.

**호스팅: Cloud Run, 최소 인스턴스 0.** 근거:

1. **비용**: 공식 가격표(`cloud.google.com/run/pricing`, Seoul/
   asia-northeast3, Instance-based billing, Tier 2 확인) 기준
   최소 인스턴스 1을 30일 상시 유지하면 1GiB 구성 약 **$56/월**,
   full u2net에 필요한 2GiB 구성 약 **$62/월**(무료 등급 적용 후).
   옷 등록이 며칠에 한 번인 현재 워크로드에서 상시 인스턴스는
   과하다 — 논문 7.1절이 경계한 "사용자 수·사용량과 무관하게
   고정적으로 발생하는 비용"에 정확히 해당하는 사례다.
2. **콜드스타트(최소 인스턴스 0)**: 로컬 실측(완전히 새 Python
   프로세스, 3회 반복) 하한값 — u2netp **~1.29초**(import 1.04s +
   모델 로드 0.08s + 첫 추론 0.16s), u2net **~2.02초**. 컨테이너
   부팅 시간은 미포함이라 실제 값은 이보다 크다. 다만 배경 제거는
   **업로드 후 백그라운드 작업**이고 처리 완료 전까지 화면은 원본을
   그대로 보여주므로(§3 폴백 원칙) 수 초 지연이 사용자에게 체감되지
   않는다 — 지금 화면 흐름과 정합적이다.
3. **기준선**: 지금 릴리스는 **배경 제거가 완전히 꺼져 있어 컷아웃이
   아예 없다.** u2netp의 18/22(82%)도 이 기준선 대비 순수한 개선이고,
   실패 4벌은 "컷아웃이 없는" 현재 상태로 남을 뿐 더 나빠지지
   않는다 — 실패를 감수하는 게 아니라 실패해도 손해가 없는 구조다.
4. **부수 확인**: 콜드스타트의 절반 이상(u2netp 1.29초 중 1.04초)이
   **rembg 임포트 자체**(두 모델 공통, scipy/scikit-image/numba 등
   무거운 의존성)에서 나온다 — 모델을 u2netp로 유지해도 줄일 수
   있는 콜드스타트 폭 자체가 크지 않다는 뜻이고, 반대로 이건 모델
   선택과 무관하게 개선 여지가 남아있다는 뜻이기도 하다(재검토
   조건 (c) 참고).

**재검토 조건(아래 중 하나라도 성립하면 full u2net 전환을
재검토한다)**:
- (a) 실사용에서 흰색 신발 컷아웃 품질에 대한 불만이 실제로 제기됨.
- (b) 등록 빈도가 올라가 인스턴스가 사실상 상시 가동됨(콜드스타트가
  드물어짐) — 이 경우 이미 상시 비용이 발생하므로 min-instances=0을
  유지할 이유와 함께 full의 "비용 이점"도 같이 사라진다. 즉 이
  조건이 성립하면 모델·호스팅 둘 다 재평가 대상.
- (c) rembg 의존성을 걷어내고 onnxruntime을 직접 호출하는 경량
  런타임으로 교체 — import 시간이 콜드스타트의 절반 이상을 차지하는
  구조 자체를 줄이는 변경이라, 이러면 u2net의 콜드스타트 페널티도
  같이 줄어들어 재평가할 가치가 생긴다.

### 2-4. 배포 실측 — §2-3의 콜드스타트 전제가 틀렸다 (2026-08-06/07)

**전제 붕괴.** §2-3 결정은 로컬 하한(u2netp 1.29초) + "컨테이너
부팅은 몇 초 더 붙을 것"이라는 가정 위에서 "업로드 후 백그라운드라
체감 안 됨"이라고 판단했다. `tools/bg_removal_spike/cloud_run_spike/`
(HTTP 최소 구성, u2netp 컨테이너 번들링, 최소 인스턴스 0, invoker를
Admin SDK 서비스 계정으로 제한, 트리거 배선 없음)를 실제 배포해
재보니:

- **콜드스타트 실측 5회, 64~70초.** GCP 공식 지표
  (`run.googleapis.com/container/startup_latencies` — 내 코드가
  아니라 Cloud Run 자체가 잰 값) 4회: 67.9s/70.3s/67.9s/68.0s. 내
  직접 호출(외부 wall-clock) 2회: 69.5s/65.3s(그중 1회는 GCP 지표와
  같은 사건). **로컬 하한의 ~50배.**
- **원인은 모델도 onnxruntime도 아니다.** 함수 내부 타이머로 분해한
  결과 `moduleImportSeconds`(=rembg의 `import` 문 자체)가 63~67초로
  전체의 93% 이상, 모델 로드(0.1초)·요청 처리(1~1.6초)는 로컬과
  비슷하게 빠르다.
- **스케일다운이 예상(15분)보다 훨씬 공격적이다.**
  `run.googleapis.com/container/instance_count` 지표 실측 —
  마지막 요청 후 **1~3분 안에** 인스턴스가 사라진다. 연속으로 호출한
  두 요청도 각각 콜드스타트였다(둘 다 moduleImportSeconds
  63~67초로 동일). 콜드스타트가 드물 것이라는 가정도 같이 무너진다.
- **메모리·품질은 이상 없음** — 피크 메모리 실측 695MB/1024MB(68%,
  `run.googleapis.com/container/memory/utilizations`), 로컬 실측
  (693MB)과 거의 일치. 결과 이미지는 로컬과 픽셀 대조(평균 절대
  차이 0.39/255, 치수 동일) — 배포 함수가 입력을 JPEG로 한 번
  재인코딩하는 정규화 단계 때문의 미세 차이일 뿐 품질 문제 아님.
- 이번 배포+테스트 호출로 든 실제 비용: 콜드 5회+웜 2회 ≈ 350
  vCPU-초, 무료 등급(180,000/월)의 0.19% — §2-3의 비용 그림 자체는
  안 바뀐다.

**결론: 68~70초는 감수하지 않는다(사용자 판단, 2026-08-07) — min-
instances=1로 되돌리지도 않는다(월 $56, "비용 없는 개발" 원칙에
어긋남).** 재검토 조건 (c)(경량 런타임)를 즉시 착수.

### 2-5. 재검토 조건 (c) 착수 — 원인 확정 + 경량 재구현 검증 (2026-08-07)

**원인 확정(로컬, `python -X importtime -c "import rembg"`)**: 예상
(numba/scipy)은 맞았지만 경로가 달랐다 — **`rembg.bg`가 모듈 로드
시점에 `pymatting.alpha`를 무조건 임포트한다.** `pymatting.alpha`
→ `pymatting.util` → `pymatting.util.kdtree` → `numba` →
`numba.np.arraymath`/`numba.core.config` → `scipy.linalg`가 로컬
기준 전체 임포트 시간(1.9초)의 **63%(1.2초)**를 차지 — onnxruntime
자체는 176ms(9%)뿐이다. **결정적으로, 이 경로는 죽은 코드다**:
`remove(img, session=session)`(우리가 실제로 쓰는 기본 인자)는
`alpha_matting=False`가 기본값이라 `naive_cutout()`만 실행되고
`pymatting`은 임포트만 되고 한 번도 호출되지 않는다. Cloud Run
콜드 컨테이너의 디스크 I/O가 로컬 SSD보다 훨씬 느려서(추정 — 정확한
원인은 GCP 인프라 내부라 확인 불가) 이 무거운 체인(특히 numba의
LLVM JIT 백엔드 초기화)이 로컬 대비 불균형하게 느려진 것으로 보인다
(63~67초/1.2초 ≈ 50~55배, onnxruntime 자체의 로컬~클라우드 배율과
직접 비교할 클라우드 실측치는 없음 — §2-4의 68초는 rembg 전체
import 한 덩어리로만 쟀지 패키지별로 분해하지 않았다).

**경량 재구현(`tools/bg_removal_spike/minimal_runtime.py`)**:
rembg 없이 onnxruntime+numpy+Pillow만으로 동일 파이프라인을
재현했다 — `rembg.sessions.base.BaseSession.normalize()`(ImageNet
평균/표준편차, 320×320, LANCZOS)와
`rembg.sessions.u2netp.U2netpSession.predict()`의 후처리, `rembg.bg
.naive_cutout()`/`fix_image_orientation()`을 소스에서 그대로 확인해
옮겼다(정규화 파라미터를 임의로 정하지 않음).

**검증 — 34건(기존 15건 표본 + 신발 22벌 전수의 합집합, 중복 제거),
크롭 전 상태로 rembg u2netp 출력과 픽셀 대조**:
- **픽셀 차이 0.0000/255, 34건 전부 — 완전히 동일한 마스크.**
  결정론적 추론이라 당연한 결과지만, 재구현이 rembg의 전처리/
  후처리를 정확히 재현했다는 직접 증거다.
- **임포트 시간 0.107초**(rembg 1.04~1.36초 대비 **~10~13배
  감소**, 로컬 기준).
- 모델 로드 0.077초, 장당 추론 평균 0.128초(rembg와 사실상 동일 —
  같은 onnxruntime 호출이므로 예상대로).
- 피크 RSS 646.4MB — rembg 버전(693MB)보다 오히려 낮음(scipy/numba/
  pymatting을 안 올리므로).

**아직 확인 안 된 것(당시)**: 이 로컬 개선이 클라우드 콜드스타트에
그대로 반영되는지는 미실측이었다 — §2-4의 교훈이 정확히 "로컬
배율로 클라우드를 추정하면 틀린다"였으므로 재배포해 실측했다(§2-6).

### 2-6. 클라우드 재실측 — 채택 확정 (2026-08-07)

`tools/bg_removal_spike/cloud_run_spike/main.py`를 minimal_runtime
기반으로 교체해 **같은 서비스에** 재배포했다 — 리전(asia-northeast3)·
메모리(1GiB)·최소 인스턴스 0·u2netp 번들링·입력 JPEG 재인코딩
정규화·invoker 제한 전부 §2-4와 동일, 모델 로딩/추론 부분만 rembg→
minimal_runtime으로 교체(§2-4/§2-6 비교 가능성 확보).

**콜드스타트 측정 방법론 수정**: 자연 스케일다운 대기가 예측 불가능
하다는 걸 이번에 발견했다 — 처음엔 §2-4처럼 스케일다운을 기다렸는데,
200초·600초를 기다려도 인스턴스가 안 죽고 계속 같은
`moduleImportSeconds` 값을 반환했다(14분+ 유지). **§2-4에서 관측한
"1~3분 스케일다운"은 자연 유휴 종료가 아니라 재배포로 이전 리비전이
교체되면서 생긴 현상이었을 가능성이 높다** — 이번엔 그 혼동을
피하려고 기능 변경 없는 마커 주석만 바꿔 재배포해서(리비전 3개:
-00004/-00005/-00006) 매번 확실히 새 컨테이너를 강제했다.

**콜드스타트 3회(전부 서로 다른 리비전, `moduleImportSeconds` 값이
매번 달라 진짜 새 인스턴스임을 자체 확인)**:

| # | 외부 wall-clock | moduleImportSeconds | modelLoad | requestHandling | GCP 공식(`startup_latencies`) |
|---|---|---|---|---|---|
| 1 | 1.260s | 1.217s | 0.207s | 1.103s | **2.125s** |
| 2 | 1.435s | 1.057s | 0.144s | 1.299s | **1.924s** |
| 3 | 1.381s | 0.826s | 0.129s | 1.216s | (지표 반영 지연으로 미확인 — 내부 타이머는 #1/#2와 같은 패턴) |

GCP 공식 지표 2건이 내 외부 wall-clock보다 0.5~0.7초 크게 나온다 —
두 지표가 재는 경계가 다른 것으로 보이나(아마 `startup_latencies`가
컨테이너 프로세스 시작~트래픽 수신 준비까지를 포함하고 내 wall-clock은
연결 이후만 잼) 정확한 경계 차이는 이번 조사로 확정 못 했다. **다만
어느 쪽 수치를 기준으로 삼아도 판정 기준(5초 이하)에 압도적으로
못 미친다**는 결론은 안 바뀐다.

**웜 요청 3회**(같은 인스턴스, 연속 호출): 0.900s~1.336s(요청 처리만
0.789~1.103s) — 로컬 웜 추론(0.128s) 대비 ~6~9배 느리지만, 이건
Cloud Run의 vCPU가 로컬 개발 머신보다 약해서로 보이는 기존에 이미
관측된 현상(§2-4에서도 동일 폭으로 나타남)이지 이번 교체와 무관.

**메모리**: 피크 **673MB/1024MB(66%)**
(`container/memory/utilizations` 공식 지표) — rembg 버전(695MB)·
로컬 minimal_runtime(646MB)과 전부 같은 범위, 1GiB 그대로 충분.

**품질**: 이번 배포 결과를 §2-4(rembg 배포) 결과와 픽셀 대조 —
**평균 절대 차이 0.0, 최대 차이 0(완전 동일, 같은 입력 이미지
기준)**. 로컬 34건 검증(0.0000/255)에 이어 배포 환경에서도 무손실
교체임을 재확인.

**판정 — 사전 등록 기준 적용**: 콜드스타트 1.3~2.1초(측정 방식
무관하게) < 5초 → **채택.** minimal_runtime 기반 파이프라인 구현으로
진행한다. 근거 요약: 원인은 rembg가 무조건 임포트하지만 우리
파이프라인(`alpha_matting=False`)에서는 한 번도 실행되지 않는
pymatting/numba/llvmlite 죽은 코드였고, 제거 후 34건 무손실
검증(로컬)·배포 환경 픽셀 동일성(클라우드) 둘 다 확인했다.
콜드스타트가 68~70초→1.3~2.1초로 줄어 §2-3의 min-instances=0
결정이 그대로 유지 가능해졌다 — §2-3의 재검토 조건 (a)/(b)는
그대로 유효, (c)는 이번에 해소.

### 2-7. 이번 스파이크 트랙에서 남긴 세 가지 기록 (2026-08-07)

**정정 — "1~3분 스케일다운" 관측은 틀렸다.** §2-4에서 "인스턴스가
마지막 요청 후 1~3분 안에 사라진다"고 적었는데, §2-6에서 같은
리비전에 200초·600초 유휴 대기 후 호출해도 인스턴스가 안 죽고
14분+ 유지되는 걸 확인했다. §2-4의 관측은 **자연 유휴 종료가
아니라, 그 사이 여러 번 재배포하면서 이전 리비전이 새 리비전으로
교체돼 종료된 것**이었을 가능성이 높다 — 재배포 타이밍과 관측
타이밍이 겹쳐 원인을 착각했다. **판단에 준 영향**: §2-3의 "스케일
다운이 예상보다 빨라 콜드스타트가 잦을 것"이라는 우려가 과장된
것이었다는 뜻 — 실제 유휴 종료는 더 드물 가능성이 높고, 이 저장소의
실제 등록 패턴(§0 참고 — 70일 중 13일에만 활동, 그중 하루에 57%가
몰린 버스트형)에서는 한 버스트 안의 등록 대부분이 **첫 1건만
콜드, 나머지는 웜으로 처리될 가능성이 §2-4 때 판단한 것보다 높다**
— 다만 정확한 유휴 타임아웃 값 자체는 이번에도 확정 못 했다(GCP가
공개된 고정값을 안 씀).

**자체 타이머의 함정 — 계측 필드명 규칙.** `moduleImportSeconds`류
필드는 **인스턴스 수명 값**(모듈이 처음 로드될 때 딱 한 번 기록되고
그 인스턴스가 살아있는 동안 모든 요청에 그대로 반환됨)인데, 필드
이름만 보면 "이번 요청의 import 시간"처럼 보여서 §2-4·§2-6 둘 다
초반에 "연속 호출인데 값이 똑같다"를 곧바로 콜드스타트로 오인할
뻔했다(§2-4에서는 실제로 한 번 오인한 채 보고했다가 GCP 지표 대조로
정정). **파이프라인 구현의 계측 설계에 반영**: 요청 단위로 항상
달라지는 값(예: `requestHandlingSeconds`, 처리 시각)과 인스턴스
수명 동안 고정인 값(예: `moduleImportSeconds`, 콜드스타트 여부)을
필드명에서부터 구분한다 — 예: `instanceXxx` / `requestXxx` 접두어,
또는 인스턴스 시작 시각을 별도 필드로 같이 내려줘 "이 응답이 그
인스턴스의 몇 번째 요청인지" 호출부가 스스로 판단할 수 있게 한다.

**논문 rev8 반영 메모(지금 반영 안 함)**: rembg가 `alpha_matting=
False`(우리가 실제 쓰는 기본값)일 때 `pymatting`을 무조건
임포트만 하고 한 번도 실행하지 않는 죽은 코드 경로(§2-5)를 갖고
있다 — 이게 로컬 임포트 시간의 63%, 클라우드 콜드스타트의 93%를
차지했다. 논문 5.8절 "실행되지 않는 코드"가 지금까지는 우리 자신의
애플리케이션 코드 층위 사례만 다뤘다면, 이건 **같은 패턴이 의존성
(서드파티 라이브러리) 층위에서 나타나 성능에 직접 영향을 준 사례**
— "죽은 코드는 버그가 없어도 비용이다"라는 논지를 강화하는 각주
후보로 rev8 세션에 남긴다.
## 3. 컷아웃 없는 상태의 처리

현행 동작과 동일하게 유지한다(4장 원칙 — "폴백은 아무것도 하지
않음"과 같은 결):

- 업로드 직후 ~ 서버 처리 완료 전까지 화면은 **원본
  (`imageUrl`/`imagePath`)만 사용**한다 — 지금 릴리스에서 배경 제거가
  꺼져있을 때와 화면상 구분이 안 되는 상태이므로 새로 만들 UI가
  없다. `cutoutImageUrl`/`cutoutPath`가 `null`인 문서는 이미
  전 화면이 `cutoutImageUrl ?? imageUrl` 패턴으로 처리하고 있어
  (`docs/task_signed_urls_v1.md`의 A-5/A-6 24곳 전수 배선에서 이미
  확인됨) 그대로 작동한다.
- **서버 처리 실패 시(모델 추론 오류, 타임아웃 등) 문서는 그대로
  `cutoutImageUrl` 없는 상태로 남는다 — 재시도하지 않는다.** 옷
  등록 자체(Firestore 문서 생성)는 이미 끝난 뒤의 일이므로 등록은
  성공으로 유지된다. 사용자에게 실패를 알리지 않는다(현행 릴리스
  비활성 상태와 동일한 사용자 경험 — "원본만 있는 옷"은 이미 정상
  상태로 취급되고 있다).
- 나중에 재시도하고 싶다면 §2의 결정과 별개로, `sweepStorageTokens`와
  같은 패턴의 일 1회 스윕("컷아웃 없는 오래된 문서"를 찾아 재처리)을
  추가할 수 있다 — **이번 1단계 범위 밖, 필요성이 확인되면 별도
  승인 후 추가.**

### 3-1. 출력 캔버스 크기 — 타이트 크롭 확정 (2026-08-06)

u2netp 품질 스파이크(`tools/bg_removal_spike/`) 중 발견한 부수
차이: 기존 온디바이스 ONNX 컷아웃은 피사체 경계로 **타이트하게
크롭**돼 있는데(예: 원본 626×676 → 컷아웃 532×269), rembg 기본
출력(u2netp/u2net 공통)은 **원본 캔버스 전체 크기를 유지**하고
여백을 투명 처리한다 — 마스크 품질과는 무관한 순수 출력 포맷 차이.

**결정: 기존 관행(타이트 크롭)을 따른다.** 근거 — 기존 컷아웃
111건이 전부 타이트 크롭이고, 화면 레이아웃이 이미 그 관행 위에서
잡혀 있다. 신규 생성분만 캔버스가 커지면 같은 화면(옷장 그리드
등)에서 두 관행이 섞여 카드 크기가 들쭉날쭉해진다 — 이건 마스크
품질 문제가 아니라 **일관성 문제**이므로 어느 모델(u2netp/u2net)을
쓰든 상관없이 확정한다.

**구현 요구사항(§1-1 트리거 파이프라인에 추가)**: 서버 함수가
`remove()` 결과(RGBA)를 저장하기 전에 **알파 채널 bbox로 크롭**하는
후처리 단계를 거친다 — `PIL.Image.getbbox()`로 불투명 픽셀의
경계 상자를 구해 그 영역만 잘라낸다(라이브러리 추가 불필요,
Pillow 표준 기능). §2-1의 품질 스파이크 산출물
(`tools/bg_removal_spike/outputs/`)은 이 후처리 적용 **전** 상태라
원본 캔버스 그대로다 — 크롭 자체가 마스크 경계를 바꾸지 않으므로
품질 판단에는 영향 없다.

## 4. 신규 컷아웃 경로 — 서명 URL 이행에서 미실행 확인 항목

컷아웃 신규 *생성* 경로(배경 제거 재개 자체)는 서명 URL 이행 트랙
전체에서 한 번도 실행된 적이 없다(회수 이후 등록된 컷아웃은 전신
사진 1건 등 다른 경로였고, 온디바이스 배경 제거는 릴리스에서 계속
꺼져 있었다). 구현 후 반드시 확인:

- **a. `cutoutPath`가 실제로 기록되는가 — 확인됨(2026-08-07, §1-7).**
  `ref.fullPath`와 동일 형식(`wardrobe_cutouts/{fileName}.png`)으로
  기록, `getSignedImageUrls`가 정상적으로 읽어 서명함(§1-3 아래
  진단 참고).
- **b. 서명 경로로 정상 로드되는가 — 확인됨, 단 한 번 걸림돌
  있었음(2026-08-07).** 서명 자체(`getSignedUrl`)는 처음부터
  정상이었으나, **이미 화면에 떠 있던 위젯이 문서 갱신을 재해석하지
  않는 별개 결함**(`task_signed_urls_v1.md` §13)이 최초 실기기
  검증에서 걸렸다 — 컷아웃 신규 생성 경로가 이 결함을 처음으로
  드러낸 자리였다. 수정 후 재검증은 다음 등록 때 진행.
- **c. 업로드 트리거의 토큰 제거가 신규 컷아웃에도 적용되는가 —
  확인됨, 단 예상과 다른 메커니즘(2026-08-07, §1-7 Q2 정정).**
  `revokeTokenOnUpload`가 신규 컷아웃 경로에서도 매번 발화하지만,
  Admin SDK 원시 쓰기라 애초에 토큰이 생기지 않아 매번
  `result=already_clean`으로 응답한다 — "지운다"가 아니라 "지울 게
  없다"였다.

## 5. 기존 111건과 신규 생성분의 구분

Phase C 회수 시점(`docs/task_signed_urls_v1.md` §9,
`wardrobe_cutouts/` 111건)의 컷아웃은 전부
**과거 온디바이스 배경 제거가 살아있던 시절(릴리스 비활성 전) 생성분
또는 백필분**이다. 신규 서버 생성분과 관측이 섞이지 않도록:

- 검증 시 사용할 신규 옷은 **등록 시각을 정확히 기록**하고, 그
  `imagePath`/`cutoutPath`를 `task_signed_urls_v1.md` §12류 증거
  파일 패턴(JSON, `tools/` 아래 영속 경로, 커밋 제외)으로 남긴다.
- Firestore 문서에 "이 컷아웃을 만든 주체"를 구분할 수 있는 필드가
  없다(기존 스키마엔 그런 메타데이터가 없음) — 필요하면
  `cutoutSource: 'server_v1'` 같은 필드를 새 함수가 쓰게 하는 안을
  구현 시 검토(스키마 변경이므로 별도 확인 후 결정, 이 문서에서는
  제안만).
- 21항목류 회귀 확인을 할 때는 "기존 111건 화면(옷장 그리드 등)이
  여전히 정상"과 "신규 1~2건이 새로 컷아웃을 갖게 됨"을 **분리해서
  기록**한다 — 두 관측을 한 문장으로 뭉뚱그리면 신규 경로의 실제
  동작 여부가 안 보인다.

## 6. 클라이언트 정리 범위

**서버 경로가 검증되기 전에는 아무것도 제거하지 않는다.**

- `lib/screens/wardrobe_screen.dart`의 `kReleaseMode` 조기 반환(현재
  `_initBackgroundRemover()`)은 **유지** — 서버 검증 완료 후에도

  (디버그에서도 안 씀) 별도 판단이 필요하다(예: 디버그 빌드에서는
  비교용으로 당분간 남겨둘 수도 있음 — 이건 이 문서 범위 밖의
  판단).
- `image_background_remover`/`tflite_flutter` 의존성 제거는 **서버
  경로가 프로덕션에서 안정 확인된 뒤**로 미룬다 — 지금 지우면 되돌릴
  때 pubspec 복원+빌드 검증을 다시 해야 한다(작은 비용이지만
  "안전망을 미리 없애지 말자"는 이 세션 내내 반복된 원칙,
  `task_signed_urls_v1.md` C-4a/§12 참고).
- `tflite_flutter`는 애초에 온디바이스 CLIP 임베딩 스파이크에서
  release 안정성이 검증된 채로 남아있던 것(스파이크 노트 결론)이라,
  배경 제거를 서버로 이관해도 이 의존성 자체의 재사용 가치(다른
  온디바이스 모델에 재활용 가능)는 남는다 — 제거 여부는 배경 제거와
  독립적으로 판단해도 된다는 점만 기록해둔다.

## 7. 되돌릴 수단

- **트리거 비활성화**: `firebase functions:delete <신규함수이름>
  --region asia-northeast3` — C-4b에서 이미 실증한 것과 동일한
  방식(`task_signed_urls_v1.md` §12 "배포 즉시 활성화" 대응 경로).
  즉시 신규 컷아웃 생성이
  멈춘다. 원본 업로드·기존 컷아웃 표시는 영향 없음(신규 함수는
  읽기만 하고 원본을 건드리지 않으므로).
- **잘못 생성된 컷아웃 일괄 정리**: 신규 함수가 쓴 파일만 골라
  지우려면 §5에서 제안한 `cutoutSource` 필드(구현 시 채택하면)로
  필터링하거나, 검증 기간의 생성 시각 범위로 걸러(`timeCreated`
  범위 쿼리) `tools/` 아래 새 스크립트로 대상 나열 → dry-run → 승인
  → 삭제(파일 + 문서의 `cutoutImageUrl`/`cutoutPath` 필드 제거,
  `revoke.py`/`backfill_image_paths`와 같은 dry-run 우선 관례
  그대로 적용). **파일 삭제가 포함되므로(§1-2류 "파일은 절대 안
  지운다" 원칙과 달리 이번엔 실제로 지워야 하는 대상이 생김) —
  각 삭제는 이 세션 원칙대로 dry-run 먼저, 실행 전 승인 필수.**
